Book Chapter 14

Metaprogramming

Everything up to this point has been about writing code that manipulates data. This chapter is about writing code that manipulates other code — or, more precisely, that manipulates the rules by which JavaScript objects behave. You'll rarely reach for this material in application code, but it's exactly what you need to understand how libraries "lock down" objects, how frameworks like Vue and MobX detect reads and writes to plain objects without any getter/setter boilerplate, how ORMs build query DSLs out of tagged template strings, and what's actually happening when instanceof, for...in, or JSON.stringify() silently skip certain properties. The line between "programming" and "metaprogramming" is blurry in a dynamic language like JavaScript, but the features in this chapter — property attributes, extensibility controls, well-known symbols, template tags, Reflect, and Proxy — are the ones that let you rewrite the rules rather than just play by them.

14.1 Property attributes Deep dive

Every property on an object is more than just a name paired with a value. Internally, the language tracks a small set of boolean and functional attributes alongside that value, and those attributes — not the value — are what determine whether the property can be overwritten, whether it shows up when you enumerate the object, and whether it can be deleted or reconfigured later. Because a plain object literal or an ordinary assignment (obj.x = 1) always produces a property with every attribute turned on, most day-to-day JavaScript never has to think about this layer at all. Library authors do, though, because it's the only way to add methods to a prototype without them cluttering up for...in loops, and the only way to build objects that resist being tampered with by code you don't control.

Recall the distinction between data properties and accessor properties from the chapter on objects: a data property has an actual stored value, while an accessor property is a getter and/or setter pair that computes or intercepts the value. This distinction carries all the way down into the attribute system. A data property has four attributes:

  • value — the property's actual value.
  • writable — whether assignment can change the value.
  • enumerable — whether the property appears in for...in, Object.keys(), and similar enumeration.
  • configurable — whether the property can be deleted, and whether its other attributes (besides value, in some cases) can be changed at all.

An accessor property has no value or writable attribute — writability is implicit in whether a setter exists — and instead has:

  • get — the getter function, or undefined if there is none.
  • set — the setter function, or undefined if there is none.
  • enumerable — same meaning as for a data property.
  • configurable — same meaning as for a data property.

JavaScript represents this bundle of attributes as a plain object called a property descriptor, whose own keys are literally named value, writable, get, set, enumerable, and configurable. You read one with Object.getOwnPropertyDescriptor() and write one with Object.defineProperty().

Reading descriptors: getOwnPropertyDescriptor

Object.getOwnPropertyDescriptor({ x: 1 }, "x");
// => { value: 1, writable: true, enumerable: true, configurable: true }

const random = {
  get octet() { return Math.floor(Math.random() * 256); },
};
Object.getOwnPropertyDescriptor(random, "octet");
// => { get: [Function: get octet], set: undefined,
//      enumerable: true, configurable: true }

// It only ever looks at OWN properties -- never the prototype chain.
Object.getOwnPropertyDescriptor({}, "x");        // => undefined: no such property
Object.getOwnPropertyDescriptor({}, "toString");  // => undefined: it's inherited

That last point trips people up: to inspect an inherited property's attributes you have to walk the prototype chain yourself, calling Object.getPrototypeOf() (covered in §14.3) repeatedly until you find the object that actually owns the property. There is also a Reflect.getOwnPropertyDescriptor() with an almost identical signature — see §14.6 — the only practical difference is that the Reflect version throws a TypeError if you pass it something that isn't an object, whereas the Object version just coerces or returns undefined.

Writing descriptors: defineProperty and defineProperties

Object.defineProperty(obj, name, descriptor) either creates a brand-new property with exactly the attributes you specify, or modifies an existing own property, changing only the attributes you mention and leaving the rest untouched. When you're creating a property and you omit an attribute, it defaults to false or undefined — nothing is implicitly turned on the way it is for object-literal properties. 

let o = {};
Object.defineProperty(o, "x", {
  value: 1, writable: true, enumerable: false, configurable: true,
});
o.x;             // => 1 -- it works normally
Object.keys(o);  // => [] -- but it's invisible to enumeration

// Existing property: change just one attribute, leave the rest alone.
Object.defineProperty(o, "x", { writable: false });
o.x = 2;         // fails silently (throws in strict mode) -- no longer writable
o.x;             // => 1

// It's still configurable, so we CAN still overwrite value directly:
Object.defineProperty(o, "x", { value: 2 });
o.x;             // => 2

// We can even flip a data property into an accessor property, as long
// as it's configurable:
Object.defineProperty(o, "x", { get() { return 0; } });
o.x;             // => 0

To create or modify several properties in one call, use Object.defineProperties(obj, descriptorsMap), where the second argument maps each property name to its own descriptor object. Both functions return the object that was modified, which makes them chainable, and both are also the mechanism behind the second argument of Object.create() — see §14.3 — which accepts the exact same descriptor-map shape to add properties to the object it creates. 

let p = Object.defineProperties({}, {
  x: { value: 1, writable: true, enumerable: true, configurable: true },
  y: { value: 1, writable: true, enumerable: true, configurable: true },
  r: {
    get() { return Math.sqrt(this.x * this.x + this.y * this.y); },
    enumerable: true,
    configurable: true,
  },
});
p.r;  // => Math.SQRT2

The rules governing when defineProperty throws

Calls to Object.defineProperty() and Object.defineProperties() don't fail arbitrarily — they enforce a specific, slightly asymmetric set of rules, and violating any of them throws a TypeError:

  • You cannot add a brand-new property to an object that has been made non-extensible (§14.2) — but you can still edit that object's existing own properties.
  • If a property is not configurable, you cannot change its configurable or enumerable attribute.
  • A non-configurable accessor property's getter/setter cannot be changed, and it cannot be converted into a data property.
  • A non-configurable data property cannot be converted into an accessor property.
  • A non-configurable data property's writable attribute can be flipped from true to false, but never back from false to true.
  • If a data property is both non-configurable and non-writable, its value is truly frozen. But if it's non-configurable yet still writable, its value can still be changed — logically that's fine, because you could always achieve the same result by making it writable, changing it, then making it non-writable again.
Configurable is (mostly) a one-way door

Once configurable is false, it can never be turned back to true, and the property can never be deleted. But configurable: false does not by itself freeze the value — that's writable's job. The two attributes are independent: a property can be non-configurable yet perfectly writable, meaning you can still reassign its value with plain =, you just can't delete it, hide it from enumeration, or convert it to an accessor.

Enumerability: what for/in, Object.keys, and JSON.stringify can't see Deep dive

The enumerable attribute is the one with the most far-reaching, and most frequently misunderstood, consequences. It doesn't just control one API — it's the single switch that hides a property from essentially every mechanism JavaScript provides for listing "what properties does this object have." A non-enumerable property still exists, still holds a real value, and can still be read or written directly by name — it simply refuses to show up when something iterates. 

let obj = { visible: 1 };
Object.defineProperty(obj, "hidden", {
  value: 2, writable: true, enumerable: false, configurable: true,
});

obj.hidden;                 // => 2 -- direct access still works fine

for (let key in obj) console.log(key);   // logs only "visible"

Object.keys(obj);           // => ["visible"]
Object.values(obj);         // => [1]
Object.entries(obj);        // => [["visible", 1]]

JSON.stringify(obj);        // => '{"visible":1}' -- "hidden" is gone entirely

Object.getOwnPropertyNames(obj);  // => ["visible", "hidden"] -- this ONE
                                   // function still sees it: it lists ALL
                                   // own string-keyed properties regardless
                                   // of enumerability

That last line is the important escape hatch. Every "casual" enumeration API (for...in, Object.keys(), Object.values(), Object.entries(), the spread operator on an object, and JSON.stringify()) filters by enumerability. Only the more deliberate, introspection-oriented functions — Object.getOwnPropertyNames(), Object.getOwnPropertySymbols(), and Reflect.ownKeys() — bypass the filter and show you everything.

This is precisely why every method built into the standard library — Array.prototype.map, Object.prototype.toString, and so on — never appears when you do for (let k in []) or Object.keys(Array.prototype): the built-in methods were all defined as non-enumerable properties of the prototype. When you write your own reusable library, mimicking that convention for your own prototype methods keeps consumers' for...in loops and serialization code clean: 

function Range(from, to) { this.from = from; this.to = to; }
Object.defineProperty(Range.prototype, "includes", {
  value: function (x) { return this.from <= x && x <= this.to; },
  writable: true, enumerable: false, configurable: true,
});

let r = new Range(1, 10);
for (let key in r) console.log(key);   // logs "from" and "to" -- not "includes"
JSON.stringify(r);                      // => '{"from":1,"to":10}' -- clean output,
                                         //    even though `includes` is reachable via r.includes(5)

As a worked example of the whole attribute API together, Object.assign() (see the objects chapter) copies enumerable values from source objects into a target — if a source has an accessor property, assign() calls its getter and copies the resulting value, not the getter function itself. The following assignDescriptors() helper instead copies the full descriptor — including non-enumerable properties, and including getters/setters as live functions rather than one-time snapshots — by pairing getOwnPropertyDescriptor() with defineProperty(): 

Object.defineProperty(Object, "assignDescriptors", {
  writable: true, enumerable: false, configurable: true,
  value: function (target, ...sources) {
    for (let source of sources) {
      for (let name of Object.getOwnPropertyNames(source)) {
        Object.defineProperty(target, name,
          Object.getOwnPropertyDescriptor(source, name));
      }
      for (let symbol of Object.getOwnPropertySymbols(source)) {
        Object.defineProperty(target, symbol,
          Object.getOwnPropertyDescriptor(source, symbol));
      }
    }
    return target;
  },
});

let src = { c: 1, get count() { return this.c++; } };
let byValue = Object.assign({}, src);              // copies the CURRENT value
let byDescriptor = Object.assignDescriptors({}, src); // copies the GETTER itself

byValue.count;      // => 1 every time -- it's now a frozen-in-time data property
byValue.count;      // => 1
byDescriptor.count; // => 2 -- the getter ran once during the copy (bumping `c`)...
byDescriptor.count; // => 3 -- ...and keeps incrementing, because it's still live
defineProperty and defineProperties throw, Reflect's versions don't

Object.defineProperty() throws a TypeError the instant any of the rules above is violated. Its Reflect.defineProperty() counterpart (§14.6) performs the exact same check but returns false instead of throwing, which is what makes it suitable for use inside a Proxy's defineProperty trap — you often want to report failure as a value, not unwind the stack.

14.2 Object extensibility

Alongside each property's own attributes, every object as a whole carries a single boolean attribute, extensible, which governs whether new properties can be added to it at all. Ordinary objects start out extensible. Three functions let you progressively lock an object down, each one a strict superset of the restrictions imposed by the previous:

FunctionBlocks adding new properties?Blocks delete / reconfigure of existing?Blocks changing existing writable values?
Object.preventExtensions(o)YesNoNo
Object.seal(o)YesYes (all own props become non-configurable)No — writable properties can still be reassigned
Object.freeze(o)YesYesYes — all own data properties become non-writable too

Each of the three has a matching predicate — Object.isExtensible(), Object.isSealed(), Object.isFrozen() — and each of the three locking functions returns the object it was passed, which makes nesting them convenient: 

let frozenProto = Object.freeze({ x: 1 });
let o = Object.seal(
  Object.create(frozenProto, { y: { value: 2, writable: true, enumerable: true } })
);
Object.isSealed(o);        // => true
Object.isFrozen(o);        // => false -- y is still writable, only sealed props are non-configurable
o.y = 20;                  // works: seal doesn't touch writability
o.z = 3;                   // silently fails (or throws in strict mode): sealed means non-extensible too

Note that unlike accessor properties, Object.freeze() leaves setter functions alone — if an object has an accessor property with a setter, that setter can still run even on a frozen object, because freezing only affects data properties.

There's no way to reverse any of these three operations once applied — you cannot make a sealed or frozen object extensible again. There is also no built-in "deep freeze": these functions only touch the own properties of the exact object you pass in, never its prototype and never any object stored as a property value.

Freeze/seal are shallow — and prototypes are untouched too

Object.freeze(obj) does nothing to obj.child — obj.child.x = 1 still succeeds freely unless obj.child is frozen separately. Likewise, freezing obj has zero effect on Object.getPrototypeOf(obj); if you want a truly tamper-proof object graph you must walk it and freeze every object in it, including the prototype chain. A common use case is freezing objects handed to third-party callback code so that library consumers can't accidentally mutate your internal state — but be aware this can break testing tools that rely on being able to stub or monkey-patch objects.

Reflect.isExtensible() and Reflect.preventExtensions() exist too, with the usual Reflect-vs-Object difference: they throw on non-object arguments rather than coercing or silently succeeding (§14.6).

14.3 The prototype attribute

Every object also carries a [[Prototype]] internal attribute — the object it inherits properties from, as covered in depth in the prototype chain. This section is specifically about querying and changing that attribute programmatically, rather than through the normal channels (object literals default to Object.prototype; new SomeClass() uses SomeClass.prototype; Object.create(proto) uses whatever you pass as proto, including null). 

Object.getPrototypeOf({});       // => Object.prototype
Object.getPrototypeOf([]);       // => Array.prototype
Object.getPrototypeOf(() => {}); // => Function.prototype

A matching Reflect.getPrototypeOf() exists too; the difference is narrow — Object.getPrototypeOf() coerces a primitive argument to its wrapper object and only throws for null/undefined, while Reflect.getPrototypeOf() throws a TypeError for any non-object argument.

To test whether one object sits anywhere in another's prototype chain, use isPrototypeOf() rather than manually walking the chain: 

let p = { x: 1 };
let o = Object.create(p);
p.isPrototypeOf(o);                 // => true: o inherits from p
Object.prototype.isPrototypeOf(p);  // => true: p inherits from Object.prototype
Object.prototype.isPrototypeOf(o);  // => true: transitively, so does o

isPrototypeOf() answers essentially the same question as instanceof, but the two aren't interchangeable: instanceof takes a constructor function on its right side and checks whether Constructor.prototype appears in the chain, whereas p.isPrototypeOf(o) checks directly against the object p — useful when you built your prototype object with Object.create() and never bothered defining a constructor function for it at all.

The prototype is normally fixed for the life of an object, but Object.setPrototypeOf() (and a matching Reflect.setPrototypeOf()) can change it after the fact: 

let o = { x: 1 };
let newProto = { y: 2 };
Object.setPrototypeOf(o, newProto);
o.y;   // => 2 -- o now inherits y

let a = [1, 2, 3];
Object.setPrototypeOf(a, newProto);
a.join;  // => undefined -- a lost every Array.prototype method in one call!
Avoid setPrototypeOf in anything performance-sensitive

There's rarely a real need to call Object.setPrototypeOf() in application code. JS engines aggressively optimize property access on the assumption that an object's prototype — and therefore its whole "shape" — never changes after creation. Call this function even once on an object, and every subsequent operation on it (and often on other objects that share its former shape) can fall out of those fast paths and run measurably slower. Prefer setting the prototype once, up front, with Object.create(proto).

You may also encounter the legacy __proto__ property — two underscores on each side — which some early browsers exposed as a getter/setter view onto the prototype attribute. It's deprecated but standardized for web-facing JS engines because too much existing code depends on it, and it remains readable/writable today. One legitimate surviving use is setting the prototype directly inside an object literal, which no other syntax can do: 

let base = { z: 3 };
let o = { x: 1, y: 2, __proto__: base };
o.z;  // => 3 -- inherited via the literal's own __proto__ entry

14.4 Well-known symbols

ES6 introduced the Symbol primitive type specifically so that new language hooks could be added without any risk of colliding with a string-keyed property some existing website already happened to be using. The result is a small family of "well-known symbols" — values stored as static properties on the global Symbol function — each of which lets your own classes plug into a piece of behavior that used to be reserved for built-ins only.

14.4.1 Symbol.iterator and Symbol.asyncIterator

You've already met these two: implementing a method named [Symbol.iterator]() makes instances of a class work with for...of, spread, and destructuring, and [Symbol.asyncIterator]() does the same for for await...of. Both are covered at length in Iterators & Generators and are mentioned here only so the family of well-known symbols is complete.

14.4.2 Symbol.hasInstance

Ordinarily, o instanceof F requires F to be a function and works by searching for F.prototype in o's prototype chain. But if the object on the right-hand side of instanceof defines a method named [Symbol.hasInstance], that method is invoked with the left-hand value instead, and its return value (coerced to boolean) becomes the result of the whole expression — the right-hand side doesn't even need to be a function anymore. 

// A "pseudotype": an ordinary object usable as instanceof's right operand
let uint8 = {
  [Symbol.hasInstance](x) {
    return Number.isInteger(x) && x >= 0 && x <= 255;
  },
};
128 instanceof uint8;      // => true
256 instanceof uint8;      // => false: out of range
Math.PI instanceof uint8;  // => false: not an integer
Clever, but often clearer as a plain function

Overloading instanceof to mean "satisfies this predicate" reads as surprising to anyone maintaining the code later — a standalone isUint8(x) function does the exact same job with none of the misdirection. Reach for Symbol.hasInstance mainly when you're already deep in library code that other people expect to compose with instanceof-based logic.

14.4.3 Symbol.toStringTag

Calling Object.prototype.toString() on a plain object gives the unhelpful "[object Object]", but calling that same generic method on instances of built-ins is surprisingly more informative: 

Object.prototype.toString.call([]);      // => "[object Array]"
Object.prototype.toString.call(/./);     // => "[object RegExp]"
Object.prototype.toString.call(() => {}); // => "[object Function]"

function classof(o) {
  return Object.prototype.toString.call(o).slice(8, -1);
}
classof(null);      // => "Null"
classof(10n ** 100n); // => "BigInt"
classof(new Map());   // => "Map"

Before ES6 this "class tag" mechanism was hardwired to recognize only built-in types — running classof() on an instance of a class you wrote yourself just returned "Object". In ES6 and later, Object.prototype.toString() looks for a property (typically a getter) named Symbol.toStringTag on its argument and, if present, splices that string into the output instead: 

class Range {
  get [Symbol.toStringTag]() { return "Range"; }
}
let r = new Range();
Object.prototype.toString.call(r);  // => "[object Range]"
classof(r);                         // => "Range"

14.4.4 Symbol.species

Since ES6 you can subclass built-ins like Array directly with extends (see Classes and Arrays), which raises a design question: when an inherited method like map(), filter(), slice(), splice(), or concat() constructs and returns a brand-new array, should that new array be a plain Array or an instance of your subclass? 

class EZArray extends Array {
  get first() { return this[0]; }
  get last() { return this[this.length - 1]; }
}
let e = new EZArray(1, 2, 3);
let f = e.map(x => x * x);
f.last;  // => 9 -- f is ALSO an EZArray, with a working `.last` getter

The spec's answer is: array-returning methods create their result by effectively calling new this.constructor[Symbol.species]() instead of new Array(). Array itself defines Symbol.species as a read-only accessor whose getter just returns this — and because subclass constructors inherit that getter, every subclass is, by default, its own species. If you want array-returning methods on your subclass to yield plain arrays instead, override the getter (a direct assignment fails, since the inherited property is read-only, so you either use defineProperty() or, more simply, declare your own static getter up front): 

class EZArray extends Array {
  static get [Symbol.species]() { return Array; }
  get first() { return this[0]; }
  get last() { return this[this.length - 1]; }
}
let e = new EZArray(1, 2, 3);
let f = e.map(x => x - 1);
f.last;  // => undefined: f is a plain Array now, no `.last` getter

The same species protocol governs typed arrays, ArrayBuffer.prototype.slice(), and Promise methods like then() that return a new promise — so subclassing any of those has the identical default-species behavior baked in.

14.4.5 Symbol.isConcatSpreadable

Array.prototype.concat() (see Arrays) treats array-like arguments differently from ordinary values: arrays (including this) are flattened one level into the result, while everything else is just appended as a single element. Before ES6, that decision was made purely with Array.isArray(); since ES6, if the candidate value has a Symbol.isConcatSpreadable property, its boolean value wins instead, which lets you opt array-like objects in or array subclasses out: 

let arraylike = { length: 1, 0: 1, [Symbol.isConcatSpreadable]: true };
[].concat(arraylike);  // => [1] -- would be [[1]] without the flag

class NonSpreadableArray extends Array {
  get [Symbol.isConcatSpreadable]() { return false; }
}
let a = new NonSpreadableArray(1, 2, 3);
[].concat(a).length;   // => 1 -- would be 3 if `a` were spread as normal

14.4.6 Pattern-matching symbols

The string methods match(), matchAll(), search(), replace(), and split() — introduced with regular expressions — were generalized in ES6 to accept not just a RegExp but any object exposing the right symbolically named methods: Symbol.match, Symbol.search, Symbol.replace, Symbol.split. A call like string.replace(pattern, arg) is really dispatched as pattern[Symbol.replace](string, arg). This lets you build entirely custom matching semantics — fuzzy matching, locale-aware comparison via Intl.Collator, Soundex, Levenshtein-distance matching — that plug into the exact same call sites regular expressions use. As an illustration, here's a small "glob" pattern class implementing shell-style */? wildcards on top of an internally-built RegExp: 

class Glob {
  constructor(glob) {
    this.glob = glob;
    let regexpText = glob.replace("?", "([^/])").replace("*", "([^/]*)");
    this.regexp = new RegExp(`^${regexpText}$`, "u");
  }
  toString() { return this.glob; }
  [Symbol.search](s) { return s.search(this.regexp); }
  [Symbol.match](s) { return s.match(this.regexp); }
  [Symbol.replace](s, replacement) { return s.replace(this.regexp, replacement); }
}

let pattern = new Glob("docs/*.txt");
"docs/js.txt".search(pattern);   // => 0
"docs/js.htm".search(pattern);   // => -1: no match
"docs/js.txt".replace(pattern, "web/$1.htm");  // => "web/js.htm"

14.4.7 Symbol.toPrimitive

The default rules for converting an object to a primitive — preferring toString() for string contexts, valueOf() for numeric contexts, and Date objects reversing the usual "default" tie-break — were covered earlier as the object-to-primitive algorithm. Symbol.toPrimitive replaces all of that with one method you fully control, invoked with a hint string telling you what conversion context triggered it:

  • "string" — a string is preferred but not required (e.g. template-literal interpolation).
  • "number" — a number is preferred but not required (e.g. <, >, arithmetic operators).
  • "default" — either would do (e.g. +, ==, !=).
class Money {
  constructor(cents) { this.cents = cents; }
  [Symbol.toPrimitive](hint) {
    if (hint === "number") return this.cents / 100;
    if (hint === "string") return `$${(this.cents / 100).toFixed(2)}`;
    return this.cents / 100;  // "default" -- used by +, ==, etc.
  }
}
`${new Money(150)}`;   // => "$1.50" (hint: "string")
new Money(150) - 0;    // => 1.5     (hint: "number")
new Money(150) + "";   // => "1.5"   (hint: "default", result then string-coerced)

Defining Symbol.toPrimitive is also the cleanest way to make a value class comparable with </> without needing separate comparison methods.

14.4.8 Symbol.unscopables

This is a niche, backward-compatibility-only symbol tied to the deprecated with statement, which executes a block as if an object's properties were local variables. When ES6 added new Array.prototype methods, existing with-based code on the web could break if one of those method names happened to collide with a variable already used inside a with block. Symbol.unscopables is the fix: a with(o) statement computes Object.keys(o[Symbol.unscopables] || {}) and simply ignores any of those names when constructing its simulated scope. In practice, the only reason to ever look at this symbol is archaeological curiosity: 

// The newest Array methods, as of whichever spec version you're running:
Object.keys(Array.prototype[Symbol.unscopables]);

14.5 Template tags

A template literal preceded directly by a function reference — no parentheses, no space required — becomes a tagged template literal: an ordinary function call in disguise. Writing a tag function is metaprogramming in a very literal sense — you're effectively inventing new syntax, because the tag decides what the whole expression evaluates to, not just what string gets built. This is the exact mechanism behind Emotion's css`` tag and GraphQL's gql`` tag: each parses (or otherwise transforms) the literal's text into something that isn't a plain string at all.

How a tag function receives its pieces

There's no special syntax for defining a tag function — any ordinary function can be used as one. What's special is how it's called: its first argument is an array of the literal text segments (the parts outside the ${...} interpolations), and it's followed by one additional argument per interpolated expression, in source order. If there are n interpolated values, the tag receives n + 1 arguments total: an array of n + 1 strings (any of which may be empty), then the n values themselves. 

function inspectTag(strings, ...values) {
  console.log(strings);  // the literal text, split around each interpolation
  console.log(values);   // the interpolated values, in order
}
let x = 5, y = 10;
inspectTag`x is ${x} and y is ${y}!`;
// strings => ["x is ", " and y is ", "!"]
// values  => [5, 10]

The value of a plain template literal is always a string, but the value of a tagged template literal is simply whatever the tag function returns — which is what makes tags suitable for building DSLs: the return value can be a query object, a parsed AST, a styled-component descriptor, anything at all.

Writing your own tag function

A tag that returns a string — for instance, one that automatically HTML-escapes interpolated values to guard against injection — simply reassembles the strings array around the (transformed) values: 

function html(strings, ...values) {
  let escape = s => String(s).replace(/[&<>"']/g, c => ({
    "&": "&amp;", "<": "&lt;", ">": "&gt;",
    '"': "&quot;", "'": "&#39;",
  }[c]));
  return strings.reduce((out, str, i) =>
    out + (i > 0 ? escape(values[i - 1]) : "") + str, "");
}
let name = "<script>alert(1)</script>";
html`<p>Hello, ${name}!</p>`;
// => "<p>Hello, &lt;script&gt;...!</p>" -- injection defused automatically

A tag doesn't have to return a string at all. Reusing the Glob class from §14.4.6, a glob tag can assemble the raw pieces into one string and then hand that string to the Glob constructor, returning a parsed pattern object rather than text: 

function glob(strings, ...values) {
  let s = strings[0];
  for (let i = 0; i < values.length; i++) s += values[i] + strings[i + 1];
  return new Glob(s);
}
let root = "/tmp";
let filePattern = glob`${root}/*.html`;
"/tmp/test.html".match(filePattern)[1];  // => "test"

This same pattern — parse-not-concatenate — is exactly how a SQL query builder can be made injection-safe: rather than the tag interpolating each value directly into a SQL string, it can keep the literal text and the values separate, producing something like { text: "SELECT * FROM users WHERE id = $1", values: [userId] } for a parameterized query API — the interpolated values never touch the SQL text at all, which is what actually prevents injection (as opposed to escaping, which merely reduces the risk). The same strings-plus-values shape is also a natural fit for i18n tag functions, where the strings array (being a stable, repeatable sequence for a given call site) can double as a lookup key into a translation table, with the values slotted back in afterward.

The raw property: unescaped text

The strings array passed to a tag function carries one more piece of information beyond its own elements: a .raw property, itself an array of the same length, containing the literal text with backslash escape sequences left completely uninterpreted. This is exactly how the built-in String.raw` ` tag is implemented, and it matters whenever your DSL's own grammar wants to use backslashes for something other than a JS escape sequence — for example, extending the glob tag above to support Windows-style paths without forcing every caller to double every backslash: 

function rawGlob(strings, ...values) {
  let s = strings.raw[0];  // use .raw instead of the (escape-interpreted) strings
  for (let i = 0; i < values.length; i++) s += values[i] + strings.raw[i + 1];
  return new Glob(s);
}
rawGlob`C:\Users\*\Desktop`;  // \U, \D are passed through literally via .raw,
                              // instead of being interpreted (and likely erroring)
                              // as JS escape sequences
Trade-off

Switching a tag over to strings.raw means you also lose the ability to use real JS escapes like \n or \u00e9 inside that particular literal — every backslash becomes meaningful only to your DSL's own grammar, not to JavaScript's. Choose whichever behavior your DSL's users will actually expect.

14.6 The Reflect API

Reflect, like Math, is not a class or constructor — it's simply a namespace object bundling a set of related static functions, added in ES6. None of what it offers is a genuinely new capability: every Reflect function duplicates something already expressible through core syntax (property access, delete, in, function calls, new) or through an existing Object static method. What Reflect actually buys you is uniformity: one flat API of ordinary callable functions, each with a signature that lines up — argument for argument — with one Proxy trap (§14.7). That correspondence is the entire reason Reflect exists: it gives every Proxy trap a trivial way to "do the normal thing" after intercepting an operation.

That difference is exactly what makes the Reflect functions pleasant to call from inside a Proxy trap, where a boolean return value is usually what the trap protocol expects anyway.

14.7 Proxy objects The big one

Proxy is the most powerful metaprogramming feature in the language: it lets you construct an object that has essentially no fixed behavior of its own, and instead forwards every fundamental operation performed on it — reading a property, writing one, deleting one, checking in, enumerating keys, querying or changing the prototype, calling it as a function, using it with new — to a handlers object you supply. Any operation whose corresponding handler ("trap") you don't define simply falls through to the real operation on an underlying target object. 

let proxy = new Proxy(target, handlers);

With an empty handlers object, a proxy is a fully transparent pass-through to its target — reads, writes, and deletes on the proxy really happen on the target: 

let t = { x: 1, y: 2 };
let p = new Proxy(t, {});
p.x;         // => 1
delete p.y;  // => true
t.y;         // => undefined -- the delete really happened on the target
p.z = 3;
t.z;         // => 3 -- likewise, the write really happened on the target

A transparent wrapper on its own isn't very useful — but as a revocable proxy it becomes a genuine access-control tool. Proxy.revocable(target, handlers) returns { proxy, revoke }; calling revoke() permanently disables the proxy, turning every subsequent operation on it into a thrown TypeError. This gives you a way to hand a reference to code you don't fully trust and then cut off its access later, without that code being able to keep working around the cutoff: 

function accessTheDatabase() { return 42; }
let { proxy, revoke } = Proxy.revocable(accessTheDatabase, {});
proxy();   // => 42 -- works like the real function (proxies wrap functions too)
revoke();  // cut off access
proxy();   // !TypeError -- can never be called again, even by whoever holds `proxy`

Every trap name matches, argument-for-argument, one of the Reflect functions from §14.6 — which is why the two are almost always used together: a trap logs, validates, or transforms, and then calls the identically-shaped Reflect function to actually perform the operation.

With enough traps defined, the target object becomes almost irrelevant — the handlers alone can conjure up behavior no ordinary object could ever have, such as an object that appears to already possess an infinite number of read-only properties: 

let identity = new Proxy({}, {

  has(o, name) { return true; },

  getOwnPropertyDescriptor(o, name) {

  defineProperty(o, name, desc) { return false; },

  setPrototypeOf(o, proto) { return false; },
});
identity.x;              // => "x"
identity[0];             // => "0"
identity.x = 1;          // no-op: set trap returns false

Worked example: a validating proxy Worked example

One of the most common real-world uses of Proxy is input validation — rejecting writes that would put an object into an invalid state, without changing a single line of the code that reads and writes the object normally: 

function validated(target, rules) {
  return new Proxy(target, {
    set(obj, prop, value, receiver) {
      let rule = rules[prop];
      if (rule && !rule(value)) {
        throw new TypeError(`Invalid value for "${String(prop)}": ${value}`);
      }
      return Reflect.set(obj, prop, value, receiver);
    },
    defineProperty(obj, prop, desc) {
      if ("value" in desc && rules[prop] && !rules[prop](desc.value)) {
        throw new TypeError(`Invalid value for "${String(prop)}": ${desc.value}`);
      }
      return Reflect.defineProperty(obj, prop, desc);
    },
  });
}

let user = validated({ name: "Ada", age: 30 }, {
  age: n => Number.isInteger(n) && n >= 0,
});
user.age = 31;      // fine
user.name = "Ada L."; // fine -- no rule for "name", so anything goes
user.age = -5;       // !TypeError: Invalid value for "age": -5
Object.defineProperty(user, "age", { value: 3.5 });  // !TypeError, same rule applies

Read-only wrappers are the same idea with the failure mode hardcoded, which is handy for defensive testing — pass one of these into a function under test and any attempt by that function to mutate its argument surfaces immediately as a thrown error instead of a silent, hard-to-detect side effect: 

function readOnlyProxy(o) {
  const fail = () => { throw new TypeError("read-only"); };
  return new Proxy(o, {
    set: fail, defineProperty: fail, deleteProperty: fail, setPrototypeOf: fail,
  });
}
let ro = readOnlyProxy({ x: 1, y: 2 });
ro.x;             // => 1: reads pass through fine
ro.x = 2;         // !TypeError
delete ro.y;      // !TypeError
ro.__proto__ = {}; // !TypeError -- setPrototypeOf is trapped too

Worked example: a contagious logging proxy

Because a trap can call Reflect to delegate while still doing something else first, proxies are an excellent way to observe exactly how an unfamiliar function uses an object it's given — including third-party or built-in functions whose internals you can't otherwise inspect. The following generates a trap for every operation automatically by iterating Reflect.ownKeys(Reflect), and — crucially — has its get trap wrap any object or function property value in another logging proxy before returning it, so the logging follows values as they're passed around ("contagious" logging): 

function loggingProxy(o, label) {
  const handlers = {
    get(target, prop, receiver) {
      console.log(`get(${label}, ${String(prop)})`);
      let value = Reflect.get(target, prop, receiver);
      if (Reflect.ownKeys(target).includes(prop) &&
          (typeof value === "object" || typeof value === "function") && value !== null) {
        return loggingProxy(value, `${label}.${String(prop)}`);
      }
      return value;
    },
    set(target, prop, value, receiver) {
      console.log(`set(${label}, ${String(prop)}, ${value})`);
      return Reflect.set(target, prop, value, receiver);
    },
    apply(target, thisArg, args) {
      console.log(`${label}(${args})`);
      return Reflect.apply(target, thisArg, args);
    },
  };
  Reflect.ownKeys(Reflect).forEach(name => {
    if (!(name in handlers)) {
      handlers[name] = (target, ...args) => {
        console.log(`${name}(${label}, ${args})`);
        return Reflect[name](target, ...args);
      };
    }
  });
  return new Proxy(o, handlers);
}

let data = loggingProxy([10, 20], "data");
for (let x of data) { /* ... */ }
// get(data, Symbol(Symbol.iterator))
// get(data, length)
// get(data, 0)
// get(data, length)
// get(data, 1)
// get(data, length)
// -- revealing that for/of re-checks .length on EVERY iteration rather
//    than assuming a fixed length

Proxy invariants: where the illusion breaks down Deep dive

A trap can return almost anything it wants — but "almost" is the key word. The Proxy class is not a pure pass-through: after invoking a trap, the engine runs a sanity check against the target object to make sure the result doesn't contradict a guarantee JavaScript makes elsewhere about non-extensible objects or non-configurable properties. If a trap's return value violates one of these invariants, the engine throws a TypeError itself — no matter what the trap tried to return. A Proxy can extend an object's behavior in almost unlimited ways, but it can never be used to make a frozen or sealed object lie about being frozen or sealed.

The most common invariant in practice: if the target has a non-configurable, non-writable data property, the get trap is not allowed to return anything other than that property's real, current value. 

let target = Object.freeze({ x: 1 });
let proxy = new Proxy(target, { get() { return 99; } });
proxy.x;  // !TypeError: 'get' on proxy: property 'x' is a read-only and
          //             non-configurable data property on the proxy target
          //             so the trap can't report a different value

A second invariant guards isExtensible: if the target is non-extensible, the trap is not allowed to report the object as extensible. 

let target2 = Object.preventExtensions({});
let proxy2 = new Proxy(target2, { isExtensible() { return true; } });
Reflect.isExtensible(proxy2);  // !TypeError: invariant violation --
                                // the trap disagrees with the actual target

A closely related invariant covers deleteProperty: a trap cannot report a non-configurable own property of the target as successfully deleted, because that property is, by definition, undeletable. 

let target3 = {};
Object.defineProperty(target3, "id", { value: 1, configurable: false });
let proxy3 = new Proxy(target3, {
  deleteProperty(t, prop) { return true; },  // lying: claims every delete succeeds
});
delete proxy3.id;
// !TypeError: 'deleteProperty' on proxy: property 'id' is a
//             non-configurable property of the proxy target and can't be
//             reported as deleted

Other invariants in the same family: a getPrototypeOf trap on a non-extensible target must return that target's actual prototype, and a set trap can't successfully report writing to a non-writable, non-configurable data property. Practically, this whole invariant system means Proxy is safe to hand to library consumers even when the underlying data must stay provably frozen — no combination of traps can be used to punch a hole in that guarantee.

Minor inconsistencies are still allowed

The readOnlyProxy() from earlier traps set but not isExtensible or getOwnPropertyDescriptor — so querying it with Reflect.isExtensible() will happily (and misleadingly) report the object as extensible, even though every write attempt actually throws. That's a real inconsistency, but it's not one of the invariants the engine enforces, so no error is thrown for it — it's simply a gap you may want to close yourself by adding those traps too.

A few more practical Proxy patterns

Beyond validation and logging, two small patterns show up often enough to be worth naming directly. First, negative array indices — indexing from the end of an array the way Python's a[-1] does, which JavaScript arrays don't support natively: 

function negativeArray(arr) {
  return new Proxy(arr, {
    get(target, prop, receiver) {
      if (typeof prop === "string" && /^-\d+$/.test(prop)) {
        prop = String(target.length + Number(prop));
      }
      return Reflect.get(target, prop, receiver);
    },
  });
}
let a = negativeArray([10, 20, 30]);
a[-1];  // => 30
a[-2];  // => 20

Second, default values for otherwise-missing keys — useful for configuration objects where you'd rather not sprinkle ?? fallback at every call site: 

function withDefault(obj, defaultValue) {
  return new Proxy(obj, {
    get(target, prop, receiver) {
      return prop in target ? Reflect.get(target, prop, receiver) : defaultValue;
    },
  });
}
let config = withDefault({ retries: 3 }, "unset");
config.retries;  // => 3
config.timeout;  // => "unset" -- instead of undefined

This "trap the get, delegate everything else" shape is exactly what reactive-UI libraries like Vue 3 build on: wrap a plain state object in a proxy whose get trap records which reactive computation is currently reading which property, and whose set trap re-runs every computation that depends on the property just written — all without the application code ever calling a special .get()/.set() method or the library needing to redefine accessor properties one by one.

14.8 Summary

Every property carries attributes beyond its value — writable, enumerable, and configurable for data properties, with get/ set replacing value/writable for accessors — queryable and settable through Object.getOwnPropertyDescriptor() and Object.defineProperty()/defineProperties(), and it's specifically enumerable that determines invisibility to for...in, Object.keys(), and JSON.stringify(). Whole objects carry an extensible attribute, escalated by Object.preventExtensions(), seal(), and freeze() — each shallow, each one-way. The prototype attribute can be read with Object.getPrototypeOf() and, at a real performance cost, changed with Object.setPrototypeOf(). Well-known symbols (Symbol.hasInstance, Symbol.toStringTag, Symbol.toPrimitive, Symbol.species, Symbol.isConcatSpreadable, the pattern-matching symbols, Symbol.unscopables) let your own classes hook into behavior that used to be exclusive to built-ins. Tagged template literals turn a function call into what looks like new syntax, receiving the literal's text (both interpreted and, via .raw, uninterpreted) alongside its interpolated values. And Reflect and Proxy together are the deepest layer of all: Reflect exposes every fundamental object operation as a plain function, and Proxy lets you intercept those same operations on an object you hand out to the rest of your program — bounded by a set of invariants that keep a proxied frozen object provably frozen no matter what its traps try to claim.
