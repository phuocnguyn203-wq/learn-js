Classes

A JavaScript object represents one unique bag of properties. A class represents a whole family of objects that share the same behavior — instances that differ in their own state (a particular Range's from and to) but agree on their methods (every Range's includes()). Long before class existed as a keyword, JavaScript already had classes: a class is nothing more than a set of objects that inherit from the same prototype object, built with the prototype mechanism covered in Objects. ES6's class syntax doesn't introduce a new object model — it's a cleaner notation for exactly that old mechanism. This chapter works bottom-up: first the prototype-only version with no constructor at all, then constructor functions and new, then the modern class keyword built on top of both, and finally subclassing with extends and super.

9.1 Classes and prototypes

Strip away every convenience the language has added and a class is just: one shared prototype object holding the methods, plus some way to produce new objects that inherit from it. Object.create() is that "some way." Nothing else is required. Example: a class of Range objects, defined with a plain factory function and a hand-built prototype object, no constructor, no new, no class keyword anywhere in sight. 

// A factory function: returns a new range object, doesn't need `new`
function range(from, to) {
  // Object.create() makes an object that inherits from range.methods.
  // The name "methods" is just a convenient property to hang the
  // prototype off of -- nothing about it is special to the language.
  let r = Object.create(range.methods);
  r.from = from;   // Own, per-instance properties: the object's state
  r.to = to;
  return r;
}

// The shared prototype: every range object inherits these members.
range.methods = {
  includes(x) { return this.from <= x && x <= this.to; },
  *[Symbol.iterator]() {
    for (let x = Math.ceil(this.from); x <= this.to; x++) yield x;
  },
  toString() { return `(${this.from}...${this.to})`; }
};

let r = range(1, 3);
r.includes(2);   // => true
r.toString();    // => "(1...3)"
[...r];          // => [1, 2, 3] -- works because of the Symbol.iterator method

Every method here uses this to reach the caller's from/to, which is the defining trait of a method as opposed to an ordinary function: it's meaningless without an object to be invoked on. Because range.methods is a single shared object, all range objects created this way point at the exact same method implementations in memory — that sharing, not anything about syntax, is what makes this "a class." Two objects belong to the same class precisely when they inherit from the same prototype object; nothing else about how they were built matters.

There's no built-in instanceof here

instanceof (covered properly in Expressions & Operators) normally takes a constructor function on its right side, and this class has none. To test membership against a bare prototype object you reach for isPrototypeOf() instead: range.methods.isPrototypeOf(r). Once a constructor enters the picture in the next section, instanceof becomes the natural tool again.

9.2 Classes and constructors

The factory-function approach works but isn't idiomatic, because real JavaScript classes are built around a constructor: a function specifically designed to be invoked with new (see constructor invocation in Functions). When you call new F(), the runtime does three things automatically, before a single line of F's body runs: it creates a brand-new plain object, it sets that object's prototype to F.prototype, and it binds that object to this for the duration of the call. The function itself only has to fill in state — it never has to call Object.create(), and it doesn't even need to return the object (the new expression returns it regardless, unless the constructor explicitly returns some other object). 

// A constructor: capitalized by convention, invoked only with `new`.
function Range(from, to) {
  this.from = from;
  this.to = to;
}

// Every function has a `prototype` property from the moment it's created.
// For a constructor, THIS is the object new instances will inherit from --
// and unlike range.methods above, the property name is not negotiable.
Range.prototype = {
  includes(x) { return this.from <= x && x <= this.to; },
  *[Symbol.iterator]() {
    for (let x = Math.ceil(this.from); x <= this.to; x++) yield x;
  },
  toString() { return `(${this.from}...${this.to})`; }
};

let r = new Range(1, 3);   // `new` does the work range() used to do by hand
r.includes(2);              // => true
[...r];                     // => [1, 2, 3]

Compare the two Range classes carefully and the only real differences are: the function is capitalized and invoked with new instead of called plainly, and the prototype property has to be named exactly prototype because that's the name the new algorithm looks up on the constructor. Everything about how the methods are written and used is identical. This is why the book insists on teaching the constructor-function form before class: class changes none of this, it only changes the spelling.

Arrow functions cannot be constructors

Arrow functions have no prototype property at all, so new SomeArrow() throws a TypeError. They also capture this lexically from their surrounding scope rather than from however they're invoked, which makes them unusable as methods too — a method's whole job is to read this from its caller. Neither old-style constructor functions nor the class keyword will let you write a method as an arrow function for exactly this reason. See Functions for the full rules on this binding.

Detecting constructor invocation with new.target

Inside any function you can inspect the special expression new.target. When the function was invoked with new, it evaluates to the constructor that was invoked (usually the function itself — but see subclassing below, where it can refer to a subclass constructor instead). When the function was called plainly, without new, it's undefined. Some built-ins (the error constructors, for instance) tolerate being called either way; you can emulate that in your own old-style constructors: 

function C() {
  if (!new.target) return new C();   // called as a function -- fix it up
  // ... normal initialization of `this` continues here
}
C();        // still works, and still returns a proper instance
new C();    // also works

This escape hatch only exists for the old function-based style. Classes defined with the class keyword refuse outright to run their constructor without new — calling SomeClass() throws a TypeError unconditionally, no new.target check can save it.

Class identity: instanceof and the constructor property

The prototype object, not the constructor function, is what actually defines a class — two constructors could point their .prototype at the very same object, and objects built by either one would be full-fledged members of one class. Even so, the constructor is treated as the class's public face: its name is conventionally the class's name, and it's the righthand operand of instanceof. 

r instanceof Range   // => true: Range.prototype is in r's prototype chain

// instanceof only walks the prototype chain -- it never actually checks
// whether `r` was built by calling Range(). This can be exploited (and
// occasionally exploited by accident):
function Strange() {}
Strange.prototype = Range.prototype;
new Strange() instanceof Range   // => true, even though .from/.to were
                                  // never set and none of its methods will
                                  // behave sensibly

Every ordinary function automatically gets a prototype object the moment it's defined, and that object automatically carries one non-enumerable property: constructor, pointing back at the function. So F.prototype.constructor === F holds for any plain function F, and any instance new F() inherits a .constructor property that identifies its class. The catch: as soon as you replace Range.prototype wholesale with an object literal (as both examples above do), that auto-generated constructor link is gone — the new object literal never had one. If code downstream relies on instance.constructor, you must restore it by hand, or avoid overwriting the prototype and instead add methods to the existing one: 

// Option 1: put the back-reference back explicitly
Range.prototype = {
  constructor: Range,
  includes(x) { /* ... */ },
};

// Option 2: never replace the prototype object -- extend it in place,
// which preserves the automatically created constructor property
Range.prototype.includes = function(x) { return this.from <= x && x <= this.to; };
Range.prototype.toString = function() { return `(${this.from}...${this.to})`; };

9.3 Classes with the class keyword ES2015

ES6 gave classes a dedicated syntax, but the machinery underneath — a constructor function plus a shared prototype object holding the methods — is unchanged. class is best understood as a more disciplined way to write exactly the code from the previous section, with mistakes (forgetting prototype, using = instead of a method shorthand, forgetting to restore constructor) made structurally impossible. 

class Range {
  constructor(from, to) {
    this.from = from;
    this.to = to;
  }
  includes(x) { return this.from <= x && x <= this.to; }
  *[Symbol.iterator]() {
    for (let x = Math.ceil(this.from); x <= this.to; x++) yield x;
  }
  toString() { return `(${this.from}...${this.to})`; }
}

let r = new Range(1, 3);
r.includes(2);   // => true
[...r];          // => [1, 2, 3]
  • The constructor keyword names the function that runs on new — but the variable the whole declaration produces is named Range, not "constructor".
  • If you need no initialization at all, you can omit constructor entirely; an empty one is generated for you.
  • Method bodies use object-literal shorthand syntax, but — unlike an object literal — there are no commas between members, and a class body cannot hold plain key: value data properties the way an object literal can.

Deep dive: what class desugars to Not a new object model

It's worth seeing this stated as plainly as possible, because it's the single fact that makes every other rule in this chapter predictable rather than arbitrary: a class declaration produces a constructor function. Nothing more exotic happens. typeof Range === "function" is true. Range.prototype exists and holds the instance methods, exactly as in the previous section. The two examples below are behaviorally interchangeable. 

// Written with the class keyword
class Point {
  constructor(x, y) { this.x = x; this.y = y; }
  dist() { return Math.hypot(this.x, this.y); }
  static origin() { return new Point(0, 0); }
}

// The desugared, pre-ES6 equivalent -- run either and Point behaves the same
function PointOld(x, y) { this.x = x; this.y = y; }
PointOld.prototype.dist = function() { return Math.hypot(this.x, this.y); };
PointOld.origin = function() { return new PointOld(0, 0); };

typeof Point                              // => "function"
Point.prototype.dist === Point.prototype.dist  // => true, one shared method
new Point(3, 4).dist()                    // => 5
Object.getPrototypeOf(new Point(3, 4)) === Point.prototype  // => true

A second worked example, showing that instanceof means exactly what it meant for old-style constructors — a prototype-chain check, nothing about the class keyword makes it "more real": 

class Animal {}
let a = new Animal();

// Swap out the prototype object after the fact, same as with function
// constructors -- class instances are ordinary objects with an ordinary
// prototype chain, and nothing prevents this (it's just rarely useful).
function Impostor() {}
Impostor.prototype = Animal.prototype;
new Impostor() instanceof Animal   // => true -- same loophole as §9.2

Two real differences do exist, and they're the only two: class bodies are always evaluated in strict mode even with no directive, and class declarations, like let, are not hoisted — the binding exists in a temporal dead zone until the declaration is actually reached (see Statements). A function declared with function can be called from code that textually precedes it; a class cannot.

Static methods

A method marked static is attached to the constructor function itself, not to prototype — so it's called on the class, never on an instance. Static methods are also called "class methods" for this reason, in contrast to ordinary "instance methods." 

class Range {
  constructor(from, to) { this.from = from; this.to = to; }
  static parse(s) {
    let matches = s.match(/^\((\d+)\.\.\.(\d+)\)$/);
    if (!matches) throw new TypeError(`Cannot parse Range from "${s}"`);
    return new Range(Number(matches[1]), Number(matches[2]));
  }
}

let r = Range.parse("(1...10)");   // OK -- called on the class
r.parse("(1...10)");               // TypeError: r.parse is not a function

Because a static method is invoked through the constructor rather than through any particular instance, using this inside one almost never makes sense (it would refer to the constructor function itself, not to any Range).

Getters, setters, and other method forms

Every shorthand method form legal in an object literal is legal in a class body too: getters and setters (accessed like a plain property but backed by a function — see Objects), generator methods marked with *, async methods, and methods whose name is computed via a bracketed expression (most commonly [Symbol.iterator], as in the Range examples above). The only syntactic wrinkle relative to object literals is that there's no trailing comma after a getter or setter. 

class Temperature {
  #celsius;
  constructor(celsius) { this.#celsius = celsius; }
  get fahrenheit() { return this.#celsius * 9 / 5 + 32; }
  set fahrenheit(f) { this.#celsius = (f - 32) * 5 / 9; }
}
let t = new Temperature(0);
t.fahrenheit;        // => 32 -- read like a property, runs like a method
t.fahrenheit = 212;  // invokes the setter
t.fahrenheit;        // => 212

Public fields, private fields, and static fields ES2022

The original ES6 class spec only let you declare methods — any per-instance data ("fields," an OOP synonym for properties) had to be assigned inside constructor. Field declaration syntax was standardized later, letting you declare fields directly in the class body instead: 

// Old way: fields only exist as assignments inside the constructor
class Buffer {
  constructor() {
    this.size = 0;
    this.capacity = 4096;
    this.buffer = new Uint8Array(this.capacity);
  }
}

// New way: field declarations move to the top of the class body, and are
// still run as part of construction -- `this.` is required on the right
// side of an initializer even though it's dropped on the left side
class Buffer2 {
  size = 0;
  capacity = 4096;
  buffer = new Uint8Array(this.capacity);
}

A field declared with no initializer (just name;) starts out undefined; it's better style to always give an explicit initial value. Prefixing a field (or a method, or a static member) with static attaches it to the constructor function instead of to instances — useful for shared constants or lookup tables the whole class needs but no individual instance owns. 

class Range {
  static integerRangePattern = /^\((\d+)\.\.\.(\d+)\)$/;
  static parse(s) {
    let matches = s.match(Range.integerRangePattern);
    if (!matches) throw new TypeError(`Cannot parse Range from "${s}"`);
    return new Range(Number(matches[1]), Number(matches[2]));
  }
}

Deep dive: # private fields are real encapsulation Enforced by the language, not by politeness

Long before private fields existed, JavaScript programmers signaled "don't touch this from outside" with a leading underscore — this._size. That convention communicates intent to other programmers, but the language enforces nothing: obj._size is a completely ordinary, readable, writable, enumerable property. Anyone (or any library) with a reference to the object can read it, overwrite it, or iterate over it with for...in or Object.keys(). The only true privacy technique before # fields was to capture state in variables closed over by methods created inside the constructor — but that forces every method to be redefined per-instance instead of shared once on the prototype, which is slower and less idiomatic.

A field name starting with # is different in kind, not just in convention. It's a distinct piece of syntax: the field is accessible only by code lexically written inside the same class body, and it doesn't merely hide from casual enumeration — it's unreachable and undetectable from the outside by any means at all, including reflection. 

class Account {
  #balance = 0;                 // private -- only this class's own code can see it
  constructor(openingBalance) { this.#balance = openingBalance; }
  deposit(amount) { this.#balance += amount; }
  get balance() { return this.#balance; }   // the only sanctioned way out
}

let a = new Account(100);
a.balance;          // => 100, via the getter
a.#balance;          // SyntaxError -- outside the class body, `#balance` is
                     // not even parseable as a property reference
Object.keys(a);      // => [] -- private fields never show up in enumeration
JSON.stringify(a);   // => "{}" -- and never get serialized either

Contrast that with merely making a property non-enumerable via Object.defineProperty() (see Objects): a non-enumerable property still shows up under Object.getOwnPropertyNames(), is still directly readable as obj.secret, and can still be deleted or overwritten by any caller. It hides from enumeration only. A # field hides from everything — there is no reflection API that can list, read, or write it from outside the declaring class, and even asking whether #balance in obj only type-checks inside that same class body. 

// Non-enumerable is NOT the same thing as private:
class LooksPrivate {
  constructor() {
    Object.defineProperty(this, "secret", {
      value: 42, enumerable: false, writable: true
    });
  }
}
let lp = new LooksPrivate();
Object.keys(lp);                          // => [] -- hidden from enumeration
lp.secret;                                // => 42 -- but freely readable!
lp.secret = 99; lp.secret;                // => 99 -- and freely writable!
Object.getOwnPropertyNames(lp);           // => ["secret"] -- and discoverable

// True privacy requires the # syntax -- there is no runtime configuration
// of an ordinary property that achieves the same guarantee.
Declare before you use

A private field must be declared with the field syntax directly in the class body (even with no initializer: #size;) before any method can reference this.#size. You cannot conjure a private field into existence with a bare assignment inside the constructor the way you can with a public one.

Class expressions

Like function declarations, class declarations have an expression form. A class expression can be anonymous, or carry a name that's only visible inside its own body: 

let Square = class { constructor(x) { this.area = x * x; } };
new Square(3).area;   // => 9

let Named = class Inner {
  whoAmI() { return Inner.name; }   // "Inner" is only visible in here
};
typeof Inner;   // ReferenceError outside the class body

Class expressions are far less common in everyday code than function expressions (arrow functions cover most of that use case), but they matter when you need to write a function that takes a class and returns a new one built on top of it — a "mixin factory," covered under subclassing below.

Worked example: a Complex number class

Pulling every piece from this section together — constructor, instance methods, getters, static methods, and static "constant" fields attached after the fact: 

class Complex {
  constructor(real, imaginary) {
    this.r = real;
    this.i = imaginary;
  }
  plus(that) { return new Complex(this.r + that.r, this.i + that.i); }
  times(that) {
    return new Complex(
      this.r * that.r - this.i * that.i,
      this.r * that.i + this.i * that.r
    );
  }
  static sum(c, d) { return c.plus(d); }
  static product(c, d) { return c.times(d); }
  get real() { return this.r; }
  get imaginary() { return this.i; }
  get magnitude() { return Math.hypot(this.r, this.i); }
  toString() { return `{${this.r},${this.i}}`; }
  equals(that) {
    return that instanceof Complex && this.r === that.r && this.i === that.i;
  }
}
// Static "constants" attached after the class body, since this example
// predates static field syntax being usable everywhere:
Complex.ZERO = new Complex(0, 0);
Complex.ONE = new Complex(1, 0);
Complex.I = new Complex(0, 1);

let c = new Complex(2, 3);
let d = new Complex(c.i, c.r);
c.plus(d).toString();     // => "{5,5}"
c.magnitude;               // => Math.hypot(2, 3)
Complex.product(c, d);     // => Complex {r: 0, i: 13}
Complex.ZERO.toString();   // => "{0,0}"
Classes should almost always define toString()

Without one, template literals, string concatenation, and console.log fall back to the default "[object Object]". A short custom toString() pays for itself the first time you debug an instance.

9.4 Adding methods to existing classes

Because prototype-based inheritance is fully dynamic, methods added to a prototype object after instances already exist are immediately visible to those instances too — property lookup walks the prototype chain at access time, not at creation time. That means any class, including your own and including JavaScript's built-ins, can be extended after the fact simply by assigning a new method onto its .prototype. 

// Add a method to a class you already defined
Complex.prototype.conj = function() { return new Complex(this.r, -this.i); };

// The same trick works on built-in prototypes -- useful historically for
// polyfilling a method a JS engine didn't yet implement:
if (!String.prototype.startsWith) {
  String.prototype.startsWith = function(s) {
    return this.indexOf(s) === 0;
  };
}

// Or for adding conveniences the language never had:
Number.prototype.times = function(f, context) {
  let n = this.valueOf();
  for (let i = 0; i < n; i++) f.call(context, i);
};
(3).times(i => console.log(`hello ${i}`));
Monkey-patching built-ins is usually a bad idea

Adding methods to built-in prototypes risks colliding with a same-named method a future JavaScript version defines — your polyfill and the real spec can silently disagree about edge cases. It's especially dangerous on Object.prototype: any property you add there becomes visible on every object via for...in loops, unless you go out of your way to define it with Object.defineProperty() and enumerable: false.

9.5 Subclasses

A subclass extends a superclass: its instances inherit the superclass's methods, may override some of them, and its constructor typically has to run the superclass constructor so the object is fully initialized on both levels. This section first shows the manual machinery of subclassing before ES6, then the same thing expressed with extends and super, then discusses when to avoid subclassing altogether in favor of composition, and finishes with a worked hierarchy of abstract and concrete classes.

Subclassing the old way

Making B a subclass of A boils down to one line: point B.prototype at an object that itself inherits from A.prototype, rather than at a plain object. Object.create() does exactly this. 

function Span(start, span) {
  if (span >= 0) { this.from = start; this.to = start + span; }
  else { this.to = start; this.from = start + span; }
}

// The line that actually creates the subclass relationship:
Span.prototype = Object.create(Range.prototype);
// Object.create() gives us a plain object as the prototype, with no
// constructor back-reference -- restore it explicitly:
Span.prototype.constructor = Span;
// Overriding toString() shadows the one inherited from Range.prototype:
Span.prototype.toString = function() {
  return `(${this.from}... +${this.to - this.from})`;
};

let s = new Span(1, 3);
s.includes(2);     // => true -- inherited straight from Range.prototype
s.toString();      // => "(1... +3)" -- Span's own override wins

This works, but only because Span happens to know enough about Range's internals to fully reimplement initialization and stringification itself, without ever calling into Range(). A general-purpose subclassing mechanism needs a way to actually invoke the superclass's constructor and the superclass's overridden methods — before ES6, doing that reliably was awkward. That's the gap super closes.

extends and super Rules to know cold

extends added onto a class declaration wires up the prototype chain automatically — including, uniquely, chaining the constructors' own static members together, something no amount of manual prototype-juggling could do before ES6. 

class EZArray extends Array {
  get first() { return this[0]; }
  get last() { return this[this.length - 1]; }
}
let a = new EZArray(1, 2, 3, 4);
a instanceof EZArray;   // => true
a instanceof Array;     // => true -- a genuine Array under the hood
a.push(5); a.pop();     // inherited instance methods still work
a.first;                // => 1 -- subclass getter
Array.isArray(a);       // => true
EZArray.isArray(a);     // => true -- static methods are inherited TOO

// This last line only works because of `extends` specifically:
Array.isPrototypeOf(EZArray);   // => true -- EZArray itself inherits from
                                 // Array, not just EZArray.prototype from
                                 // Array.prototype. Pre-ES6 prototype
                                 // surgery had no equivalent for this.

The interesting rules all live in the constructor. Consider a TypedMap that layers key/value type-checking on top of the built-in Map: 

class TypedMap extends Map {
  constructor(keyType, valueType, entries) {
    if (entries) {
      for (let [k, v] of entries) {
        if (typeof k !== keyType || typeof v !== valueType) {
          throw new TypeError(`Wrong type for entry [${k}, ${v}]`);
        }
      }
    }
    super(entries);              // MUST come before any use of `this`
    this.keyType = keyType;      // now safe to set subclass-owned state
    this.valueType = valueType;
  }
  set(key, value) {               // overrides Map.prototype.set
    if (this.keyType && typeof key !== this.keyType) {
      throw new TypeError(`${key} is not of type ${this.keyType}`);
    }
    if (this.valueType && typeof value !== this.valueType) {
      throw new TypeError(`${value} is not of type ${this.valueType}`);
    }
    return super.set(key, value);  // delegate the real work upward
  }
}

These are the four rules worth memorizing, not just skimming:

RuleWhy it exists
If your class uses extends, its constructor must call super(...)The superclass is responsible for laying down its own part of the object first; the engine enforces this instead of trusting convention
You may not reference this before super() has run — doing so throws a ReferenceErrorthis is not fully "alive" until the superclass constructor has had a chance to initialize its share of the object
Omit the constructor entirely and one is synthesized that forwards all its arguments straight to super(...)So a subclass adding only methods, no new state, needs zero constructor boilerplate
super.method(...) inside any method calls the superclass's version, and — unlike super() in the constructor — has no restriction on when in the method body you call itOverriding a method usually means extending, not fully replacing, the inherited behavior

Two more worked examples make the "why" concrete rather than abstract. First, what actually happens if you skip super(): 

class Base { constructor() { this.tag = "base"; } }

class Broken extends Base {
  constructor() {
    this.oops = true;   // ReferenceError: must call super before accessing 'this'
  }
}
new Broken();   // throws immediately -- never even reaches the assignment

class Fixed extends Base {
  constructor() {
    super();          // Base's constructor runs first, sets this.tag
    this.oops = true;  // NOW this is usable
  }
}
new Fixed().tag;   // => "base"

Second, the override-and-delegate pattern with super.method(), showing it's legal to call the superclass version at any point — beginning, middle, or end — unlike the constructor's hard "before this" rule: 

class Logger {
  log(msg) { return `[LOG] ${msg}`; }
}
class TimestampedLogger extends Logger {
  log(msg) {
    let base = super.log(msg);     // call the overridden version first...
    return `${new Date().toISOString()} ${base}`;  // ...then extend its result
  }
}
new TimestampedLogger().log("started");
// => "2026-...Z [LOG] started"

One more subtlety: inside a superclass constructor, new.target refers to whichever constructor was originally invoked with new — so if TimestampedLogger is instantiated, code running inside Logger's own constructor (if it had one) would see new.target === TimestampedLogger, not Logger. A well-behaved superclass rarely needs to branch on this, but it's occasionally handy for logging or for blocking direct instantiation of an abstract base (see below).

Composition instead of subclassing

extends is easy to reach for, but every layer of subclassing is a permanent coupling between two classes' internals. When you want to reuse another class's behavior without committing to a true is-a relationship (and without being on the hook for instanceof checks succeeding), it's often simpler and more flexible to hold an instance of that class privately and delegate to it. 

// A Histogram counts occurrences, unlike Set which only tracks membership.
// It could try to subclass Set, but the counting logic actually wants a
// Map internally -- so delegate to a Map instead of inheriting from Set.
class Histogram {
  #map = new Map();
  count(key) { return this.#map.get(key) ?? 0; }
  has(key) { return this.count(key) > 0; }
  get size() { return this.#map.size; }
  add(key) { this.#map.set(key, this.count(key) + 1); }
  delete(key) {
    let n = this.count(key);
    if (n === 1) this.#map.delete(key);
    else if (n > 1) this.#map.set(key, n - 1);
  }
  [Symbol.iterator]() { return this.#map.keys(); }
}
Favor composition over inheritance

Reach for extends when a subclass genuinely is a more specific version of its parent, needs to pass instanceof checks against it, or a framework requires you to extend its base class. Otherwise, wrapping another object as a private field and delegating to it is usually easier to reason about and harder to break by accident — a lesson borrowed directly from classic object-oriented design literature, not something unique to JavaScript.

Class hierarchies and abstract classes

JavaScript has no formal notion of an "abstract class" or "abstract method" the way Java does — there's no keyword that forbids instantiation or that marks a method as unimplemented. The pattern is instead just a convention: a method body of throw new Error("Abstract method"), which makes any subclass that forgets to override it fail loudly and immediately rather than silently misbehaving. 

class AbstractSet {
  has(x) { throw new Error("Abstract method"); }   // subclasses must override
}

class NotSet extends AbstractSet {
  constructor(set) { super(); this.set = set; }
  has(x) { return !this.set.has(x); }
  toString() { return `{ x | x not in ${this.set} }`; }
}

class RangeSet extends AbstractSet {
  constructor(from, to) { super(); this.from = from; this.to = to; }
  has(x) { return x >= this.from && x <= this.to; }
  toString() { return `{ x | ${this.from} <= x <= ${this.to} }`; }
}

// A second layer of abstraction: this class implements isEmpty(),
// toString(), and equals() concretely, purely in terms of an abstract
// `size` getter and an abstract iterator that its OWN subclasses supply.
class AbstractEnumerableSet extends AbstractSet {
  get size() { throw new Error("Abstract method"); }
  [Symbol.iterator]() { throw new Error("Abstract method"); }
  isEmpty() { return this.size === 0; }
  toString() { return `{${Array.from(this).join(", ")}}`; }
  equals(other) {
    if (!(other instanceof AbstractEnumerableSet)) return false;
    if (this.size !== other.size) return false;
    for (let el of this) if (!other.has(el)) return false;
    return true;
  }
}

class SingletonSet extends AbstractEnumerableSet {
  constructor(member) { super(); this.member = member; }
  has(x) { return x === this.member; }         // only the 3 abstract methods
  get size() { return 1; }                      // need real implementations --
  *[Symbol.iterator]() { yield this.member; }    // isEmpty/toString/equals are free
}

new SingletonSet(5).toString();   // => "{5}"
new SingletonSet(5).equals(new SingletonSet(5));  // => true

This is the payoff of a class hierarchy done well: each concrete leaf class only has to implement the handful of primitive operations that are genuinely specific to it, while every derived, composable operation (isEmpty, equals, toString) is written exactly once, high up in the hierarchy, and inherited everywhere below.

Mixins: working around single inheritance

A class can only extends one thing — JavaScript, like most class-based languages, has single inheritance, not multiple inheritance. When you want to blend in behavior from more than one source (say, both "is serializable" and "is comparable" onto a class that already extends something else), the common workaround is a mixin: a function that takes a base class and returns a new subclass adding the extra behavior. Because a class is just a value, and extends accepts any expression that evaluates to a constructor (not just a bare identifier), you can extends someMixin(Base). 

// A mixin is a function from class to class
const Serializable = Base => class extends Base {
  serialize() { return JSON.stringify(this); }
};
const Comparable = Base => class extends Base {
  equals(other) { return this.serialize?.() === other.serialize?.(); }
};

class Point { constructor(x, y) { this.x = x; this.y = y; } }

// Stack mixins by nesting the calls -- each layer extends the last
class SmartPoint extends Comparable(Serializable(Point)) {}

let p = new SmartPoint(1, 2);
p.serialize();                                   // => '{"x":1,"y":2}'
p.equals(new SmartPoint(1, 2));                  // => true
p instanceof Point;                              // => true -- still a Point

This is a pattern built entirely out of ordinary class expressions and extends, not a separate language feature — which is exactly why it works: since class is sugar over constructor functions, an anonymous class expression returned from a function is just another constructor function, perfectly legal as the operand of extends.

Customizing instanceof with Symbol.hasInstance

instanceof's prototype-chain walk is itself just the default behavior — it can be overridden per-constructor by defining a [Symbol.hasInstance] method (a facet of the metaprogramming hooks covered in Metaprogramming). This lets a "class" that isn't built through real subclassing still participate correctly in instanceof checks — useful for duck-typing or for interfaces assembled out of mixins where no single prototype chain captures "is one of these." 

class Iterable {
  static [Symbol.hasInstance](obj) {
    return obj != null && typeof obj[Symbol.iterator] === "function";
  }
}

[1, 2, 3] instanceof Iterable;   // => true -- arrays are iterable
"hello" instanceof Iterable;      // => true -- strings are iterable
(42) instanceof Iterable;         // => false -- numbers are not
// None of these values are in any real prototype relationship with
// Iterable -- the check is entirely custom logic, not a chain walk.

9.6 Summary

  • Objects belong to the same class exactly when they inherit from the same prototype object — that shared prototype, buildable with nothing more than Object.create(), is the one truly essential feature of a JavaScript class.
  • Before ES6, classes were defined with a constructor function: every function carries a prototype property, and new uses it as the new object's prototype. The prototype object is the class's mechanism; the constructor is its public name and identity.
  • class is syntax sugar over that same constructor-and-prototype mechanism — it changes the spelling (strict mode by default, no hoisting, a dedicated place for static members and fields) but not the underlying object model.
  • Public fields, private # fields, static methods, static fields, getters, setters, and generator methods can all be declared directly in a class body.
  • #-prefixed fields are enforced by the language as genuinely private — invisible to enumeration, reflection, and outside code — unlike the older underscore-naming convention, which was purely cosmetic.
  • A subclass is declared with extends; its constructor must call super(...) before touching this, and its methods may call super.method(...) to build on rather than replace inherited behavior.
  • When a true is-a relationship and passing instanceof checks aren't required, composing another object as a private field and delegating to it is often more flexible than subclassing it.
