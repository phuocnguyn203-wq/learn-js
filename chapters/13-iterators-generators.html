Iterators & Generators

Every for...of loop, every use of ... to spread something into an array, and every destructuring assignment that pulls values out of a Map or a Set is leaning on the same small, formal contract: the iteration protocol. This chapter takes that protocol apart piece by piece, shows you how to implement it by hand so your own classes become "loopable," and then introduces generators — an ES6 language feature that gives you almost all of that power for a fraction of the ceremony. The second half of the chapter is about the part of generators that trips up almost everyone the first time: they are not just a one-way stream of yielded values, they are a genuine two-way communication channel between the code driving the generator and the code inside it.

12.1 How iterators work Core concept

It is entirely possible to use for...of, spread, and destructuring for years without knowing what actually happens underneath them. But every one of those features is implemented in terms of three cooperating, separately-defined types, and understanding all three is what lets you build your own iterable data structures instead of only consuming the built-in ones.

The three types: iterable, iterator, iteration result

RoleWhat it isThe contract
Iterable object Any type you can loop over: Array, String, Set, Map, typed arrays, or your own class Has a method named with the symbol Symbol.iterator that, when called with no arguments, returns an iterator object
Iterator object A one-shot cursor over the iterable's values, created fresh each time you start iterating Has a next() method that, when called with no arguments, returns an iteration result object
Iteration result A plain object describing "one step" of the iteration Has a value property (the yielded value) and/or a boolean done property (true once iteration has finished)

Note the oddity right away: the method that makes something iterable is not named iterator() or anything else you'd guess as a string — it is keyed by the well-known symbol Symbol.iterator. That's deliberate. A regular string-named method like "iterator" could collide with an unrelated property some other library or user code already defined; a symbol key can't collide with anything. To iterate an iterable "by hand," you call its Symbol.iterator method once to obtain an iterator, and then call that iterator's next() repeatedly until you get back a result whose done is true: 

let iterable = [99];
let iterator = iterable[Symbol.iterator]();  // step 1: get an iterator
for (let result = iterator.next();           // step 2: pump next() until done
     !result.done;
     result = iterator.next()) {
  console.log(result.value);                 // result.value == 99
}

// This hand-rolled loop is EXACTLY what the engine does for you when you write:
for (let x of iterable) { console.log(x); }

for...of is nothing more than syntax sugar over that get-iterator-then-pump-next loop. Once you can see that, a lot of JavaScript's iteration-related behavior stops being magic.

Everything that consumes the protocol

A surprising number of separate-looking language features all bottom out in the same call to [Symbol.iterator]() followed by repeated next() calls: 

// for/of — loop once per iterated value
let sum = 0;
for (let i of [1, 2, 3]) { sum += i; }
sum   // => 6

// spread (...) — expand an iterable into an array literal or argument list
let chars = [..."abcd"];       // ["a", "b", "c", "d"]
let data = [1, 2, 3, 4, 5];
Math.max(...data)              // => 5

// destructuring assignment — pulls values out positionally via next()
let purpleHaze = Uint8Array.of(255, 0, 255, 128);
let [r, g, b, a] = purpleHaze; // a == 128

// Array.from() — also iterates rather than requiring an array-like object
Array.from("hello")            // => ["h", "e", "l", "l", "o"]

None of these features know or care what kind of object they're given — an Array, a Set, a string, or a class you wrote yourself last week. As long as the object honors the protocol, all of these "just work."

Iterating Map: key/value pairs by default

Map is worth calling out specifically because its default iteration yields two-element [key, value] arrays rather than keys or values alone — which reads very naturally when combined with destructuring in a for...of loop: 

let m = new Map([["one", 1], ["two", 2]]);
for (let [k, v] of m) console.log(k, v);   // logs "one 1" then "two 2"

[...m]            // => [["one", 1], ["two", 2]]  — default iteration
[...m.entries()]  // => [["one", 1], ["two", 2]]  — entries() is the same thing
[...m.keys()]     // => ["one", "two"]             — keys() iterates keys only
[...m.values()]   // => [1, 2]                     — values() iterates values only

Set works the same way you'd expect (iterating its elements in insertion order); see Set and Map for the full API.

A convention: iterators are iterable too

The built-in iterator objects returned by arrays, strings, Map, and Set are themselves iterable — each has a Symbol.iterator method that simply returns this. That sounds redundant, but it means an iterator can be dropped anywhere an iterable is expected, including into another for...of loop or a spread. This is genuinely useful when you want to consume part of a sequence and hand off "the rest" to something else: 

let list = [1, 2, 3, 4, 5];
let iter = list[Symbol.iterator]();
let head = iter.next().value;   // head == 1  (consume just the first value)
let tail = [...iter];           // tail == [2, 3, 4, 5]  (spread consumes the rest)

This only works because the iterator remembers where it left off — a fresh call to list[Symbol.iterator]() would have started over from the beginning.

Built-ins that accept any iterable, not just arrays

Since ES6, many constructors and functions that historically expected an array will happily accept any iterable object instead: 

// Strings are iterable, so these two Sets are identical:
new Set("abc")        // => Set(3) {"a", "b", "c"}
new Set(["a", "b", "c"])

// Array.from also accepts iterables (and array-likes) as its source:
Array.from(new Set([1, 2, 2, 3]))   // => [1, 2, 3]
Design implication

When you write your own APIs, prefer accepting "an iterable" over specifically requiring "an array" wherever that's practical. It costs you nothing and lets callers pass a Set, a generator, or a custom class instead of forcing them to materialize an array first.

12.2 Implementing iterable objects Hand-rolled vs. generator

Once your own class represents something that can sensibly be walked through one value at a time — a range of numbers, a linked list, the nodes of a tree — making it iterable is what lets it plug into for...of, spread, destructuring, and every API in the previous section for free. To do that you implement a method named [Symbol.iterator]() that returns an iterator object with a next() method, and that next() method returns iteration result objects with value and/or done.

Worked example: an iterable Range class, by hand

Here is a Range class that represents the set of numbers between from and to inclusive. It supports membership testing with has(), a readable string form, and — the part we care about — iteration over every integer in the range: 

class Range {
  constructor(from, to) {
    this.from = from;
    this.to = to;
  }

  // Make a Range act like a Set of numbers.
  has(x) { return typeof x === "number" && this.from <= x && x <= this.to; }

  // Return a string representation using set-builder notation.
  toString() { return `{ x | ${this.from} <= x <= ${this.to} }`; }

  // Make a Range iterable by returning an iterator object.
  // The method name is a symbol, NOT the string "Symbol.iterator" — this
  // detail is exactly the thing that's easy to get wrong when typing it out.
  [Symbol.iterator]() {
    // Each call to [Symbol.iterator]() must produce an INDEPENDENT iterator,
    // so all mutable "where am I" state lives in local variables captured
    // by this closure, not on `this`. Two simultaneous for/of loops over the
    // same Range must not interfere with each other.
    let next = Math.ceil(this.from);  // next value this iterator will return
    let last = this.to;               // never return anything greater than this

    return {                          // the iterator object
      next() {                        // must return an iteration result
        return (next <= last)
          ? { value: next++ }         // more to give: hand it out, advance
          : { done: true };           // exhausted
      },
      // Convention: make the iterator itself iterable, by returning `this`.
      [Symbol.iterator]() { return this; },
    };
  }
}

for (let x of new Range(1, 10)) console.log(x);  // logs 1 through 10
[...new Range(-2, 2)]                            // => [-2, -1, 0, 1, 2]

Walk through what happens on each next() call: the closure variable next is the mutable cursor, last is the fixed upper bound captured once. Every call either returns the current cursor value and increments it, or — once the cursor has passed last — returns { done: true } forever after (calling next() again after exhaustion should keep returning a done result, not throw or restart).

The same class, rewritten with a generator

Section 12.3 below covers generator syntax in full, but it's worth seeing the payoff immediately, side by side with the hand-rolled version above, so the motivation for generators is concrete rather than abstract. Here is Range again, with its [Symbol.iterator]() method replaced by a generator method (note the added *): 

class Range {
  constructor(from, to) {
    this.from = from;
    this.to = to;
  }
  has(x) { return typeof x === "number" && this.from <= x && x <= this.to; }
  toString() { return `{ x | ${this.from} <= x <= ${this.to} }`; }

  // A generator method: the * marks it as a generator, and calling it
  // automatically produces an object with a working next() AND a
  // [Symbol.iterator]() that returns itself — both for free.
  *[Symbol.iterator]() {
    for (let x = Math.ceil(this.from); x <= this.to; x++) {
      yield x;
    }
  }
}

for (let x of new Range(1, 10)) console.log(x);  // identical behavior
[...new Range(-2, 2)]                            // => [-2, -1, 0, 1, 2]

Compare the two [Symbol.iterator]() bodies directly. The hand-rolled version needed: an object literal to represent the iterator, two closure variables to track state that used to just be loop variables, an explicit done: true branch, and a manual "make me iterable too" convention line. The generator version is a single for loop with a yield in it — the next/last/done bookkeeping is handled entirely by the language runtime. This is the whole reason generators exist: they are not a different feature from iterators, they are an easier way to implement the exact same iterator protocol. Every generator object already satisfies the iterable contract (it has a working Symbol.iterator that returns itself) and the iterator contract (it has a working next()) without you writing either by hand.

Functions that return iterables, not just classes

Making a class iterable is one pattern; another equally useful one is writing plain functions that accept an iterable and return a new iterable, lazily, without ever materializing an intermediate array. Here are iterator-based reimplementations of map() and filter(): 

// Return an iterable object that lazily applies f() to each value of iterable.
function map(iterable, f) {
  let iterator = iterable[Symbol.iterator]();
  return {                                  // this object is both iterator AND iterable
    [Symbol.iterator]() { return this; },
    next() {
      let v = iterator.next();
      return v.done ? v : { value: f(v.value) };
    },
  };
}
[...map(new Range(1, 4), x => x * x)]   // => [1, 4, 9, 16]

// Return an iterable object that yields only the elements of `iterable`
// for which predicate(element) is true.
function filter(iterable, predicate) {
  let iterator = iterable[Symbol.iterator]();
  return {
    [Symbol.iterator]() { return this; },
    next() {
      for (;;) {
        let v = iterator.next();
        if (v.done || predicate(v.value)) return v;
      }
    },
  };
}
[...filter(new Range(1, 10), x => x % 2 === 0)]   // => [2, 4, 6, 8, 10]

These read a lot like Array.prototype.map/filter (see the array functional toolbox), but they never allocate a full result array — each value is computed exactly when something asks the returned object's next() for it.

Laziness: the whole point of doing this at all

That "compute only when asked" property is the single biggest practical payoff of the iterator protocol. Consider tokenizing a long string into words. String.prototype.split() would work, but it forces the entire string to be scanned and an entire array of substrings to be allocated before you can even look at the first word. An iterator-based tokenizer can hand back one word at a time, computed on demand: 

function words(s) {
  let r = /\s+|$/g;                       // match runs of whitespace, or end-of-string
  r.lastIndex = s.match(/[^ ]/).index;    // start at the first non-space character
  return {                                // an object that is both iterable and iterator
    [Symbol.iterator]() { return this; },
    next() {
      let start = r.lastIndex;            // resume where the last match left off
      if (start < s.length) {
        let match = r.exec(s);
        if (match) return { value: s.substring(start, match.index) };
      }
      return { done: true };
    },
  };
}
[...words(" abc def  ghi! ")]   // => ["abc", "def", "ghi!"]
A simpler way to get the same laziness today

Since ES2020, String.prototype.matchAll() already returns a lazy iterator of match objects with the g flag, which makes hand-writing a tokenizer like the one above rarely necessary in modern code. See using regex patterns: the string methods.

12.2.1 "Closing" an iterator: the return() method

Not every iteration runs to completion. A for...of loop can exit early via break, return, or a thrown exception; destructuring assignment only calls next() as many times as there are variables to fill, and simply abandons the iterator after that, even if it had more values left to give.

That matters when an iterator is holding a resource that needs cleanup — picture a hypothetical iterator that reads words out of a file: it opens a file handle up front and needs to close it, but if the consuming loop breaks out early, the iterator's next() will simply never be called again, and nothing will tell it to close the file.

The protocol's answer is an optional return() method on the iterator object. If iteration stops before a result with done: true was produced, the interpreter checks whether the iterator has a return() method and, if so, calls it with no arguments — giving the iterator one last chance to release memory, close a file, or cancel a subscription. return() must itself return an iteration result object (its properties are ignored, but returning a non-object is an error). 

function readLines(iterable) {
  let iterator = iterable[Symbol.iterator]();
  return {
    [Symbol.iterator]() { return this; },
    next() { return iterator.next(); },
    return(value) {
      console.log("cleaning up: closing the resource now");
      // ... release a file handle, socket, etc. here ...
      return iterator.return ? iterator.return(value) : { done: true };
    },
  };
}

for (let line of readLines(["a", "b", "c", "d"])) {
  if (line === "b") break;   // triggers an automatic call to return() above
}
// logs: "cleaning up: closing the resource now"
You don't get this for free

return() is entirely opt-in — nothing forces you to implement it, and plenty of iterators (including the plain object-literal ones shown earlier in this section) don't. If your iterator holds no resources, skip it. If it does, this is the only reliable hook the protocol gives you for early-exit cleanup.

Writing this triad of iterable object, iterator object, and iteration result by hand every time is exactly the ceremony generators exist to eliminate — which brings us to the rest of the chapter.

12.3 Generators

A generator is a special kind of iterator, produced by a special kind of function, that is defined with new ES6 syntax rather than assembled from object literals by hand. Generators are most valuable when the values you're iterating are the result of an ongoing computation (the next Fibonacci number, the next node of a traversal) rather than simply the existing elements of some data structure.

Generator syntax: three ways to write one

A generator function looks like a regular function but is marked with an asterisk after the function keyword. Calling a generator function does not run its body — it immediately returns a generator object (which is an iterator). The body only actually executes, incrementally, as that generator object's next() is called: 

function* f() {}                    // generator function declaration

const g = function*() {};           // generator function expression

const obj = {
  *m() { /* ... */ },                // shorthand generator method
};

class C {
  *m() { /* ... */ }                 // generator method in a class
  *[Symbol.iterator]() { /* ... */ } // generator as the well-known iterator method
}

// There is NO arrow-function form of a generator — this is a syntax error:
// const bad = *() => {};

How next() drives a generator forward

Calling next() on a generator object runs the function body from wherever it last left off, up to the next yield expression, and hands back yield's operand as the value of the iteration result: 

function* oneDigitPrimes() {
  yield 2;
  yield 3;
  yield 5;
  yield 7;
}

let primes = oneDigitPrimes();   // nothing has run yet — just a generator object
primes.next().value               // => 2
primes.next().value               // => 3
primes.next().value               // => 5
primes.next().value               // => 7
primes.next().done                // => true

// Generators are iterable — their Symbol.iterator method returns themselves:
primes[Symbol.iterator]() === primes   // => true (once you have a fresh one)

// Which means all the usual consumers just work:
[...oneDigitPrimes()]             // => [2, 3, 5, 7]
let sum = 0;
for (let prime of oneDigitPrimes()) sum += prime;
sum                                // => 17

Because generator objects satisfy the iterator/iterable contract automatically, using a generator as a class's [Symbol.iterator]() method — as in the Range rewrite above — is by far the most common way custom classes are made iterable in modern JavaScript code; hand-rolling the object-literal iterator from 12.2 is mostly useful for understanding what a generator is doing for you under the hood.

Generators as ongoing computation: Fibonacci, take(), and zip()

Generators get more interesting once yield is producing values from a real computation rather than a fixed list. A generator's loop can even run forever, because nothing forces it to finish — the loop only advances one step per next() call: 

function* fibonacciSequence() {
  let x = 0, y = 1;
  for (;;) {                    // infinite loop — this generator never finishes
    yield y;
    [x, y] = [y, x + y];        // destructuring assignment, computed as a pair
  }
}

// Safe: a for/of loop can stop consuming an infinite generator whenever it wants.
function fibonacci(n) {
  for (let f of fibonacciSequence()) {
    if (n-- <= 0) return f;
  }
}
fibonacci(20)   // => 10946

// UNSAFE: spreading an infinite generator directly runs until memory is exhausted.
// [...fibonacciSequence()]   // don't do this

A small reusable take() generator turns "safe consumption of an infinite source" into a one-liner, by delegating to the source iterable's own next() and stopping itself after n values: 

// Yield only the first n elements of the given iterable, then stop.
function* take(n, iterable) {
  let it = iterable[Symbol.iterator]();
  while (n-- > 0) {
    let next = it.next();
    if (next.done) return;    // source ran out early — stop cleanly
    else yield next.value;
  }
}
[...take(5, fibonacciSequence())]   // => [1, 1, 2, 3, 5]

And a zip() generator shows how several independent iterators can be driven side by side, round-robin, entirely from inside one generator function: 

// Given multiple iterables, yield their elements interleaved.
function* zip(...iterables) {
  let iterators = iterables.map(i => i[Symbol.iterator]());
  let index = 0;
  while (iterators.length > 0) {
    if (index >= iterators.length) index = 0;         // wrap back to the first
    let item = iterators[index].next();
    if (item.done) {
      iterators.splice(index, 1);                      // that source is exhausted
    } else {
      yield item.value;
      index++;
    }
  }
}
[...zip(oneDigitPrimes(), "ab", [0])]   // => [2, "a", 0, 3, "b", 5, 7]

12.3.2 yield*: delegating to another iterable

A common shape in generator code is looping over some other iterable and yielding each of its elements one by one: 

function* sequence(...iterables) {
  for (let iterable of iterables) {
    for (let item of iterable) {
      yield item;
    }
  }
}
[...sequence("abc", oneDigitPrimes())]   // => ["a", "b", "c", 2, 3, 5, 7]

This pattern is common enough that ES6 gives it dedicated syntax: yield* takes an iterable and yields each of its values in turn, so the inner loop above collapses to one line: 

function* sequence(...iterables) {
  for (let iterable of iterables) {
    yield* iterable;     // yield EVERY value that `iterable` would yield
  }
}
[...sequence("abc", oneDigitPrimes())]   // => ["a", "b", "c", 2, 3, 5, 7]

Because yield* accepts any iterable — including another generator — it's the tool that makes recursive generators practical, for example walking a tree structure non-recursively from the caller's point of view while the generator itself recurses internally: 

function* flatten(tree) {
  for (let node of tree) {
    if (Array.isArray(node)) {
      yield* flatten(node);   // recurse into the nested array via yield*
    } else {
      yield node;
    }
  }
}
[...flatten([1, [2, 3, [4, [5]], 6]])]   // => [1, 2, 3, 4, 5, 6]
Gotcha: yield only works inside a real generator function

It's tempting to reach for Array.prototype.forEach() to replace a loop, but this does not work: 

function* sequence(...iterables) {
  iterables.forEach(iterable => yield* iterable);   // SyntaxError
}

yield and yield* are only legal directly inside a function* body. The callback passed to forEach() is an ordinary (arrow) function — and since arrow functions can never be generators in the first place — the yield* inside it has no enclosing generator to belong to. Stick with an explicit for...of loop, as in the working version above.

12.4 Advanced generator features Where it gets counterintuitive

Everything so far treats a generator as a fancy read-only stream: something pulls values out with next() and the generator never hears back. That's the common case, but it undersells what a generator actually is. The fundamental capability a generator gives you is the ability to pause a running computation, hand control back to the caller, and later resume exactly where it left off — with the caller able to feed a value, or an exception, into that resumption. That makes a generator less like an iterator and more like a suspendable thread of execution living inside your single-threaded program.

12.4.1 The return value of a generator function

A generator function can return a value just like any other function. Doing so produces one final iteration result whose done is true and whose value is the returned value — the one case where value and done: true appear together. Both for...of and the spread operator silently ignore this final value (they stop as soon as they see done: true and never look at its accompanying value), but code that calls next() manually can retrieve it: 

function* oneAndDone() {
  yield 1;
  return "done";     // a real return value, not just an early exit
}

[...oneAndDone()]           // => [1]  — the return value never shows up here

let generator = oneAndDone();
generator.next()            // => { value: 1, done: false }
generator.next()            // => { value: "done", done: true }
generator.next()            // => { value: undefined, done: true } — asks again, gets nothing

That last call matters: once a generator has reported done: true, every subsequent next() keeps returning { value: undefined, done: true } rather than re-running or throwing. A finished generator stays finished.

12.4.2 Two-way communication: what .next(value) actually sends where The counterintuitive part

Here is the detail that catches almost everyone the first time: yield is not a statement, it's an expression, and expressions have values. Specifically:

  • Calling next() resumes the generator and runs it forward until the next yield is reached. Whatever follows that yield keyword is evaluated and becomes the value returned by this call to next().
  • The generator is then frozen in the middle of evaluating that yield expression — it has produced an output value, but it hasn't yet decided what the yield expression itself is worth as an input.
  • The next time next(someArgument) is called, someArgument becomes the value that the paused yield expression evaluates to, and execution continues from there.

In other words, a generator and its caller are two independent streams of execution, passing values back and forth in both directions: values flow out to the caller via each yield's operand, and values flow in to the generator via each subsequent next()'s argument. The tricky asymmetry: the very first next() call only starts the generator running — it can't deliver a value anywhere, because execution hasn't reached any yield expression yet to receive it. Any argument passed to that first next() call is silently discarded.

Worked example, with the mapping between each next() call and the yield expression it "answers" made explicit: 

function* smallNumbers() {
  console.log("started; the first next()'s argument is discarded");
  let y1 = yield 1;    // this yield's VALUE (to y1) comes from the *second* next()
  console.log("resumed; y1 =", y1);
  let y2 = yield 2;    // comes from the *third* next()
  console.log("resumed; y2 =", y2);
  let y3 = yield 3;    // comes from the *fourth* next()
  console.log("resumed; y3 =", y3);
  return 4;
}

let g = smallNumbers();
console.log("generator object created; no generator code has run yet");

let n1 = g.next("a");   // "a" is discarded (nothing was paused at a yield yet)
console.log("got", n1.value);   // n1.value == 1

let n2 = g.next("b");   // "b" becomes the value of the FIRST yield -> y1
console.log("got", n2.value);   // n2.value == 2

let n3 = g.next("c");   // "c" becomes the value of the SECOND yield -> y2
console.log("got", n3.value);   // n3.value == 3

let n4 = g.next("d");   // "d" becomes the value of the THIRD yield -> y3
console.log("got", n4.value, n4.done);   // n4.value == 4, n4.done == true

Running that code prints, in order:

generator object created; no generator code has run yet
started; the first next()'s argument is discarded
got 1
resumed; y1 = b
got 2
resumed; y2 = c
got 3
resumed; y3 = d
got 4

Notice the one-call offset: the value logged as "got 1" was produced by g.next("a"), but the argument "a" itself never appears anywhere in the output — it's the second call, g.next("b"), whose argument "b" shows up (as y1), even though that call's return value is 2, from the yield after the one "b" filled in. Every next(arg) call does two jobs at once: it delivers arg as the result of the yield the generator is currently paused at, and it runs the generator forward to the next yield (or to a return) to determine what value comes back out.

A second, more practical example: a generator-based running accumulator, where each call to next() both retrieves a running total and supplies the next number to add to it: 

function* runningTotal() {
  let total = 0;
  while (true) {
    // the value received here becomes `addend`; the value sent out
    // is the *previous* total, since yield evaluates before we add.
    let addend = yield total;
    total += (addend || 0);
  }
}

let acc = runningTotal();
acc.next();          // => { value: 0, ... }   prime the generator (no addend yet)
acc.next(10)          // => { value: 10, ... }  0 + 10
acc.next(5)           // => { value: 15, ... }  10 + 5
acc.next(20)          // => { value: 35, ... }  15 + 20

That "prime with an argument-less next() first" step is unavoidable for any generator that wants to receive input via yield: the first next() call can only ever start the generator, never deliver a value, precisely because nothing is paused at a yield yet.

Why this used to matter for asynchronous code

Because next(value) can resume a paused generator with any value — including the result of some asynchronous operation that finished after the yield — this mechanism is powerful enough to make asynchronous code read as if it were synchronous: pause at a yield until a network response arrives, then call next(response) to feed it back in. Libraries did exactly this before ES2017. That's precisely the problem async/await was added to solve natively — see async/await: Promises without the ceremony — so there's no longer a good reason to hand-roll it with raw generators.

12.4.3 return() and throw(): controlling a generator from outside

Beyond feeding values in through next(), calling code can also redirect a generator's control flow from the outside using two more methods every generator object has:

MethodEffect inside the paused generator
gen.return(value)Acts as though the currently-paused yield were replaced by return value — the generator finishes immediately with that value
gen.throw(error)Acts as though the currently-paused yield were replaced by throw error — the generator can catch it, or let it propagate and end

return() is exactly what makes generator-based iterators play nicely with the return() cleanup convention from 12.2.1: when a for...of loop over a generator exits early (break, a thrown exception, an early function return), the interpreter automatically calls the generator's built-in return() for you. You can't override that method's identity, but you can make it meaningful by wrapping cleanup-sensitive code in try/finally — the finally block runs even when the generator is terminated from outside this way: 

function* withResource() {
  console.log("resource acquired");
  try {
    yield 1;
    yield 2;
    yield 3;
  } finally {
    console.log("resource released");   // guaranteed to run, even on early exit
  }
}

for (let v of withResource()) {
  console.log("got", v);
  if (v === 2) break;   // triggers the generator's implicit return()
}
// logs: resource acquired / got 1 / got 2 / resource released

throw() gives you a way to send arbitrary "signals," in the form of exceptions, into a running generator — not necessarily fatal ones, if the generator is written to catch and handle them: 

function* resettableCounter() {
  let count = 0;
  while (true) {
    try {
      yield count;
      count++;
    } catch (e) {
      if (e === "reset") {
        console.log("counter reset to 0");
        count = 0;             // handled: keep going instead of dying
      } else {
        throw e;               // unrecognized signal: let it propagate and end the generator
      }
    }
  }
}

let counter = resettableCounter();
counter.next().value    // => 0
counter.next().value    // => 1
counter.next().value    // => 2
counter.throw("reset")  // logs "counter reset to 0", => { value: 0, done: false }
counter.next().value    // => 1

One more wrinkle worth knowing: when a generator uses yield* to delegate to another iterable, calling return() or throw() on the outer generator forwards that call to the delegated-to iterator's own return()/throw(), if it defines them — delegation applies to all three of next(), return(), and throw(), not just to next().

Which methods are required vs. optional

Every iterator must have next(). An iterator that holds a resource needing cleanup should define return(). Any iterator may define throw(), but there's rarely a practical reason for a plain (non-generator) iterator to bother — it's mainly generators, with their try/catch bodies, that make throw() genuinely useful.

12.4.4 Generators as coroutines and state machines

Pulling the two-way-communication features together: a generator is a general-purpose control structure that can pause with yield and resume later with an arbitrary input value supplied by whoever calls next(). That's powerful enough to build a form of cooperative multithreading inside single-threaded JavaScript — a generator can represent a state machine where each yield marks a state boundary, and the value sent in via next() or throw() decides which state comes next. This same mechanism is also, historically, how people simulated async/await before that syntax existed: a "runner" function would drive a generator forward, treating each yielded value as a promise to wait on and resuming the generator with the resolved result.

Prefer async/await for asynchronous code

Using generators to fake synchronous-looking asynchronous control flow works, but the resulting code is genuinely difficult to read and reason about — you're manually reimplementing a scheduler. Modern JavaScript has async functions and await for exactly this purpose, and — for async iteration — for await...of and async generators. There is no longer a good reason to hand-roll either with plain generators; see async/await and for await...of: async iteration on the next page. State-machine-style uses of synchronous generators (parsers, game loops, undo/redo systems) remain a legitimate and idiomatic use of the coroutine-like behavior described in this section.

12.5 Summary

  • for...of and the ... spread operator both work by calling an iterable's [Symbol.iterator]() method to get an iterator, then calling that iterator's next() repeatedly until a result comes back with done: true.
  • An object is iterable if it has a [Symbol.iterator]() method returning an iterator; an iterator is any object with a next() returning iteration result objects shaped { value, done }.
  • You can implement iterables by hand — writing [Symbol.iterator]() to return a fresh object with its own next() — and, when the iteration might end early, an optional return() for cleanup.
  • Generator functions (function*) are a vastly easier way to write the same iterator/iterable pair: calling one returns a generator object immediately, without running the function body; each call to its next() runs the body forward to the next yield, whose operand becomes that call's returned value.
  • yield* delegates to another iterable's values (including another generator's), which is what makes recursive generators practical.
  • Generators are two-way channels, not one-way streams: the argument passed to a next(value) call becomes the value of the previously paused yield expression, offset by one call from the value that same yield handed out.
  • gen.return(value) and gen.throw(error) let outside code force a paused generator to finish or to raise an exception at its current yield — the same mechanism for...of relies on to run a generator's finally blocks after an early break.
  • A generator function itself can return a value, which shows up as the value on the one iteration result where done is also true — ignored by for...of and spread, but visible to manual next() calls.
