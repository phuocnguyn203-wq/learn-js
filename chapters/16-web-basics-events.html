Web Basics & Events

A web browser is JavaScript's original host environment, and it is a much stranger place to run code than Node or a bare interpreter: pages load in stages, scripts from unrelated authors share a single global namespace, and almost everything your program does happens in response to an event rather than as a straight-line script. This page works through the mechanics of that environment — how a document and its scripts are parsed and run, what the global object looks like in a browser, how input arrives and output leaves, the browser's security boundaries, and the event system that ties it all together. The DOM API itself, CSS scripting, layout, components, graphics, navigation, networking, and storage are each their own topic and live on the sibling pages linked throughout.

The <script> element

A browser only executes JavaScript that is embedded in, or referenced from, an HTML document via a <script> tag. Code can appear directly between the opening and closing tags: 

<script>
  function displayTime() {
    document.querySelector("#clock").textContent =
      new Date().toLocaleTimeString();
  }
  displayTime();
  setInterval(displayTime, 1000);
</script>

or the tag's src attribute can point at an external file (an absolute URL or one relative to the hosting document) instead of inlining the code: 

<script src="scripts/digital_clock.js"></script>

A file loaded this way behaves exactly as if its text appeared between the tags — but note that HTML always requires the closing </script>, even when src is present; there is no self-closing <script/> form. Using src instead of inlining has several practical advantages: it separates behavior from markup, lets multiple pages share one copy of the code (and one cached download after the first page fetches it), and lets a page load script served from an entirely different origin — the mechanism most ad and analytics snippets rely on.

The tag's type attribute is essentially vestigial today. Early in the web's history, authors wrote type="application/javascript" or the older language="javascript" in case browsers ever supported other scripting languages; neither ever materialized, JavaScript is the platform's only language, and both attributes are dead weight now. There are exactly two live reasons to set type today: to mark a script as an ES module with type="module" (see Modules for the language-level import/export mechanics), or to embed a blob of non-executable data — JSON, an HTML template — inside the page using an inert type such as type="application/json", a pattern covered on DOM & CSS Scripting.

Loading order: default, defer, async, and module When exactly does it run?

In the earliest browsers there was no API for editing an already-parsed document, so the only way a script could affect page content was to call document.write() while the page was still being parsed, injecting raw HTML text at the script's own location in the stream. That legacy is why a plain <script> tag is, by default, synchronous and blocking: the HTML parser must stop, fetch the script (if it has a src), run it top-to-bottom, and only then resume parsing — because the engine has no way to know in advance whether that script is about to call document.write() and alter the rest of the document. For a large page with several external scripts, that blocking behavior can add seconds of delay before anything is visible.

The defer and async boolean attributes (both meaningful only alongside src) exist to opt out of that default. Both tell the browser "this script will not call document.write(), so you're free to keep parsing the rest of the document while it downloads." They differ in when the downloaded code actually executes:

FormParsing blocked?DownloadsExecutesRelative order
<script src=…>Yes — parser halts to fetch and run itSerially, at the point encounteredImmediately, before parsing resumesDocument order (trivially — nothing else can be running)
<script defer src=…>NoIn parallel with parsingAfter parsing finishes, just before DOMContentLoadedDocument order, always
<script async src=…>NoIn parallel with parsingAs soon as the download completes, which may interrupt parsingWhichever finishes downloading first — may be out of document order
<script type="module">NoIn parallel; recursively fetches every imported module tooDeferred by default (same timing as defer); add async to run as soon as the module graph is readyDocument order unless async is added

If a tag carries both defer and async, async wins. And because a module script defaults to deferred timing, most of the reasoning below for defer applies to plain <script type="module"> tags too.

Walking the timeline makes the difference concrete. Given:

<script src="a.js"></script>
<script defer src="b.js"></script>
<script async src="c.js"></script>
<script defer src="d.js"></script>
  1. The parser hits a.js (no attributes) and stops dead: it fetches the file, runs it completely, then resumes parsing.
  2. It hits b.js (defer) and c.js (async) in turn; both start downloading in the background, and parsing continues immediately past them without waiting.
  3. It hits d.js (defer) and queues its download too, still without blocking.
  4. c.js (async) may finish downloading at any point — even while the parser is still mid-document — and when it does, it runs right away, momentarily pausing the parser. Its execution point relative to b.js/d.js is not guaranteed.
  5. Once parsing of the whole document completes, b.js then d.js run, strictly in that document order, regardless of which one finished downloading first.
  6. Only after all deferred/module scripts have run does DOMContentLoaded fire.

A second worked example shows why this matters for correctness, not just performance. Two deferred scripts can depend on each other's declaration order because deferred execution always preserves document order: 

<script defer src="utils.js"></script>   <!-- defines window.formatDate -->
<script defer src="app.js"></script>     <!-- calls formatDate() at top level -->

If app.js were marked async instead, it could legally execute before utils.js if it happened to download faster, crashing with "formatDate is not a function." This is exactly the class of bug async introduces, and why it should be reserved for scripts with no dependency on document order or on other scripts — typically third-party, self-contained widgets like analytics or ad snippets.

Default to defer or a module script

It gives you non-blocking downloads and predictable, document-order execution — the combination almost every application-level script wants. Reach for plain, attribute-less <script> tags only for truly tiny inline snippets, and reach for async only when a script is independent of everything else on the page.

A simpler, older alternative to any of these attributes — especially for an inline script — is simply placing the <script> tag at the very end of <body>, after all the markup it needs to touch. By the time the parser reaches it, everything above has already been parsed and is ready to query.

Loading scripts on demand

Sometimes code is only needed after some user action — opening a settings panel, say — and there's no reason to pay its download cost on every page load. With modules, the dynamic import() operator (see Modules) loads a module and its dependency graph lazily and returns a promise. Without modules, the classic technique is to create a <script> element yourself and append it to the document, listening for its load/error events to know when it's ready: 

function importScript(url) {
  return new Promise((resolve, reject) => {
    let s = document.createElement("script"); // Build a <script> element
    s.onload = () => resolve();               // Fulfilled once it has run
    s.onerror = (e) => reject(e);              // Rejected if the fetch fails
    s.src = url;                               // Setting src starts the fetch
    document.head.append(s);                   // Must be inserted to load
  });
}

importScript("widgets/date-picker.js").then(() => {
  new DatePicker(document.querySelector("#start-date"));
});

The Document Object Model, briefly

The Document object represents the loaded page, and the API for reading and mutating it — the Document Object Model, or DOM — is the single most important browser API and gets its own dedicated treatment on DOM & CSS Scripting. It's worth previewing the mental model here because everything else on this page assumes it. An HTML document is a tree: every tag becomes an Element node, every run of text becomes a Text node, and Element, Text, and Document are all subclasses of the more general Node. Given: 

<html>
  <head><title>Sample Document</title></head>
  <body>
    <h1>An HTML Document</h1>
    <p>This is a <i>simple</i> document.</p>
  </body>
</html>

the <html> node has <head> and <body> as children; <body> has <h1> and <p> as children; the <p> has a text node, an <i> element, and another text node as its children. Family-tree vocabulary carries over directly: the node directly above another is its parent, nodes one level below are its children, nodes sharing a parent are siblings, everything below a node at any depth is its descendants, and everything above it is its ancestors. Each HTML tag type has a corresponding JavaScript class — <body> is an HTMLBodyElement, <img> is an HTMLImageElement with a src property mirroring the attribute, <video> is an HTMLVideoElement with methods like play() and pause() — and the full API for traversing, creating, and mutating these nodes lives on the DOM & CSS Scripting page.

window: the global object, and why scripts share one

Every browser tab has exactly one global object for its main-thread code (workers get their own; see Storage & Workers), and every non-module script and every inline handler on the page shares it. That global object plays double duty: it hosts the ordinary JavaScript standard library (parseInt, Math, Set, and so on) and it represents the browser window itself, with properties like document (the current page), fetch (network requests, see Navigation & Networking), innerWidth, and history. One of its own properties is named window, and its value is the global object itself — so window and the implicit top-level scope are the same thing, and window.innerWidth means exactly what bare innerWidth means, though the explicit prefix is often clearer for window-specific members.

Because non-module scripts share one global object, they also share one top-level namespace — a historical wart that predates any notion of module scoping. If script A defines a function f() and script B defines a class C, script C can call f() and construct new C() with no import step at all, simply because all three shared <script> tags execute as if concatenated into one program. There's a subtlety in how that sharing happens, though: top-level var and function declarations become actual properties of window, so f() is reachable as either f() or window.f(). Top-level const, let, and class declarations are shared with sibling scripts too, but they do not become properties of window — new C() works, new window.C() does not.

Modules opt out of this entirely

Give a script type="module" and its top-level declarations become private to that module, visible elsewhere only via explicit export/import. That single change is one of the strongest practical reasons to prefer modules for anything beyond a trivial page — see Modules.

An <iframe>'s embedded document gets its own separate window and Document, distinct from the page that contains it — there's no single, formally defined boundary for "a JavaScript program" on the web, but an embedded frame is usually the practical dividing line, subject to the same-origin policy below.

Two phases: loading, then events

It helps to think of a page's JavaScript as running in two distinct phases. During the first, synchronous phase, the document is being parsed and <script> elements run — generally in document order, subject to the defer/async rules above — each one running top to bottom before the next begins. Many scripts do nothing more in this phase than define functions and register the event handlers that will matter later; others do real, one-time work here, such as a trailing script that scans the document for <h1>/<h2> tags and builds a table of contents before the page is ever shown.

Once loading finishes, execution shifts into the second, event-driven phase, which lasts for as long as the tab stays open. Nothing runs here unless the first phase registered a handler for it: from this point on, the browser calls into your code only in response to user input, timers, network completions, or errors, with potentially long idle gaps in between. Spelled out in full, the load sequence looks like this:

  1. The browser creates the Document and begins parsing, adding nodes as it goes; document.readyState is "loading".
  2. A plain <script> (no async/defer/module) is added to the tree and run synchronously the instant the parser reaches it; it may see and mutate document content only up to that point, and it's the only kind of script that can safely call document.write().
  3. async scripts (and their module dependency graphs) start downloading without pausing the parser, and run as soon as they finish — possibly interleaved with parsing.
  4. Once parsing completes, document.readyState becomes "interactive".
  5. defer scripts, and module scripts without async, run in document order.
  6. DOMContentLoaded fires on document — the DOM is fully built and every deferred/module script has run, though outstanding async scripts may not have executed yet.
  7. When every remaining resource (images, stylesheets, iframes, any pending async scripts) finishes, readyState becomes "complete" and load fires on window.
  8. From here on, only asynchronous event handlers run.
document.addEventListener("DOMContentLoaded", () => {
  // The full DOM exists here, but images/stylesheets may still be in flight.
});

window.addEventListener("load", () => {
  // Everything, including images and stylesheets, has finished loading.
});

With a deferred or module script, top-level code already runs after the DOM is fully parsed, so such scripts frequently don't need to wait for DOMContentLoaded at all — one more argument for preferring that loading style.

Single-threaded execution

JavaScript in the browser runs on a single thread shared by the page's script execution and its event handlers. That constraint buys real simplicity: two handlers can never run at once, nothing else can be mutating the DOM out from under your code mid-handler, and there is no need for locks or to reason about race conditions the way you would in a genuinely concurrent language.

A long-running script freezes the whole page

Single-threaded also means the browser stops responding to all input — clicks, scrolling, repainting — for as long as your script or event handler is running. A computationally heavy loop in a click handler doesn't just delay that one feature; it makes the tab look hung to the user. There is no built-in way to "pause" a synchronous script from outside; the fix is either to break the work into chunks yielded back to the event loop (e.g., via setTimeout) or to move it off the main thread entirely with a web worker, a background thread that has no access to the DOM and communicates only via asynchronous messages — covered in full on Storage & Workers.

Program input

A client-side program can read from several sources beyond the DOM itself:

  • The URL. document.URL gives the full address of the current page as a string; wrapping it in new URL(document.URL) gives structured access to the path, query string, and fragment — see Navigation & Networking for how URLs are parsed and used to make requests.
  • Cookies. document.cookie exposes the content of the HTTP Cookie request header as a single, awkward, semicolon-joined string. Cookies exist mainly for server-side session tracking, but client-side code can read and write them too; the full storage picture, including why cookies are usually the wrong tool today, is on Storage & Workers.
  • document.referrer holds the URL of the page that linked to the current one, when the browser supplied one — useful for basic analytics, but not something to trust for security decisions since it can be empty or spoofed-adjacent depending on referrer policy.
  • User input events — clicks, taps, typing into form fields — are the dominant input channel for interactive pages and are the whole subject of the event system below.
  • navigator and screen are the closest thing the browser has to environment variables: navigator.userAgent identifies the browser, navigator.language the user's preferred locale, navigator.hardwareConcurrency the number of logical CPUs available, and screen.width/screen.height the display size.

Program output

The normal way a client-side program produces output is by mutating the document — inserting, removing, or restyling DOM nodes, as detailed on DOM & CSS Scripting — or by delegating that job to a UI framework built on top of the DOM. console.log() and its relatives remain available for diagnostic output, but that output lands only in the developer console, invisible to an ordinary user, so it is strictly a debugging tool, never a user-facing output mechanism.

Avoid document.write()

This is the original, historical way scripts produced output: called while the page is still parsing, it injects raw HTML text directly into the input stream at the script's location. It is exactly why a plain <script> tag must block parsing by default (the engine can't know in advance whether a script will call it), and calling it after the page has finished loading doesn't insert content at all — it implicitly calls document.open() first, which erases the entire existing document and starts a new one. Between the parsing slowdown it forces on every plain script and the destructive behavior post-load, document.write() is considered obsolete; use DOM methods instead.

Program errors

A browser tab has no process to crash the way a Node script can crash the OS process running it: an uncaught exception logs a message to the developer console, and every previously registered event handler keeps working exactly as before. To install a last-resort handler for exceptions that nothing else caught, assign a function to window.onerror: 

window.onerror = function (message, url, line, column, error) {
  reportErrorToServer({ message, url, line, column });
  return true; // Tell the browser we've handled it: suppress its own console message
};

// Equivalent, addEventListener form:
window.addEventListener("error", (event) => {
  reportErrorToServer({ message: event.message, url: event.filename, line: event.lineno });
  event.preventDefault(); // Also suppresses the default console logging
});

window.onerror is invoked with a message string, the URL of the offending script, and a line number (plus, in modern browsers, a column number and the actual Error object); returning true tells the browser the error was handled and it should not also print its own message. A rejected promise with no .catch() is the asynchronous equivalent of an uncaught exception, and is reported the same general way, via window.onunhandledrejection or an "unhandledrejection" listener; the event object carries a promise property (the rejected promise) and a reason property (whatever value it rejected with), and calling preventDefault() on that event marks it handled. Neither handler is required for correct code, but both are the standard hook for shipping client-side error telemetry back to a server via fetch().

The web security model

Letting arbitrary pages run arbitrary code on a visitor's device is inherently dangerous, and the platform balances that against wanting powerful client-side APIs by simply refusing to expose certain capabilities at all: there is no JavaScript API for reading or writing arbitrary files, listing directories, or opening a raw network socket to an arbitrary host. A page can make HTTP requests and, with WebSockets, talk to specially cooperating servers (see Navigation & Networking), but it cannot act as a general-purpose network client.

The same-origin policy

The same-origin policy is the platform's broadest security boundary. It matters most when a page embeds another via <iframe>: script in one frame may read the properties of a window or document only if that document shares the same origin — protocol, host, and port — as the document the script is embedded in. https://example.com:443 and http://example.com are different origins purely because the protocol differs; two different ports on the same host are different origins; and browsers generally treat every file: URL as its own separate origin, which is why testing a multi-document app by opening files directly (rather than via a local static server) often breaks in confusing ways.

What matters for this check is the origin of the document containing a script, not the origin the script's source file was downloaded from. A script fetched via src from host A but embedded in a page served by host B is treated as having host B's origin, and gets full access to that page and any same-origin <iframe>s within it. As soon as one of those frames contains a document from a different origin, the boundary snaps back into place.

Large sites split across subdomains have two escape hatches. A script can widen its own origin by setting document.domain to a suffix of its current host — a script at orders.example.com can set document.domain = "example.com" to interoperate with a document at plain example.com, but it cannot set it to anything shorter than a valid registrable suffix like "com". The more general and modern mechanism is CORS (Cross-Origin Resource Sharing): a server opts in to being read from other origins by sending an Access-Control-Allow-Origin response header (naming specific origins, or * for any), and the browser only relaxes its restriction when that header is present — full request-side details are on Navigation & Networking.

Cross-site scripting (XSS)

XSS is the vulnerability class where an attacker gets their own JavaScript to run inside a victim site's origin, most often by getting unsanitized, attacker-controlled data injected into the page's HTML. This is a classic vulnerable pattern: 

let name = new URL(document.URL).searchParams.get("name");
document.querySelector("h1").innerHTML = "Hello " + name; // DANGEROUS

Visited as greet.html?name=David, this innocently prints "Hello David." But a query string of name=<img src="x.png" onload="alert('hacked')"/> (URL-encoded in the real link) gets assigned straight into innerHTML, and the browser dutifully parses and runs the injected onload handler as if the site's own author had written it — with full access to that origin's cookies and DOM. Because the attack usually arrives as a crafted link hosted or shared on a different site that lures a victim into clicking through to the vulnerable one, it's called cross-site scripting even though the damage happens entirely within the target site's own origin.

The fix is to never let untrusted text reach innerHTML (or an equivalent HTML sink) without escaping its special characters first: 

function escapeHtml(s) {
  return s
    .replace(/&/g, "&amp;")
    .replace(/</g, "&lt;")
    .replace(/>/g, "&gt;")
    .replace(/"/g, "&quot;")
    .replace(/'/g, "&#x27;")
    .replace(/\//g, "&#x2F;");
}
document.querySelector("h1").textContent = "Hello " + name; // safest: no HTML parsing at all
Prefer textContent over escaping innerHTML

Assigning to textContent (or building nodes with document.createElement/append) never parses its argument as markup at all, which sidesteps the whole class of bug rather than relying on remembering to escape correctly every time. When a page must render content it truly cannot trust, sandboxing it inside an <iframe sandbox> (which disables scripting by default) is another layer of defense. Full DOM-writing APIs are covered on DOM & CSS Scripting.

15.2 Events: core vocabulary

Client-side JavaScript is fundamentally event-driven: the browser raises an event whenever something notable happens — a document finishes loading, the pointer moves over a link, a key goes down — and a program registers functions to run when events of interest occur. Five terms describe the whole model precisely:

TermMeaning
Event typeA string naming the kind of event, e.g. "click", "keydown", "load" — also called the event's name.
Event targetThe object the event happened on: most often a Window, Document, or Element, but any object with addEventListener() qualifies — a Worker, for instance, fires "message" events.
Event handler / listenerThe function registered to run when a matching type/target pair fires; this book treats "handler" and "listener" as synonyms.
Event objectPassed as the sole argument to the handler; always has type and target, plus type-specific detail (mouse coordinates, key codes, and so on).
Event propagationHow the browser decides which objects' handlers to invoke for one event — see capturing and bubbling below.

Many events additionally have a default action the browser performs on its own — following a clicked link, submitting a form, scrolling on a touch drag — which a handler can suppress; see event cancellation.

Event categories

There are far too many distinct event types across the platform to enumerate, but they fall into recognizable groups:

  • Device-dependent input — tied to one specific input mechanism: mousedown/mousemove/mouseup, touchstart/touchmove/touchend, keydown/keyup.
  • Device-independent input — abstract over the underlying device: click fires whether the activation came from a mouse, keyboard, or tap; input covers keyboard typing as well as paste and IME composition; pointerdown/pointermove/pointerup unify mouse, touch, and stylus input under one API.
  • User interface events — higher level, usually on form controls: focus, change, submit.
  • State-change events — triggered by the browser or network rather than direct user action: DOMContentLoaded and load (see the load timeline), online/offline, and popstate from history navigation (Navigation & Networking).
  • API-specific events — defined alongside a particular API: <video>/<audio> fire waiting, playing, seeking, volumechange, and more (Web Components & Graphics); older, pre-promise APIs like IndexedDB are built entirely around success/error events (Storage & Workers).

Registering event handlers

There are three ways to attach a handler to a target; only one of them scales.

Handler properties

Setting a property named on plus the lowercase event type — onclick, onchange, onload — to a function registers it as a handler: 

window.onload = function () {
  let form = document.querySelector("form#shipping");
  form.onsubmit = function (event) {   // "this" is the form itself here
    if (!isFormValid(this)) {
      event.preventDefault();          // block submission on invalid input
    }
  };
};

The property names are case-sensitive and always entirely lowercase, even for a multiword type like mousedown — note this is different from frameworks like React, which use camelCase (onClick) for its own synthetic handler props. The fundamental limitation is that a property can hold only one function; assigning a second one silently replaces the first.

HTML handler attributes

The same handler properties can be set directly as HTML attributes, with the attribute value being the body of the function (not a full function declaration): 

<button onclick="console.log('Thank you');">Please Click</button>

The browser wraps that string in a function roughly like function(event) { with(document) { with(this.form||{}) { with(this) { /* your code */ } } } } — which is why such code can refer to event, and to properties of the target, its containing form, and the document, as bare identifiers. That convenience comes from nested with statements, which are forbidden in strict-mode script but are always legal (and always in effect) for HTML attribute handlers — a recipe for confusing name collisions, and the main reason this form is considered obsolete in modern code, even though it still appears in legacy pages.

addEventListener() and removeEventListener()

Every event target — Window, Document, every Element — defines addEventListener(type, handler, options). Unlike a handler property, it never clobbers a previously registered handler; calling it repeatedly with different functions registers all of them, and the browser invokes them in registration order when the event fires: 

<button id="mybutton">Click me</button>
<script>
  let b = document.querySelector("#mybutton");
  b.onclick = () => console.log("Thanks for clicking me!");
  b.addEventListener("click", () => console.log("Thanks again!"));
  // A single click now logs BOTH messages, in registration order.
</script>

Calling addEventListener() never touches the onclick property, and vice versa — the two registration mechanisms coexist peacefully, and invocation order across both is simply the order in which each was registered. Registering the exact same function for the exact same type on the exact same target more than once has no effect: it's stored only once. removeEventListener() takes matching arguments and deregisters a handler — a common pattern is registering temporary mousemove/mouseup handlers on mousedown to track a drag, then removing them once the drag ends: 

function onMouseDown(event) {
  document.addEventListener("mousemove", onMouseMove);
  document.addEventListener("mouseup", onMouseUp);
}
function onMouseUp(event) {
  document.removeEventListener("mousemove", onMouseMove);
  document.removeEventListener("mouseup", onMouseUp);
}

The third argument controls dispatch details. Passing a bare true is shorthand for {capture: true} (registers the handler for the capturing phase instead of the default bubbling phase) — and if you register with true, you must also pass true to removeEventListener() to remove it. More commonly the third argument is an options object: 

let controller = new AbortController();
el.addEventListener("click", handler, { once: true });     // auto-removes after first firing
el.addEventListener("scroll", handler, { passive: true });  // promises never to call preventDefault()
document.addEventListener("click", handler, {
  capture: true, once: true, passive: true,
  signal: controller.signal,                                // abortable via the controller
});
controller.abort(); // removes the listener regardless of capture/once/passive
passive: true matters for scroll performance

Chrome and Firefox register touchmove/wheel listeners as passive by default because a handler that might call preventDefault() forces the browser to wait for it to finish before it can safely start scrolling — on a touch device, that delay is felt as jank. Marking a listener { passive: true } is a promise that it will never call preventDefault(), letting the browser scroll immediately in parallel; if you genuinely need to block scrolling from such a handler, pass { passive: false } explicitly to opt back into the blocking behavior.

removeEventListener() also accepts an options object, but only its capture property is checked — once and passive are meaningless when removing a listener and are silently ignored.

Event handler invocation

The event object argument

Every handler receives a single Event object. Fields present on essentially all events include:

PropertyMeaning
typeThe event type string, e.g. "click".
targetThe object the event originally occurred on.
currentTargetThe object the currently running handler was registered on — differs from target whenever the event propagated to reach this handler.
timeStampMilliseconds since an arbitrary reference point — useful for measuring elapsed time between two events, not as an absolute clock reading.
isTrustedtrue if the browser itself dispatched the event (a real click), false if script did (see custom events).

Specific event types layer on extra fields — mouse and pointer events add clientX/clientY, keyboard events add key and modifier details, and so on.

The this value

Ordinary (non-arrow) function handlers are invoked as if they were a method of the target — this inside the handler refers to the object the handler was registered on, whether it was registered via a property or via addEventListener(). This does not apply to arrow function handlers, which have no this of their own and instead see whatever this was in scope where they were defined — a common source of confusion when converting old-style handlers to arrow functions.

Return value and invocation order

Modern handlers shouldn't return anything meaningful; the preferred way to cancel a default action is event.preventDefault(), described next. Some legacy code instead returns false from a handler (for example, a form onsubmit handler) to signal that the default action should be skipped — supported for backward compatibility, but not the idiom to write going forward. When multiple handlers are registered on one target for one type, they run in the order they were registered, and this ordering is consistent even when property-based and addEventListener()-based handlers are mixed on the same object.

Event propagation: capturing and bubbling Two-phase (really three-phase) dispatch

When an event's target is a standalone object like Window or a Worker, dispatch is simple: the browser just invokes that object's own handlers. But when the target is a Document or an Element nested inside others, the browser doesn't stop at the target — it walks the whole ancestor chain in two directions, giving every event exactly three phases:

  1. Capturing phase. Starting at window and moving down the tree — document, then <html>, then <body>, and so on — only handlers registered with {capture: true} fire, stopping just short of the target itself.
  2. Target phase. Handlers registered directly on the target element run, in registration order, regardless of how they were registered.
  3. Bubbling phase. Starting back at the target's parent and moving up to window, ordinary (non-capturing) handlers on each ancestor fire in turn. This is where the overwhelming majority of handlers live, since it's the default when no capture option is given.

Not every event bubbles: notably focus, blur, and scroll do not. The load event on a document element bubbles as far as Document but no further — it never reaches window; the window-level load event described earlier is a distinct firing, triggered only once the entire page has finished.

A single, concrete example makes all three phases visible at once. Given nested markup: 

<div id="outer">
  <div id="inner">
    <button id="btn">Click</button>
  </div>
</div>

registering both a capturing and a bubbling listener on the outer element:

let outer = document.querySelector("#outer");
let btn = document.querySelector("#btn");

outer.addEventListener("click", () => console.log("outer capture"), { capture: true });
outer.addEventListener("click", () => console.log("outer bubble"));
btn.addEventListener("click", () => console.log("target"));

// Clicking the button logs, in this exact order:
//   "outer capture"   (capturing phase, on the way down)
//   "target"          (target phase)
//   "outer bubble"    (bubbling phase, on the way back up)

A second example shows why capturing is useful on its own: it lets a container intercept an event before it can ever reach a target, which is exactly how drag interactions are often implemented — motion needs to be tracked by the element being dragged, not by whatever element happens to sit underneath the pointer as it moves: 

function startDrag(downEvent) {
  let dragTarget = downEvent.currentTarget;
  function onMove(moveEvent) {
    dragTarget.style.left = moveEvent.clientX + "px";
    dragTarget.style.top = moveEvent.clientY + "px";
  }
  function onUp() {
    document.removeEventListener("mousemove", onMove, { capture: true });
    document.removeEventListener("mouseup", onUp, { capture: true });
  }
  // Capture on document so intervening elements can't "steal" the drag events.
  document.addEventListener("mousemove", onMove, { capture: true });
  document.addEventListener("mouseup", onUp, { capture: true });
}

Event delegation

Bubbling's more everyday payoff is event delegation: instead of registering a handler on every individual child element, register one handler on a shared ancestor and inspect event.target to figure out which descendant was actually involved. 

document.querySelector("ul#todo-list").addEventListener("click", (event) => {
  if (event.target.matches("button.delete")) {
    event.target.closest("li").remove();
  } else if (event.target.tagName === "LI") {
    event.target.classList.toggle("done");
  }
});
// One listener handles every <li> and every delete button --
// including ones added to the list long after this handler was registered.
Why delegate

A delegated handler keeps working for elements added to the DOM later, since it never needed to know about any specific child in the first place — it just relies on bubbling to see the click. It also uses less memory and setup time than attaching a separate listener to every row of a long list, which matters once that list has hundreds of items.

Event cancellation

Browsers perform default actions for many events regardless of whether your code reacts too: clicking a link navigates, typing in a focused text field inserts the character, dragging a finger on a touchscreen scrolls. Three methods on the event object give a handler control over that behavior and over further propagation, and they are independent of one another:

MethodEffect
event.preventDefault()Suppresses the browser's built-in default action for this event (following the link, submitting the form, scrolling). Has no effect on propagation, and is itself ineffective if the listener was registered with { passive: true }.
event.stopPropagation()Stops the event from continuing on to any further ancestors (or descendants, during capture) — but any other handlers already registered on the current element still run.
event.stopImmediatePropagation()Everything stopPropagation() does, plus it skips any remaining handlers on the current element too.
form.addEventListener("submit", (event) => {
  if (!isFormValid(form)) {
    event.preventDefault(); // Don't actually submit -- but propagation continues normally
  }
});

link.addEventListener("click", (event) => {
  event.stopPropagation(); // Container's delegated click handler will never see this click
});

Dispatching custom events CustomEvent

Any object that supports addEventListener() is, by definition, an "event target," and every event target also has a dispatchEvent() method — meaning application code can define and fire its own events with the same API the browser uses internally. This is a clean way to decouple a piece of code that detects something from the code that reacts to it: a data-loading module, say, that has no idea a loading spinner even exists. 

// The module doing the work only needs to know how to announce its state:
document.dispatchEvent(new CustomEvent("app:busy", { detail: { loading: true } }));

fetch(url)
  .then(handleResponse)
  .catch(handleError)
  .finally(() => {
    document.dispatchEvent(new CustomEvent("app:busy", { detail: { loading: false } }));
  });

// The UI module reacts, with zero knowledge of what triggered the state:
document.addEventListener("app:busy", (event) => {
  spinner.hidden = !event.detail.loading;
});

The first argument to CustomEvent() is the event type string; the second is an options object whose detail property carries whatever payload — primitive, object, anything — you want handlers to receive. If the event is meant to be dispatched on a document element and should propagate the normal way, add bubbles: true to that same options object, since events created via CustomEvent() don't bubble by default. Custom events go through the identical capturing/target/bubbling pipeline as native ones, and their isTrusted property is false, marking them as script-dispatched rather than generated by an actual user or browser action.
