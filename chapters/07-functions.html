Functions & Closures

A function is a block of code, written once, that can be invoked any number of times with different arguments. In JavaScript, functions are also full-fledged values — they can be stored in variables, passed around, attached to objects as methods, and even carry their own properties. This page works through every part of that story: the three ways to define a function, the five ways to invoke one (and the wildly different rules each applies to this), how parameters really work under the hood, what a closure actually is and why the classic loop bug happens, and how treating functions as data opens the door to a functional style of programming.

8.1 Defining functions

JavaScript gives you three distinct syntaxes for creating a function, and they are not interchangeable — they differ in hoisting behavior, in whether they get a name, and (for arrows) in which variables they capture from the surrounding scope. There is also a fourth, rarely-used mechanism, the Function() constructor, covered later in §8.7.7. Generator functions (function*) and async functions are specialized variants covered in Iterators & Generators and Asynchronous JavaScript.

Function declarations

A function declaration is the function keyword followed by a required name, a parenthesized parameter list, and a body in curly braces. The name becomes a variable in the enclosing scope that refers to the function object. 

// Print every enumerable property name and value of an object.
function describeProps(o) {
  for (let key in o) {
    console.log(`${key}: ${o[key]}`);
  }
}

// A recursive function: it calls itself.
function factorial(n) {
  if (n <= 1) return 1;
  return n * factorial(n - 1);
}

// distance() computes a value and returns it; describeProps() above
// has no return statement, so invoking it always yields undefined.
function distance(x1, y1, x2, y2) {
  let dx = x2 - x1, dy = y2 - y1;
  return Math.sqrt(dx * dx + dy * dy);
}

A function that never reaches a return statement — or reaches a bare return; with no expression — simply evaluates to undefined when invoked. That's fine for functions like describeProps() above, whose entire job is a side effect (printing), not a computed value.

Declarations are hoisted, in full

A function declaration's name and its entire body are processed before any statement in the enclosing script, function, or (as of ES6, in strict-mode blocks) block begins to run. That means you can legally call a declared function from code that appears textually above the declaration. Prior to ES6 it was technically illegal (though widely tolerated) to put a function declaration inside a loop or if block; ES6 formalized block-scoped function declarations, but a function declared inside a block is only visible inside that block.

Function expressions

A function expression looks similar but appears as part of a larger expression or statement, and its name is optional. Because it's an expression, you typically assign it to a variable, pass it directly as an argument, or invoke it immediately. 

// Anonymous function expression, assigned to a const.
const square = function (x) { return x * x; };

// A named function expression — the name is useful for self-recursion
// and shows up in stack traces, but it is NOT visible outside the function.
const fact = function recur(n) { return n <= 1 ? 1 : n * recur(n - 1); };

// Passed directly as an argument — no variable needed at all.
[3, 1, 2].sort(function (a, b) { return a - b; });

// Defined and invoked immediately (an IIFE — see §8.5).
let hundred = (function (x) { return x * x; })(10);

Two consequences follow from a function expression not being hoisted the way a declaration is: first, the variable it's assigned to doesn't hold a callable function until that line of code actually executes, so calling it earlier fails; second, prefer const for the assignment so you don't accidentally clobber the function reference later in the file.

Arrow functions ES2015

Arrow functions drop the function keyword entirely and use => to separate the parameter list from the body. They are always expressions, never declarations, so they're never hoisted and never have an implicit name of their own (though JavaScript will infer a display name from the variable they're assigned to, for debugging purposes). 

const sum = (x, y) => { return x + y; };   // Full block body
const sum2 = (x, y) => x + y;              // Concise body: implicit return
const square = x => x * x;                 // One parameter: parens optional
const answer = () => 42;                   // Zero parameters: parens required

// Danger: an arrow function's params and `=>` must be on the same line.
// const bad = x
//   => x * 2;   // parses as two statements, not one arrow function!

// Returning an object literal from a concise body needs parens, or the
// `{` is parsed as the start of a block, not an object.
const wrap = x => ({ value: x });   // Correct: returns {value: x}
const broken = x => { value: x };   // Wrong: `value:` is parsed as a label,
                                     // the function body is a no-op, and it
                                     // returns undefined.

Their concise syntax is exactly why arrows dominate as callback arguments to map(), filter(), and reduce() (see Arrays): 

let cleaned = [4, null, 9, undefined, 16].filter(x => x != null); // [4,9,16]
let roots   = cleaned.map(x => Math.sqrt(x));                     // [2,3,4]

But arrows are not just a shorthand for function — they genuinely behave differently, and the differences all point the same direction: an arrow function has no invocation identity of its own. It does not create its own binding for this, arguments, super, or new.target — instead it transparently inherits all four from whichever non-arrow function textually encloses it. It also has no prototype property, so it can never be used as a constructor — new (() => {})() throws a TypeError.

What "no own arguments" means in practice

Reference arguments inside an arrow function and you'll get the arguments object of the nearest enclosing non-arrow function (or a ReferenceError if there isn't one) — never an arguments list for the arrow itself. This is one more reason to reach for a rest parameter (§8.3.2) instead of arguments when a callback needs to accept a variable number of values.

Nested functions

Functions may be defined inside other functions. A nested function can read and write every parameter and local variable of the function(s) it's textually nested inside, following ordinary lexical scoping rules — this is the seed of closures, treated fully in §8.6. 

function hypotenuse(a, b) {
  function sq(x) { return x * x; }   // sq() can see a and b
  return Math.sqrt(sq(a) + sq(b));
}
hypotenuse(3, 4);   // => 5

8.2 Invoking functions

Defining a function does not run its body — only invoking it does. JavaScript has five invocation mechanisms, and — this is the single most important idea in this chapter — which one you use determines the value of this inside the function body. The function's own source code never changes; only the way it's called does.

Function invocation

A plain invocation expression — a function expression followed by parentheses that is not a property access — is a regular function call. Each argument expression is evaluated left to right and the resulting values are bound to the corresponding parameters. 

describeProps({ x: 1 });
let total = distance(0, 0, 2, 1) + distance(2, 1, 3, 5);

In non-strict mode, a plain function call sets this to the global object. In strict mode — which every ES module and every class body is implicitly in — this is undefined instead, which is why calling an ordinary method-style function without an object produces a TypeError the moment it tries to read a property off this.

Optional call: f?.() ES2020

Insert ?. between the function expression and the parentheses to invoke only if the expression isn't null/undefined: callback?.(value) is shorthand for callback === null || callback === undefined ? undefined : callback(value). See Expressions & Operators for the full optional-chaining family.

Recursion and the call stack

Every active function invocation needs an execution context kept somewhere so the interpreter knows where to resume once that call returns; these contexts stack up as functions call other functions. A recursive function that calls itself hundreds of times is ordinarily fine on modern hardware, but one that recurses tens of thousands of levels deep will typically fail with something like RangeError: Maximum call stack size exceeded. Deeply recursive algorithms are often better rewritten iteratively, or restructured to use tail position (though JavaScript engines are not required to optimize tail calls).

Method invocation

A method is nothing more than a function stored as a property of an object. When the expression being invoked is a property access — obj.f() or obj["f"]() — the invocation is a method invocation, and the object to the left of the dot (or inside the brackets) becomes this for the duration of that call. 

let calculator = {
  a: 3,
  b: 4,
  add() {                        // Method shorthand syntax
    this.result = this.a + this.b;
  },
};
calculator.add();                // Method invocation: this === calculator
calculator.result;                // => 7

// Bracket access and array-element access invoke as methods too:
calculator["add"]();
let handlers = [() => {}, function () { return this; }];
handlers[1]();                    // this is whatever's left of the brackets

Because this is rebound on every method call, the same function value can serve as a method of many different objects, each time operating on whichever object it was invoked through: 

function reportBalance() { return `${this.owner}: $${this.balance}`; }
let acctA = { owner: "Amina", balance: 200, report: reportBalance };
let acctB = { owner: "Bilal", balance: 50,  report: reportBalance };
acctA.report();   // "Amina: $200"
acctB.report();   // "Bilal: $50" — same function, different this

When a method returns an object — often this itself — you can chain further method calls onto the result in a single expression, a style sometimes called method chaining: doStepOne().then(doStepTwo).then(doStepThree).catch(onError). Designing your own methods to return this when they have no other meaningful return value lets callers of your API chain calls the same way.

Constructor invocation

Preceding a function or method call with new makes it a constructor invocation, and constructors follow different rules for arguments, invocation context, and return value than the other styles. (Constructors are covered in full alongside classes in Classes.)

  • A brand-new, empty object is created first. It inherits from whatever object is currently the constructor function's prototype property.
  • That new object — not any object the call syntax might resemble — becomes this inside the constructor body, even for something that looks like a method call: in new obj.M(), obj is not the invocation context.
  • If the constructor returns no value, or returns a primitive, the newly created object is used as the result of the whole new expression regardless. Only an explicit return of an object overrides that and becomes the result instead.
  • The empty parentheses are optional when there are no arguments: new Date() and new Date are equivalent.

Indirect invocation

Because functions are objects, they carry methods of their own. call() and apply() invoke a function while letting you dictate this explicitly, effectively pretending the function is a method of whatever object you name — even if it never was. Full mechanics, including bind(), are covered in the dedicated deep dive at §8.7.4 and §8.7.5, since this is one of the load-bearing ideas of the chapter.

Implicit invocation

Several JavaScript language features quietly invoke a function without any call syntax appearing at the use site. These deserve extra care, precisely because a bug or an expensive side effect hidden inside one of them is much harder to spot than in a function you can see being called:

  • Getters and setters — reading or assigning a property backed by an accessor (see Objects) runs the getter or setter function even though the syntax at the call site is just property access.
  • Object-to-primitive conversion — using an object where a string is expected calls its toString() method; using it where a number is expected calls valueOf() (and Symbol.toPrimitive, if defined, takes priority over both).
  • The iterator protocol — a for/of loop or spread over an iterable calls obj[Symbol.iterator]() and then repeatedly calls .next() on the result; see Iterators & Generators.
  • Tagged template literals — writing tag\`Hello ${name}\` is really a function call: tag is invoked with the literal's string pieces and interpolated values as arguments.
  • Proxy traps — a Proxy object (see Metaprogramming) routes nearly every operation performed on it — property reads, writes, deletion, enumeration — through handler functions you supplied.

How this is chosen, invocation by invocation Core mental model

Pull the five invocation styles together and one rule governs all of them except arrow functions: this is not lexical — it is re-decided at every single call, based purely on the syntax used to make that call, never on where the function was defined. Arrow functions are the sole exception: they never receive their own this binding at all, no matter how they're called.

Invocation styleExamplethis inside the function body
Plain function callf(a, b)Global object (non-strict) or undefined (strict mode)
Method callobj.f(a, b)obj — whatever sits to the left of the dot/bracket at call time
Constructor callnew F(a, b)The freshly created object, before it's even returned
Indirect callf.call(obj, a, b) / f.apply(obj, [a, b])Whatever object you pass as the first argument
Bound callconst g = f.bind(obj); g(a, b)obj — permanently, cannot be re-bound again
Arrow functionconst g = (a, b) => {...}Whatever this was in the enclosing (lexical) scope — fixed forever at definition time

Worked example 1 — the same function object, called four different ways:

function whoAmI() { return this && this.label; }

whoAmI();                          // undefined (strict) — plain call
let alice = { label: "alice", whoAmI };
alice.whoAmI();                    // "alice" — method call
whoAmI.call({ label: "carol" });   // "carol" — indirect call
const asDave = whoAmI.bind({ label: "dave" });
asDave();                          // "dave" — bound call
new whoAmI();                      // {} — the new object; this.label is undefined
                                    // (whoAmI doesn't set any property on it)

Worked example 2 — the bug almost everyone hits once: a plain (non-arrow) nested function does not automatically see the outer method's this, because calling it as helper() (not obj.helper()) is a plain function call, and plain function calls get their own, independent this: 

let widget = {
  label: "widget",
  report() {
    console.log(this.label);        // "widget" — called as widget.report()
    function helper() {
      console.log(this && this.label); // undefined! plain call, own this
    }
    helper();
    const arrowHelper = () => {
      console.log(this.label);      // "widget" — arrow inherits report's this
    };
    arrowHelper();
  },
};
widget.report();
Three ways to fix the nested-function-loses-this bug

1. Arrow function — define the nested helper as an arrow so it inherits this lexically (shown above). 2. Capture a variable — write const self = this; at the top of the outer method and reference self instead of this inside the nested plain function. 3. bind() — call helper.bind(this)(), or store the bound version before invoking it. All three are common in real codebases; arrow functions are the modern default.

8.3 Function arguments and parameters

JavaScript never checks argument types, and it never enforces argument count either — you can call a function with too few arguments, too many arguments, or arguments of the "wrong" type, and the call proceeds regardless. What happens to unsupplied or extra arguments is entirely governed by the parameter-list features below.

Optional parameters and defaults ES2015

Any parameter not given a corresponding argument is simply undefined inside the function — unless the parameter list assigns it a default. A default-value expression is evaluated fresh on every call that needs it (never once, at definition time), and it may reference any parameter declared before it in the list: 

// Pre-ES6 idiom for a missing/falsy argument:
function collectKeys(o, target) {
  target = target || [];          // falsy target (incl. undefined) -> new array
  for (let k in o) target.push(k);
  return target;
}

// ES6 default parameter — cleaner, and only triggers on `undefined`
// specifically (not on other falsy values like 0, "", or null).
function rectangle(width, height = width * 2) {
  return { width, height };
}
rectangle(5);        // => { width: 5, height: 10 }
rectangle(5, 1);      // => { width: 5, height: 1 }
Put optional parameters last

A caller can't skip an earlier parameter to supply a later one — they'd have to pass undefined explicitly for every parameter in between. Always place parameters with defaults after the required ones.

Rest parameters ES2015

A parameter prefixed with ... must be the last one in the list; it gathers every remaining argument into a genuine array (never undefined, worst case an empty array). Functions built this way — accepting any number of arguments — are called variadic functions. 

function largest(first = -Infinity, ...others) {
  return others.reduce((best, n) => (n > best ? n : best), first);
}
largest(4, 19, 2, 77, 3);   // => 77
Don't confuse the two ...s

... in a parameter list (rest parameter) gathers arguments into an array. ... at a call site (the spread operator, next section) does the opposite — it unpacks an iterable into individual arguments. Same three dots, opposite jobs, depending entirely on which side of the call boundary they appear on.

The arguments object

Before rest parameters existed, every non-arrow function body had access to an implicit local called arguments: an array-like object (numeric indices and a length, but no Array.prototype methods) exposing whatever was actually passed at the call site, by position. 

function largestLegacy() {
  let best = -Infinity;
  for (let i = 0; i < arguments.length; i++) {
    if (arguments[i] > best) best = arguments[i];
  }
  return best;
}
largestLegacy(4, 19, 2, 77, 3);   // => 77
Quirks that make arguments worth avoiding in new code

It is not a real array, so .map()/.filter()/.reduce() require first converting it (Array.from(arguments) or [...arguments]). Historically, in non-strict mode, its indexed properties were even "linked" to the named parameters (mutating arguments[0] could change the first parameter's value, and vice versa) — a source of confusing bugs that strict mode disables. Arrow functions have no arguments of their own at all — inside an arrow, the name resolves to the nearest enclosing non-arrow function's arguments, which is rarely what's wanted. And in strict mode, arguments is treated as effectively reserved — you cannot name a parameter or local variable arguments. Prefer a rest parameter in every function you write today.

The spread operator at a call site

... in an argument list unpacks an array (or any other iterable, including strings) into individual positional arguments: 

let readings = [5, 2, 10, -1, 9, 100, 1];
Math.min(...readings);          // => -1

// Rest params (gather) and spread (unpack) often pair up, e.g. to wrap
// a function with instrumentation while forwarding its real arguments:
function timed(f) {
  return function (...args) {
    console.log(`entering ${f.name}`);
    let start = Date.now();
    try {
      return f(...args);        // spread the collected args back out
    } finally {
      console.log(`exiting ${f.name} after ${Date.now() - start}ms`);
    }
  };
}

Destructured parameters

Because binding arguments to parameters is fundamentally an assignment, every destructuring pattern usable in a variable declaration is usable in a parameter list too — array patterns, object patterns, defaults within the pattern, nesting, and rest elements inside the pattern. 

// Array destructuring: unpack a 2-element array into two named parameters.
function addVectors([x1, y1], [x2, y2]) {
  return [x1 + x2, y1 + y2];
}
addVectors([1, 2], [3, 4]);     // => [4, 6]

// Object destructuring: property names on the left of the colon,
// parameter names on the right — easy to mix up, so keep it in mind.
function scaleVector({ x, y, z = 0 }, factor) {
  return { x: x * factor, y: y * factor, z: z * factor };
}
scaleVector({ x: 1, y: 2 }, 3);           // => { x: 3, y: 6, z: 0 }

// Renaming during destructuring: `x: x1` means "read property x,
// bind it to local name x1".
function addNamedVectors({ x: x1, y: y1 }, { x: x2, y: y2 }) {
  return { x: x1 + x2, y: y1 + y2 };
}

// Object destructuring simulates named/keyword arguments — handy once
// a function has many optional parameters and callers would otherwise
// have to remember positional order.
function copyRange({ from, to = from, count = from.length, fromIndex = 0, toIndex = 0 }) {
  let slice = from.slice(fromIndex, fromIndex + count);
  to.splice(toIndex, 0, ...slice);
  return to;
}
copyRange({ from: [1, 2, 3, 4, 5], count: 3, to: [9, 8, 7, 6, 5], toIndex: 4 });
// => [9, 8, 7, 6, 1, 2, 3, 5]

// Rest inside a destructuring pattern (array or object) vs. a true rest
// parameter for the function itself — these are two independent concepts:
function splitFirstTwo([a, b, ...restOfArray], ...restOfArgs) {
  return [a + b, ...restOfArgs, ...restOfArray];
}
splitFirstTwo([1, 2, 3, 4], 5, 6);  // => [3, 5, 6, 3, 4]

// Object rest parameter (ES2018) captures whatever wasn't destructured:
function scaleKeepingExtras({ x, y, z = 0, ...rest }, factor) {
  return { x: x * factor, y: y * factor, z: z * factor, ...rest };
}
scaleKeepingExtras({ x: 1, y: 2, label: "P" }, 2); // => {x:2,y:4,z:0,label:"P"}

Destructuring can nest arbitrarily deep — arrays of objects, objects containing arrays, objects containing objects — but readability degrades quickly past two or three levels. If a destructuring pattern is hard to read at a glance, plain property access and indexing is often the clearer choice.

Argument types

Since nothing about a parameter list declares an expected type, self-documenting parameter names and comments are your main defense. JavaScript's automatic type coercion (see Types, Values & Variables) means passing the "wrong" primitive type to a function expecting a string, for instance, rarely throws — it just gets converted. But that safety net doesn't extend to every case, so functions that would otherwise fail confusingly deep inside their logic are often better off validating up front and failing loudly and immediately: 

function sumAll(iterable) {
  let total = 0;
  for (let value of iterable) {          // throws TypeError if not iterable
    if (typeof value !== "number") {
      throw new TypeError("sumAll(): every element must be a number");
    }
    total += value;
  }
  return total;
}
sumAll([1, 2, 3]);      // => 6
sumAll([1, 2, "3"]);    // throws TypeError — fails fast and clearly

8.4 Functions as values

A function's name is just a variable holding a reference to a function object — there is nothing more special about square in function square(x){...} than about any other variable. That's why the same function object can be aliased, stored in an object property (where we call it a method), or stashed in an array with no name at all: 

function square(x) { return x * x; }
let alias = square;         // alias and square refer to the same function
alias(4);                   // => 16

let obj = { square: function (x) { return x * x; } };
obj.square(4);               // => 16 — invoked as a method

let arr = [x => x * x, 5];
arr[0](arr[1]);               // => 25 — an unusual-looking, but legal, call

This is exactly why Array.prototype.sort() can accept a comparator function: passing behavior as data is what makes sort() generic over any ordering you can express as a two-argument function (see Arrays for the sort-callback contract). A lookup table of functions works the same way: 

const operators = {
  add:      (x, y) => x + y,
  subtract: (x, y) => x - y,
  multiply: (x, y) => x * y,
  divide:   (x, y) => x / y,
  power:    Math.pow,             // built-in functions work here too
};
function apply(opName, a, b) {
  if (typeof operators[opName] !== "function") throw "unknown operator";
  return operators[opName](a, b);
}
apply("multiply", 4, 5);   // => 20
apply("power", 2, 10);     // => 1024

Functions can have their own properties

Functions are a specialized object type, so — just like any other object — you can attach arbitrary properties to a function value. This is occasionally the cleanest place to keep state that should persist across calls but has no business living in a global variable, because it stays visually and lexically tied to the function that uses it: 

// A counter that hands out a new integer every call, using a property
// of the function itself as storage (declarations are hoisted, so this
// assignment above the declaration is legal).
nextId.count = 0;
function nextId() {
  return nextId.count++;
}
nextId();   // => 0
nextId();   // => 1

// Self-caching factorial, using the function object itself as the cache.
function fact(n) {
  if (Number.isInteger(n) && n > 0) {
    if (!(n in fact)) fact[n] = n * fact(n - 1);
    return fact[n];
  }
  return NaN;
}
fact[1] = 1;   // seed the base case
fact(6);       // => 720, caching fact[2] through fact[6] along the way

A closure (§8.6) achieves the same persistence with real privacy — nothing outside the closure can tamper with the counter — so closures are generally the preferred tool when the state genuinely needs to be protected.

8.5 Functions as namespaces

A variable declared anywhere inside a function body — with var, let, or const — is invisible outside that function. Before ES6 block scope existed, this was the standard trick for keeping a chunk of throwaway code from leaking variables into the global scope: wrap it in a function, then call that function once. 

function setupWidgets() {
  // Every variable declared in here is local to setupWidgets,
  // no matter how many of them there are.
}
setupWidgets();   // Don't forget to actually invoke it!

If you don't even want to leave a named function sitting in scope, define and invoke it in the same expression — an Immediately Invoked Function Expression, or IIFE: 

(function () {
  // Runs once, right now; nothing here is visible outside.
})();
Why the leading parenthesis is required

Without the opening (, the parser sees the function keyword at the start of a statement and tries to read a function declaration — which requires a name and cannot be immediately invoked. Wrapping the whole function literal in parentheses forces the parser to treat it as an expression instead, so it can legally be followed by a call. The leading parenthesis also acts as a visual signal to human readers: "this function is meant to run immediately, not to be reused later."

The technique becomes genuinely powerful once the namespace function defines inner functions that use its private variables and then hands those inner functions back out as its return value — at that point you've built a closure, which is the subject of the next section. In modern code, an ES module (Modules) gives every file this same private-by-default scoping without any IIFE ceremony at all.

8.6 Closures The central idea of this chapter

JavaScript is lexically scoped: a function's variables resolve according to where that function was written in the source, not according to who calls it or from where. To make that work, every function object must internally remember not just its own code but a reference to the entire chain of scopes that surrounded it at definition time. That pairing — a function plus the scope it closes over — is a closure. Every JavaScript function is technically a closure; it's just that closures only become visible and interesting once a nested function is invoked from somewhere other than the scope it was defined in — most commonly because the outer function returned it. 

let scope = "global";
function outerA() {
  let scope = "outerA";
  function inner() { return scope; }
  return inner();          // called right here — nothing surprising
}
outerA();                  // => "outerA"

function outerB() {
  let scope = "outerB";
  function inner() { return scope; }
  return inner;             // returns the FUNCTION, not its result
}
let laterCall = outerB();
laterCall();                // => "outerB", NOT "global" — inner() still
                             // resolves `scope` in the scope it was
                             // defined in, even though outerB already
                             // finished running long ago.

That last example is the whole trick: inner keeps a live link to outerB's variable environment for as long as anything can still reach inner — even after outerB() itself has returned and, from the outside, looks like it's "finished." This gives JavaScript native private state, no special syntax required: a variable declared in an outer function is unreachable to any code outside it, yet stays alive as long as an inner function still references it. 

function makeCounter() {
  let n = 0;                       // unreachable from outside this closure
  return {
    increment() { return ++n; },
    reset() { n = 0; },
  };
}
let c1 = makeCounter();
let c2 = makeCounter();            // an entirely separate `n`
c1.increment(); c1.increment();    // c1's n is now 2
c2.increment();                    // c2's n is 1 — totally independent
c1.reset();                        // only resets c1's n; c2 unaffected

Multiple closures can also deliberately share one private variable, simply by being defined together in the same invocation of the outer function: 

function counter(start = 0) {
  let n = start;                   // shared private state
  return {
    get count() { return n++; },   // getter: read-and-increment
    set count(newValue) {          // setter: only allow increasing
      if (newValue > n) n = newValue;
      else throw new Error("count can only increase");
    },
  };
}
let c = counter(1000);
c.count;          // => 1000
c.count;          // => 1001
c.count = 2000;
c.count;          // => 2000
c.count = 500;     // throws Error — this looks like plain property access
                    // syntax at the call site, but it's really invoking a
                    // closure-backed setter function (see §8.2.5).

The var-in-a-loop capture bug Classic gotcha

A closure captures the variable itself, live, not a snapshot of whatever value that variable happened to hold at the moment the closure was created. That distinction is invisible until you create several closures inside one loop — at which point, depending on whether the loop variable was declared with var or with let, you get either one shared variable or a fresh, independent one per iteration. 

// BUGGY — var is function-scoped, so there is only ONE variable i,
// shared by all 10 closures created in this loop.
function makeReadersVar() {
  let readers = [];
  for (var i = 0; i < 10; i++) {
    readers.push(() => i);
  }
  return readers;
}
let rv = makeReadersVar();
rv[5]();     // => 10 — NOT 5! By the time any reader runs, the loop has
             // already finished and i has already reached its final value.
rv[0]();     // => 10 as well — every single closure shares that one i.
// FIXED with let — each iteration of a for(let ...) loop gets its OWN
// fresh binding of i, independent of every other iteration's binding.
function makeReadersLet() {
  let readers = [];
  for (let i = 0; i < 10; i++) {
    readers.push(() => i);
  }
  return readers;
}
let rl = makeReadersLet();
rl[5]();     // => 5, exactly as expected
rl[0]();     // => 0 — each closure has its own private i

Before let existed, the standard workaround was to wrap the loop body in an IIFE that takes the current value as a parameter — a fresh function invocation means a fresh parameter binding, which is exactly the isolation we need: 

// PRE-ES6 FIX: an IIFE creates a new function-call scope per iteration,
// and the parameter `iCopy` captures that iteration's value by value.
function makeReadersIIFE() {
  let readers = [];
  for (var i = 0; i < 10; i++) {
    readers.push((function (iCopy) {
      return function () { return iCopy; };
    })(i));
  }
  return readers;
}
let ri = makeReadersIIFE();
ri[5]();     // => 5 — the IIFE's parameter froze this iteration's value
Why this is more than a loop quirk

The underlying rule generalizes far past loops: with var, every iteration of any loop — and indeed every statement in the whole enclosing function — shares one variable per name, because var is function-scoped, not block-scoped. With let/const, each block (including each loop iteration) gets an independent binding. This single fact is one of the strongest practical reasons to default to let/const everywhere and reserve var for maintaining legacy code.

Closures and this

Remember that this is a keyword, not a lexically scoped variable — a plain function-defined closure does not automatically see the this of the code that encloses it, for exactly the reasons covered in §8.2's this-binding deep dive. The same three fixes apply here: define the closure as an arrow function, capture const self = this; before defining it, or .bind(this) it explicitly.

8.7 Function properties, methods, and the constructor

typeof reports "function", but under the hood a function is just a specialized object, so it can carry properties and expose methods exactly as any other object can.

MemberWhat it gives you
lengthRead-only. The number of declared parameters before the first default or rest parameter (a rest parameter itself is never counted).
nameRead-only. The name used at definition, or the variable/property name an anonymous function expression was first assigned to. Mainly useful for debugging and error messages.
prototypeEvery ordinary function (not arrows, not most built-ins) gets one automatically; it becomes the object that instances created with new inherit from. Covered fully with Classes.

The call() and apply() methods Explicit this, deep dive

call() and apply() both invoke a function immediately with a this value you supply as their first argument — as though the function had been a method of that object all along, even if it never was and never will be again. They differ only in how you supply the remaining arguments: call() takes them individually, comma-separated; apply() takes a single array (or array-like) containing them. 

function reportBalance(currency) {
  return `${this.owner}: ${currency}${this.balance}`;
}
let acct = { owner: "Priya", balance: 340 };

reportBalance.call(acct, "$");     // "Priya: $340" — args listed individually
reportBalance.apply(acct, ["$"]);  // "Priya: $340" — args packed in an array

// This is conceptually equivalent to temporarily attaching the function
// as a method, calling it, then removing it again:
acct.tmp = reportBalance;
acct.tmp("$");
delete acct.tmp;

apply()'s array-of-arguments form is especially handy when you're forwarding a caller's arguments to another function without knowing in advance how many there are — the traditional use case before the spread operator existed for exactly this purpose: 

let readings = [4, 19, 2, 77, 3];
let biggest = Math.max.apply(Math, readings);   // pre-ES6 idiom
let biggestModern = Math.max(...readings);       // equivalent, modern spread

// A logging wrapper that preserves the wrapped method's `this` AND its
// original arguments, using apply() to forward both:
function withLogging(obj, methodName) {
  let original = obj[methodName];
  obj[methodName] = function (...args) {
    console.log(`calling ${methodName}`);
    let result = original.apply(this, args);   // same this, same args
    console.log(`returned`, result);
    return result;
  };
}
Arrow functions ignore the this argument

Arrow functions never accept a new this binding from anywhere, including from call()/apply(). Calling arrowFn.call(someObj) silently ignores someObj for binding purposes — the arrow still uses whatever this was in effect at its own definition site. Any extra arguments after that first one, however, are still passed through normally.

The bind() method Permanent binding, deep dive

bind() does not invoke the function — it returns a brand-new function permanently wired to call the original with a fixed this, no matter how that new function is later invoked (as a plain call, as a method of some other object, even with another bind() — the original binding wins). 

function greet(greeting) { return `${greeting}, ${this.name}`; }
let user = { name: "Noor" };
let greetUser = greet.bind(user);
greetUser("Hello");                 // "Hello, Noor"

// Binding survives being reassigned as someone else's method:
let other = { name: "Ravi", greetUser };
other.greetUser("Hi");               // "Hi, Noor" — still bound to `user`,
                                      // NOT to `other`, despite the syntax
                                      // looking like a method call on other.

bind() also performs partial application: any arguments supplied after the this value are baked into every future call, prepended before whatever arguments the caller supplies later. This works even on arrow functions (which otherwise ignore the this argument) since binding arguments has nothing to do with this. 

let sum = (x, y) => x + y;
let addOne = sum.bind(null, 1);     // this is irrelevant here; bind arg 1
addOne(9);                           // => 10

function scaleThenAdd(y, z) { return this.factor * y + z; }
let scaleBy10AndAddTwo = scaleThenAdd.bind({ factor: 10 }, 2);
scaleBy10AndAddTwo(5);               // => 10*2 + 5 = 25

// bind()'s name property is the original name, prefixed with "bound ":
scaleThenAdd.name;              // "scaleThenAdd"
scaleBy10AndAddTwo.name;         // "bound scaleThenAdd"

In practice, the single most common reason to reach for bind() is making an ordinary function behave like an arrow — permanently pinning it to a particular this before handing it off as a callback (an event handler, a setTimeout callback, a promise .then()), so it doesn't lose track of its intended receiver once JavaScript's normal call-site-determines-this rule would otherwise kick in.

The Function() constructor

Because functions are objects, there's naturally a constructor that builds one from strings at runtime: every argument except the last is a parameter name, and the last argument is the body's source text. 

const multiply = new Function("x", "y", "return x * y;");
multiply(3, 4);   // => 12 — equivalent to function(x,y){ return x*y; }
Why you'll basically never use this

Three problems make Function() a poor everyday tool. First, it re-parses and recompiles its source text on every single call, unlike an ordinary nested function or function expression, which is compiled once — calling it inside a hot loop is a real performance liability. Second, functions it creates are always anonymous. Third, and most surprising: functions created this way do not close over the lexical scope where the new Function(...) expression appears — they behave as if defined at the top level, with access only to global variables: 

let scope = "global";
function makeReader() {
  let scope = "local";
  return new Function("return scope;");   // does NOT capture local scope
}
makeReader()();   // => "global", not "local"

Function() is best thought of as a global-scoped cousin of eval(), useful only for the rare case of compiling genuinely dynamic, string-sourced code at runtime.

8.8 Functional programming

JavaScript isn't a functional language the way Lisp or Haskell are, but treating functions as ordinary data — combined with array methods like map() and reduce() — makes a functional style perfectly workable, and sometimes strikingly concise.

Processing arrays with functions

Compare an imperative computation of a mean and standard deviation with the same computation expressed functionally: 

// Imperative style
let data = [2, 4, 4, 4, 5, 5, 7, 9];
let total = 0;
for (let i = 0; i < data.length; i++) total += data[i];
let mean = total / data.length;                 // => 5
let sumSquares = 0;
for (let i = 0; i < data.length; i++) {
  let d = data[i] - mean;
  sumSquares += d * d;
}
let stddev = Math.sqrt(sumSquares / (data.length - 1));

// Functional style, using map() and reduce() from Array (see §7.8.1)
const add = (x, y) => x + y;
const squareOf = x => x * x;
let mean2 = data.reduce(add) / data.length;
let deviations = data.map(x => x - mean2);
let stddev2 = Math.sqrt(deviations.map(squareOf).reduce(add) / (data.length - 1));

Higher-order functions

A higher-order function is one that accepts a function as an argument, returns a function as its result, or both. They're the backbone of functional composition: 

// Takes a predicate, returns its logical negation as a new function.
function negate(predicate) {
  return (...args) => !predicate.apply(this, args);
}
const isEven = n => n % 2 === 0;
const isOdd = negate(isEven);
[1, 3, 5, 7].every(isOdd);        // => true

// Takes two functions, returns their composition f(g(...)).
function compose(f, g) {
  return function (...args) {
    return f.call(this, g.apply(this, args));
  };
}
const double = x => x * 2;
const increment = x => x + 1;
compose(double, increment)(5);    // => 12 : double(increment(5))

Partial application and currying

bind()'s partial-application behavior (§8.7.5) fixes arguments starting from the left. It's straightforward to write variants that fix arguments from the right, or that fill in a template with gaps: 

function partialLeft(f, ...boundArgs) {
  return function (...callArgs) {
    return f.apply(this, [...boundArgs, ...callArgs]);
  };
}
function partialRight(f, ...boundArgs) {
  return function (...callArgs) {
    return f.apply(this, [...callArgs, ...boundArgs]);
  };
}
const divide = (x, y) => x / y;
partialLeft(divide, 100)(4);    // => 25   : 100 / 4
partialRight(divide, 4)(100);   // => 25   : 100 / 4

// Curry a 2-argument function into a chain of 1-argument functions:
function curry2(f) {
  return x => y => f(x, y);
}
const addC = curry2((x, y) => x + y);
addC(3)(4);   // => 7
const addThree = addC(3);   // partially applied, reusable
addThree(10); // => 13

Memoization

Memoization wraps a function so that results are computed once per distinct set of arguments and then served from a cache on every repeat call — trading memory for time, and turning naive exponential recursive algorithms into linear ones. 

function memoize(f) {
  const cache = new Map();
  return function (...args) {
    let key = JSON.stringify(args);      // works when args stringify uniquely
    if (!cache.has(key)) {
      cache.set(key, f.apply(this, args));
    }
    return cache.get(key);
  };
}

function gcd(a, b) {
  if (a < b) [a, b] = [b, a];
  while (b !== 0) [a, b] = [b, a % b];
  return a;
}
const fastGcd = memoize(gcd);
fastGcd(187, 85);   // => 17, computed and cached

// Recursive functions should recurse through the MEMOIZED name, so that
// every recursive call — not just the outermost one — benefits from cache.
const fib = memoize(function (n) {
  return n <= 1 ? n : fib(n - 1) + fib(n - 2);
});
fib(40);   // fast, thanks to caching every intermediate result

8.9 Summary

  • Three syntaxes define functions — declarations (hoisted, named), expressions (not hoisted, name optional), and arrow functions (concise, and lexically inherit this, arguments, super, and new.target rather than binding their own).
  • Five invocation styles exist, and this is determined entirely by which one you use — plain call, method call, constructor call, indirect call via call()/apply()/bind(), and implicit invocation through getters/setters, coercion, iteration, and tagged templates. Arrow functions opt out of this rebinding entirely.
  • Parameters support default values, rest parameters (gathering extra arguments into a real array), and full destructuring patterns; the legacy arguments object still exists but is superseded by rest parameters in new code.
  • Because functions are ordinary objects, they can be stored, passed, aliased, and given their own properties — the foundation of treating behavior as data.
  • A closure is a function bundled with the scope it was defined in; it stays alive and mutable as long as any reference to that function survives, which is what gives JavaScript private state without special syntax — and what causes the classic var-in-a-loop capture bug, fixed by let or by an IIFE.
  • call(), apply(), and bind() let you override or permanently fix this and, for bind(), pre-fill leading arguments (partial application).
  • Combining higher-order functions, partial application, and memoization enables a genuinely functional programming style on top of ordinary JavaScript functions.

Functions become even more capable once you attach them to prototypes and wrap them in class syntax — the subject of Classes next — and once they gain the ability to pause and resume, which is where Iterators & Generators and Asynchronous JavaScript pick up the story.
