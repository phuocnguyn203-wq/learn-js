Modules

A module is a file that gets its own private namespace: nothing it declares leaks into the global scope, and nothing from outside gets in, unless it's explicitly exported or imported. That sounds like a simple idea, but JavaScript took an unusually long and messy road to get there. For most of its life the language had no module keyword at all, so programmers faked modularity with closures; then Node invented its own require()-based system that became a de facto standard; and only with ES6 did the language finally define its own import/export syntax — one that still isn't fully interchangeable with Node's original system. This chapter walks through all three eras, because production code written in any of them is still something you'll have to read.

What "modularity" is actually solving

Modular programming lets you assemble a large program out of pieces written independently, by different authors, without those pieces stepping on each other. Concretely that means two things: hiding implementation details so a module's internal helper functions and variables can't be poked at or accidentally overwritten from outside, and keeping the global namespace tidy so that two unrelated files that both happen to declare a variable named result or a function named parse() don't clobber one another. Every module system this chapter covers — hand-rolled closures, Node's CommonJS, and ES6 modules — is ultimately just a different mechanism for achieving those same two goals.

10.1 Modules with classes, objects, and closures

Before looking at any dedicated module syntax, it's worth noticing that JavaScript already gives you two informal tools for modularity: objects and closures. A class is already a kind of module for its own methods — the has() method defined on one class can't collide with a has() method defined on a completely unrelated class, because each is a property of its own separate prototype object, not a global function named has. The built-in Math object works the same way: instead of polluting the global scope with dozens of loose functions and constants like sin, cos, and PI, the language groups them as properties of a single Math object. You can borrow that same trick for your own code — instead of a pile of global classes, define one namespace object whose properties are the classes: 

// Instead of global SingletonSet, BitSet, AbstractSet classes...
const Sets = {
  Singleton: class SingletonSet { /* ... */ },
  Bit: class BitSet { /* ... */ },
  Abstract: class AbstractSet { /* ... */ }
};

// Consumers reach through the namespace object
let s = new Sets.Bit(64);

This is real modularity in the sense that it keeps the global namespace clean, but it doesn't go far enough: it gives you no way to hide implementation details inside the module. If BitSet has private helper methods or internal lookup tables that users of the class have no business touching, putting them on Sets.Bit doesn't hide them — they're still public properties, just nested one level deeper.

The tool that actually hides things is the closure, covered in depth in the chapter on closures: local variables and nested functions declared inside a function body are private to that function and invisible from outside it. Wrap an entire module's implementation in an immediately invoked function expression (IIFE), keep the private helpers and internal state as ordinary local variables, and return only the public API as the function's return value. The module's "exports" become whatever object (or class, or function) that IIFE hands back; everything else — every helper function, every internal constant — stays sealed inside the closure and is completely unreachable from outside code, even by accident. 

const BitSet = (function () {
  // --- Private implementation details, invisible outside this IIFE ---
  function isValid(set, n) { /* ... */ }
  function has(set, byte, bit) { /* ... */ }
  const BITS = new Uint8Array([1, 2, 4, 8, 16, 32, 64, 128]);
  const MASKS = new Uint8Array([~1, ~2, ~4, ~8, ~16, ~32, ~64, ~128]);

  // --- The public API: just the class itself ---
  // It can freely use isValid(), has(), BITS, and MASKS from its
  // enclosing scope, but nothing outside this IIFE ever can.
  return class BitSet extends AbstractWritableSet {
    // ... implementation omitted ...
  };
}());

The same pattern scales to a module that exports several related values rather than one class. A small "stats" module that exposes mean() and stddev() while keeping its working functions private looks like this: 

const stats = (function () {
  // Private utility functions — not part of the public API
  const sum = (x, y) => x + y;
  const square = x => x * x;

  // Public functions, to be exported
  function mean(data) {
    return data.reduce(sum) / data.length;
  }
  function stddev(data) {
    let m = mean(data);
    return Math.sqrt(
      data.map(x => x - m).map(square).reduce(sum) / (data.length - 1)
    );
  }

  // Export the public functions as properties of a plain object
  return { mean, stddev };
}());

stats.mean([1, 3, 5, 7, 9]);   // => 5
stats.stddev([1, 3, 5, 7, 9]); // => Math.sqrt(10)
This is exactly what a class's private fields formalize

If this feels familiar, it's because ES2022 private class fields (#field, covered in the classes chapter) are a direct, built-in answer to the same problem this IIFE pattern was solving by hand: hiding implementation state that only the module's own code should touch.

10.1.1 Automating closure-based modularity

Turning a plain file of JavaScript into an IIFE-wrapped module like the ones above is a mechanical transformation: wrap the file's contents in a function, decide by convention which names get attached to an exports object, and return that object. Because it's mechanical, it's exactly the kind of thing a build tool can do for you — and this is, historically, where Node's require() function and later bundlers like webpack and Parcel came from. You can sketch the whole idea in a few lines: take a set of source files, wrap each one's contents in an IIFE that creates a local exports object, stash each IIFE's return value in a shared registry keyed by filename, and concatenate everything into one bundle: 

const modules = {};
function require(moduleName) { return modules[moduleName]; }

modules["sets.js"] = (function () {
  const exports = {};
  // ... the contents of sets.js go here ...
  exports.BitSet = class BitSet { /* ... */ };
  return exports;
}());

modules["stats.js"] = (function () {
  const exports = {};
  // ... the contents of stats.js go here ...
  const sum = (x, y) => x + y;
  const square = x => x * x;
  exports.mean = function (data) { /* ... */ };
  exports.stddev = function (data) { /* ... */ };
  return exports;
}());

// Elsewhere in the bundle, other code can now do:
const stats = require("stats.js");
const BitSet = require("sets.js").BitSet;
let s = new BitSet(100);
s.insert(10); s.insert(20); s.insert(30);
let average = stats.mean([...s]); // 20

This toy registry is a fair approximation of what a real bundler produces, and it's also a plain-JavaScript reimplementation of the exact function signature Node exposes natively: require(moduleName) returning whatever the target module chose to export. Understanding this sketch makes Node's real module system — up next — much less mysterious, since it's doing essentially the same thing, just backed by the filesystem instead of a precomputed bundle.

10.2 Modules in Node

Node programs are ordinarily split across as many files as makes sense, because unlike a browser fetching script over the network, Node reads files from a fast local filesystem — there's no strong pressure to bundle everything into one giant file the way there historically was on the web. Node treats every file as an independent module with its own private namespace: top-level constants, variables, functions, and classes declared in a file stay private to that file unless the file explicitly exports them, and a value exported by one module is visible elsewhere only if some other module explicitly imports it. This system is commonly called CommonJS, after the community specification it grew out of. A module imports its dependencies by calling the global require() function, and it exposes its own public API by mutating the global exports object or by replacing module.exports outright.

Full Node coverage lives elsewhere

This section explains the CommonJS module mechanics themselves. For everything else about writing real Node programs — package.json, npm, the built-in modules, the event loop, streams, and so on — see the Node.js chapter.

10.2.1 Node exports

Every Node module has a global-looking exports object available automatically (it is in fact just a local variable that Node arranges to exist inside the function it secretly wraps your module code in). If a module exports several values, the simplest approach is to assign each one as a property of exports as you go: 

// stats.js
const sum = (x, y) => x + y;
const square = x => x * x;

exports.mean = data => data.reduce(sum) / data.length;
exports.stddev = function (d) {
  let m = exports.mean(d);
  return Math.sqrt(d.map(x => x - m).map(square).reduce(sum) / (d.length - 1));
};

Notice that stddev calls exports.mean rather than a bare mean — that's necessary because mean was never declared as a local variable, only attached to exports.

Often, though, a module has exactly one thing to export — a single class or function that is the module — rather than a bag of named utilities. For that case you replace the entire module.exports object instead of adding properties to it: 

// bitset.js
module.exports = class BitSet extends AbstractWritableSet {
  // implementation omitted
};

exports starts out as a plain alias for module.exports — the same underlying object, reachable two ways. That's why assigning properties onto exports works: you're mutating the object that module.exports also points at. But if you reassign exports itself to a brand-new object (exports = { ... }), you've only repointed the local variable; module.exports — the thing Node actually hands to whoever calls require() — still points at the original, now-abandoned object, and none of your exports show up. Always reassign module.exports, never bare exports, when you want to replace the whole thing.

A third common style, useful when a module exports several related functions, is to define everything as ordinary local variables and then export only the public subset in one statement at the end, which also gives private helpers real names instead of forcing them to dangle unattached: 

// Define everything, public and private, as plain locals
const sum = (x, y) => x + y;
const square = x => x * x;
const mean = data => data.reduce(sum) / data.length;
const stddev = d => {
  let m = mean(d);
  return Math.sqrt(d.map(x => x - m).map(square).reduce(sum) / (d.length - 1));
};

// Export only the public ones, in one place
module.exports = { mean, stddev };

10.2.2 Node imports

A module pulls in another module's exports by calling require(moduleName); the return value is whatever that target module assigned to module.exports. How Node interprets moduleName depends entirely on its shape:

  • A bare name with no leading slash or dot, like "fs" or "express", is treated as either one of Node's own built-in modules or a package installed under node_modules. Node walks up the directory tree looking for a matching node_modules folder.
  • A path starting with ./ or ../ is resolved relative to the file doing the requiring — this is how you pull in your own project's files.
  • An absolute path starting with / is legal too, though rarely used in practice. 
// Built-in Node modules — no path characters
const fs = require("fs");
const http = require("http");

// A third-party package installed via npm — also no path characters
const express = require("express");

// Your own code — always begins with ./ or ../
const stats = require("./stats.js");
const BitSet = require("./utils/bitset.js");

You're allowed to drop the .js extension and just write require("./stats") — Node will try appending .js, then .json, then .node, and will also check whether the path is actually a directory containing an index.js (or whatever its package.json "main" field names). Explicit extensions are still common in practice because they make the resolution unambiguous at a glance.

When a module exports a single function or class, importing it is a one-liner: const BitSet = require("./bitset.js"). When a module exports an object bag of multiple properties, you have a choice between importing the whole namespace object or destructuring out just the pieces you need: 

// Import the whole object — everything hangs off one namespace
const stats = require('./stats.js');
let average = stats.mean(data);

// Or destructure exactly what you plan to use into local names
const { stddev } = require('./stats.js');
let sd = stddev(data); // succinct, but loses the "stats." context
CommonJS on the web

Because require()/exports aren't part of the JavaScript language itself, they only work natively in Node. For years, though, bundlers like webpack let web developers write code in exactly this style and compiled it down to something browsers could run — which is why a lot of older web-facing code you'll encounter still looks like CommonJS even though it never touched a Node server. New code doing this is now more likely to be written with the standard ES6 import/export syntax covered below.

CommonJS vs. ES modules, side by side Deep dive

CommonJS and ES modules (ESM) solve the same problem — private per-file namespaces with explicit exports — but they differ in ways that go well beyond spelling. These differences aren't trivia: they explain real bugs you'll hit when mixing the two systems, and they explain why Node still, years after adding ESM support, treats .cjs and .mjs (or the package.json "type" field) as meaningfully different file types.

CommonJS (Node's original)ES Modules (the language standard)
Resolving the module graph require() is an ordinary synchronous function call. It runs, blocking, at the exact point it's written — including inside an if, a loop, or a function body. import/export are declarations, not expressions. The whole graph of static imports is resolved before any module body runs, purely by reading the syntax — no code executes to discover it.
Where they may appear Anywhere — conditionally, dynamically, computed from a variable. Only at the top level of a module, never nested in a block, loop, function, or condition. (The dynamic import() operator, covered later, is the deliberate escape hatch.)
What crosses the module boundary A copy of a reference taken at require() time — really, a snapshot of whatever module.exports pointed to at that moment. Live, read-only bindings. An imported name stays permanently linked to the exporting module's variable; if the exporter later reassigns an exported let, every importer observes the new value immediately.
Reassigning the imported name Legal — it's just a local variable holding whatever require() returned. A SyntaxError/TypeError — imported bindings behave like const from the importer's side, even if the exporter declared them with let.
Top-level this module.exports (an empty object, before you assign to it). undefined, even in top-level code — stricter than plain strict mode, where a function called as a function gets undefined but a script's top level still gets the global object.
require, __dirname, __filename All three exist automatically — Node injects them as parameters/locals when it wraps your file. None of them exist. The equivalent of __dirname/__filename has to be reconstructed from import.meta.url.
File loading Synchronous readFileSync-style disk reads, one module at a time, depth-first as require() calls are reached. Conceptually asynchronous — a browser (or Node) can fetch/read every module in the static graph in parallel before executing any of them.
Strict mode Opt-in — you write "use strict" yourself, or don't. Always on, automatically, no pragma needed.

Worked example: live bindings vs. copied values

This is the difference that causes the most confusing bugs in practice. In an ES module, an exported mutable variable keeps updating for every importer, because what crosses the boundary is a binding, not a value: 

// counter.mjs
export let count = 0;
export function increment() { count++; }
// main.mjs
import { count, increment } from "./counter.mjs";

console.log(count); // 0
increment();
console.log(count); // 1 — the SAME live binding, automatically up to date

count = 5; // TypeError: Assignment to constant variable.

The CommonJS equivalent doesn't have live bindings at all — only objects, whose properties you can still read fresh, but a destructured local variable is frozen at the moment of require(): 

// counter.js
let count = 0;
function increment() { count++; }
module.exports = { get count() { return count; }, increment };
// main.js
const counter = require("./counter.js");
const { increment } = counter;

console.log(counter.count); // 0
increment();
console.log(counter.count); // 1 — works, but only because we exported a
                             // getter; a plain `exports.count = count`
                             // would have frozen 0 forever at require time.

Without the explicit getter trick, module.exports.count would just be a plain number copied out at export time, and every importer's copy would be permanently stuck at whatever it was the instant require() ran — no amount of later mutation inside counter.js would ever be visible again.

Worked example: this, require, and __dirname

// info.cjs — CommonJS
console.log(typeof require);  // "function"
console.log(__dirname);       // e.g. "/home/user/project"
console.log(__filename);      // e.g. "/home/user/project/info.cjs"
console.log(this === module.exports); // true
// info.mjs — ES module
console.log(typeof require); // ReferenceError: require is not defined
console.log(__dirname);      // ReferenceError: __dirname is not defined
console.log(this);           // undefined

// The ESM replacement for __dirname/__filename:
import { fileURLToPath } from "node:url";
import { dirname } from "node:path";

const __filename = fileURLToPath(import.meta.url);
const __dirname = dirname(__filename);
Interop gotchas going between the two systems

Node lets an ES module import a CommonJS file: the entire module.exports object becomes the default export, and Node's static analyzer makes a best-effort guess at named exports by scanning for obvious exports.x = ... assignments — a heuristic that can miss dynamically computed exports. The reverse direction is the real trap: a CommonJS file cannot require() an ES module at all — require() is synchronous and ESM loading fundamentally is not, so Node throws ERR_REQUIRE_ESM. The only way for CommonJS code to consume an ES module is the asynchronous import() operator, which means the calling code has to become async whether it wants to or not.

Circular dependencies Deep dive

Two modules that require or import each other, directly or through a longer chain, create a cycle. Cycles are legal in both systems, but the two systems handle the moment of "the module isn't fully finished loading yet" very differently, and the difference has real consequences for which values you actually see.

Circular require() in CommonJS

Node's algorithm is simple and a little unforgiving: the first time a module is required, Node starts running it top to bottom and immediately caches a reference to its (still-incomplete) module.exports object. If, partway through, that module requires something that circles back and requires the original module again, Node does not re-run it — it hands back whatever module.exports looks like right now, mid-execution, which may well be missing properties that appear later in the file. 

// a.js
console.log("a starting");
exports.done = false;
const b = require("./b.js");
console.log("in a, b.done =", b.done);
exports.done = true;
console.log("a done");
// b.js
console.log("b starting");
exports.done = false;
const a = require("./a.js"); // a is mid-execution — this returns the
                              // PARTIAL exports object from a.js as it
                              // exists right now: { done: false }
console.log("in b, a.done =", a.done); // "in b, a.done = false"
exports.done = true;
console.log("b done");
// main.js
const a = require("./a.js");
// Output, in order:
// a starting
// b starting
// in b, a.done = false      <-- the circular require sees a STALE, partial a.js
// b done
// in a, b.done = true
// a done

The rule to internalize: whichever module is required second inside the cycle sees a partial, in-progress version of the module that required it. If a.js instead exported a function that calls b.done lazily, at call time rather than at require time, it would see the correct final value — the problem is only ever about reading a circularly required value too early, not about the cycle itself being broken. 

// A second worked example: fixing the stale read by deferring access.
// a.js
exports.getBDone = () => require("./b.js").done; // read lazily, not eagerly
const b = require("./b.js");

// b.js
exports.done = true;
const a = require("./a.js");
console.log(a.getBDone()); // true — called AFTER b.js finished, so it's safe

Circular import in ES modules

ESM handles the same scenario more gracefully, precisely because imports are live bindings resolved statically rather than copied values captured at call time. Both modules in the cycle are linked together before either one's body runs, so a binding you import can become valid later even if it wasn't ready the instant the cycle was entered — as long as you don't actually read it before it's initialized. The classic textbook case is mutually recursive function declarations, which work cleanly because function declarations are hoisted: 

// even.mjs
import { isOdd } from "./odd.mjs";
export function isEven(n) { return n === 0 ? true : isOdd(n - 1); }
// odd.mjs
import { isEven } from "./even.mjs";
export function isOdd(n) { return n === 0 ? false : isEven(n - 1); }
// main.mjs
import { isEven } from "./even.mjs";
console.log(isEven(10)); // true — the circular import "just works" because
                          // isOdd/isEven are hoisted function declarations,
                          // fully defined by the time either is called

The failure mode in ESM isn't a stale value the way it is in CommonJS — it's a temporal dead zone error if you try to read a circularly imported let/const binding before its module has gotten around to initializing it: 

// x.mjs
import { y } from "./y.mjs";
console.log(y); // ReferenceError: Cannot access 'y' before initialization
export const x = 1;
// y.mjs
import { x } from "./x.mjs"; // x.mjs is mid-evaluation when this runs
export const y = 2;

Compare the two failure modes directly: CommonJS silently hands you an incomplete object and lets you read undefined properties off it without complaint, which can fail quietly and far from the actual cause; ESM refuses outright with a loud ReferenceError pointing at the exact binding that wasn't ready. Neither system makes circular dependencies free — they're still a design smell worth refactoring away when you can — but ESM at least fails fast instead of fail-silent.

10.3 Modules in ES6 ES2015

ES6 finally gave JavaScript its own built-in module system, using import and export keywords rather than a library-provided require() function. Conceptually it's the same idea as Node's system — each file is its own module, and top-level declarations are private unless exported — but the syntax differs, and so does how a module gets loaded into a web page. Modules also differ from ordinary "classic" scripts in ways that go beyond having import/export available:

  • Code inside a module is automatically in strict mode — you never write "use strict" in a module, because it's implied. That means no with statement, no silent creation of undeclared globals, and other strict-mode restrictions apply unconditionally.
  • Top-level this is undefined inside a module. Contrast this with a classic script, where top-level this is the global object.
  • Each module has its own top-level scope. Declaring let x at the top of one module has zero effect on any other module or on the global object — unlike classic scripts, which all share one global namespace.

10.3.1 ES6 exports

The most direct way to export something is to put the export keyword directly in front of a top-level declaration: 

export const PI = Math.PI;
export function degreesToRadians(d) { return d * PI / 180; }
export class Circle {
  constructor(r) { this.r = r; }
  area() { return PI * this.r * this.r; }
}

As an alternative to scattering export throughout a file, declare everything normally and list what's public in a single statement, typically at the end — many style guides prefer this because it gives you one place to scan for a module's entire public surface: 

const PI = Math.PI;
function degreesToRadians(d) { return d * PI / 180; }
class Circle { /* ... */ }

export { PI, degreesToRadians, Circle };

Despite the curly braces, that last line is not an object literal — it's dedicated export syntax that takes a comma-separated list of identifiers already in scope. That distinction matters because it means you can't put an arbitrary expression inside those braces (more on that in the renaming section below).

When a module has exactly one primary thing to offer, use export default instead: 

export default class BitSet {
  // implementation omitted
}
Default vs. named exports

A module can have at most one default export, but any number of named exports, and it's legal (if uncommon) to have both at once. Plain export only works on a declaration that has a name attached, whereas export default can export any expression at all — an anonymous function expression, an anonymous class expression, even an object literal — since the importer, not the exporting module, is the one who assigns it a name. That's also why, unlike the list form above, curly braces really are an object literal when they follow export default.

Export only at the top level

export — like import — is only legal at the top level of a module. You cannot export from inside a function, a loop, a conditional, or a class body. This is deliberate: it guarantees a module's exports are the same on every run and can be determined by static analysis before any of the module's code actually executes, which is exactly what lets tools eliminate unused exports ("tree shaking") without running your code first.

10.3.2 ES6 imports

Importing a default export binds it to whatever local name you choose — the exporting module never names it, so there's nothing to collide with: 

import BitSet from './bitset.js'; // name it anything you like locally

Imported names behave as if declared with const: you cannot reassign them. Like exports, imports are legal only at a module's top level — never inside a function, loop, or conditional — though by convention (not requirement) they're placed at the very top of the file. They are, in fact, hoisted, the same way function declarations are, so their position in the file doesn't matter to the rest of the module's code.

To import specific named exports, use the destructuring-flavored list syntax: 

import { mean, stddev } from "./stats.js";

To grab every named export at once as properties of a single namespace object — handy when a module exports many things and you don't want a long import list — use the wildcard form: 

import * as stats from "./stats.js";
stats.mean(data);
stats.stddev(data);

The properties of that namespace object are themselves effectively constant — you can't overwrite or delete them from the importing side. If a module happens to define both a default export and named exports (uncommon, but legal), you can pull in both on one line: 

import Histogram, { mean, stddev } from "./histogram-stats.js";

Finally, a module can be imported purely for its side effects, without binding any of its exports (or even if it has none at all): 

import "./analytics.js"; // runs once, on first import; later imports no-op

This is the right shape for a module whose entire job is to run some setup code — registering event listeners, say — rather than to hand back values for other code to call.

Module specifiers must be constant strings

The string naming the module — "./stats.js" — must be a literal single- or double-quoted string. It cannot be a variable, a computed expression, or even a template literal (template literals can interpolate variables, so the engine can't guarantee they're constant). Per the ES6 spec, that string must also be an absolute path starting with /, a relative path starting with ./ or ../, or a full URL with a protocol and host — bare specifiers like "lodash" with no leading path are technically disallowed by the language spec itself (they're ambiguous — is that a sibling file or an installed package?), though bundlers and Node's own ESM loader relax this and resolve bare specifiers against installed packages anyway.

10.3.3 Renaming on import and export

If two modules happen to export something under the same name, or an imported name would collide with something already in scope, use as to rename on the way in: 

import { render as renderImage } from "./imageutils.js";
import { render as renderUI } from "./ui.js";

Default exports never need this — since they carry no name to begin with, the importer always supplies one. That said, renaming provides a second way to combine a default import with named imports on one line, using the literal keyword default as a placeholder for "the unnamed default export": 

import { default as Histogram, mean, stddev } from "./histogram-stats.js";

Renaming works symmetrically on export, again only in the curly-brace list form: 

export {
  layout as calculateLayout,
  render as renderLayout
};
The braces aren't an object literal — expressions aren't allowed

Because the list form of export only accepts bare identifiers, not expressions, you cannot export a property access or any other expression this way, even with renaming: 

export { Math.sin as sin, Math.cos as cos }; // SyntaxError

10.3.4 Re-exports

A common design is to split implementation across small, focused files — a mean.js and a stddev.js instead of one big stats.js — so consumers who need only one function don't pull in code they don't use, while still offering a single convenient stats.js "barrel" file for consumers who want everything. Doing that with plain import-then-export works, but ES6 provides a dedicated one-line re-export form that combines the two steps and doesn't even need to name the value locally: 

// The manual way:
import { mean } from "./stats/mean.js";
import { stddev } from "./stats/stddev.js";
export { mean, stddev };

// The dedicated re-export form — equivalent, more direct:
export { mean } from "./stats/mean.js";
export { stddev } from "./stats/stddev.js";

To re-export absolutely everything a module names, without listing each one, use the wildcard form: 

export * from "./stats/mean.js";
export * from "./stats/stddev.js";

Re-exports support renaming with as exactly like regular imports and exports do — useful for giving a function a second, friendlier public alias: 

export { mean, mean as average } from "./stats/mean.js";

Re-exporting gets slightly more involved when the source module used export default rather than a named export, since a default export has no name to reference — you supply one using the same default as placeholder trick seen earlier: 

export { default as mean } from "./stats/mean.js";
export { default as stddev } from "./stats/stddev.js";

The reverse direction works too — promoting someone else's named export to be your module's default export: 

export { mean as default } from "./stats.js";

And, rarely useful but legal, forwarding another module's default export as your own module's default export: 

export { default } from "./stats/mean.js";

10.3.5 Loading modules in a browser

Native browser support for ES6 modules is triggered by a dedicated script type — a plain <script> tag with no type attribute is always treated as a classic, non-modular script: 

<script type="module" src="main.js"></script>
<script nomodule src="legacy-bundle.js"></script>

A module has a completely static set of imports, which means the browser can discover the entire dependency graph — every module this one imports, and everything those import, recursively — purely by parsing, before running a single line. Given the entry point named by <script type="module">, the module specifiers it imports are resolved as URLs relative to that entry module's own location, and each imported file is fetched, parsed, and recursively scanned for its own imports the same way. None of those dependency modules need — or are permitted to have — their own <script> tags; they're pulled in purely through the import graph.

Module scripts behave like classic scripts tagged with defer: the browser starts fetching the code as soon as the parser reaches the tag (recursively fetching the whole graph), but delays running any of it until HTML parsing has finished. Once parsing completes, module scripts and any deferred classic scripts execute in the order they appear in the markup. The async attribute overrides this for a module script just as it does for a classic one: an async module runs the moment its code (and its whole dependency graph) is ready, even mid-parse, and even if that reorders it relative to other scripts on the page.

Same-origin restrictions and the file:// gotcha

Module scripts are subject to the same cross-origin rules as fetch(): a module can only be loaded from the same origin as the page, unless the server sends proper CORS headers allowing it. In practice this means opening an HTML file straight off disk with a file:// URL frequently fails to load its modules — there's no meaningful "origin" for the browser to check permissions against. Serve the page over http://localhost (any small static file server will do) instead of double-clicking the HTML file.

Browsers new enough to understand type="module" also recognize the nomodule attribute and skip any script carrying it; older browsers do the opposite — they don't recognize either attribute, so they run the nomodule script and ignore the (to them meaningless) type="module" one. That pairing gives you a clean compatibility fallback: ship modern code natively as a module, and ship a transpiled, bundled fallback build for old browsers via nomodule, without any feature detection logic of your own.

Some codebases use a .mjs extension to mark modular files at a glance. Browsers don't actually care about file extensions — only the served MIME type matters, so a web server may need configuring to serve .mjs with the same JavaScript MIME type as .js. Node, on the other hand, does use the extension (or the "type" field in the nearest package.json) as the deciding signal for which module system — CommonJS or ESM — to parse a given file as; see the Node chapter for that configuration.

Import maps: teaching the browser bare specifiers

Native import normally rejects bare specifiers like "lodash" for the ambiguity reasons already mentioned. Modern browsers support an import map — a <script type="importmap"> block declared before any module script — that lets a page define its own bare-specifier aliases, resolved entirely client-side with no build step: 

<script type="importmap">
{
  "imports": {
    "lodash": "/vendor/lodash.js",
    "chart/": "/vendor/chart-lib/"
  }
}
</script>
<script type="module">
  import _ from "lodash";       // resolved via the import map
  import { Bar } from "chart/bar.js";
</script>

Treat this as a bundler-free convenience for small projects and demos rather than a wholesale replacement for a real build pipeline; a full survey of module tooling lives in the tools chapter.

10.3.6 Dynamic import() ES2020

Static import is deliberately rigid — top-level only, constant string specifiers only — precisely so tools can analyze the whole dependency graph without running any code. That rigidity is exactly wrong for loading code on demand: a web app usually wants to ship only the JavaScript needed for the first screen, then fetch the rest lazily as the user navigates, and a page that conditionally needs one of several possible modules can't express that with a static import at all. import() is the escape hatch — an expression, legal anywhere ordinary expressions are, that loads a module on demand and resolves to a Promise for that module's namespace object (the same shape you'd get from import * as ns): 

import("./stats.js").then(stats => {
  let average = stats.mean(data);
});

// Or, inside an async function:
async function analyzeData(data) {
  let stats = await import("./stats.js");
  return { average: stats.mean(data), stddev: stats.stddev(data) };
}

// And because it's a real expression, the specifier can be computed —
// something a static `import` flatly cannot do:
async function loadLocale(locale) {
  const strings = await import(`./locales/${locale}.js`);
  return strings.default;
}

This is the mechanism underlying "code splitting" in every modern bundler: rather than one monolithic bundle, strategically placed import() calls let the bundler carve the app into smaller chunks loaded only when actually needed. See the async JavaScript chapter for a full treatment of the Promises that import() returns.

Operator, not function

import() looks exactly like a function call, but it isn't one — it's a special operator, and the parentheses are part of its required syntax. That's necessary because import() has to resolve relative specifiers against the URL of the module it's called from, something an ordinary function has no way to know. The practical upshot is syntax you'd never expect to fail suddenly does: console.log(import) and let load = import; are both syntax errors, because import can't be referenced as a plain value the way a real function could.

10.3.7 import.meta.url ES2020

Inside a module — never inside a classic script or a require()-loaded CommonJS file — the special syntax import.meta refers to an object holding metadata about the currently running module. Its most useful property, url, is the absolute URL the module itself was loaded from (a file:// URL under Node). The typical use is resolving paths to sibling resources — images, JSON data, localization files — that live alongside the module on disk or on a server, regardless of what page or script ultimately imported it: 

function localStringsURL(locale) {
  return new URL(`l10n/${locale}.json`, import.meta.url);
}

Using import.meta.url as the base for the URL() constructor means the relative path always resolves correctly no matter where the consuming page lives, which a path hardcoded relative to the page's own URL could not guarantee.

10.4 Summary

Modularity exists to let code from different sources — different files, different authors, different points in a project's history — be assembled into one program without one piece silently overwriting another's variables or functions. This chapter traced three distinct systems JavaScript has used to get there:

  • In the language's early years, the only tool for real modularity was disciplined use of closures and IIFEs — private state and helper functions sealed inside a function body, with only a deliberately chosen public API returned outward.
  • Node layered its own module system, CommonJS, on top of plain JavaScript: modules import each other synchronously with require() and declare their public API by mutating the exports object or replacing module.exports outright. It resolves module graphs dynamically, at runtime, one require() call at a time.
  • ES6 finally gave JavaScript a module system as a genuine part of the language: import and export declarations, resolved statically before any module code runs, exposing live read-only bindings rather than copied values — plus, as of ES2020, the import() operator for loading a module dynamically at runtime when static resolution is too rigid.

The two systems are similar enough to invite assumptions and different enough to punish them — synchronous versus static resolution, copied values versus live bindings, and outright incompatible behavior around circular dependencies are the traps worth remembering. New code should default to ES6 modules; CommonJS remains essential reading knowledge because of how much existing Node code — and how much of Node's own documentation and ecosystem — is still written in it.
