Tools & Extensions

Almost nobody ships plain, unprocessed JavaScript anymore. A real project sits inside a pipeline: a linter flags likely bugs, a formatter normalizes style, a test runner proves the code still works, a package manager tracks what the code depends on, a bundler squashes a tree of modules into something a browser can load efficiently, a transpiler rewrites new syntax for older engines, and — increasingly — a type checker catches a whole category of mistakes before the code ever runs. None of this is part of the JavaScript language itself, but you cannot read someone else's project, follow a tutorial, or work on a team without running into all of it. This chapter is a tour of that surrounding ecosystem: what each tool actually does under the hood, why it exists, and where the rough edges are.

17.1 Linting with ESLint

The word lint describes code that runs correctly but is nevertheless a problem: a variable that's declared and never used, a loose == comparison where a strict === was clearly intended, a var in code that should use let or const. None of this stops the program from executing, which is exactly what makes it dangerous — nothing crashes to tell you about it. A linter is a static-analysis tool that reads your source code without executing it and reports on patterns like these. ESLint is the linter almost every JavaScript project uses today.

It's worth being precise about the difference between a linter and a formatter (the subject of the next section): a formatter rewrites whitespace and punctuation — indentation, quote style, line breaks — without changing what the code does. A linter looks for things that are more substantive than whitespace: correctness risks, dead code, and API misuse that a formatter has no opinion about. Historically ESLint did both jobs (it has rules for quote style and indentation too), but in most modern setups those stylistic rules are switched off and delegated entirely to Prettier, leaving ESLint to focus on the bugs a formatter can't see.

Take this small, syntactically valid, buggy function:

var x = 'unused';
export function factorial(x) {
  if (x == 1) {
    return 1;
  } else {
      return x * factorial(x-1)
  }
}

Running ESLint against it surfaces several distinct problems at once:

$ eslint linty.js
linty.js
  1:1   error    Unexpected var, use let or const instead      no-var
  1:5   error    'x' is assigned a value but never used        no-unused-vars
  1:9   warning  Strings must use doublequote                  quotes
  4:11  error    Expected '===' and instead saw '=='            eqeqeq
  5:1   error    Expected indentation of 8 spaces but found 6   indent
  7:28  error    Missing semicolon                              semi

✖ 6 problems (5 errors, 1 warning)
  3 errors and 1 warning potentially fixable with the `--fix` option.

Each line names the specific rule that fired (no-var, eqeqeq, no-unused-vars, and so on) — ESLint ships with a large built-in rule set, and an ecosystem of plugins layers on more rules for specific frameworks (eslint-plugin-react, eslint-plugin-vue) or concerns (accessibility, import ordering, security-sensitive patterns). Every rule can be individually turned off, set to "warn", or set to "error" in a config file — historically .eslintrc.json, though newer ESLint versions favor a flat eslint.config.js.

SeverityEffect
"off" / 0Rule is disabled entirely
"warn" / 1Reported, but doesn't fail a CI run (exit code stays 0)
"error" / 2Reported and fails the run (nonzero exit code)

Rather than hand-picking hundreds of individual rules, most projects extend a shareable config — a curated bundle of rule settings published as a package, such as eslint:recommended, Airbnb's popular style guide config, or the "standard" config — and then layer a handful of project-specific overrides on top: 

{
  "extends": ["eslint:recommended", "plugin:react/recommended"],
  "rules": {
    "no-console": "warn",
    "eqeqeq": "error"
  }
}

Finally, notice the last line of the ESLint output above: several of those problems are auto-fixable. Running eslint --fix mechanically rewrites the file to correct anything ESLint can safely correct on its own — missing semicolons, quote style, indentation — while leaving semantic issues like the unused variable or the == comparison for you to fix by hand, since fixing those could change program behavior and ESLint won't guess at your intent.

17.2 JavaScript Formatting with Prettier

Enforcing a consistent visual style across a codebase used to mean configuring dozens of ESLint stylistic rules and arguing about tabs versus spaces in a pull request. Prettier replaces that entire argument: it's an opinionated formatter that parses your code into a syntax tree and reprints it from scratch in one canonical style, with almost no configuration surface. You don't tell Prettier how to format things — you just run it, and it decides.

Given deliberately mangled but functioning code:

function factorial(x)
{
         if(x===1){return 1}
           else{return x*factorial(x-1)}
}

Prettier rewrites it into the conventional form the whole team will now share:

$ prettier factorial.js
function factorial(x) {
  if (x === 1) {
    return 1;
  } else {
    return x * factorial(x - 1);
  }
}

Run plain, Prettier prints the reformatted file to stdout; pass --write and it rewrites the file in place instead. The options it does expose are deliberately few — maximum line length, indent width, whether to add semicolons, single versus double quotes — and the defaults are considered good enough that most teams never touch them. That's the whole philosophy: adopt it once, agree to stop having opinions about formatting, and let the tool decide every time.

Prettier earns its keep through integration rather than through manual invocation. Editors can be configured to run it automatically on every save, so you write sloppy, quickly-typed code and watch it snap into shape. Teams commonly go further and wire it into a Git pre-commit hook (with tools like husky and lint-staged) so that nobody can commit code that hasn't been formatted, regardless of their editor setup: 

{
  "lint-staged": {
    "*.js": ["prettier --write", "eslint --fix"]
  }
}
Prettier and ESLint, together

Because ESLint's own stylistic rules can conflict with what Prettier decides, most projects install eslint-config-prettier, which simply turns off every ESLint rule that overlaps with Prettier's job. The result is a clean split: ESLint watches for bugs, Prettier owns formatting, and the two tools never fight over the same line of code.

17.3 Unit Testing with Jest

Writing tests is what turns "it worked when I tried it" into a repeatable guarantee. Jest is a popular all-in-one testing framework for JavaScript — it bundles a test runner, an assertion library, and a mocking system into a single dependency, so you don't have to assemble one yourself out of smaller pieces.

Suppose this function exists, with a suspicious unverified TODO in it:

const getJSON = require("./getJSON.js");

// getTemperature() looks up a city's current temperature (in Fahrenheit)
// via a web service that reports temperatures in Celsius.
module.exports = async function getTemperature(city) {
  let c = await getJSON(
    `https://globaltemps.example.com/api/city/${city.toLowerCase()}`
  );
  return (c * 5 / 9) + 32; // TODO: double-check this formula
};

A Jest test file groups related tests with describe(), defines each individual test with test() (an alias, it(), is equally common), and makes assertions with expect(actual).toBe(expected) and its many related matchers (toEqual, toThrow, toHaveBeenCalledWith, and so on). Because getTemperature() depends on a real network call through getJSON(), the test replaces that dependency with a mock using jest.mock(), so the test suite runs instantly and deterministically instead of hitting a real server: 

const getTemperature = require("./getTemperature.js");

// Replace the getJSON module with an auto-mocked version
jest.mock("./getJSON");
const getJSON = require("./getJSON.js");

describe("getTemperature()", () => {
  test("invokes the correct API", async () => {
    getJSON.mockResolvedValue(0);
    let expectedURL = "https://globaltemps.example.com/api/city/vancouver";
    await getTemperature("Vancouver");
    // Jest mocks remember every call they received, so we can assert on them
    expect(getJSON).toHaveBeenCalledWith(expectedURL);
  });

  test("converts C to F correctly", async () => {
    getJSON.mockResolvedValue(0);                 // pretend the API said 0°C
    expect(await getTemperature("x")).toBe(32);
    getJSON.mockResolvedValue(100);                // pretend the API said 100°C
    expect(await getTemperature("x")).toBe(212);
  });
});

Note that both tests are declared async and await the function under test — testing asynchronous code (see Asynchronous JavaScript for the underlying Promise mechanics) works naturally in Jest as long as the test function itself returns a Promise that the runner can wait on. Running this suite catches the TODO's bug immediately: 

$ jest getTemperature
 FAIL  getTemperature.test.js
  getTemperature()
    ✓ invokes the correct API (4ms)
    ✕ converts C to F correctly (3ms)

  ● getTemperature() › converts C to F correctly

    expect(received).toBe(expected)
    Expected: 212
    Received: 87.55555555555556

The formula was multiplying by 5 and dividing by 9, backward. Once that's fixed, adding --coverage reports exactly which statements, branches, functions, and lines were actually executed by the test run: 

$ jest --coverage getTemperature
------------------|--------|---------|---------|---------|
File              | % Stmts| % Branch|  % Funcs|  % Lines|
------------------|--------|---------|---------|---------|
All files         |   71.43|      100|    33.33|    83.33|
 getJSON.js       |   33.33|      100|        0|       50|
 getTemperature.js|     100|      100|      100|      100|
------------------|--------|---------|---------|---------|

100% coverage of getTemperature.js is exactly what was wanted; the partial coverage of getJSON.js is expected and fine, since that module was mocked out rather than exercised for real.

Vitest common alternative

A newer test runner, Vitest, has become a very common alternative to Jest, especially in projects already built on Vite. It deliberately mirrors Jest's API almost line for line — describe, test/it, expect().toBe(), vi.mock() in place of jest.mock() — so switching between the two is mostly a matter of changing an import and a config file rather than relearning how to write a test.

17.4 Package Management with npm

Almost no nontrivial project is self-contained: a Node server likely depends on a framework like Express, and a browser UI likely depends on a frontend library. A package manager finds and installs third-party code, and — just as importantly — records exactly which packages and versions your project depends on, so that anyone else can clone your repository and reconstruct an identical set of dependencies. npm is the package manager bundled with Node (see Node.js), and it's used just as heavily for browser-targeted frontend code as for server-side Node code. 

npm install               # (no args) install everything package.json lists
npm install express         # add a runtime dependency, and record it
npm install --save-dev jest   # add a dev-only tool, and record it separately
npm install -g eslint          # install a tool globally, usable outside any project
npx eslint src/                  # run a locally-installed tool without a global install
npm uninstall express             # remove a dependency
npm update                          # bump dependencies within their allowed ranges
npm audit --fix                       # find (and try to fix) known vulnerabilities

Every installed package is recorded in package.json, split into two lists that matter for very different reasons:

FieldMeaning
"dependencies"Needed to run the shipped code — e.g. Express, React
"devDependencies"Needed only to develop the project — e.g. ESLint, Prettier, Jest, a bundler

Both dependency lists specify version numbers using semantic versioning (semver) ranges rather than exact pins, so that installs can pick up compatible bug-fix and feature releases automatically:

RangeMeans
"1.2.3"Exactly this version, nothing else
"^1.2.3"Any 1.x.y release >= 1.2.3 (no breaking major bump)
"~1.2.3"Any 1.2.x release >= 1.2.3 (patch releases only)
"*" / "latest"Whatever the newest published version is

A second file, package-lock.json, is generated automatically and records the exact resolved version (and often a content hash) of every package actually installed, transitively included dependencies and all. This is what makes builds reproducible: two different machines running npm install against the same package.json could, in principle, resolve slightly different versions from the same semver ranges over time, but they'll resolve identically if a lockfile is present and respected.

npm install vs. npm ci

npm install reads package.json, may update the lockfile if a range now resolves to something new, and merges into whatever's already in node_modules/. npm ci instead deletes node_modules/ entirely and installs the exact versions frozen in package-lock.json, failing outright if the lockfile and package.json disagree. That determinism is exactly why CI pipelines and Docker builds should use npm ci, not npm install.

npx, bundled with npm, runs a command-line tool without requiring a global install or a manual reference to ./node_modules/.bin/ — and if you point it at a package that isn't installed yet, it will fetch and run it on the fly. npm's own registry at npmjs.com hosts hundreds of thousands of packages, but npm isn't the only client that can install from it: yarn and pnpm are widely used alternatives, both compatible with the same package.json format, offering their own take on install speed, disk usage (pnpm famously hard-links a single shared package store instead of duplicating files per project), and lockfile behavior.

17.5 Code Bundling

Browsers today support ES modules natively (see Modules), yet production web code is still almost always shipped through a bundler first. A bundler starts at your program's entry point (or points), follows every import statement it finds to discover the full graph of modules the program depends on, and combines all of that into a small number of optimized output files. The practical reason this remains standard practice even though the browser could load modules directly is performance: loading one well-optimized bundle is typically faster for a first-time visitor than loading dozens or hundreds of small module files individually, each with its own request overhead.

The one variable you fully control

Web performance is genuinely hard to reason about in general — network conditions, caching, and browser internals all move the numbers around. But code size is the one variable entirely under your control: less JavaScript always loads and runs faster than more JavaScript, regardless of which bundler or browser is involved.

Beyond the basic module-graph-to-bundle transformation, bundlers commonly add:

  • Multiple entry points — a multi-page app can produce one bundle per page, or one shared bundle covering several entry points.
  • Code splitting — using the functional, dynamic form of import() (rather than the static form) lets a bundler defer part of the graph into a separate chunk that's fetched only when actually needed, improving initial load time.
  • Source maps — a generated mapping from bundled/minified line and column positions back to the original source, so browser DevTools can show you your real file and line number when an error is thrown in a bundle.
  • Non-JS module plugins — a plugin architecture that lets you write import data from "./widgets.json" or import a .css file directly. This is convenient but nonstandard: it works only because your bundler specifically supports it, not because it's part of JavaScript.
  • Filesystem watching and dev servers with HMR — a watcher rebuilds affected bundles the instant a source file changes; "hot module replacement" goes further and pushes the updated module into the still-running page in the browser without a full reload, preserving in-memory app state.

Tree-shaking, precisely hard part

"Tree-shaking" is the whimsical name for a bundler eliminating code you imported but never actually use, so it doesn't bloat the final bundle. The mechanism behind it is worth understanding precisely, because it explains a gotcha that trips people up constantly: tree shaking is reliable with ES modules and fundamentally unreliable with CommonJS, and the reason is structural, not a tooling limitation that will eventually get fixed.

ES module import/export declarations are static: they must appear at the top level of a file (never inside an if or a function body), the module specifier must be a fixed string literal, and the set of named exports is fully known just by parsing the text — without running any of it. That means a bundler can build a precise graph of exactly which exported bindings are imported anywhere, and mechanically delete any export (and anything it exclusively depends on) that no importer ever references: 

// math.js — an ES module
export function add(a, b) { return a + b; }
export function multiply(a, b) { return a * b; } // never imported anywhere

// main.js
import { add } from "./math.js";
console.log(add(2, 3));
// A bundler can statically prove `multiply` is unreachable and drop it
// from the output bundle entirely — it never has to execute math.js to know that.

CommonJS's require(), by contrast, is an ordinary function call, not a special syntax form (see Node.js for the full CommonJS picture). Because it's just a function, it can be called conditionally, inside a loop, with a string built at runtime, and its result — the entire module.exports object — can be destructured, passed around, or mutated arbitrarily: 

// This is completely legal CommonJS, and completely opaque to static analysis
const moduleName = condition ? "./featureA" : "./featureB";
const mod = require(moduleName);
const fn = mod[computeKeyAtRuntime()];

A bundler has no way to know, just by reading the text, which key of mod will actually be accessed, or even which file require() will resolve to — that information only exists once the code actually runs. So a tool would have to either keep the entire module (safe, but no tree-shaking benefit at all) or guess (unsafe, and liable to silently strip code that's actually used). This is precisely why the modern JavaScript build tooling story pushes so hard toward ES modules even in Node-targeted code: static import/export isn't just cleaner syntax, it's the thing that makes tree-shaking possible at all.

The bundler landscape

ToolKnown for
webpackThe longest-established option; enormous plugin ecosystem, highly configurable, can bundle older non-module code too — but configuration can get complex
RollupPopular specifically for bundling libraries, thanks to especially clean ES-module tree-shaking and small output

The original edition of this material also highlighted Parcel as a zero-configuration option; that spirit lives on today mostly in Vite, which has become the default starting point for most new frontend projects.

17.6 Transpilation with Babel

Babel compiles JavaScript that uses newer language features (or nonstandard language extensions) into JavaScript that doesn't need those features — because it turns JS into JS, it's usually called a transpiler rather than a compiler. Babel exists because browser support for new syntax has always lagged behind the language specification, and it lets developers write against the latest syntax while still shipping code that runs on whatever engines they actually need to support.

Some transformations are mechanical and cheap: the ** exponentiation operator becomes a call to Math.pow(), arrow functions become ordinary function expressions (with some care around lexical this). Others, like compiling away the class keyword into prototype-based constructor functions, are considerably more involved, and the output Babel produces for those cases is not meant to be human-readable — which is exactly why Babel, like bundlers, can emit source maps that point DevTools back at your real source.

Babel is configured through .babelrc or babel.config.js, and its behavior is composed from plugins (each handling one specific syntax transformation) grouped into presets — a bundle of plugins for a coherent goal, such as "compile for these target browsers" or "strip JSX." A bundler will typically be configured to run Babel automatically on each module as part of the build — for example, webpack's babel-loader — so the transpilation step disappears into the normal build pipeline rather than being a separate manual command.

Browser engines have gotten dramatically better at keeping up with the language specification since Babel was first created, so there's far less day-to-day need today to compile away arrow functions or class declarations for baseline browser support. But Babel hasn't become irrelevant — it remains the standard way to compile syntax that plain browsers will never understand no matter how modern they are, because it isn't standard JavaScript at all: JSX, decorators, and (via a preset) stripped TypeScript type annotations all still routinely go through Babel today.

17.7 JSX: Markup Expressions in JavaScript

JSX is a syntax extension, most closely associated with the React UI framework, that lets you write HTML-like markup directly as a JavaScript expression. It's worth being clear that this section describes the syntax, not React itself: JSX is just a literal notation that a compiler (typically Babel) turns into ordinary function calls, and understanding that transformation is enough to read JSX-based code even if you never touch React.

You can think of angle brackets in JSX the way you think of quotation marks for a string literal or slashes for a regular expression literal: they delimit a new kind of expression. 

let line = <hr/>;
// Babel compiles that expression to an ordinary function call:
let line = React.createElement("hr", null);

Attributes on a JSX element become properties of an object passed as createElement()'s second argument: 

let image = <img src="logo.png" alt="The JSX logo" hidden/>;

// compiles to:
let image = React.createElement("img", {
  src: "logo.png",
  alt: "The JSX logo",
  hidden: true
});

JSX elements nest, just as HTML elements do, and nested JSX compiles into nested createElement() calls, with each child passed as a third-and-beyond argument: 

let sidebar = (
  <div className="sidebar">
    <h1>Title</h1>
    <hr/>
    <p>This is the sidebar content</p>
  </div>
);
React.createElement(
  "div", { className: "sidebar" },
  React.createElement("h1", null, "Title"),
  React.createElement("hr", null),
  React.createElement("p", null, "This is the sidebar content")
);

The single most important thing to understand about JSX is that curly braces drop you back into plain JavaScript. Anything between { and }, whether it's an attribute value or a child, is evaluated as an ordinary expression — conceptually similar to ${} inside a template literal. 

function sidebar(className, title, content, drawLine = true) {
  return (
    <div className={className}>
      <h1>{title}</h1>
      { drawLine && <hr/> }
      <p>{content}</p>
    </div>
  );
}

which compiles to: 

function sidebar(className, title, content, drawLine = true) {
  return React.createElement("div", { className: className },
    React.createElement("h1", null, title),
    drawLine && React.createElement("hr", null),
    React.createElement("p", null, content));
}

The drawLine && <hr/> idiom is exactly the short-circuit evaluation the && operator has always had — there is no special "conditional rendering" syntax in JSX. If drawLine is falsy, the fourth argument to the outer createElement() call simply evaluates to false, and React is defined to silently render nothing for false/null/undefined children. Because it's ordinary JavaScript inside the braces, arbitrarily complex expressions are fair game — including array methods that produce a list of child elements: 

function List(items, callback) {
  return (
    <ul style={ {padding: 10, border: "solid red 4px"} }>
      {items.map((item, index) =>
        <li onClick={() => callback(index)} key={index}>{item}</li>
      )}
    </ul>
  );
}

Note the doubled braces on style — the outer pair enters JS-expression mode, and the inner pair is an ordinary object literal. React flattens array children automatically, so an element whose only child is an array (here, the array map() produces) is equivalent to that element having each array entry as its own child.

Two more pieces of JSX syntax are worth knowing. First, the object spread operator (see Objects) can spread a whole object's properties in as attributes at once, handy when a set of attributes is reused across many elements: 

let hebrew = { lang: "he", dir: "rtl" };
let shalom = <span className="emphasis" {...hebrew}>שלום</span>;

Second — and this is the mechanism that makes React components work — the capitalization of a JSX tag name changes what gets compiled. A lowercase tag name (div, hr, li) compiles to a plain string, the first argument you've seen in every example so far. An uppercase tag name compiles to a reference to an actual JavaScript identifier in scope, whose value is passed as createElement()'s first argument instead of a string: 

function Sidebar(props) {
  return (
    <div>
      <h1>{props.title}</h1>
      { props.drawLine && <hr/> }
      <p>{props.content}</p>
    </div>
  );
}

let sidebar = <Sidebar title="Something snappy" content="Something wise"/>;
// compiles to:
let sidebar = React.createElement(Sidebar, {
  title: "Something snappy",
  content: "Something wise"
});

A component, in other words, is just a function that accepts a single "props" object and returns a JSX expression — naming it with an initial capital letter is what tells the JSX compiler (and, by convention, other developers) to treat it as a reference rather than a literal tag string.

17.8 Type Checking: Flow, and TypeScript Today

JavaScript itself has no static type system — every type check happens at runtime, which is exactly why TypeError exceptions can surface deep into a program's execution, far from the mistake that caused them. The book covers Flow, Facebook's type-annotation language extension and checker, as the representative tool for this idea: you annotate your code with types using Flow's syntax, run the flow tool to find type errors statically, and then use Babel to strip the annotations back out before the code ships, since none of it is real JavaScript syntax.

In current practice: TypeScript, overwhelmingly

Flow was a reasonable bet at the time, but the years since have settled this decisively: TypeScript is, by a very wide margin, the dominant static type checker for JavaScript today. Flow still exists and a handful of legacy codebases still use it, but essentially all new typed-JavaScript work — and the surrounding tooling, editor integration, and library ecosystem (published .d.ts type declaration files) — targets TypeScript. The rest of this section covers TypeScript directly as the modern answer to "how do I add types to JavaScript," rather than teaching Flow's now-niche syntax.

TypeScript is a superset language: essentially all valid JavaScript is valid TypeScript, plus a layer of optional type annotations and a few extra constructs (interface, enum) that don't exist in plain JS. Its own compiler, tsc, checks your annotations for consistency and then compiles everything down to plain JavaScript — it is a standalone compiler, not a Babel plugin, though Babel can also strip TypeScript's type syntax via a preset when you only want the syntax removed without full type-checking as part of the build. 

interface User {
  name: string;
  age: number;
  email?: string;      // optional property
}

function greet(user: User): string {
  return `Hello, ${user.name}!`;
}

greet({ name: "Ada", age: 30 });         // OK — email is optional
greet({ name: "Ada", age: "thirty" });   // compile-time error: age must be a number
greet({ age: 30 });                        // compile-time error: name is required

This is TypeScript's core value proposition: mistakes like a misspelled property name, a swapped argument order, or a value that might unexpectedly be null get caught by the compiler (and, in practice, live in your editor as you type) instead of surfacing as a runtime crash — or worse, silently propagating wrong data — after the code has shipped.

Types are erased: zero runtime cost hard part

A detail that's easy to get wrong in your mental model: TypeScript's type annotations, interface declarations, and generic parameters are a compile-time-only layer. None of it exists in the emitted JavaScript, and none of it costs anything at runtime — there is no hidden type-checking code running in production, because by production there's no type information left to check. Compiling the snippet above (roughly what tsc produces, module wrapper details aside) makes this concrete: 

function greet(user) {
  return `Hello, ${user.name}!`;
}

greet({ name: "Ada", age: 30 });
greet({ name: "Ada", age: "thirty" }); // ← no longer an error; this is now just JS
greet({ age: 30 });

The interface User declaration doesn't appear anywhere in the output at all — interfaces are a pure compile-time construct with no runtime representation whatsoever, unlike a class, which really does produce a constructor function. The : string, : number, ?, and the whole interface block are simply deleted; what's left is exactly the JavaScript you'd have written by hand without ever knowing TypeScript existed. This is why TypeScript can be adopted incrementally on an existing project and why it adds no runtime dependency: the type checker is strictly a development-time tool that happens to also emit your JavaScript for you.

Not everything TypeScript adds is erased

This "purely erased" rule has real exceptions worth knowing before they surprise you. TypeScript's enum keyword compiles to an actual object that exists at runtime (a reverse-mapping lookup object, by default) — it is not erased. Decorators, where supported, likewise compile to real function calls that run when the class is defined. If you want the "purely erased, zero runtime footprint" guarantee to hold without exception, stick to type annotations, interface, and generics, and reach for a plain object literal or a union of string literals instead of enum when it matters.

Type annotations aren't limited to simple named types — TypeScript supports union types (string | number), array and tuple types, generic type parameters on functions and classes, and structural typing (an object satisfies an interface as long as its shape matches, with no explicit "implements" declaration required). All of that machinery exists purely to let tsc reason about your code before it runs; all of it disappears the moment compilation finishes.

17.9 Summary

None of the tools in this chapter are part of the JavaScript language as defined by the ECMAScript specification, and yet it's hard to find a serious JavaScript project that skips all of them. ESLint and Prettier keep a codebase correct-looking and consistent-looking, respectively; Jest (or Vitest) turns "it should work" into a repeatable, automated check; npm tracks and reproduces your dependency tree; bundlers and Babel bridge the gap between the code you want to write and the runtimes that have to execute it; and JSX and TypeScript both extend the language itself — one to describe UI trees as expressions, the other to describe and check the shapes of your data before a single line of it runs. Understanding what each piece actually does — rather than treating config files as magic incantations to copy from a starter template — is what turns this whole ecosystem from a wall of unfamiliar acronyms into a toolbox you can reach into deliberately.
