Types, Values & Variables

Every JavaScript value is either a primitive or an object, and almost every "weird" behavior beginners run into — strings that don't mutate, arrays that compare unequal to identical arrays, 0.1 + 0.2 not being 0.3, == doing things you didn't ask for — traces back to that one split. This chapter builds up the full type system from the ground up: numbers and their binary-floating-point quirks, text and its UTF-16 encoding, booleans, the null/undefined distinction, symbols, the global object, and then the two topics that cause the most real-world bugs — implicit type conversion and variable scoping — in enough depth to stop guessing and start reasoning.

Overview and definitions

JavaScript's values split into two categories, and which category a value belongs to determines how it's copied, compared, and stored:

  • Primitive types: numbers, strings, booleans, plus three special-purpose types — null, undefined, and (since ES6) Symbol — each of which is really the sole member of its own tiny type. As of ES2020, BigInt is a second numeric primitive type alongside Number.
  • Object types: everything else. A plain object is an unordered bag of named properties; an array is a specialized object with an ordered, numbered set of properties; and JavaScript defines further specialized object types on top of these basics — Map, Set, typed arrays, RegExp, Date, Error and its subtypes (see Collections & Typed Arrays, Regular Expressions, and Dates, JSON & Intl). Functions and classes are themselves objects too — a specialized, callable kind — which is why they can be passed around, stored in variables, and attached to other objects just like any other value (see Functions and Classes).

The most consequential difference between the two categories is mutability: object types are mutable, primitive types are immutable. It doesn't even make sense to ask to "change" the number 3 into some other value in place — you can only make a variable refer to a different number. Strings look like they might be mutable, since you can index into them like an array of characters, but JavaScript gives you no way to alter the characters of an existing string; every string-producing method returns a brand new string. Objects and arrays, by contrast, really can be changed after creation: you can reassign a property, push a new array element, or delete a key, all without creating a new object identity. This distinction has a second, equally important consequence for how values are copied and compared, which gets its own deep dive in §3.8 below.

JavaScript is also extremely liberal about converting values from one type to another — pass a number where a string is expected and it becomes a string; pass anything where a boolean is expected and it becomes true or false. This flexibility is convenient but it is also the source of some of the language's most notorious gotchas, and it gets the full treatment in §3.9.

Two more housekeeping notes before diving into the individual types. First, JavaScript is garbage collected: you never explicitly free memory. Once nothing in your running program can reach a value anymore, the engine is free to reclaim it; your only responsibility is to avoid accidentally keeping references alive longer than you mean to (a stale entry in a long-lived cache or event listener list, for example). Second, JavaScript variables and constants are untyped — a let or const declaration says nothing about what kind of value may be assigned, and a single variable can legally hold a number at one point in a program and a string later (though doing so on purpose is usually a sign of a design problem, not a feature to lean on).

Object-oriented, even for primitives

JavaScript favors calling methods on values (a.sort()) over passing them to free functions (sort(a)). Technically only true objects have methods, but numbers, strings, booleans, and symbols behave as if they have methods too — the engine briefly wraps them in an object when you call (3).toString() or "x".toUpperCase(), then discards the wrapper. null and undefined are the only values with no methods at all; calling anything on them throws a TypeError.

Numbers

JavaScript has exactly one everyday numeric type: Number, a 64-bit IEEE 754 double — the same representation Java and C++ call double. There is no separate integer type, and no distinction in the language between 3 and 3.0. The format can represent magnitudes up to roughly ±1.7976931348623157 × 10³⁰⁸ and as small as ±5 × 10⁻³²⁴, and it represents every integer exactly between −9,007,199,254,740,992 (−2⁵³) and 9,007,199,254,740,992 (2⁵³) inclusive — beyond that range, integers start silently losing precision in their low bits. (Bitwise operators and array indices, covered in Expressions & Operators, additionally coerce down to 32-bit integers for the duration of the operation.) If you need exact integers beyond 2⁵³, reach for BigInt.

Integer literals

A base-10 integer literal is just a run of digits. JavaScript also recognizes hexadecimal (0x/0X) literals, and, since ES6, binary (0b/0B) and octal (0o/0O) literals. Any numeric literal may be preceded by a unary minus to negate it, and, informally supported since ES2021 but already implemented everywhere well before that, underscores may be inserted between digits purely for readability — the engine strips them before parsing: 

0             // Zero
3
10000000

0xff          // => 255   (15*16 + 15)
0xBADCAFE     // => 195939070

0b10101       // => 21    (1*16 + 0*8 + 1*4 + 0*2 + 1*1)
0o377         // => 255   (3*64 + 7*8 + 7*1)

let billion = 1_000_000_000;   // Underscore as a thousands separator
let bytes   = 0x89_AB_CD_EF;   // ...or a byte separator
let bits    = 0b0001_1101_0111; // ...or a nibble separator
let frac    = 0.123_456_789;    // Works in the fractional part too

Floating-point literals

A floating-point literal may include a decimal point and/or an exponent: a mantissa followed by e or E, an optional sign, and an integer power of ten to multiply by. Formally, the grammar is [digits][.digits][(E|e)[(+|-)]digits]: 

3.14
2345.6789
.333333333333333333
6.02e23         // 6.02 × 10²³
1.4738223E-32   // 1.4738223 × 10⁻³²

Arithmetic and the Math object

The familiar operators +, -, *, /, and % (remainder) all work as expected; ES2016 added ** for exponentiation (ES2016). Operator details, including precedence, live in Expressions & Operators. Beyond the operators, the built-in Math object supplies everything else you'd expect from a scientific calculator: 

Math.pow(2, 53)          // => 9007199254740992
Math.round(.6)           // => 1     Math.ceil(.6)  // => 1
Math.floor(.6)           // => 0     Math.abs(-5)   // => 5
Math.max(1, 2, 3)        // => 3     Math.min(1,2,3) // => 1
Math.random()            // 0 <= x < 1
Math.PI                  // π       Math.E          // e
Math.sqrt(3)             // Math.pow(3, 0.5)
Math.sin(0)              // Also Math.cos, Math.atan, ...
Math.log(10)             // Natural log; Math.log(100)/Math.LN10 for base 10

// ES6 additions:
Math.cbrt(27)     // => 3      cube root
Math.hypot(3, 4)  // => 5      sqrt of sum of squares
Math.log10(100)   // => 2      Math.log2(1024) // => 10
Math.sign(x)      // -1, 0, or 1
Math.trunc(3.9)   // => 3      drop the fraction, no rounding at all
Math.clz32(0xf)   // => 28     leading zero bits in a 32-bit int
Math.imul(2, 3)   // => 6      optimized 32-bit integer multiply
Math.sinh(x), Math.cosh(x), Math.tanh(x)          // Hyperbolic trig
Math.asinh(x), Math.acosh(x), Math.atanh(x)       // ...and their inverses

Note that Math.trunc() and Math.floor() disagree on negative numbers: Math.trunc(-3.9) is -3 (toward zero), while Math.floor(-3.9) is -4 (toward negative infinity).

Overflow, underflow, and the special numeric values

JavaScript arithmetic never throws for overflow, underflow, or division by zero — it produces one of three special sentinel values instead:

ValueHow you get itNotes
InfinityA result bigger than the largest representable number, e.g. 1/0 or Number.MAX_VALUE * 2Arithmetic with infinity behaves as you'd expect (still infinite, sign flips as needed)
-Infinity-1/0, -Number.MAX_VALUE * 2Same idea, negative
NaN0/0, Infinity/Infinity, Math.sqrt(-1), any arithmetic operator with a non-numeric operand that can't convertNever equal to anything, including itself
-0 ("negative zero")Underflow of a negative value, e.g. -Number.MIN_VALUE / 2 or -1 / Infinity-0 === 0 is true, but 1/-0 !== 1/0

Infinity and NaN are available as global constants and also as Number.POSITIVE_INFINITY / Number.NEGATIVE_INFINITY / Number.NaN. ES6 adds a cluster of useful Number static methods and constants for inspecting values without accidentally triggering global-function quirks (see the warning below): 

Number.isNaN(x)          // Is x exactly the NaN value? (the ONLY reliable check)
Number.isFinite(x)       // Is x a number and neither NaN, Infinity, nor -Infinity?
Number.isInteger(x)      // Is x a whole number?
Number.isSafeInteger(x)  // Is x an integer strictly between -(2**53) and 2**53?
Number.MIN_SAFE_INTEGER  // => -(2**53 - 1)
Number.MAX_SAFE_INTEGER  // => 2**53 - 1
Number.EPSILON           // => 2**-52: smallest representable gap between two numbers
Number.parseInt(), Number.parseFloat()  // Same as the global functions, namespaced
Global isNaN()/isFinite() are looser than the Number.* versions

The legacy global isNaN(x) first tries to convert x to a number and returns true if that is NaN — so isNaN("hello") is true, which is rarely what you want. Prefer Number.isNaN(x), which only returns true if x is already, literally, the NaN value. The same caveat applies to isFinite() vs. Number.isFinite(). 

let zero = 0, negz = -0;
zero === negz          // => true: 0 and -0 are equal by ===
1 / zero === 1 / negz  // => false: Infinity !== -Infinity — the only way to tell them apart

let x = NaN;
x === NaN         // => false — NaN never equals anything, not even itself!
x !== x           // => true — a classic (if cryptic) NaN test
Number.isNaN(x)   // => true — the clear, intention-revealing way to ask

Binary floating-point and rounding errors Hard

There are infinitely many real numbers but only a finite number of 64-bit patterns, so most decimal fractions cannot be stored exactly — this is a property of binary floating point itself, not a JavaScript bug, and it affects Python, Java, C, and every other IEEE 754 language equally. Binary floating point represents fractions whose denominator is a power of two exactly (1/2, 1/8, 1/1024), but the fractions people actually write down — tenths, hundredths, the stuff of money and percentages — are decimal fractions like 1/10, which have no exact binary representation. JavaScript stores the closest available double instead, and every arithmetic operation performed on that already-approximate value can compound the error further. 

let x = 0.3 - 0.2;   // "thirty cents minus twenty cents"
let y = 0.2 - 0.1;   // "twenty cents minus ten cents"
x === y              // => false! Both LOOK like they should be 0.1
x === 0.1            // => false: 0.3 - 0.2 is actually 0.09999999999999998
y === 0.1            // => true:  0.2 - 0.1 happens to land exactly on 0.1's approximation

0.1 + 0.2            // => 0.30000000000000004, not 0.3
0.1 + 0.2 === 0.3    // => false

The values above are all extremely close to mathematically correct — close enough for almost any purpose — and the trouble arises specifically when you compare floating-point results for exact equality. A second, equally common trap is accumulation: summing many imprecise values compounds the error further than a single subtraction does. 

// Worked example 2: error compounds across repeated operations
let total = 0;
for (let i = 0; i < 10; i++) {
  total += 0.1;
}
total          // => 0.9999999999999999, not 1
total === 1    // => false

// A robust equality check uses a small tolerance ("epsilon") instead
function nearlyEqual(a, b, epsilon = Number.EPSILON * 8) {
  return Math.abs(a - b) < epsilon;
}
nearlyEqual(total, 1)   // => true
Never compare floating-point results with ===

For money, store integer cents (or use BigInt) instead of fractional dollars — 1050 cents instead of 10.50 dollars sidesteps the whole problem for addition and subtraction. For general numeric comparisons where fractional values are unavoidable, compare against a small epsilon rather than for exact equality, as in the nearlyEqual helper above.

BigInt for arbitrary precision ES2020

BigInt is a second numeric primitive type, added specifically so JavaScript could represent 64-bit integers exactly (for interoperability with other languages and binary formats) and, more generally, integers of any size — potentially thousands or millions of digits. A BigInt literal is a string of digits (in any of the same four bases as regular integer literals) followed by a lowercase n. BigInt is not appropriate for cryptography: implementations make no attempt to run in constant time, so they can leak information via timing attacks. 

1234n                  // A modest BigInt literal
0b111111n              // Binary
0o7777n                // Octal
0x8000000000000000n    // => 2n ** 63n, a 64-bit integer

BigInt(Number.MAX_SAFE_INTEGER)      // => 9007199254740991n: convert a Number
BigInt("1" + "0".repeat(100))        // => 10n**100n, one googol, from a string

1000n + 2000n   // => 3000n
2000n * 3000n   // => 6000000n
3000n / 997n    // => 3n  — integer division: the remainder is dropped, toward zero
3000n % 997n    // => 9n  — and the remainder is available separately
(2n ** 131071n) - 1n   // A Mersenne prime with 39,457 decimal digits

BigInt and Number deliberately refuse to mix in arithmetic — not as an arbitrary restriction, but because neither type can losslessly represent everything the other can: BigInt can't hold fractions, and Number can't hold huge integers exactly, so there's no single "obviously correct" type to promote a mixed expression to. Comparison operators are the one exception, since ordering two values doesn't require picking a common representation: 

1 + 1n         // TypeError: Cannot mix BigInt and other types
1n * 2.5       // TypeError: same reason

1 < 2n         // => true  — relational operators DO compare across types
2 > 1n         // => true
0 == 0n        // => true  — == converts before comparing
0 === 0n       // => false — === also checks the type, and BigInt !== Number

Bitwise operators generally work fine with BigInt operands, but no method of the Math object accepts them — Math.sqrt(4n) throws.

Converting between numbers and strings, and choosing a base

Beyond the automatic conversions covered in §3.9, the Number type exposes methods for precise, deliberate control over formatting and parsing — essential once you need a specific number of decimal places, a specific base, or to avoid exponential notation creeping into output. 

// Number.prototype.toString() accepts an optional radix (2-36), default 10
let n = 17;
n.toString(2)    // => "10001"
n.toString(8)    // => "21"
n.toString(16)   // => "11"
let hex = "0x" + n.toString(16);  // "0x11"

// Fixed decimal places, exponential notation, and significant digits:
let big = 123456.789;
big.toFixed(0)         // => "123457"   never uses exponential notation
big.toFixed(2)         // => "123456.79"
big.toExponential(1)   // => "1.2e+5"   one digit before the decimal
big.toExponential(3)   // => "1.235e+5"
big.toPrecision(4)     // => "1.235e+5" switches to exponential if it must
big.toPrecision(7)     // => "123456.8"
big.toPrecision(10)    // => "123456.7890"

Parsing strings back into numbers has three tools with different strictness. Number(str) requires the entire string (aside from surrounding whitespace) to be a valid numeric literal in base 10, or it fails to NaN. parseInt() and parseFloat() are more forgiving global functions: they skip leading whitespace, parse as many valid characters as they can, and silently ignore whatever comes after — and parseInt() accepts an explicit radix as its second argument for parsing non-decimal input. 

Number("3 blind mice")     // => NaN: Number() needs the WHOLE string to be numeric
parseInt("3 blind mice")   // => 3:   parses a prefix, ignores the rest
parseFloat(" 3.14 meters") // => 3.14
parseInt("-12.34")         // => -12: parseInt stops at the decimal point
parseInt("0xFF")           // => 255: auto-detects the hex prefix
parseFloat(".1")           // => 0.1
parseInt(".1")             // => NaN: an integer literal can't start with "."
parseFloat("$72.47")       // => NaN: numbers can't start with "$"

// Explicit radix as the second argument:
parseInt("11", 2)    // => 3    (1*2 + 1)
parseInt("ff", 16)   // => 255  (15*16 + 15)
parseInt("zz", 36)   // => 1295 (35*36 + 35)
parseInt("077", 8)   // => 63   (7*8 + 7)  -- WITHOUT a radix, leading zero does NOT mean octal
parseInt("077")      // => 77   (parsed as base 10 in modern JS)

JavaScript also has a simple built-in Date class for working with calendar dates and timestamps — Date.now() returns the current time as a millisecond count since the Unix epoch, and new Date() gives you a full Date object. Dates matter for type conversion too, since (as covered in §3.9) they're the one built-in type that prefers a string representation over a numeric one. Full coverage is in Dates, JSON, Intl & Utilities.

Text: strings

A JavaScript string is an immutable, ordered sequence of 16-bit values, most of which correspond to a single Unicode character. Like arrays, strings are zero-indexed, and .length gives you the number of 16-bit code units — not necessarily the number of visible characters, which is the source of a subtle gotcha covered below. There is no separate "character" type — a single character is just represented as a string of length 1.

String literals and quoting

A string literal is delimited by single quotes, double quotes, or (as of ES6) backticks. A string delimited by one quote style can freely contain the other quote characters unescaped, which is handy when mixing JavaScript with HTML — pick one quote style for your JavaScript strings and the other for your HTML attributes so neither needs escaping: 

""                                     // The empty string
'testing'
"Wouldn't you prefer O'Reilly's book?" // Double quotes let ' through unescaped
`"She said 'hi'", he said.`            // Backticks let both through unescaped
<!-- Single quotes for the JS string, double quotes for the HTML attribute -->
<button onclick="alert('Thank you')">Click Me</button>

Historically, string literals had to fit on one line; a trailing backslash before a line break lets you continue a single-quoted or double-quoted literal onto the next line without inserting a newline character into the string (the backslash and the following line terminator are simply dropped). Backtick-delimited literals are the exception: they may span multiple lines directly, and any newlines you type inside them become real newline characters in the resulting string. 

'two\nlines'      // A string representing 2 lines, written on one line

"one\
 long\
 line"            // A one-line string written across 3 source lines

`the newline character at the end of this line
is included literally in this string`   // A genuine two-line string
"Characters," codepoints, and JavaScript strings

JavaScript strings use the UTF-16 encoding, and every element of a string is one 16-bit code unit. Characters from the Unicode "Basic Multilingual Plane" (the overwhelming majority of characters people type day to day) fit in one 16-bit unit, but characters outside it — many emoji, some rarer scripts — are represented as a pair of two 16-bit units called a surrogate pair. That means .length can report more units than there are visible characters: 

let euro = "€";
let love = "❤️" ; // presentation-selector emoji, multiple code units
euro.length     // => 1: this character fits in one 16-bit unit
"😀".length     // => 2: a surrogate pair, not one character!

// Most string methods operate on 16-bit units, not "characters" —
// they don't special-case surrogate pairs or normalize anything.
// for/of and the spread operator, however, iterate actual Unicode
// characters (ES6):
[..."😀"].length     // => 1
for (const ch of "😀") { console.log(ch); }  // Logs one iteration, not two

Escape sequences

A backslash inside a string literal introduces an escape sequence — a way to represent a character that can't (or shouldn't) be typed literally. Three of these are "generic": they let you specify any Unicode character by its numeric code point in hex.

SequenceCharacter
\0NUL, the null character (\u0000)
\bBackspace
\tHorizontal tab
\nNewline
\vVertical tab
\fForm feed
\rCarriage return
\" / \' / \`Literal quote character, whichever delimiter you're inside
\\A literal backslash
\xnnThe character with hex code nn (exactly 2 hex digits), e.g. \xA9 for ©
\unnnnThe character with hex code nnnn (exactly 4 hex digits), e.g. π for π
\u{n}ES6: the character at codepoint n, 1-6 hex digits, e.g. \u{1f600} for 😀 — this is the only escape that can produce codepoints outside the BMP directly

A backslash before any other character is simply ignored — \# is the same as # — but relying on that is fragile, since a future language version could give that sequence meaning.

Comparing, searching, and manipulating strings

Strings concatenate with + and compare with ===/!== (equal only if same length and every code unit matches) as well as the relational operators < <= > >=, which compare code-unit values directly — not a linguistically aware ordering (for locale-aware comparison and sorting, see Intl.Collator in Dates, JSON, Intl & Utilities). Beyond that, the string prototype defines a large, useful API: 

let s = "Hello, world";

// Extracting a portion
s.substring(1, 4)     // => "ell"
s.slice(1, 4)         // => "ell": same result, but slice() accepts negative indices
s.slice(-3)           // => "rld": last 3 characters, only slice() can do this
s.split(", ")         // => ["Hello", "world"]

// Searching
s.indexOf("l")        // => 2:  first occurrence
s.indexOf("l", 3)     // => 3:  first occurrence at or after index 3
s.lastIndexOf("l")    // => 10: last occurrence
s.indexOf("zz")       // => -1: not found
s.startsWith("Hell")  // => true   (ES6)
s.endsWith("!")       // => false  (ES6)
s.includes("or")      // => true   (ES6)

// Producing modified copies (never mutates s)
s.replace("llo", "ya")  // => "Heya, world"
s.toLowerCase()         // => "hello, world"
s.toUpperCase()         // => "HELLO, WORLD"
s.normalize()           // Unicode NFC normalization (ES6); also "NFD","NFKC","NFKD"

// Individual code units
s.charAt(0)           // => "H"
s.charCodeAt(0)        // => 72: the 16-bit code unit at that index
s.codePointAt(0)       // => 72: like charCodeAt but correct for surrogate pairs (ES6)
s[0]                   // => "H": strings can be read like arrays with []

// Padding and trimming
"x".padStart(3)        // => "  x"   (ES2017)
"x".padStart(3, "*")   // => "**x"
"x".padEnd(3, "-")     // => "x--"
" hi ".trim()          // => "hi"
" hi ".trimStart()     // => "hi "   (ES2019; also trimLeft alias)
" hi ".trimEnd()       // => " hi"   (ES2019; also trimRight alias)

// Misc
"<>".repeat(3)         // => "<><><>"  (ES6)

Every method above returns a new string; none of them alter s. That's not an implementation detail — it's a direct consequence of strings being an immutable primitive type (see §3.8).

Template literals and tagged templates ES6

Backtick-delimited strings do more than allow multi-line text — they support interpolated expressions. Anything between ${ and the matching } is parsed as a full JavaScript expression, evaluated, converted to a string, and spliced into the result in place of the placeholder: 

let name = "Bill";
let greeting = `Hello ${name}, ${2 + 2} is 4.`;
// => "Hello Bill, 4 is 4."

// Multiple expressions, escape sequences, and multiple lines all work:
let errorMessage = `\
✘ Test failure at ${filename}:${linenumber}:
${exception.message}
Stack trace:
${exception.stack}
`;
// The leading backslash swallows the newline right after it, so the string
// begins with the ✘ character rather than a blank line.

A less-often-used but powerful feature: if an expression (called a "tag") immediately precedes the opening backtick — with no parentheses — the literal's raw text chunks and interpolated values are passed to that function instead of being combined automatically. The tag function's return value (which need not even be a string) becomes the value of the whole expression. This is how libraries implement things like automatic SQL/HTML escaping or the css/html tags used by some templating systems. The one built-in tag is String.raw, which returns the text between the backticks with escape sequences left unprocessed: 

`\n`.length            // => 1: a single newline character
String.raw`\n`.length  // => 2: a literal backslash followed by the letter n

Pattern matching with regular expressions

JavaScript defines a RegExp type for describing textual patterns. Regular expressions aren't a primitive type, but they have their own literal syntax — text between a pair of slashes, optionally followed by flag letters — which makes them feel almost as fundamental as strings and numbers: 

/^HTML/            // Match "HTML" at the start of a string
/[1-9][0-9]*/      // A nonzero digit followed by any number of digits
/\bjavascript\b/i  // "javascript" as a whole word, case-insensitive

let text = "testing: 1, 2, 3";
let pattern = /\d+/g;
pattern.test(text)          // => true: a match exists
text.search(pattern)        // => 9: index of the first match
text.match(pattern)         // => ["1", "2", "3"]
text.replace(pattern, "#")  // => "testing: #, #, #"
text.split(/\D+/)           // => ["", "1", "2", "3"]: split on non-digit runs

The full grammar and API — capture groups, lookaround, sticky and Unicode flags, and every string/RegExp method that consumes a pattern — is covered in Regular Expressions.

Boolean values

There are exactly two boolean values, true and false, most often produced by comparisons like a === 4 and consumed by control-flow statements such as if (see Statements). Since any value can be converted to boolean, JavaScript defines exactly seven falsy values — everything else, including every object and array, no matter how "empty," is truthy: 

false, 0, -0, 0n, NaN, "", null, undefined  // The complete list of falsy values

Boolean([])    // => true: an empty array is still an object, hence truthy
Boolean({})    // => true: same story for an empty object
Boolean(" ")   // => true: a non-empty string, even just whitespace

The three boolean operators are && (true only if both operands are truthy), || (true if either operand is truthy), and unary ! (flips truthy/falsy to the opposite boolean). Full operator semantics, including short-circuiting, are in Expressions & Operators.

if (o) vs. if (o !== null)

if (o) is perfectly fine when you truly want to treat 0, "", and null/undefined the same way — as "nothing here." If you need to distinguish a legitimate 0 or "" from "no value at all," use an explicit o !== null && o !== undefined check, or more idiomatically the nullish coalescing operator ?? described next.

null and undefined

Both null and undefined represent "no value," both are falsy, and neither has any properties or methods — accessing one throws a TypeError. They are loosely equal to each other (null == undefined is true) but not strictly equal (null === undefined is false), and typeof null famously (if confusingly) returns "object" — a decades-old bug baked permanently into the language — while typeof undefined returns "undefined".

The book's convention for which one to use is worth adopting:

  • undefined is the "system-level" absence of value: the value of a declared-but-unassigned variable, of a missing object property or array element, of a function called with too few arguments, and of a function that falls off the end without an explicit return.
  • null is the "program-level" absence you assign deliberately, to say "this variable holds no object right now" as an intentional, expected state.

Because the two overlap so much in practice, ES2020 added the nullish coalescing operator ?? (ES2020), which evaluates its right operand only when the left is null or undefined — critically different from ||, which also falls through on any other falsy value: 

let count = 0;
count || 10   // => 10: WRONG if 0 is a valid value — || treats 0 as "missing"
count ?? 10   // => 0:  RIGHT — ?? only falls through on null/undefined

let userInput = "";
userInput || "default"  // => "default": probably not what you want
userInput ?? "default"  // => ""       : the empty string is preserved

Symbols ES6

A Symbol is a unique, unforgeable primitive value with no literal syntax — you obtain one by calling the Symbol() function, optionally passing a descriptive string that shows up when the symbol is stringified but otherwise has no effect on identity. Symbols exist mainly to serve as object property keys that are guaranteed never to collide with a string key or with another symbol — useful both for keeping a library's internal properties out of a user's way, and for extending the language itself without breaking backward compatibility (this is exactly how Symbol.iterator was introduced for the for/of protocol — see Iterators & Generators — without claiming any string method name that existing code might already be using). 

let strname = "string name";
let symname = Symbol("propname");
typeof strname   // => "string"
typeof symname   // => "symbol"

let o = {};
o[strname] = 1;
o[symname] = 2;
o[strname]   // => 1
o[symname]   // => 2

let s1 = Symbol("id");
let s2 = Symbol("id");
s1 === s2         // => false — Symbol() NEVER returns the same value twice,
                  //            even with an identical description string
s1.toString()     // => "Symbol(id)"

For the opposite need — a symbol you deliberately want to share across independent parts of a program — use the global symbol registry via Symbol.for(), which returns the same symbol every time it's called with the same key (creating it on first use), and Symbol.keyFor() to recover the key from a registry symbol: 

let shared1 = Symbol.for("app.id");
let shared2 = Symbol.for("app.id");
shared1 === shared2       // => true — Symbol.for() reuses the registry entry
Symbol.keyFor(shared1)    // => "app.id"

The global object

Every JavaScript environment maintains one special object — the global object — whose properties are exactly the identifiers available globally to every script: constants like undefined, NaN, and Infinity; global functions like isNaN(), parseInt(), and eval(); constructors like Date, RegExp, Array, and Object; and global namespace objects like Math and JSON. None of these are technically reserved words, but treating them as if they were — never shadowing Math or Date with a local variable, for instance — will save you real confusion.

Historically, referring to "the" global object required different syntax in different environments: in browsers it's the window object (which also has a self-referential window property), Node exposes it as global, and a web worker (see Storage & Workers) refers to its own global object as self, since it isn't associated with any window. ES2020 finally unified all of this with globalThis (ES2020), a single standard name that refers to the global object in whatever environment your code is running in. 

globalThis.isNaN === isNaN   // => true: same function, referenced two ways
var leaked = 1;
globalThis.leaked            // => 1: top-level `var` really does create a
                              //      property on the global object (see §3.10.2)

Immutable primitives vs. mutable object references Hard

This is the single distinction that explains the largest share of confusing JavaScript behavior, so it's worth being precise about it. Primitive values — undefined, null, booleans, numbers, BigInts, strings, and symbols — are immutable and are always copied and compared by value. Objects — including arrays and functions — are mutable and are always copied and compared by reference. Two variables can never secretly share a primitive value in a way that lets mutating through one affect the other, because primitives can't be mutated at all; two variables absolutely can share an object, and mutating through either one is visible through both. 

// Worked example 1: primitives are copied by value, always independent
let a = "hello";
let b = a;      // b gets its OWN copy of the value "hello"
b = "world";    // reassigning b cannot possibly affect a
a               // => "hello": completely unaffected

let s = "hello";
s.toUpperCase();  // Returns "HELLO" as a NEW string...
s                 // => "hello": ...but never alters s itself — strings can't be altered
// Worked example 2: objects are copied by reference, so aliases share state
let o = { x: 1 };
let p = o;       // p is not a copy — p and o refer to the SAME object
p.x = 2;
o.x              // => 2: mutating through p is visible through o!

o === p          // => true: same underlying object identity
let q = { x: 2 }; // a DIFFERENT object that happens to have equal contents
o === q          // => false: distinct objects are never equal, no matter what they contain

let arr1 = [], arr2 = [];   // two distinct, both empty, arrays
arr1 === arr2               // => false: never equal by reference alone

A direct, practical consequence: passing an object into a function, or storing it in a second variable, never "copies" it — you get a second handle onto the exact same mutable value. To make a real, independent copy you must explicitly copy every property (or element), for instance with a loop, Array.from(), the spread operator, or structuredClone(): 

let original = ["a", "b", "c"];
let copy = [...original];              // shallow copy: new array, same-value elements
let copy2 = { ...someObject };         // shallow copy of a plain object
let deep = structuredClone(original);  // deep copy (modern browsers & Node 17+)

// Shallow copies still share nested objects/arrays:
let nested = { list: [1, 2, 3] };
let shallow = { ...nested };
shallow.list.push(4);
nested.list          // => [1, 2, 3, 4] — the inner array was shared, not copied!

// Comparing two arrays/objects for equal CONTENT requires comparing
// element-by-element or property-by-property; === alone only tells you
// about identity:
function equalArrays(a, b) {
  if (a === b) return true;                  // identical arrays trivially "equal"
  if (a.length !== b.length) return false;
  for (let i = 0; i < a.length; i++) {
    if (a[i] !== b[i]) return false;
  }
  return true;
}
Mental model

Think of a variable holding an object not as "containing" the object, but as holding a sticky note with the object's address written on it. Copying the variable copies the sticky note, not the object — both notes still point at the one object. Assigning to const point = {} locks the ink on the sticky note (you can't write a new address on it), but says nothing about the object at that address, which can still be freely edited.

Type conversions Hard

JavaScript converts values between types automatically almost everywhere a specific type is expected — arithmetic, string concatenation, if conditions, and more. Understanding the actual rules turns "wait, why is that true?" into something predictable instead of magical: 

10 + " objects"    // => "10 objects": the number 10 converts to a string
"7" * "4"          // => 28: both strings convert to numbers for *
let n = 1 - "x";   // n is NaN: "x" can't convert to a number
n + " objects"     // => "NaN objects": NaN converts to the string "NaN"

Every value converts to a string and to a boolean without exception; conversion to a number can fail, producing NaN. Entries in bold below are the ones people find genuinely surprising:

Two rows are worth memorizing precisely because they look like typos but aren't: Number([]) is 0, and Number([99]) is 99. Both go through the same pipeline — the array converts to a primitive via its toString() (which comma-joins elements: an empty array joins to "", a one-element array joins to that one element's string form), and then that string is parsed as a number. It has nothing to do with array length as a number and everything to do with string conversion happening first.

Converting a string to a number tolerates surrounding whitespace but not anything else: any leading or trailing non-space character that isn't part of a valid numeric literal causes the whole conversion to fail to NaN — this is what makes Number() stricter than parseInt()/parseFloat(), covered in §3.2.7 above.

How an object becomes a primitive

Converting an object to a string or number is a two-step process: first the object is converted to some primitive value, then (if needed) that primitive is converted again using the ordinary rules from the table above. The first step is the interesting one, because some objects — Date especially — have more than one reasonable primitive representation (a timestamp number, or a human-readable string). JavaScript resolves the ambiguity with three named algorithms:

AlgorithmTries, in orderUsed by
prefer-stringtoString(), then valueOf()Template-literal interpolation, String(obj)
prefer-numbervalueOf(), then toString()Number(obj); relational operators < > <= >= (the result is not converted to a number afterward, unlike ordinary number conversion)
no-preferenceSame as prefer-number for every built-in type except Date, which behaves as prefer-stringThe + operator and the ==/!= operators, whenever one operand is an object and the other a primitive

Two methods every object inherits drive all three algorithms. toString() returns a string representation — the default is the unhelpful "[object Object]", but built-ins override it usefully: arrays join their elements with commas, functions return their own source text, Date returns a human-readable date/time string, and RegExp returns literal-like source (/\d+/g). valueOf() is supposed to return a primitive that meaningfully represents the whole object, if one exists — the default just returns the object itself (not a primitive, so it's skipped), but the numeric wrapper types (Number, Boolean, String) return their wrapped primitive, and Date returns its millisecond timestamp. 

({ x: 1, y: 2 }).toString()          // => "[object Object]"
[1, 2, 3].toString()                 // => "1,2,3"
(function(x) { return x; }).toString() // => "function(x) { return x; }"
/\d+/g.toString()                    // => "/\\d+/g"

let d = new Date(2020, 0, 1);
d.toString()   // => "Wed Jan 01 2020 00:00:00 GMT-0800 (...)" — prefer-string wins
d.valueOf()    // => 1577865600000 — the millisecond timestamp
+d             // => 1577865600000: unary + forces prefer-number, using valueOf()
`${d}`         // => the toString() text: template literals use prefer-string
d + ""         // => the toString() text too: no-preference is prefer-string FOR DATES

You can override this behavior for your own classes by defining toString(), valueOf(), or, for full control over all three algorithms at once, a Symbol.toPrimitive method — see Metaprogramming.

== vs. === Hard

===, the strict equality operator, never converts types: two values of different types are simply never ===-equal, full stop. ==, by contrast, performs one of the object-to-primitive conversions above and then a cascade of further conversions whenever its two operands have different types, hunting for a way to consider them equal. Internalizing that cascade — rather than memorizing individual surprising cases — is the only way to actually predict what == will do.

The (simplified) rules == applies, in order, when the operand types differ:

  • null == undefined is special-cased to true — and neither one is ever == to anything else, including 0, false, or "".
  • number vs. string: the string converts to a number.
  • boolean vs. anything: the boolean converts to a number (true → 1, false → 0) and the comparison is retried.
  • object vs. primitive (number, string, or BigInt): the object converts to a primitive via the no-preference algorithm, and the comparison is retried.
  • BigInt vs. number or string: converted and compared numerically, as long as the string/number is a valid integer value.
// Worked example 1: chasing the cascade one step at a time
"0" == 0        // => true:  "0" converts to the number 0, then 0 == 0
0 == false      // => true:  false converts to 0, then 0 == 0
"0" == false    // => true:  BOTH sides convert to 0 before comparing — two hops!
null == undefined  // => true: special-cased, no conversion happens at all
null == 0          // => false: null is ONLY == to undefined, never to 0
undefined == 0     // => false: same rule, other spelling

// Worked example 2: the object case
"1,2,3" == [1, 2, 3]  // => true: the array's no-preference conversion
                      //          calls toString(), joining to "1,2,3",
                      //          then both sides are equal strings
0 == []               // => true: [] converts (via "" then Number("")) to 0
0 == [0]              // => true: [0] converts (via "0" then Number("0")) to 0
"" == []              // => true: [] stringifies to ""

Crucially, "value X converts to false in a boolean context" does not mean X == false — different operators trigger different conversion targets, and == never converts either operand to boolean as part of its own algorithm: 

if (undefined) { /* never runs: undefined is falsy in a boolean context */ }
undefined == false   // => false! == does not convert undefined to a boolean here
Default to ===/!==

The one broadly accepted idiomatic use of == is x == null, which conveniently tests for null or undefined in a single comparison — everywhere else, prefer === and !== so that a type mismatch is a bug you notice immediately rather than a silent conversion.

Explicit conversion idioms

Sometimes you want a conversion to happen visibly rather than as a side effect of some other operation. The clearest way is calling Boolean(), Number(), or String() as plain functions (not with new — that instead produces a boxed wrapper object, a historical wart with essentially no legitimate modern use). A handful of shorthand idioms rely on operators' implicit conversions and show up often enough in real code to be worth recognizing: 

Number("3")     // => 3
String(false)   // => "false"       (or: false.toString())
Boolean([])     // => true

x + ""    // => String(x): + with a string operand forces string conversion
+x        // => Number(x): unary + forces prefer-number conversion
x - 0     // => Number(x): same idea, using subtraction instead
!!x       // => Boolean(x): the double-negate idiom

Variable declaration and assignment

Modern JavaScript declares variables with let and constants with const; both were introduced in ES6 to replace the older, quirkier var (still legal, and still common in code written before ES6 — or by developers who haven't caught up). None of the three declaration forms specify a type: a JavaScript variable can hold a number at one point in the program and a string moments later, for better or worse.

Declaring with let and const

let i;                    // Declared, value is undefined until assigned
let sum;
let i, sum;               // Multiple declarations in one statement
let message = "hello";    // Initialize at declaration — good practice when possible
let x = 2, y = x * x;     // Later initializers may reference earlier ones

const H0 = 74;            // Hubble constant — MUST be initialized...
const AU = 1.496e8;
H0 = 100;                 // ...and TypeError: cannot reassign a constant

const point = { x: 1 };
point.x = 2;              // Fine! const only locks the BINDING, not the object's contents
point = {};               // TypeError: Assignment to constant variable

Loop variables can be declared right in the loop header, and — a detail that surprises people — const works there too, as long as the loop body doesn't try to reassign it; a fresh binding is created each iteration, so declaring it const only promises "not reassigned within this iteration," not "the same value across iterations": 

for (let i = 0, len = data.length; i < len; i++) console.log(data[i]);
for (const datum of data) console.log(datum);       // legal: no reassignment inside
for (const key in someObject) console.log(key);     // also legal, same reason
Which default should you reach for?

Two reasonable conventions exist. One camp uses const only for values that are fundamentally, conceptually unchanging (physical constants, version strings). The other defaults to const for everything and only switches a given declaration to let once it turns out to actually need reassignment — this catches accidental reassignment bugs early. The book favors the first approach, but either is defensible; what matters is picking one and being consistent.

It's a SyntaxError to declare the same name twice with let/const in the same scope — but perfectly legal (if often confusing) to declare a new variable with the same name in a nested scope, which temporarily shadows the outer one: 

const x = 1;          // global x
if (x === 1) {
  let x = 2;           // a DIFFERENT x, scoped to this block
  console.log(x);      // => 2
}
console.log(x);        // => 1: back in the outer scope

let x = 3;             // SyntaxError: Identifier 'x' has already been declared

Scope, hoisting, and the temporal dead zone: let/const vs. var Hard

var predates block scope in JavaScript entirely, and the differences between it and let/const are not cosmetic — they change which bugs are even possible to write:

let / constvar
ScopeThe nearest enclosing block { } — if, loop body, function body, or bare blockThe nearest enclosing function, completely ignoring block boundaries
Redeclaring the same name in the same scopeSyntaxErrorLegal and harmless — common with loop counters named i across sibling loops
Using the variable before its declaration line runsReferenceError — the "temporal dead zone"Evaluates to undefined, no error at all
As a top-level globalNot added as a property of the global objectBecomes a real property of globalThis (and can't be deleted)

var is hoisted: wherever a var declaration appears in a function, the declaration — but not the initializer — is conceptually moved to the very top of that function. This is what lets var variables be referenced anywhere in their enclosing function without error, even textually "above" the line that declares them; if the initializing assignment hasn't run yet, you simply get undefined rather than an error. 

// Worked example 1: var leaks out of blocks; let/const don't
if (true) {
  var legacy = "I exist outside this block";
}
console.log(legacy);   // => "I exist outside this block": var ignored the block

if (true) {
  let modern = "I do not";
}
console.log(modern);   // ReferenceError: modern is not defined — block-scoped correctly

// Worked example 2: hoisting gives var a silent "undefined" phase;
// let/const give you a hard error instead (the temporal dead zone)
console.log(hoisted);  // => undefined: the declaration was hoisted, not the value
var hoisted = 5;

console.log(inTDZ);    // ReferenceError: Cannot access 'inTDZ' before initialization
let inTDZ = 5;         // "inTDZ" is unusable from the top of its scope until this line runs

That second example is the important mental model: let and const variables are technically hoisted too (their name is known throughout the enclosing block from the start), but unlike var they remain in an unusable "temporal dead zone" from the top of the block until the declaration statement itself executes — accessing them early is treated as a real error instead of quietly handing back undefined. This is exactly the class of bug let/const were designed to catch at the source instead of at 3 a.m. in production.

Accidentally-global variables

Outside of strict mode, assigning to a name that was never declared with let, const, or var silently creates a new global variable — no matter how deeply nested inside functions and blocks the assignment is. In strict mode (the default inside ES modules and classes; see Statements), the same code throws a ReferenceError instead, which is one of the best reasons to always write in strict mode.

Practical rule

Default to const, switch to let only when a binding genuinely needs reassignment, and treat var as legacy syntax you need to be able to read in old code but should not write in new code.

Destructuring assignment

Destructuring unpacks values out of an array or object into individual variables in a single statement, using syntax on the left-hand side of = that mirrors array/object literal syntax on the right. It's most commonly combined with a let/const/var declaration, but it also works as a plain assignment to already-declared variables, and — covered in Functions — directly in a function's parameter list. 

// Array destructuring
let [x, y] = [1, 2];              // Same as let x = 1, y = 2
[x, y] = [x + 1, y + 1];          // Ordinary assignment works too
[x, y] = [y, x];                  // The classic swap idiom — no temp variable needed

// Extra variables on the left become undefined; extra values on the right
// are silently ignored; commas skip values you don't care about:
let [a] = [1, 2, 3];              // a == 1; 2 and 3 are dropped
let [, second, , fourth] = [1, 2, 3, 4]; // second == 2; fourth == 4

// Rest pattern collects everything left over into a real array:
let [first, ...rest] = [1, 2, 3, 4];  // first == 1; rest == [2, 3, 4]

// Works with ANY iterable, not just arrays — including strings:
let [firstChar, ...restChars] = "Hello"; // firstChar == "H"; restChars == ["e","l","l","o"]

// Nesting mirrors the shape of the data:
let [p, [q, r]] = [1, [2, 2.5]];  // p == 1; q == 2; r == 2.5

// A function that "returns multiple values" via an array reads naturally:
function toPolar(x, y) {
  return [Math.sqrt(x * x + y * y), Math.atan2(y, x)];
}
let [radius, theta] = toPolar(1.0, 1.0);
// Object destructuring: pattern mirrors an object literal
let { r, g, b } = { r: 0, g: 128, b: 255, a: 1 }; // extra props (a) simply ignored

// Rename while destructuring with a colon: "propertyName: localVariableName"
let { cos: cosine, tan: tangent } = Math;  // cosine === Math.cos, tangent === Math.tan

// Default values kick in only when the source property is undefined/missing:
let { width = 100, height = 100 } = { width: 320 }; // width == 320; height == 100

// Nested object/array combinations, however unwieldy, are legal:
let points = [{ x: 1, y: 2 }, { x: 3, y: 4 }];
let [{ x: x1, y: y1 }, { x: x2, y: y2 }] = points;
(x1 === 1 && y1 === 2 && x2 === 3 && y2 === 4)  // => true

let byArrays = { p1: [1, 2], p2: [3, 4] };
let { p1: [px1, py1], p2: [px2, py2] } = byArrays; // destructure an object OF arrays

// A common, very readable pattern: iterating an object's entries
let obj = { x: 1, y: 2 };
for (const [name, value] of Object.entries(obj)) {
  console.log(name, value); // "x 1" then "y 2"
}
Sanity-checking complex destructuring

When a destructuring pattern gets hard to read, there's a reliable trick: after the assignment runs, the left-hand side — used unmodified as an ordinary expression — should reconstruct something equivalent to the original right-hand side. If flipping it around that way doesn't look right, the pattern is probably wrong too: 

let points = [{ x: 1, y: 2 }, { x: 3, y: 4 }];
let [{ x: x1, y: y1 }, { x: x2, y: y2 }] = points;

// Sanity check: rebuild something equal to `points` using x1,y1,x2,y2
let points2 = [{ x: x1, y: y1 }, { x: x2, y: y2 }]; // deep-equal to points

If a pattern is genuinely this deep in practice, it's often clearer to just write out points[0].x explicitly instead.

Summary

Key ideas to carry forward from this chapter:

  • Every value is a primitive (number, string, boolean, BigInt, symbol, null, undefined) or an object — and that split determines mutability and copy/comparison semantics.
  • Numbers are a single 64-bit floating-point type with well-defined but sometimes surprising rounding behavior; BigInt exists specifically for exact large integers.
  • Strings are immutable sequences of UTF-16 code units; template literals and tagged templates (ES6) make string-building far more ergonomic than concatenation.
  • null and undefined both mean "no value" but conventionally signal different things; ?? lets you supply a default only for genuinely missing values.
  • Primitives are copied/compared by value; objects are copied/compared by reference — the root cause of most "why did my variable change?!" bugs.
  • Type conversion is pervasive and rule-governed, not magical — and =='s conversions are exactly why === should be your default.
  • let/const give you block scope and a temporal dead zone that turns a whole class of var-era bugs into immediate errors; destructuring lets you unpack structured data in one expressive statement.

With the type system established, the next stop is the operators and expressions that combine these values — see Expressions & Operators.
