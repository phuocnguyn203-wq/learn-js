Storage & Workers

Two capabilities that let a web page stop behaving like a stateless document: a place to remember things between visits, and a way to run JavaScript that doesn't block the main thread. Client-side storage (Web Storage, cookies, IndexedDB) gives the browser a memory; workers give it a second brain.

Client-side storage: the four mechanisms

A web app can choose to keep data around for the lifetime of a tab, or persist it for months or years on the user's machine. Every mechanism covered here is segregated by origin — a page can never read storage written by a different protocol, host, or port, even if the two pages are served by the same company. Two pages that do share an origin, on the other hand, can use storage as a communication channel: data entered in a form on one page can show up in a table on another.

There are four mechanisms in practice, each with a different set of tradeoffs:

  • Web Storage (localStorage and sessionStorage) — a persistent string-keyed, string-valued map. Simple, synchronous, good for small-to-moderate amounts of data.
  • Cookies — the oldest mechanism, designed for the server, awkwardly scriptable from the client, and re-sent with every matching HTTP request.
  • IndexedDB — an asynchronous, transactional, indexed object database. The only one of the four that's a real database.

Deep dive: choosing a storage mechanism Hard

Picking the wrong one is a common source of bugs and performance problems — slow requests because every cookie on the domain rides along with them, or a UI that locks up because IndexedDB wasn't used for something that should never have blocked the render. The table below is the decision reference:

The single biggest gotcha in that table is the "sent to server" row. Cookies were invented for server-side session tracking, and the browser still faithfully attaches every cookie that matches a request's domain and path to that request's headers — whether or not the server has any use for that particular cookie. A page that stores 3 KB of client-only preference data in a cookie is paying that 3 KB in upload bandwidth on every single request to that origin: every image, every script, every XHR. Web Storage and IndexedDB data, by contrast, never leaves the browser unless your own code explicitly sends it (e.g. in a fetch() body). 

// Example A: a client-only setting — belongs in localStorage, never in a cookie.
localStorage.setItem("reduceMotion", "true");
// This value is never transmitted anywhere. The server never sees it, and
// never needs to — only this page's own JavaScript reads it back.
if (localStorage.getItem("reduceMotion") === "true") {
  document.documentElement.classList.add("no-animations");
}
// Example B: a session identifier the *server* needs to read on every
// request — this is the one legitimate remaining use case for a cookie,
// and it's usually set by the server (Set-Cookie response header), not by
// client JavaScript at all.
// Set-Cookie: sessionId=abc123; Secure; HttpOnly; SameSite=Lax; Max-Age=3600
//
// document.cookie can't even see this cookie once HttpOnly is set — that's
// the point: it keeps the session token out of reach of an XSS payload
// that manages to run arbitrary JavaScript on your page.
Nothing here is encrypted

Browsers store saved passwords encrypted, but localStorage, sessionStorage, cookies, and IndexedDB are all plain text on disk. They're readable by anyone with access to the device and by malicious software running on it. Never store passwords, full payment details, or high-privilege tokens in any of them — and treat Secure/HttpOnly cookies as the floor of protection for a session token, not encryption.

localStorage and sessionStorage

localStorage and sessionStorage (both properties of Window) refer to Storage objects. A Storage object behaves almost like a plain JavaScript object, with two differences: every property value must be a string, and the properties persist — reloading the page does not clear them. 

// Plain property access works, just like a regular object:
let name = localStorage.username;          // read
if (!name) {
  name = prompt("What is your name?");
  localStorage.username = name;             // write
}
delete localStorage.username;               // remove one property

// The Storage object also defines explicit methods, if you prefer them:
localStorage.setItem("theme", "dark");
localStorage.getItem("theme");              // => "dark"
localStorage.removeItem("theme");
localStorage.clear();                        // wipe every property for this origin

// Enumerate everything currently stored:
for (let key in localStorage) { console.log(key, "=", localStorage[key]); }
Object.keys(localStorage);                   // same idea, as an array

Because only strings can be stored, anything else has to be encoded going in and decoded coming out. JSON is the usual choice for anything beyond a primitive: 

// Numbers are silently stringified — remember to parse them back:
localStorage.x = 10;
let x = parseInt(localStorage.x);

// Dates need explicit conversion both ways:
localStorage.lastRead = new Date().toUTCString();
let lastRead = new Date(Date.parse(localStorage.lastRead));

// JSON is the convenient path for anything structured:
localStorage.prefs = JSON.stringify({ theme: "dark", fontSize: 14 });
let prefs = JSON.parse(localStorage.prefs);

Lifetime and scope

Data written through localStorage is permanent: it never expires and stays on the device until a script deletes it or the user clears it through browser UI. It is scoped to the document's origin — protocol, hostname, and port together — so all documents sharing an origin see the same localStorage, regardless of which script on the page actually touches it. It is also scoped per browser implementation: visiting a site in Firefox and then again in Chrome gives you two completely separate stores, even on the same machine.

sessionStorage has a different lifetime: it lives as long as the top-level tab or window that created it. Closing that tab deletes its sessionStorage for good (though a browser that offers to reopen recently closed tabs may make this last longer than it looks). Critically, sessionStorage is scoped per tab, not just per origin — open the same page in two tabs and each gets independent storage, even though they're running byte-for-byte identical scripts.

The storage event: cross-tab sync Hard

Every time localStorage changes, the browser fires a storage event on every other Window that can see that data — but never on the window that made the change. That asymmetry is what makes it usable as a broadcast channel: one tab writes, every sibling tab hears about it, and the writer doesn't get an event it has to filter out. 

window.addEventListener("storage", (event) => {
  // key        — the property name that changed (null if clear() was called)
  // newValue   — the new value (absent if removeItem() was called)
  // oldValue   — the previous value (absent if the property is brand new)
  // storageArea — the Storage object that changed (usually localStorage)
  // url        — the URL of the document whose script made the change
  console.log(`${event.key} changed from ${event.oldValue} to ${event.newValue}`);
});

A worked example: an image-editing app lets the user pop tool palettes out into separate windows. When the user picks a new tool in one window, that window writes the choice to localStorage; every other window sharing the origin receives a storage event and updates its own palette display to match — with zero direct references between the windows and no server round-trip: 

// In the window where the user clicks a tool:
function selectTool(toolName) {
  localStorage.setItem("activeTool", toolName);   // triggers "storage" in siblings
  applyTool(toolName);                             // update this window too
}

// In every window (including palette popouts):
window.addEventListener("storage", (event) => {
  if (event.key === "activeTool") {
    highlightToolInPalette(event.newValue);
  }
});

A second, simpler example: broadcasting a "reduce motion" preference so every open tab honors it immediately, without a page reload, purely because setting localStorage is itself the notification: 

function setReduceMotion(on) {
  localStorage.setItem("reduceMotion", on ? "1" : "0"); // fires storage in other tabs
  document.documentElement.classList.toggle("no-animations", on);
}
window.addEventListener("storage", (e) => {
  if (e.key === "reduceMotion") {
    document.documentElement.classList.toggle("no-animations", e.newValue === "1");
  }
});
Register with window.onstorage too

You can set window.onstorage directly instead of addEventListener if you only need one handler — both work identically, since storage is a normal DOM event.

Cookies

A cookie is a small named piece of data associated with a page or an entire site, implemented at the HTTP protocol level rather than as a JavaScript feature. Cookies were designed for server-side scripts: the browser automatically attaches matching cookies to every request it sends to a server, which is exactly what makes them expensive compared to Web Storage for anything the client alone cares about. Client-side code can still read and write cookies, through the document.cookie property — an old, cryptic API with no dedicated methods at all.

Reading and writing document.cookie

Reading document.cookie returns one string containing every cookie visible to the current document, formatted as name=value pairs separated by "; ". There's no built-in way to read a single cookie by name — you get the whole string and parse it yourself, typically with split("; "): 

document.cookie;
// => "theme=dark; sessionHint=abc123; consent=yes"  — every cookie, one string

// Parse it into a Map, decoding values that were escaped on the way in:
function getCookies() {
  let cookies = new Map();
  let list = document.cookie.split("; ");
  for (let cookie of list) {
    if (!cookie.includes("=")) continue;
    let p = cookie.indexOf("=");
    let name = cookie.substring(0, p);
    let value = decodeURIComponent(cookie.substring(p + 1));
    cookies.set(name, value);
  }
  return cookies;
}

Writing to document.cookie looks like assignment but behaves more like "merge this one cookie into the existing set" — it never clobbers other cookies, only the one whose name you specify. Cookie values can't contain semicolons, commas, or whitespace, so encodeURIComponent() is standard practice before storing anything that isn't a bare token: 

document.cookie = `version=${encodeURIComponent(document.lastModified)}`;

// A reusable setter that handles the max-age attribute:
function setCookie(name, value, daysToLive = null) {
  let cookie = `${name}=${encodeURIComponent(value)}`;
  if (daysToLive !== null) {
    cookie += `; max-age=${daysToLive * 60 * 60 * 24}`;   // max-age is in seconds
  }
  document.cookie = cookie;
}

// To delete a cookie: set it again with the same name/path/domain,
// any value, and max-age=0.
function deleteCookie(name) {
  document.cookie = `${name}=; max-age=0`;
}

Cookie attributes: lifetime and scope

By default a cookie is transient — it lasts only for the current browser session and disappears when the browser exits. Attributes, appended to the same string you assign to document.cookie, control lifetime and visibility:

  • max-age=seconds — how long the cookie should be retained. Without it, the cookie dies with the session.
  • expires=date — an older, date-based alternative to max-age.
  • path=value — by default a cookie is visible only to pages in the same directory (or subdirectories) as the page that set it. Setting path=/catalog shares it with everything under /catalog; path=/ makes it site-wide, like localStorage.
  • domain=value — shares a cookie across subdomains, e.g. setting domain=.example.com from catalog.example.com makes it visible to orders.example.com too. You cannot set a domain that isn't a parent of the current host.
  • Secure — the cookie is transmitted only over HTTPS, never plain HTTP.
  • SameSite=Strict|Lax|None — controls whether the cookie is sent on cross-site requests (e.g. when the site is loaded via a link or a third-party <img>/<iframe>); the main modern defense against cross-site request forgery.
  • HttpOnly — settable only by a server's Set-Cookie response header, never by client JavaScript. A cookie marked HttpOnly is invisible to document.cookie entirely, which is precisely the point: it keeps a session token safe even if an XSS bug lets an attacker run arbitrary JavaScript on the page.
// Client-settable attributes, all client-side:
document.cookie = "theme=dark; max-age=31536000; path=/; SameSite=Lax";
// ~1 year, whole site, not sent on most cross-site navigations.

// HttpOnly and Secure for anything sensitive are set by the SERVER, e.g.
// via an HTTP response header — never available to document.cookie:
//   Set-Cookie: sessionId=abc123; Secure; HttpOnly; SameSite=Lax; Max-Age=3600
Cookie size and count limits

Browsers aren't required to retain more than 300 cookies total, 20 per web server, or 4 KB per cookie (name and value combined count toward that limit) — though in practice most browsers allow considerably more than 300 total. This is one more reason cookies are a poor fit for anything beyond small identifiers.

IndexedDB: a transactional client-side database Hard

IndexedDB is a genuine object database built into the browser — more powerful, more efficient, and more robust than the flat key-value model of Web Storage, though also considerably more complex to use directly. It's an object database, not a relational one: there's no SQL, no joins, just named collections of JavaScript values called object stores. Like Web Storage, an IndexedDB database is scoped to the document's origin.

The core vocabulary:

  • Database — a named collection of object stores. Each origin can have any number of databases, each uniquely named.
  • Object store — holds JavaScript values, serialized with the same structured clone algorithm used for worker messages (see below), which is why you can store Maps, Sets, and typed arrays directly, not just JSON-safe values.
  • Key — every stored object needs a unique, sortable key: a string, number, or Date. You can let IndexedDB auto-generate one, or specify a key path — a property name IndexedDB pulls the key from automatically (e.g. an object's own id field).
  • Index — a secondary, non-unique key defined on an object store, letting you query by some property other than the primary key.
  • Transaction — every read or write happens inside a transaction, which guarantees all-or-nothing atomicity. Transactions auto-commit once every pending request on them has succeeded and no more are queued — there's no explicit commit() call.
It's event-based, not Promise-based

IndexedDB predates widespread Promise support, so its asynchronous operations return a request object with onsuccess/onerror callback properties rather than returning a Promise. It does not work with async/await directly. Opening a database, and reading or writing an object store, are asynchronous; creating a transaction and looking up a store or index by name from it are synchronous. In real projects, reach for a small Promise-wrapping library (e.g. idb) rather than hand-writing callback chains for every query — but it's worth understanding the raw event-based shape at least once, since that's what such libraries wrap.

Schema setup: the version-upgrade pattern

Object stores and indexes can only be created or modified inside a special event handler: onupgradeneeded. This event fires exactly once, the first time a database is opened, and again any time you open it with a higher version number than what's currently stored on disk. This is IndexedDB's migration mechanism: bump the version argument to indexedDB.open(), and your onupgradeneeded handler runs to bring the schema up to date. 

let request = indexedDB.open("myapp", 1);   // name, version

request.onupgradeneeded = () => {
  let db = request.result;
  // Object stores and indexes can ONLY be created/altered in here.
  let store = db.createObjectStore("notes", { keyPath: "id" });
  store.createIndex("byDate", "createdAt");   // secondary, non-unique key
};

request.onerror = () => console.error("could not open database:", request.error);

request.onsuccess = () => {
  let db = request.result;
  let tx = db.transaction("notes", "readwrite");   // create a transaction
  let store = tx.objectStore("notes");              // look up the store (sync)
  store.put({ id: 1, text: "Hello", createdAt: Date.now() });  // write (async)
  tx.oncomplete = () => console.log("saved");
};

Worked example: a zip-code lookup database

A more complete example ties the pieces together: a database that maps US postal codes to city/state, queryable in both directions — by zip code (the primary key) and by city name (a secondary index). It demonstrates initialization from a network fetch, populating a store inside a write transaction, and querying by both the primary key and an index: 

// Get (and lazily create/populate) the database, then hand it to a callback.
function withDB(callback) {
  let request = indexedDB.open("zipcodes", 1);
  request.onerror = console.error;
  request.onsuccess = () => callback(request.result);
  request.onupgradeneeded = () => initdb(request.result, callback);
}

// Runs only the first time — creates the schema and loads seed data.
function initdb(db, callback) {
  let store = db.createObjectStore("zipcodes", { keyPath: "zipcode" });
  store.createIndex("cities", "city");   // query by city name too

  fetch("zipcodes.json")
    .then(response => response.json())
    .then(zipcodes => {
      let tx = db.transaction(["zipcodes"], "readwrite");
      tx.onerror = console.error;
      let store = tx.objectStore("zipcodes");
      for (let record of zipcodes) store.put(record);   // { zipcode, city, state }
      tx.oncomplete = () => callback(db);                 // ready once all writes land
    });
}

// Look up a city by zip code — a primary-key query.
function lookupCity(zip, callback) {
  withDB(db => {
    let tx = db.transaction(["zipcodes"]);        // read-only by default
    let request = tx.objectStore("zipcodes").get(zip);
    request.onerror = console.error;
    request.onsuccess = () => {
      let record = request.result;
      callback(record ? `${record.city}, ${record.state}` : null);
    };
  });
}

// Look up every zip code for a given city name — a secondary-index query.
function lookupZipcodes(city, callback) {
  withDB(db => {
    let tx = db.transaction(["zipcodes"]);
    let index = tx.objectStore("zipcodes").index("cities");
    let request = index.getAll(city);
    request.onerror = console.error;
    request.onsuccess = () => callback(request.result);
  });
}

For range queries — "everything between these two keys" — construct an IDBKeyRange and pass it to getAll() or openCursor() on either an object store or an index, in place of a single key value. A cursor is the right tool when there may be too many matching rows to materialize into an array all at once; getAll() is simpler when you know the result set is small.

Wrap it, don't fight it

Every request is a fresh object with its own onsuccess/onerror handlers — verbose for anything beyond a couple of queries. A thin Promise wrapper (roll your own, or use a library like idb) turns this into ordinary async/await code without changing the underlying transaction semantics.

Worker Threads and Messaging

JavaScript in a tab is fundamentally single-threaded: the browser never runs two event handlers concurrently, and never fires a timer while a handler is still running. That's what makes client-side JavaScript approachable — there's no shared-memory race condition to reason about — but it has a sharp corollary: a function that runs too long freezes everything, including scrolling, clicking, and rendering, because it's holding the one and only thread that does all of that work. This is exactly why fetch() and friends are asynchronous rather than blocking (see Navigation & Networking for the async networking APIs themselves).

The Worker class is the browser's one carefully controlled exception to single-threadedness. A Worker runs on a genuinely separate OS thread, with its own independent global object (a WorkerGlobalScope, not a Window) — no access to window, document, or any variable from the script that created it. The only connection between a worker and the thread that spawned it is asynchronous message passing. Concurrent DOM mutation is therefore still impossible (only the main thread ever touches the DOM), but a worker can run a computation for as long as it needs without ever stalling the event loop or freezing the page.

Creating a worker isn't as heavy as opening a new browser window, but it isn't free either — it's not a lightweight "fiber" you should spin up for trivial work. Tens of workers in a complex app is reasonable; hundreds or thousands is not.

Creating a worker

// main.js — the page that creates the worker
let worker = new Worker("cruncher.js");   // URL, resolved like any other script URL

worker.postMessage({ command: "process", data: bigArray });
worker.onmessage = (event) => console.log("result:", event.data);
worker.onerror = (event) =>
  console.error(`worker error at ${event.filename}:${event.lineno}: ${event.message}`);

worker.terminate();   // force-stop the worker thread at any time

// cruncher.js — runs on its own thread, in its own WorkerGlobalScope
self.onmessage = (event) => {
  let result = heavyComputation(event.data.data);
  self.postMessage(result);
};

A relative URL passed to Worker() is resolved against the document that created the worker; an absolute URL must share the document's origin (protocol, host, and port). Inside the worker file, self refers to the worker's own global object (there is no window), and postMessage()/onmessage appear as a global function and global property, working in the opposite direction from the outside: calling postMessage() inside the worker delivers a message to the Worker object outside it, and vice versa.

A worker's global scope still has a useful subset of what a Window offers: setTimeout/setInterval and their clear-counterparts, a read-only location, a navigator with the usual identification properties, fetch(), the Console object, and even IndexedDB access — plus the Worker constructor itself, so a worker can spawn its own sub-workers. Older, pre-ES-module worker code loads dependencies with the synchronous global importScripts("a.js", "b.js") rather than import; modern code can instead pass { type: "module" } as a second argument to Worker() and use ordinary import declarations.

Dedicated vs. shared workers

Everything above describes a dedicated worker — owned by exactly one script, and terminated when that script's page goes away. A shared worker (SharedWorker) is reachable from multiple tabs or iframes of the same origin at once, communicating over a MessagePort per connecting document rather than a single implicit channel. Shared workers are useful for coordinating state across tabs (a single WebSocket connection shared by every open tab, for instance) but are less commonly needed than dedicated workers and have weaker cross-browser support; reach for a dedicated worker unless you specifically need one worker instance serving several documents simultaneously.

Deep dive: structured clone and transferable objects Hard

Every value passed to postMessage() — on a Worker, from inside a worker, or over a MessageChannel — is copied using the structured clone algorithm, the same serialization mechanism IndexedDB uses internally to store objects. It is strictly more capable than JSON.stringify/parse: it correctly handles Map, Set, Date, RegExp, typed arrays, ArrayBuffer, and circular references within the object graph. What it cannot clone: functions, DOM nodes, and anything with a prototype chain the algorithm doesn't specifically know about (class instances lose their prototype and come back as plain objects with the same properties).

The critical consequence: the receiving side gets an independent copy, never a live reference. Mutating the original object after calling postMessage() has absolutely no effect on what the other side already received (or will receive) — there is no shared memory involved at all. 

// main.js
let payload = { items: [1, 2, 3], label: "batch-1" };
worker.postMessage(payload);

// Mutating payload right after posting does NOT affect what the worker
// receives — the clone already happened synchronously inside postMessage().
payload.label = "MUTATED";
payload.items.push(999);

// worker.js
self.onmessage = (event) => {
  console.log(event.data.label);        // => "batch-1", NOT "MUTATED"
  console.log(event.data.items.length); // => 3, the push() never reached here
};

That copy has a cost: for a large payload — say, a multi-megabyte ArrayBuffer holding raw image or audio data — cloning it on every message is real, measurable overhead. postMessage() accepts an optional second argument, an array of transferable objects (currently ArrayBuffer and MessagePort) that should be moved rather than copied. A transferred ArrayBuffer is handed to the receiving side with zero copying, but the sending side's reference becomes immediately unusable — its byte length drops to 0 and any attempt to read it throws. This eliminates the copy cost entirely while guaranteeing there's never a moment where both threads could read or write the same bytes concurrently. 

// main.js
let buffer = new ArrayBuffer(8 * 1024 * 1024);  // 8 MB
let view = new Uint8Array(buffer);
view[0] = 42;

// Second argument lists which objects inside the message to TRANSFER
// instead of clone. The buffer must be reachable from the first argument.
worker.postMessage({ buffer }, [buffer]);

console.log(buffer.byteLength);   // => 0 — this thread no longer owns it!
// view[0] would throw now; the buffer has been moved, not copied.

// worker.js
self.onmessage = (event) => {
  let view = new Uint8Array(event.data.buffer);
  console.log(view[0]);   // => 42 — the worker now owns the memory
};

This transfer technique is exactly how a worker hands back the results of an image-processing task without a copy: compute into an ImageData's backing ArrayBuffer, then transfer that buffer to the main thread instead of cloning potentially tens of megabytes of pixel data. It's precisely the approach used to parallelize the book's Mandelbrot Set renderer (§15.14) across several worker threads — each worker computes one tile of the image into its own pixel buffer and transfers it back rather than copying it, which matters a great deal when you're moving many large buffers per second.

Error handling in workers

An uncaught exception inside a worker fires an error event, first on the worker's own global scope, then — unless preventDefault() was called there — on the Worker object back on the main thread. If nothing handles it there either, the error is logged to the console just like any other uncaught error. 

// Handle it from inside the worker:
self.onerror = (e) => {
  console.log(`worker error at ${e.filename}:${e.lineno}: ${e.message}`);
  e.preventDefault();   // stop it from also propagating to the main thread
};

// Or handle it from the main thread instead:
worker.onerror = (e) => {
  console.log(`worker error at ${e.filename}:${e.lineno}: ${e.message}`);
  e.preventDefault();
};

Workers also support unhandledrejection, for a Promise that rejects with no .catch() anywhere in the chain — register it with self.onunhandledrejection or addEventListener("unhandledrejection", ...); the event object carries both the rejected promise and the rejection reason.

MessageChannel: extra ports, and window-to-window messaging

A worker's default communication path is a single implicit channel. If you need more — say, a separate high-priority channel alongside ordinary data traffic, or direct communication between two sibling workers without relaying every message through the main thread — create a MessageChannel explicitly. It produces a connected pair of MessagePort objects; a message posted on one port fires a message event on the other: 

let channel = new MessageChannel();
let myPort = channel.port1;
let yourPort = channel.port2;

myPort.postMessage("can you hear me?");
yourPort.onmessage = (e) => console.log(e.data);   // => "can you hear me?"

// A port can itself be transferred to a worker, becoming that worker's
// end of the channel (and unusable on this side, just like ArrayBuffer):
let worker = new Worker("worker.js");
worker.postMessage({ command: "setUrgentPort", value: yourPort }, [yourPort]);
myPort.addEventListener("message", handleUrgentReply);
myPort.start();   // required when using addEventListener rather than onmessage —
                   // messages queue silently until the port is "started"

The same postMessage()/structured-clone model, minus the worker-specific parts, is also how a document safely talks to a cross-origin <iframe>: window.postMessage(message, targetOrigin) takes a required origin string as its second argument so the browser can refuse delivery if the target window turns out to hold content from an unexpected origin, and the receiving message event carries a source (the sending Window, useful for replying) and an unforgeable origin you should always check before trusting the payload.

When workers are (and aren't) worth it

Good candidates: parsing or crunching a large dataset, image or audio processing, and — a case worth calling out because it's easy to underestimate — work that's individually cheap but runs on every keystroke, like live syntax highlighting in an in-browser code editor. Run that parse on the main thread and it competes with the keypress handler for the same thread, and typing starts to feel laggy even though no single parse is slow in isolation.

Not good candidates: anything quick enough that the round trip of posting a message, structured-cloning the payload, and posting the result back costs more than just doing the work inline would have. Spinning up a Worker itself also has nontrivial startup cost — reuse one long-lived worker for repeated small jobs rather than creating and terminating a fresh worker per task.

Node has the same idea

Node.js exposes an almost identical model for CPU-bound work off its own single thread — see Node's worker_threads, which uses the same postMessage()/structured-clone approach described here.
