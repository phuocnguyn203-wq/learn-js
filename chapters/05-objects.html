Book Chapter 6

Objects

An object is a composite value: a named collection of properties, each pointing to a primitive or to another object. You have already been using objects informally in earlier chapters — this chapter is where we take them apart. We cover how objects get created, how property lookup and assignment actually work (and why they aren't mirror images of each other), how to delete, test, and enumerate properties, how to copy and serialize objects, the handful of methods every object inherits, and the modern shorthand syntax for writing object literals. Threaded through all of it is the single idea that explains almost every surprising thing objects do: prototypal inheritance.

6.1 Introduction to objects

Formally, an object is an unordered collection of properties, and each property is a name/value pair. Names are ordinary strings (with one twist — a property name can also be a Symbol, which we get to in §6.10.3), which is why people sometimes describe JavaScript objects as "hashes," "dictionaries," or "associative arrays." A property name may even be the empty string, and no two properties on the same object may share a name. A property's value can be any JavaScript value at all — or, as we'll see later in this chapter, it can be a pair of accessor functions (a getter and/or a setter) instead of a plain value.

Any value that isn't a string, number, boolean, Symbol, null, or undefined is an object. That includes arrays and functions, which get their own chapters (Arrays and Functions) because they add extra behavior on top of everything described here — but everything you learn in this chapter about property access, inheritance, and enumeration applies to arrays and functions too, since under the hood they are objects.

Objects in JavaScript are mutable and are manipulated by reference, never by value. If a variable x refers to an object and you write let y = x;, both variables now point at the exact same object — there is no copy. Mutating the object through y is visible through x too. Keep this in mind throughout the chapter: "copying an object" always means creating a genuinely new object and copying properties into it (§6.7), never just reassigning a variable.

Every object property carries more than just a name and a value. Three boolean attributes ride along with every property and control what you're allowed to do with it:

AttributeControls
writableWhether an assignment can change the property's value
enumerableWhether the property shows up in a for/in loop or in functions like Object.keys()
configurableWhether the property can be deleted, and whether its attributes (other than value, from writable) can be changed at all

Properties you create yourself — through an object literal or a plain assignment — default to writable: true, enumerable: true, and configurable: true. Many built-in properties are not so permissive: array length is writable but not enumerable, and most Math properties are neither writable nor configurable. We give this trio a full dedicated treatment later in the property attributes deep dive below, including how to set them yourself with Object.defineProperty().

Beyond its own properties, almost every object is also linked to a second object called its prototype, from which it inherits properties. This is the single most important idea in this chapter, and it gets a full deep dive in §6.2.3. For now, the key vocabulary word is own property: a property defined directly on an object, as opposed to one it merely inherits from somewhere up its prototype chain. Nearly every operation in this chapter — querying, setting, deleting, testing, enumerating — cares about the own/inherited distinction, so get comfortable with the term now.

Prototypal inheritance is also the mechanism underneath JavaScript's class keyword: a class is largely syntax sugar over "a constructor function whose prototype property holds the shared methods." We won't build classes in this chapter, but everything here — prototypes, Object.create(), property attributes — is the foundation Classes is built on, so it's worth understanding this chapter well before you get there.

Finally, objects come in a few different flavors of "how locked down" they are, ranging from the ordinary, wide-open objects you get by default to objects that reject new properties entirely:

LevelSet withEffect
Extensible (default)—New own properties may be added at any time
Non-extensibleObject.preventExtensions(o)No new own properties; existing ones can still be modified or deleted
SealedObject.seal(o)Non-extensible, and every existing property becomes non-configurable (no delete, no re-defining) — but writable data properties can still be reassigned
FrozenObject.freeze(o)Sealed, and every data property also becomes non-writable — the object is fully immutable at the top level

We come back to seal() and freeze() with worked examples in the property attributes deep dive below, since they're really just bulk operations over the property attributes introduced above.

6.2 Creating objects

JavaScript gives you three ways to create a new object: an object literal, the new keyword in front of a constructor call, or Object.create(). All three are common in real code, and each hands you a different amount of control over the new object's prototype.

6.2.1 Object literals

The object literal is the workhorse: a comma-separated list of name: value pairs inside curly braces. Property names can be written as bare identifiers or as string literals (useful when a name contains spaces, hyphens, or is a reserved word); values can be any expression, including another object literal. 

let empty = {};                          // An object with no properties at all
let point = { x: 0, y: 0 };              // Two numeric properties
let p2 = { x: point.x, y: point.y + 1 }; // Values can be arbitrary expressions

let book = {
  "main title": "JavaScript",           // Spaces force a string-literal name
  "sub-title": "The Definitive Guide",  // So does a hyphen
  for: "all audiences",                 // "for" is a reserved word, but fine here
  author: {                             // A property's value can be an object
    firstname: "David",
    surname: "Flanagan",
  },                                    // A trailing comma is legal and common
};

Every time an object literal is evaluated it produces a brand-new, distinct object — the property values are recomputed each time. Put a literal inside a loop body or a function that's called repeatedly, and you get a fresh object (potentially with different property values) on every pass: 

function makeCounter(start) {
  return { count: start };  // A new object each call, not a shared one
}
let a = makeCounter(0);
let b = makeCounter(0);
a.count++;
a.count === b.count   // => false: two independent objects

Every object created by an object literal automatically gets the same prototype: Object.prototype. That's where methods like toString() and hasOwnProperty() come from — see §6.2.3.

6.2.2 Creating objects with new

The new operator creates and initializes a new object. It must be followed by a function call; a function invoked this way is called a constructor, and its job is to set up the freshly created object. JavaScript ships constructors for all of its built-in reference types: 

let o = new Object();  // Same as {}
let a = new Array();    // Same as []
let d = new Date();     // The current date and time
let m = new Map();      // An empty Map — see Collections

You can also write your own constructor functions to initialize objects of your own design; that's the subject of Classes, which builds directly on the prototype mechanics introduced next.

6.2.3 Prototypes Deep dive

Nearly every JavaScript object carries a hidden link to a second object — its prototype — and inherits properties from it. Which object becomes the prototype depends entirely on how the object was created:

  • Every object created from an object literal has its prototype set to Object.prototype.
  • An object created with new Ctor() gets its prototype from Ctor.prototype — so new Date()'s prototype is Date.prototype, and new Array()'s prototype is Array.prototype.
  • An object created with Object.create(proto) gets exactly the object you pass in as its prototype — see §6.2.4.
Objects vs. functions that have a prototype property

It's easy to conflate "an object's prototype" with "an object's prototype property," but they're different things. Almost every object has a prototype. Only a relatively small number of objects — functions intended to be used as constructors — have a property named prototype. It's that property that supplies the prototype for objects created with new. Object.prototype itself is one of the rare objects with no prototype of its own — it sits at the top of every chain and inherits nothing.

Prototypes chain: a prototype object can itself have a prototype, which can have a prototype, and so on, until you reach an object whose prototype is null — that's where the chain terminates. When you read a property that an object doesn't have itself, JavaScript walks up this chain looking for it. Here's the chain built by hand with Object.create(): 

let o = {};                 // o's prototype is Object.prototype
o.x = 1;                     // o now has an own property x

let p = Object.create(o);   // p's prototype is o
p.y = 2;                     // p has its own property y, and inherits x

let q = Object.create(p);   // q's prototype is p
q.z = 3;                     // q has its own z, inherits y from p and x from o

q.x + q.y + q.z              // => 6: x and y are inherited, z is q's own
q.toString                   // inherited all the way from Object.prototype
Object.getPrototypeOf(q) === p   // => true
Object.getPrototypeOf(p) === o   // => true
Object.getPrototypeOf(Object.prototype)  // => null: chain terminates here

Object.getPrototypeOf() is the standard, non-magical way to ask "what is this object's prototype?" (the older __proto__ accessor does the same thing but is legacy — prefer the function form in new code, and see §6.10 for the one place __proto__ is still idiomatic: object literals). The instanceof operator is built directly on this chain: an expression obj instanceof Ctor walks obj's prototype chain checking whether Ctor.prototype appears anywhere in it — it is not checking a type tag, it's a search up the same chain Object.getPrototypeOf() traverses: 

let arr = [1, 2, 3];
arr instanceof Array    // => true: Array.prototype is on arr's chain
arr instanceof Object    // => true: Object.prototype is further up the SAME chain
arr instanceof Date      // => false: Date.prototype never appears on this chain

// You can see instanceof "by hand":
function isInstanceOf(obj, Ctor) {
  let proto = Object.getPrototypeOf(obj);
  while (proto !== null) {
    if (proto === Ctor.prototype) return true;
    proto = Object.getPrototypeOf(proto);
  }
  return false;
}
isInstanceOf(arr, Array)  // => true

Most built-in and user-defined constructors have a prototype that itself inherits from Object.prototype, forming a chain that's usually two or three links long. A Date instance, for example, inherits first from Date.prototype (which supplies methods like getFullYear()) and then from Object.prototype (which supplies toString() as a fallback). Chapter 9's equivalent, Classes, and the deep dive on prototype manipulation in Metaprogramming, both build directly on this mechanism.

6.2.4 Object.create()

Object.create() is the explicit, no-surprises way to create an object with a prototype of your choosing — you hand it the prototype directly as its first argument: 

let o1 = Object.create({ x: 1, y: 2 });  // o1 inherits properties x and y
o1.x + o1.y                               // => 3

let o3 = Object.create(Object.prototype); // Equivalent to {} or new Object()
Object.create(null): an object with no prototype at all

Passing null produces an object that inherits absolutely nothing — not toString(), not hasOwnProperty(), nothing. This is the closest thing JavaScript has to a "pure" dictionary: every key you ever see on it is one you (or your program) put there, with zero risk of an inherited name like constructor or toString silently shadowing a key you wanted to store. The tradeoff is that ordinary conveniences stop working — a proto-less object won't coerce to a string with +, and calling o.hasOwnProperty(k) throws a TypeError because there's no hasOwnProperty to call. Use Object.hasOwn(o, k) (or Object.prototype.hasOwnProperty.call(o, k)) to test such objects safely. 

let dict = Object.create(null);
dict["toString"] = "a plain string value now"; // Totally safe: no inherited toString to clash with
dict.toString                                    // => "a plain string value now"
Object.hasOwn(dict, "toString")                  // => true

A second, optional argument to Object.create() lets you describe the new object's own properties with full attribute control — the same descriptor objects used by Object.defineProperty(), covered in the property attributes deep dive below.

One classic use of Object.create() is defensive: guard an object against accidental modification by code you don't control, without the overhead of a deep copy. Pass the library function an object that inherits from your real object rather than the object itself: 

let original = { x: "don't change this value" };
thirdPartyLibrary.doSomething(Object.create(original));
// If the library only READS properties, it sees original's values just fine.
// If it WRITES properties, those writes land on the throwaway wrapper —
// original itself is never touched.
original.x   // => "don't change this value" — guaranteed, no matter what the library did

Why does that guard actually work? Because reading and writing properties are not symmetric operations in JavaScript — which is exactly the subject of the next section.

6.3 Querying and setting properties

You read a property with the dot operator (obj.name) or square brackets (obj["name"]), and you write one the same way, just on the left of an =. Dot notation needs a literal identifier on the right; bracket notation needs any expression that evaluates to a string (or a value coercible to one, or a Symbol) — which is the whole reason bracket notation exists, as the next section shows. 

let author = book.author;         // Read: dot notation, static name
let title = book["main title"];   // Read: bracket notation, needed for the space

book.edition = 7;                    // Write: creates a new "edition" property
book["main title"] = "ECMAScript";   // Write: bracket notation works the same way

Full coverage of the property-access operators themselves — including optional chaining — lives in Expressions & Operators; this chapter is about what happens after the operator fires: how the name gets resolved to a value (or a slot to write into).

6.3.1 Objects as associative arrays

obj.property and obj["property"] always mean the same thing, but they aren't interchangeable in practice: the dot form requires the name to be typed literally into your source code, while the bracket form takes a string value — meaning it can be computed, stored in a variable, built at runtime, or looped over. That's what makes a JavaScript object double as an associative array (a.k.a. hash, map, dictionary): arbitrary string keys, decided while the program runs, not while it's being written. 

// Property names built at runtime — only bracket notation can express this:
let addr = "";
for (let i = 0; i < 4; i++) {
  addr += customer[`address${i}`] + "\n";
}

// A portfolio keyed by ticker symbols the user types in — unknowable in advance:
function addStock(portfolio, ticker, shares) {
  portfolio[ticker] = shares;   // Can't write portfolio.ticker — "ticker" is a variable, not a name
}

function computeValue(portfolio) {
  let total = 0;
  for (let stock in portfolio) {        // for/in walks the enumerable keys
    total += portfolio[stock] * getQuote(stock);
  }
  return total;
}
Prefer Map for real dictionaries

Plain objects work fine as associative arrays, and you'll see the pattern constantly in existing code, but a real Map (see Collections & Typed Arrays) is usually the better tool in modern code: it doesn't confuse your data keys with inherited properties, its keys can be any value (not just strings and Symbols), and it tracks its own size.

6.3.2 Inheritance during property access Deep dive

This is the single most load-bearing rule in the chapter, and it's easy to state but easy to forget: querying a property walks the prototype chain; setting one (almost) never does.

When you read o.x, JavaScript first checks whether o has an own property named x. If not, it checks o's prototype. If that object doesn't have it either, it checks the prototype's prototype, and so on, all the way up to Object.prototype and then to null, at which point the read produces undefined. 

let o = {};                // Inherits from Object.prototype
o.x = 1;                    // o gets its own property x
let p = Object.create(o);  // p inherits from o (and, through o, from Object.prototype)
p.y = 2;                    // p gets its own property y
let q = Object.create(p);  // q inherits from p, o, and Object.prototype
q.z = 3;                    // q gets its own property z

q.x + q.y                  // => 3: BOTH found by walking up the chain
q.toString                 // found all the way at Object.prototype

Writing works completely differently. Assigning o.x = v does not search the chain looking for somewhere to put the value. Instead: if o already has an own property x, the assignment updates it in place. If it doesn't — even if a prototype somewhere up the chain has a property of the same name — the assignment creates a brand-new own property x directly on o. The chain is consulted only to check whether the write is allowed (an inherited read-only property blocks it — see §6.3.3), never as a place to put the value.

The practical consequence: creating an own property with the same name as an inherited one doesn't edit anything upstream — it shadows the inherited property for that one object, leaving everyone else who shares the prototype completely unaffected: 

let unitcircle = { r: 1 };          // A shared prototype object
let c = Object.create(unitcircle);  // c inherits r (= 1) from unitcircle
c.x = 1; c.y = 1;                    // c gets its own x and y
c.r = 2;                             // c now SHADOWS r with its own value 2

c.r            // => 2: c's own property wins
unitcircle.r   // => 1: the shared prototype was never touched

let d = Object.create(unitcircle);  // A second object sharing the same prototype
d.r            // => 1: unaffected by what happened to c

This is exactly the mechanism the defensive-copy trick from §6.2.4 relies on: wrap an object in Object.create(), hand the wrapper to code you don't trust, and any writes it performs create own properties on the disposable wrapper — the original object underneath is structurally incapable of being changed by that write.

The one exception: inherited accessor properties

If the property found up the chain is an accessor property with a setter function (see §6.10.6), assignment does not create a shadowing own property. Instead it calls the inherited setter — but it calls that setter as a method of the object you assigned to, so if the setter itself does this.something = ..., that write lands on the original object, not on the prototype where the setter is defined: 

let base = {
  _n: 0,
  get n() { return this._n; },
  set n(v) { this._n = v; },   // Setter writes to this._n
};
let derived = Object.create(base);
derived.n = 99;         // Calls base's setter, but with "this" bound to derived
derived.hasOwnProperty("_n")  // => true: the setter created _n on DERIVED
base._n                       // => 0: base's own _n is untouched

6.3.3 Property access errors

Reading a property that doesn't exist — as an own property or an inherited one — is never an error. It just evaluates to undefined: 

book.subtitle          // => undefined: no such property, no error

What is an error is trying to read a property of undefined or null — those two values have no properties whatsoever, so chaining a second access onto a possibly-missing result throws: 

book.subtitle.length   // TypeError: Cannot read properties of undefined (reading 'length')

The classic guard is a chain of && checks, which works because of short-circuit evaluation; the modern, concise equivalent is optional chaining, covered fully in Expressions & Operators: 

let surname = book && book.author && book.author.surname;  // Old-school guard
let surname2 = book?.author?.surname;                        // Modern equivalent

Writing has its own error modes. Assigning to a property of null or undefined always throws a TypeError. Beyond that, a write can silently fail (or, in strict mode, throw) for any of these reasons:

  • o has an own property p that is non-writable.
  • o inherits a property p that is non-writable — you cannot shadow a read-only inherited property with your own value.
  • o has no own or inherited-with-setter property p, and o itself is non-extensible (see the property attributes deep dive below) — there's simply nowhere to put a new property.
Strict mode makes failures loud

Outside strict mode, a failed write is usually silent — your program just keeps running as if nothing happened, which can hide bugs for a long time. In strict mode (the default inside ES modules and classes; see Statements), the same failure throws a TypeError immediately.

6.4 Deleting properties

The delete operator removes a property from an object entirely — name, value, and attributes all gone, as opposed to just setting the value to undefined. It only ever operates on own properties; delete-ing a name that's only inherited does nothing (and still "succeeds"). 

let o = { x: 1 };       // o has own property x, inherits toString
delete o.x               // => true: property x is gone
delete o.x               // => true: no-op (x already gone), but still true
delete o.toString        // => true: no-op (toString isn't an own property)
delete 1                 // => true: meaningless on a non-property-access, but true

A delete expression evaluates to true if the property is gone afterward (whether it actually removed something or there was nothing to remove) and false if the property still exists — which happens when the property's configurable attribute is false. Most built-in properties, and properties created at the top level with var or a function declaration, are non-configurable: 

delete Object.prototype       // => false: non-configurable, can't be removed

var g = 1;                     // A var declaration creates a non-configurable global property
delete globalThis.g            // => false

globalThis.h = 1;              // A plain assignment IS configurable
delete globalThis.h            // => true
Strict mode changes the failure mode, not just the syntax

In strict mode, attempting to delete a non-configurable property throws a TypeError instead of quietly returning false. Strict mode also outright forbids delete on a bare identifier (delete x) — that's a SyntaxError at parse time, not a runtime failure. You must delete through an explicit property access: delete globalThis.x.

6.5 Testing properties

Four different techniques answer "does this object have a property named X," and they don't all mean the same thing — the differences are almost entirely about own vs. inherited and about enumerability.

TechniqueMatches inherited?Requires enumerable?
"x" in oYesNo
o.hasOwnProperty("x")NoNo
o.propertyIsEnumerable("x")NoYes
o.x !== undefinedYesNo (but can't tell "missing" from "present but undefined")
let o = { x: 1 };
"x" in o                        // => true: own property
"y" in o                        // => false
"toString" in o                 // => true: inherited, but "in" still finds it

o.hasOwnProperty("x")           // => true
o.hasOwnProperty("toString")    // => false: inherited, not own

o.propertyIsEnumerable("x")             // => true: own AND enumerable
Object.prototype.propertyIsEnumerable("toString")  // => false: not enumerable

Simply reading the property and comparing against undefined is often good enough and reads naturally, but it has a genuine blind spot: it can't tell the difference between "no such property" and "the property exists and its value happens to be undefined." The in operator can: 

let obj = { x: undefined };   // Property explicitly set to undefined
obj.x !== undefined            // => false — looks exactly like a missing property
"x" in obj                     // => true  — but "in" reveals the property really is there
"y" in obj                     // => false — this one genuinely doesn't exist

delete obj.x;
"x" in obj                     // => false: now it's really gone

6.6 Enumerating properties

Sometimes you don't want to test for one property — you want every property. for/in (introduced in Statements) is the original tool: it loops once per enumerable property, own or inherited, assigning each property name to the loop variable in turn. Built-in methods are marked non-enumerable specifically so that routine code you write doesn't trip over them: 

let o = { x: 1, y: 2, z: 3 };       // Three enumerable own properties
o.propertyIsEnumerable("toString")   // => false

for (let key in o) {
  console.log(key);                 // Logs "x", "y", "z" — never "toString"
}

Because for/in also walks inherited enumerable properties, code that shares a prototype often needs to filter: 

for (let key in o) {
  if (!o.hasOwnProperty(key)) continue;      // Skip anything inherited
  if (typeof o[key] === "function") continue; // Skip methods too, if you like
}

Modern code usually prefers building an array of names or entries and looping over that with for/of — see why for/of is usually the right default. Four functions produce that array, differing in whether they include non-enumerable properties, inherited properties, and Symbol-named properties:

FunctionOwn only?Includes non-enumerable?Includes Symbol keys?
Object.keys(o)YesNoNo
Object.values(o)YesNoNo — returns values, not names
Object.entries(o)YesNoNo — returns [key, value] pairs
Object.getOwnPropertyNames(o)YesYesNo
Object.getOwnPropertySymbols(o)YesYesOnly Symbols
Reflect.ownKeys(o)YesYesYes — everything
let o = { x: 1, y: 2, z: 3 };
for (let [key, value] of Object.entries(o)) {
  console.log(`${key} = ${value}`);
}
// Object.keys() covers the overwhelming majority of real use cases

6.6.1 Property enumeration order

ES6 nailed down a precise order for the enumeration functions above (Object.keys(), Object.getOwnPropertyNames(), Object.getOwnPropertySymbols(), Reflect.ownKeys(), and anything built on them, including JSON.stringify()):

  1. String keys that look like non-negative integer array indices come first, sorted numerically (smallest to largest) — this is why arrays and array-like objects enumerate "in order."
  2. Every other string key comes next, in insertion order — the order the properties were first added to the object (for an object literal, that's the order they appear in the literal).
  3. Symbol keys come last, also in insertion order.
let mixed = { b: 1, 2: "two", a: 2, 1: "one" };
Object.keys(mixed)   // => ["1", "2", "b", "a"] — integer keys first & sorted, then insertion order

for/in's order is not as strictly specified, but in practice implementations enumerate an object's own properties in the order above, then move up the prototype chain and do the same for each prototype object in turn — skipping any name that's already been seen (even if the earlier sighting was non-enumerable).

6.7 Extending objects

Copying every property of one object into another is common enough — merging user-supplied options over a defaults object is the classic case — that the language provides Object.assign() specifically for it, on top of the equivalent spread syntax covered in §6.10. 

// Object.assign(target, ...sources) MUTATES and returns target;
// sources are applied left-to-right, so later sources win on conflicts:
Object.assign({ x: 1 }, { x: 2, y: 2 }, { y: 3, z: 4 })  // => { x: 2, y: 3, z: 4 }

// The spread operator expresses the same idea without mutating anything,
// and is generally the preferred modern style:
let merged = { ...defaults, ...overrides };  // overrides wins on any conflict

// Both copy only OWN, ENUMERABLE properties — inherited ones are left behind:
let base = Object.create({ x: 1 });
let copy1 = Object.assign({}, base);
let copy2 = { ...base };
copy1.x   // => undefined
copy2.x   // => undefined

A common mistake is trying to use Object.assign() to fill in missing defaults on an existing object — but Object.assign(o, defaults) does the opposite of what you want, since defaults is the source and unconditionally overwrites whatever o already had. The fix is to build a new object with defaults applied first, then let o override them: 

o = Object.assign({}, defaults, o);   // Correct order: o's own values win
o = { ...defaults, ...o };             // Equivalent, spread form

// A hand-rolled "only fill in what's missing" merge, for when neither reads right:
function merge(target, ...sources) {
  for (let source of sources) {
    for (let key of Object.keys(source)) {
      if (!(key in target)) target[key] = source[key];
    }
  }
  return target;
}
merge({ x: 1 }, { x: 2, y: 2 }, { y: 3, z: 4 })   // => { x: 1, y: 2, z: 4 }
Getters and setters fire during a copy

Object.assign() (and spread) perform ordinary property get and set operations under the hood. If a source object has a getter, it's invoked to produce the value being copied; if the target has a setter for that name, it's invoked to receive it. Neither the getter nor the setter function itself gets copied — only whatever value passes through them.

Spread/assign inside a loop is an O(n²) trap

Copying n properties is O(n) work. Doing acc = { ...acc, [key]: value } once per iteration of an n-iteration loop is therefore O(n²) overall — it silently degrades as data grows. Accumulate into a single mutable object (acc[key] = value) or a Map instead, and only spread/assign at the end if you need an immutable result.

6.8 Serializing objects

JSON.stringify() turns a JavaScript value into a JSON text string; JSON.parse() reverses the process. Together they're the standard way to serialize an object's state so it can be saved or transmitted and later reconstructed as a structurally equivalent (but distinct) object: 

let o = { x: 1, y: { z: [false, null, ""] } };
let s = JSON.stringify(o);   // '{"x":1,"y":{"z":[false,null,""]}}'
let p = JSON.parse(s);        // A new, independent object, deep-equal to o

JSON's data model is a subset of JavaScript's, so serialization is lossy at the edges: undefined, functions, and Symbol values are dropped from objects entirely (or become null when they appear inside an array); NaN and ±Infinity serialize to null; and only own, enumerable properties are ever considered. This chapter only needs the basics — the full picture, including the optional replacer/reviver arguments and the toJSON() hook, is covered in Dates, JSON, Intl & Utilities.

6.9 Object methods

Every object (except one deliberately created with no prototype — §6.2.4) inherits a handful of general methods from Object.prototype. They're not very useful in their default form, but overriding them on your own objects is how you hook into JavaScript's implicit conversions.

MethodInvoked when...
toString()The object needs to become a string: + with a string, template literals, String(x)
toLocaleString()A locale-aware string is wanted; by default just calls toString()
valueOf()The object needs to become a number or be compared with </>/arithmetic
toJSON()JSON.stringify() is about to serialize the object — return the replacement value instead
[Symbol.toPrimitive]()Any coercion to a primitive — lets one method override both toString and valueOf based on the requested "hint"

The default toString() is famously unhelpful — it produces the string "[object Object]" — which is why so many built-ins, and so much of your own code, defines a better one: 

let generic = { x: 1, y: 1 };
generic.toString()   // => "[object Object]" — the unhelpful default

let point = {
  x: 1, y: 2,
  toString() { return `(${this.x}, ${this.y})`; },
};
String(point)          // => "(1, 2)": toString() drives string conversion
`Point is ${point}`    // => "Point is (1, 2)"

toLocaleString() exists so classes can format their toString() output according to locale conventions — Date and Number both override it for this reason, and Array's version calls toLocaleString() (not toString()) on each element: 

let big = {
  x: 1000, y: 2000,
  toString() { return `(${this.x}, ${this.y})`; },
  toLocaleString() {
    return `(${this.x.toLocaleString()}, ${this.y.toLocaleString()})`;
  },
};
big.toString()        // => "(1000, 2000)"
big.toLocaleString()  // => "(1,000, 2,000)" — thousands separators, locale-dependent

valueOf() is toString()'s counterpart for numeric contexts. Date defines it to return a timestamp, which is why two Date objects can be compared with </> directly: 

let vec = {
  x: 3, y: 4,
  valueOf() { return Math.hypot(this.x, this.y); },
};
Number(vec)   // => 5: valueOf() drives numeric conversion
vec > 4        // => true
vec > 5        // => false
vec < 6        // => true

toJSON() isn't actually defined on Object.prototype — but JSON.stringify() specifically looks for one on any object it's asked to serialize, and if it finds one, serializes that method's return value instead of the object itself. Date defines a toJSON() that returns an ISO date string, which is why dates survive a JSON round trip as readable strings rather than {}: 

let point = {
  x: 1, y: 2,
  toString() { return `(${this.x}, ${this.y})`; },
  toJSON() { return this.toString(); },
};
JSON.stringify([point])   // => '["(1, 2)"]'

ES2015 Symbol.toPrimitive is the most general of the bunch: a single method that JavaScript calls for any primitive conversion, passed a "string", "number", or "default" hint so you can tailor the result instead of maintaining separate toString()/valueOf() methods that might disagree with each other: 

let temperature = {
  celsius: 100,
  [Symbol.toPrimitive](hint) {
    if (hint === "number") return this.celsius;
    if (hint === "string") return `${this.celsius}°C`;
    return `Temperature: ${this.celsius}°C`;  // "default" hint, e.g. + or ==
  },
};
Number(temperature)     // => 100
`${temperature}`         // => "100°C"
temperature + ""         // => "Temperature: 100°C"

6.10 Extended object literal syntax

Every ES6-and-later release has added convenience syntax to object literals. None of it changes what objects fundamentally are — it just removes repetition that older code was full of.

6.10.1 Shorthand properties ES2015

When a property's name matches the name of a variable already holding its value, you can drop the colon and the repeated identifier: 

let x = 1, y = 2;
let old = { x: x, y: y };   // Pre-ES6: name repeated
let modern = { x, y };       // Shorthand: identical result
modern.x + modern.y           // => 3

6.10.2 Computed property names ES2015

When the property name you need isn't a compile-time constant — it's stored in a variable, or the result of calling a function — square brackets inside the literal let you compute it inline instead of assigning it as a separate statement afterward: 

const PROPERTY_NAME = "p1";
function computeName() { return "p" + 2; }

// Before computed properties, this took two steps:
let stepwise = {};
stepwise[PROPERTY_NAME] = 1;
stepwise[computeName()] = 2;

// With computed properties, it's inline:
let inline = {
  [PROPERTY_NAME]: 1,
  [computeName()]: 2,
};
inline.p1 + inline.p2   // => 3

The expression inside the brackets is evaluated and coerced to a string (or left as-is if it's already a Symbol) to become the property name — this is what makes Symbol-named properties possible in a literal at all.

6.10.3 Symbols as property names

Property names are usually strings, but a Symbol works too, via the same computed-property bracket syntax. Every Symbol() call produces a value that is guaranteed unequal to every other value, including other Symbols created with the exact same descriptive string — that string is purely a debugging label, never a basis for equality: 

const extension = Symbol("my extension");
let o = {
  [extension]: { note: "extra data, safely out of the way" },
};
o[extension].note   // => "extra data, safely out of the way"

The point of Symbol-keyed properties isn't security — code that really wants to find them can, via Object.getOwnPropertySymbols() — it's guaranteeing no accidental collision when you need to attach a property to an object whose other property names you don't fully control (third-party objects, or objects from a library you don't own). It's also how JavaScript itself extends built-in objects with special behavior without squatting on an ordinary string name — an object becomes iterable, for instance, by defining a method named Symbol.iterator, covered in Iterators & Generators.

6.10.4 The spread operator in object literals ES2018

Three dots inside an object literal "spread" another object's own, enumerable properties directly into the new object, as if they'd been typed there by hand. (Despite the name, this isn't a general-purpose JavaScript operator — it's special-case syntax that only means something inside an object or array literal.) 

let position = { x: 0, y: 0 };
let dimensions = { width: 100, height: 75 };
let rect = { ...position, ...dimensions };
rect.x + rect.y + rect.width + rect.height   // => 175

// Later properties always win on a name conflict, spread or literal:
let p1 = { x: 0, ...{ x: 1 } };
p1.x   // => 1
let p2 = { ...{ x: 1 }, x: 2 };
p2.x   // => 2

// Only OWN properties are spread — inherited ones are left behind:
let base = Object.create({ x: 1 });
let copy = { ...base };
copy.x   // => undefined

Spreading n properties is O(n) work — see the accumulation warning in §6.7 for why that matters inside a loop.

__proto__ inside an object literal

As a special case recognized only by literal syntax (never by ordinary property access), writing __proto__: value directly inside an object literal sets the new object's prototype to value, instead of creating an own property literally named "__proto__": 

let proto = { greet() { return "hi"; } };
let obj = {
  __proto__: proto,   // Sets obj's PROTOTYPE — not a property named "__proto__"
  own: 1,
};
Object.getPrototypeOf(obj) === proto   // => true
obj.greet()                              // => "hi": inherited from proto
obj.hasOwnProperty("__proto__")          // => false: it was never a real property
Legacy outside a literal, but fine inside one

Outside of an object literal, obj.__proto__ is a legacy getter/setter accessor for the prototype — it works in every engine but is considered legacy in favor of Object.getPrototypeOf() / Object.setPrototypeOf(). The __proto__: value literal form above is different: it's standardized purely as object-literal syntax and remains the most concise way to create an object with both a custom prototype and a batch of own properties in a single expression — Object.create() can't set own data properties as conveniently.

6.10.5 Shorthand methods ES2015

A property whose value is a function is called a method (much more on methods and this in Functions). Pre-ES6, defining one meant writing out function and a colon like any other property; the shorthand form omits both: 

let oldStyle = {
  side: 10,
  area: function () { return this.side * this.side; },
};

let shorthand = {
  side: 10,
  area() { return this.side * this.side; },   // Identical behavior, less noise
};
shorthand.area()   // => 100

Shorthand method names can be anything a property name can be — plain identifiers, quoted strings, or computed names (including Symbols): 

const METHOD_NAME = "m";
const sym = Symbol();
let weird = {
  "method with spaces"(x) { return x + 1; },
  [METHOD_NAME](x) { return x + 2; },
  [sym](x) { return x + 3; },
};
weird["method with spaces"](1)   // => 2
weird[METHOD_NAME](1)             // => 3
weird[sym](1)                     // => 4

6.10.6 Property getters and setters ES5

An accessor property has no stored value of its own — instead it has a getter function, a setter function, or both, which run whenever the property is read or written. A getter-only property is effectively read-only; a setter-only property is write-only (reading it always yields undefined) — a combination that's impossible with an ordinary data property. 

let o = {
  dataProp: 1,
  get accessorProp() { return this.dataProp; },
  set accessorProp(v) { this.dataProp = v; },
};

A more useful example: represent a point with ordinary x/y data properties, and expose its polar coordinates as computed accessor properties layered on top: 

let p = {
  x: 1.0, y: 1.0,
  get r() { return Math.hypot(this.x, this.y); },
  set r(newValue) {
    let ratio = newValue / this.r;
    this.x *= ratio;
    this.y *= ratio;
  },
  get theta() { return Math.atan2(this.y, this.x); },   // read-only: getter only
};
p.r        // => Math.SQRT2
p.theta    // => Math.PI / 4
p.r = 1;   // Rescales x and y down to unit length via the setter

Because this inside a getter/setter refers to whatever object the property was accessed on, accessor properties are inherited exactly like data properties — a prototype can define r and theta once, and every object that inherits from it gets live, computed versions for free: 

let q = Object.create(p);   // Inherits the r/theta accessors
q.x = 3; q.y = 4;             // q's own data properties
q.r        // => 5: the inherited getter computes it from q's own x and y
q.theta    // => Math.atan2(4, 3)

Accessors are also how you validate writes or return a different value on every read: 

const serialNumber = {
  _n: 0,
  get next() { return this._n++; },       // Different value each read
  set next(n) {
    if (n <= this._n) throw new Error("serial number must increase");
    this._n = n;
  },
};
serialNumber.next = 10;
serialNumber.next   // => 10
serialNumber.next   // => 11

Property attributes, in depth Deep dive

Section 6.1 introduced writable, enumerable, and configurable as flags that ride along with every property. Ordinary object-literal and assignment syntax always gives you all three set to true — there's no literal syntax for creating a non-writable or non-enumerable property. To get finer control, you need Object.defineProperty(), which takes the target object, a property name, and a descriptor object spelling out exactly which attributes you want: 

let o = {};
Object.defineProperty(o, "x", {
  value: 1,
  writable: true,
  enumerable: false,     // Hide it from for/in, Object.keys(), JSON.stringify()
  configurable: true,
});

o.x                          // => 1: reading works completely normally
Object.keys(o)                // => []: x is invisible to enumeration
JSON.stringify(o)             // => "{}": also invisible here
"x" in o                      // => true: "in" still finds it
o.hasOwnProperty("x")         // => true

Any attribute you omit from the descriptor defaults to false (or undefined for value) — Object.defineProperty() is conservative by default, unlike an object literal which is permissive by default. This is exactly how a getter/setter pair from §6.10.6 is really represented under the hood: instead of a value/writable pair, an accessor descriptor has get/set functions: 

let account = {};
Object.defineProperty(account, "balanceInCents", {
  value: 0, writable: true, enumerable: false, configurable: true,
});
Object.defineProperty(account, "balance", {
  get() { return account.balanceInCents / 100; },
  set(dollars) { account.balanceInCents = Math.round(dollars * 100); },
  enumerable: true,
  configurable: true,
});
account.balance = 19.99;
account.balance          // => 19.99
account.balanceInCents   // => 1999

Making a property non-writable is a much more targeted lockdown than deep-freezing an entire object — attempting to write to it fails exactly the way an inherited read-only property does (silently, or loudly in strict mode — see §6.3.3): 

"use strict";
const config = {};
Object.defineProperty(config, "VERSION", {
  value: "1.0.0", writable: false, enumerable: true, configurable: false,
});
config.VERSION = "2.0.0";   // TypeError in strict mode: VERSION is not writable
delete config.VERSION;       // TypeError in strict mode: VERSION is not configurable

Object.seal() and Object.freeze() are shortcuts that apply attribute changes to every property on an object at once, plus flip the object's own extensibility: 

let sealed = Object.seal({ x: 1 });
sealed.x = 2;              // OK: existing writable properties can still change
sealed.y = 3;               // Silently ignored (or throws in strict mode): sealed is non-extensible
delete sealed.x;             // Silently ignored: every property became non-configurable
Object.isSealed(sealed)       // => true

let frozen = Object.freeze({ x: 1, nested: { y: 2 } });
frozen.x = 99;               // Silently ignored: frozen properties are non-writable too
frozen.x                     // => 1: unchanged
Object.isFrozen(frozen)       // => true
frozen.nested.y = 99;         // WORKS — freeze is shallow! nested objects are untouched
frozen.nested.y               // => 99
Object.freeze() is shallow

Freezing an object locks down only its own, top-level properties. Any object referenced by one of those properties is a completely separate object with its own attributes, untouched by the outer freeze. A "deep freeze" has to walk the object graph recursively and freeze every nested object individually — the language doesn't do this for you.

Reading back the attributes of an existing property — including ones you didn't define yourself — is the mirror-image operation, Object.getOwnPropertyDescriptor(): 

Object.getOwnPropertyDescriptor([], "length")
// => { value: 0, writable: true, enumerable: false, configurable: false }
// Array length is writable (you CAN resize an array by assigning it)
// but not enumerable and not configurable — you can't delete "length"

Even finer-grained control over property definition — and the related mechanics of Reflect and Proxy, which can intercept property access itself — is the subject of Metaprogramming.

6.11 Summary

This chapter covered JavaScript objects end to end:

  • Vocabulary: property, own vs. inherited property, and the writable/enumerable/configurable attribute trio every property carries.
  • Three ways to create an object — literal, new, Object.create() — and the prototype each one hands you, including Object.create(null) for a prototype-free dictionary.
  • The prototype chain, and the crucial asymmetry that reading walks it while writing (almost always) doesn't — which is how an own property comes to shadow an inherited one.
  • Reading, writing, deleting, testing, and enumerating properties, plus the specific errors and silent failures each operation can produce.
  • Copying properties between objects with Object.assign() and object-spread, and the O(n²) trap of doing either inside a loop.
  • The basics of JSON serialization, and the handful of methods — toString(), valueOf(), toJSON(), Symbol.toPrimitive — that let your objects participate in JavaScript's implicit conversions.
  • Modern object literal syntax: shorthand properties and methods, computed and Symbol-valued property names, spread, __proto__, and getter/setter accessor properties.
  • Fine-grained control over a property's own attributes with Object.defineProperty(), and the bulk lockdown operations Object.seal() and Object.freeze().

Every value that isn't a primitive is an object — including arrays and functions, which layer specialized behavior on top of everything covered here and get their own dedicated chapters next: Arrays and Functions.
