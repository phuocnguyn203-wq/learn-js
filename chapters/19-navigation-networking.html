Navigation & Networking

Two big client-side responsibilities that don't touch the DOM at all: controlling what URL the address bar shows and how the Back/Forward buttons behave, and talking to a server after the initial page has already loaded. This page covers the location and history objects in full — including the two competing techniques for building history-aware single-page apps — and then all three of the browser's networking APIs: fetch(), Server-Sent Events, and WebSockets.

The location object

Both window.location and document.location refer to the same Location object, which represents the URL of the document currently displayed in the window and doubles as the API for navigating to a new one. It shares most of its property names with the URL class you'd use to parse an arbitrary string URL, so if you already know URL, the shape here is familiar — but Location is not a URL instance, and the differences matter.

PropertyHoldsExample, for https://example.com:8080/items/3?sort=asc#reviews

search and hash deserve special attention because both are commonly repurposed by application code rather than left to their nominal meaning. search is intended for server-facing query parameters, but nothing stops client-side script from reading or writing it too. hash is nominally an in-page anchor, but as you'll see below, it has a long history as a DIY client-side routing mechanism precisely because changing it does not trigger a page load.

Unlike a URL object, Location has no searchParams property of its own. To get a parsed view of the query string, wrap the location in a real URL first: 

let url = new URL(window.location);
let query = url.searchParams.get("q");
let numResults = parseInt(url.searchParams.get("n") || "10");
document.URL is a plain string

Browsers also expose document.URL, which despite the name is not a URL object — it's just a string holding the current document's address, functionally equivalent to location.href. Don't call .searchParams on it; wrap it in new URL(...) first if you need to parse it.

Loading new documents

Assigning a string to location (or document.location) tells the browser to interpret it as a URL and navigate there, replacing the current document: 

window.location = "https://example.com";  // navigate away entirely
document.location = "page2.html";         // relative URL, resolved against the current page

A bare fragment identifier is a special case: assigning just a #-prefixed string does not load a new document. It scrolls the current page so the element whose id (or legacy name) matches the fragment is at the top of the viewport. The fragment #top is special-cased to always scroll to the very start of the document, even if no element has id="top": 

location = "#top";              // jump to the very top of the page
location.hash = "TOC";          // scroll to the element with id="TOC"

Every individual property of Location is independently writable, and setting any of them (other than hash) triggers a fresh document load built from the modified URL: 

location.pathname = "pages/3.html";        // load a new path
location.search = "?page=" + (page + 1);   // reload with a different query string
location.hash = "TOC";                     // scroll within the current document only

assign(), replace(), and reload()

location.assign(url) is exactly equivalent to assigning the string directly to location — it exists mostly for symmetry with replace(). location.replace(url) is the one worth knowing well: it navigates just like assign(), but it overwrites the current entry in the browser's history instead of adding a new one after it.

The difference shows up the moment the user presses Back. Say a script on document A calls location.assign("B.html"). The history list now reads [..., A, B], and clicking Back from B returns the user to A — where, if that script runs unconditionally on load, it would immediately navigate to B again, trapping the user in a redirect loop they can never back out of. location.replace("B.html") avoids this: it rewrites A's entry into B, leaving history as [..., B], so Back skips A entirely and returns to whatever was displayed before it. 

// A capability-detection redirect: use replace(), not assign()/href,
// so Back doesn't bounce the user right back into the redirect.
if (!isBrowserSupported()) {
  location.replace("staticpage.html");
}
Rule of thumb

Any time a script navigates unconditionally — a redirect, a "you must be logged in" bounce, a capability fallback — prefer replace(). Reserve assign()/plain href assignment for navigations the user consciously triggered, like clicking a link-like element, where they'd reasonably expect Back to return them to where they were.

Finally, location.reload() reloads the current document from scratch, equivalent to the user pressing the browser's reload button.

The history object

window.history models the window's browsing history as a list of documents and document states. Its length property reports how many entries are in the list, but for privacy reasons script can never read the actual stored URLs — if it could, any page could snoop through everywhere you'd previously been. 

history.back();     // like clicking the Back button
history.forward();  // like clicking the Forward button
history.go(-2);      // back two entries at once
history.go(0);        // go(0) reloads the current page
Iframes interleave their history with the parent

If a page contains child windows such as <iframe> elements, their navigation histories are chronologically merged with the top-level window's. Calling history.back() on the main window can therefore cause a child frame to step back to a previous document while the main window's own content stays exactly where it was.

back(), forward(), and go() are relics of an older web, where every "page" was a genuinely distinct document fetched from the server. Modern single-page apps generate and swap content dynamically without a real navigation ever happening, which means the browser has no idea a "new page" occurred — so Back and Forward would do nothing useful unless the app does its own history bookkeeping. There are two established techniques for that, covered next.

Older technique: location.hash + hashchange

The first technique predates any dedicated history API and just repurposes the URL fragment. Three facts make it work:

  • Setting location.hash does not have to name a real element ID — it can be any string you like, and as long as no element happens to share that ID, the browser won't scroll.
  • Setting it updates the address bar and pushes a new entry onto the browsing history, all without a page reload.
  • Any time the fragment changes — whether your script set it, or the user pressed Back/Forward and the browser changed it for you — the window fires a hashchange event.

Building a router on this means writing two small conversion functions — one that encodes your app's current state into a short string suitable for a fragment, and one that parses that string back into state — plus one rule of discipline: never render a new state directly. Instead, encode it and assign it to location.hash; let your hashchange handler do the actual rendering, whether the change came from a user interaction or a Back/Forward press: 

function encodeState(state) {
  return `view=${state.view}&id=${state.id}`;
}
function decodeState(hash) {
  let params = new URLSearchParams(hash.replace(/^#/, ""));
  return { view: params.get("view"), id: params.get("id") };
}

window.addEventListener("hashchange", () => {
  render(decodeState(location.hash));
});

function navigateTo(state) {
  // Don't render() here directly -- setting the hash below will
  // trigger the hashchange listener, which renders.
  location.hash = encodeState(state);
}

This still works everywhere and needs nothing from the server, which is why it lingers in older codebases, but it's largely been superseded by pushState() because it forces application state into the ugly #... tail of every URL and offers no way to change the path or query string cleanly.

Modern technique: history.pushState() hard

The History API lets an app push an arbitrary state object onto the browsing history, associate it with a real URL (not just a fragment), and be notified via a popstate event when the user navigates back to it. This is the mechanism behind virtually every modern single-page-app router. 

history.pushState(stateObject, unused, url);
  • stateObject — anything you want restored later; serialized with the structured clone algorithm, not JSON.
  • unused — a title string the spec defines but essentially no browser honors. Always pass "".
  • url — optional, resolved relative to the current document, and shown in the address bar immediately. This is what makes the resulting state bookmarkable and shareable.

The structured clone algorithm

pushState() does not run your state object through JSON.stringify(). It uses the HTML-standard structured clone algorithm, which is a strict superset of what JSON can represent.

Can it survive a structured clone?Notes
Plain objects, arrays, strings, numbers, booleans, nullYes — same as JSON
Map, Set, Date, RegExpYes — JSON cannot do any of these
Typed arrays, ArrayBufferYes
Circular references (an object that refers back to itself)Yes — JSON.stringify throws on these
Functions, class methodsNo — silently dropped / throws
DOM nodes / Element objectsNo — host-defined types aren't cloneable
Prototype chain, getters/setters, non-enumerable propertiesNot preserved — an instance of your own class comes back as a plain object
Your class instance loses its prototype

If you pass an instance of a custom class to pushState(), what comes back through event.state later is a plain object with the same own properties — not an instance of your class, and none of its methods are callable on it. Always re-wrap restored state through a factory function, as shown below.

Walking through pushState() and popstate

The sequence of events is the part people get wrong, so trace it carefully:

  1. The user is on state A. Your app calls history.pushState(stateA, "", urlA). The address bar updates to urlA, and a new entry is appended to history. No event fires from this call — pushState() is a synchronous, silent bookkeeping operation. You must render state A yourself, right after the call.
  2. The user interacts further; your app calls pushState(stateB, "", urlB). History is now [..., A, B], address bar shows urlB. Again, you render B yourself — still no event.
  3. The user clicks the browser's Back button. The browser moves the current position from B back to A and fires a popstate event on window, whose event.state is a structured-clone copy of whatever you passed as stateA. Your popstate handler is responsible for reading event.state and re-rendering the page to match — the browser only changed the URL and fired the event; it did not touch the DOM.
  4. The user clicks Forward. Another popstate fires, this time with a clone of stateB.
popstate never fires from your own pushState() call

This is the single most common bug when people first use this API: they call pushState() and expect their own popstate listener to fire so it can render the new state. It never does. popstate only fires in response to the user (or script calling history.back() / forward() / go()) moving through history that already exists. Every call to pushState() must be paired with you manually rendering the state you just pushed — typically by extracting that render logic into a shared function called both right after pushState() and inside the popstate handler.

A second subtlety: if the user bookmarks a pushState()-produced URL and returns to it in a fresh tab tomorrow, there is no history entry to pop and thus no popstate event for that visit either — you must reconstruct state by parsing the URL itself on load. That's why it's common to call history.replaceState() for the very first, initial state, so a later "back past the beginning" scenario still has something in event.state to render, and to write a "restore from URL" path for the fresh-load case.

Worked example 1 — a paginated list.

function renderPage(state) {
  document.querySelector("#list").textContent = `Showing page ${state.page}`;
}

function goToPage(page) {
  let state = { page };
  history.pushState(state, "", `?page=${page}`);
  renderPage(state);          // <-- pushState() itself fires nothing; render manually
}

// Initial load: give this starting state a history entry too.
let initialState = { page: Number(new URL(location).searchParams.get("page")) || 1 };
history.replaceState(initialState, "", location.href);
renderPage(initialState);

document.querySelectorAll(".page-link").forEach(link => {
  link.addEventListener("click", (event) => {
    event.preventDefault();
    goToPage(Number(link.dataset.page));
  });
});

// Back/Forward: the browser handles the URL, we handle the DOM.
window.addEventListener("popstate", (event) => {
  renderPage(event.state);
});

Worked example 2 — a number-guessing game. This example (adapted from the book's own case study) shows the pattern with richer, class-shaped state, plus URL-based restoration for the bookmarked case: 

class GameState {
  static newGame() {
    let s = new GameState();
    s.low = 0; s.high = 100; s.numGuesses = 0; s.guess = null;
    s.secret = s.low + Math.ceil(Math.random() * (s.high - s.low - 1));
    return s;
  }
  // Rebuild a real GameState from the plain object popstate hands us --
  // structured clone strips the class, so the prototype must be restored.
  static fromStateObject(obj) {
    let s = new GameState();
    Object.assign(s, obj);
    return s;
  }
  toURL() {
    let url = new URL(window.location);
    url.searchParams.set("l", this.low);
    url.searchParams.set("h", this.high);
    url.searchParams.set("n", this.numGuesses);
    return url.href;
  }
  updateForGuess(guess) {
    if (guess < this.secret) this.low = guess;
    else if (guess > this.secret) this.high = guess;
    this.guess = guess;
    this.numGuesses++;
  }
  render() {
    document.querySelector("#heading").textContent =
      `Guess between ${this.low} and ${this.high} (${this.numGuesses} so far)`;
  }
}

// On load: reuse a previously-pushed state if popstate gives us one to work
// with later, but on initial page load there IS no popstate event, so we
// just start (or resume from the URL) and replaceState() to seed history.
let game = GameState.newGame();
history.replaceState(game, "", game.toURL());
game.render();

document.querySelector("#guessInput").addEventListener("change", (event) => {
  game.updateForGuess(Number(event.target.value));
  history.pushState(game, "", game.toURL());   // no event fires from this call
  game.render();                                // so we render right here
});

window.addEventListener("popstate", (event) => {
  game = GameState.fromStateObject(event.state); // clone comes back as plain object
  game.render();
});

history.replaceState() takes the exact same three arguments as pushState() but overwrites the current history entry instead of adding a new one after it — the history-object counterpart of location.replace().

Networking: three APIs, three shapes

Every page load already triggers network requests for the HTML itself plus its images, scripts, and stylesheets, but browsers also expose networking directly to JavaScript for use after the page has loaded. There are three APIs, each shaped for a different traffic pattern:

  • fetch() — a Promise-based request/response API, the modern replacement for the old XMLHttpRequest object. Good for one-shot HTTP calls.
  • Server-Sent Events (EventSource) — an event-based wrapper around a long-held HTTP connection that the server writes to whenever it has something new. One-way, server to client only.
  • WebSockets — a genuinely separate protocol (layered on top of an HTTP handshake) for full-duplex, low-overhead message passing in both directions over one persistent connection.
XMLHttpRequest is not covered here

You will still encounter XMLHttpRequest ("XHR") in older code, despite the name having nothing to do with XML in practice. There's no reason to reach for it in new code — fetch() supersedes it entirely and is covered in full below.

fetch() is deliberately simple for the common case: 

fetch("/api/users/current")             // 1. make the GET request
  .then(response => response.json())    // 2. ask for the body, parsed as JSON
  .then(currentUser => {                // 3. do something with the result
    displayUserInfo(currentUser);
  });

// Equivalently, with async/await:
async function isServiceReady() {
  let response = await fetch("/api/service/status");
  let body = await response.text();
  return body === "ready";
}

Notice there are always two asynchronous hops: fetch()'s own Promise resolves once the response's status and headers have arrived, and then the Response's body-reading method (.json(), .text(), etc.) returns a second Promise that resolves once the body itself has fully arrived and been parsed. If those two examples make sense, you already understand the majority of how fetch() is used day to day; the rest of this section fills in the configuration options and edge cases.

fetch()'s error-handling model hard

This is the single most consequential thing to internalize about fetch(), because getting it wrong means your app silently treats "the server rejected this request" as success.

The Promise only rejects on NETWORK failure

fetch()'s returned Promise rejects only if the request could not be completed at the transport level at all — the user is offline, the hostname doesn't resolve, the connection was refused or reset. If the server is reachable and sends back any HTTP response — including a 404 Not Found or a 500 Internal Server Error — that still counts as a successfully fulfilled Promise. As far as fetch() is concerned, the server responded; it just responded with bad news, and it's on you to notice.

The naive, wrong pattern — relying on .catch() alone:

// WRONG: this silently treats a 404/500 as success, because the
// Promise fulfills either way -- .catch() only fires for network failure.
fetch("/api/users/current")
  .then(response => response.json())
  .then(currentUser => displayUserInfo(currentUser))
  .catch(error => console.log("Something went wrong:", error));
// A 500 response body of "Internal Server Error" gets JSON.parse'd
// (and probably throws inside response.json(), masking the real problem),
// or worse, a valid-but-wrong JSON error payload sails right through
// to displayUserInfo() as if it were a real user object.

The correct pattern — explicitly check response.ok:

fetch("/api/users/current")
  .then(response => {
    // response.ok is true for any status in the 200-299 range.
    if (response.ok &&
        response.headers.get("Content-Type") === "application/json") {
      return response.json();          // Promise for the parsed body
    } else {
      throw new Error(`Unexpected response ${response.status} ${response.statusText}`);
    }
  })
  .then(currentUser => displayUserInfo(currentUser))
  .catch(error => {
    // Now this .catch() legitimately covers BOTH cases:
    // network failure (fetch() itself rejected) and a bad HTTP
    // status (we threw it ourselves, above).
    console.log("Error while fetching current user:", error);
  });

// The async/await equivalent -- same principle, still an explicit check:
async function getCurrentUser() {
  let response = await fetch("/api/users/current");
  if (!response.ok) {
    throw new Error(`HTTP ${response.status}: ${response.statusText}`);
  }
  return response.json();
}

response.status is the numeric HTTP status code (e.g. 200, 404); response.statusText is the standard English phrase that goes with it (e.g. "Not Found"); response.ok is simply shorthand for "status is in [200, 300)". The headers property is a Headers object with case-insensitive has(name) and get(name) methods, and it's iterable: 

fetch(url).then(response => {
  for (let [name, value] of response.headers) {
    console.log(`${name}: ${value}`);
  }
});
Always pair a .catch() with your .ok check

Because network failure is always a possibility on any request, every fetch() call benefits from a .catch() (or a surrounding try/catch with await) in addition to — never instead of — an explicit response.ok check.

Configuring a request

A plain fetch(url) issues a GET request with no special headers or body. Everything else is configured through an optional second "options" argument, or by constructing an equivalent Request object yourself and passing that instead: 

// Two equivalent forms:
fetch(url, { headers, method, body });

let request = new Request(url, { headers, method, body });
fetch(request).then(response => /* ... */ null);

Query parameters

Build query strings with URL/URLSearchParams rather than hand-concatenating — it takes care of escaping for you, and fetch() happily accepts a URL object as its first argument: 

async function search(term) {
  let url = new URL("/api/search", location.origin);
  url.searchParams.set("q", term);
  let response = await fetch(url);
  if (!response.ok) throw new Error(response.statusText);
  return response.json();
}

Request headers

let authHeaders = new Headers();
// Never send Basic auth credentials over a plain http:// connection.
authHeaders.set("Authorization", `Basic ${btoa(`${username}:${password}`)}`);

fetch("/api/users/", { headers: authHeaders })
  .then(response => {
    if (!response.ok) throw new Error(response.statusText);
    return response.json();
  })
  .then(usersList => displayAllUsers(usersList));

Method and body

Use the method option for anything other than GET. As long as method isn't "GET" or "HEAD" (which can't carry a body), set body to send data along with the request: 

fetch(url, { method: "POST", body: "hello world" });
// A plain string body defaults Content-Type to text/plain;charset=UTF-8 --
// override it explicitly for anything more specific:
fetch(url, {
  method: "POST",
  headers: new Headers({ "Content-Type": "application/json" }),
  body: JSON.stringify(requestBody),
});

body isn't limited to strings. A typed array, DataView, ArrayBuffer, or Blob all work directly (a Blob's own type becomes the default Content-Type). For classic name/value form parameters, you have a choice between two encodings:

Body valueResulting encodingBest for
URLSearchParamsapplication/x-www-form-urlencoded (a query-string-shaped body)Short, simple key/value pairs
FormDatamultipart/form-data; boundary=...Long values, or File/Blob values with their own content types

The browser sets Content-Length and Content-Type for you in both cases — don't set them by hand.

Uploading files

A <input type="file"> element's change event exposes chosen files through its files array; File objects are themselves a kind of Blob, so uploading generated binary data (say, from a <canvas>) works the same way: 

// canvas.toBlob() is callback-based -- wrap it in a Promise.
function getCanvasBlob(canvas) {
  return new Promise(resolve => canvas.toBlob(resolve));
}

async function uploadCanvasImage(canvas) {
  let pngBlob = await getCanvasBlob(canvas);
  let formData = new FormData();
  formData.set("image", pngBlob, "drawing.png");
  let response = await fetch("/upload", { method: "POST", body: formData });
  if (!response.ok) throw new Error(response.statusText);
  return response.json();
}

Reading the response body

The Response object gives you a choice of five Promise-returning methods for consuming the body, each intended for a different shape of data, plus a sixth raw-stream option:

MethodResolves toUse for
response.json()Parsed valueJSON-formatted bodies
response.text()StringPlain text, HTML fragments, anything textual
response.arrayBuffer()ArrayBufferBinary data you'll read with a typed array or DataView
response.blob()BlobLarge binary payloads (images, media) — may stream to a temp file internally rather than buffering in memory
response.formData()FormDataA multipart/form-data body — uncommon in responses, common in requests

You can only successfully call one body-reading method per response; once one has consumed the stream, response.bodyUsed becomes true and further reads fail.

Streaming a response body

When you need to react to bytes as they arrive — a download progress bar being the classic case — call getReader() on response.body and pull chunks manually. Each call to reader.read() resolves to { done, value }, where value is the next chunk as a Uint8Array (or undefined once there's nothing left), and done becomes true once the stream is fully drained: 

async function streamBody(response, onProgress) {
  let expectedBytes = parseInt(response.headers.get("Content-Length"));
  let bytesRead = 0;
  let reader = response.body.getReader();
  let decoder = new TextDecoder("utf-8");
  let text = "";
  while (true) {
    let { done, value } = await reader.read();
    if (value) {
      text += decoder.decode(value, { stream: true });
      bytesRead += value.length;
      onProgress?.(bytesRead, bytesRead / expectedBytes); // NaN if no Content-Length
    }
    if (done) break;
  }
  return text;
}

fetch("big.json")
  .then(response => streamBody(response, updateProgressBar))
  .then(text => JSON.parse(text))
  .then(handleBigObject);

Aborting requests and timeouts

fetch() supports cancellation through the generic AbortController/AbortSignal pair (used by several other web APIs too, not just fetch()). Create a controller, pass its signal in the options object, and call controller.abort() whenever you want to cancel — doing so rejects any Promise tied to that request: 

let controller = new AbortController();
cancelButton.onclick = () => controller.abort();

fetch(url, { signal: controller.signal })
  .then(response => response.json())
  .catch(err => {
    if (err.name === "AbortError") console.log("Request was cancelled");
    else throw err;
  });

The same mechanism gives you request timeouts, since a timer can call abort() just as well as a click handler:

function fetchWithTimeout(url, options = {}) {
  if (options.timeout) {
    let controller = new AbortController();
    options.signal = controller.signal;
    // Calling abort() after the fetch already finished is harmless,
    // so there's no need to clear this timer on success.
    setTimeout(() => controller.abort(), options.timeout);
  }
  return fetch(url, options);
}

fetchWithTimeout("/api/slow", { timeout: 5000 })
  .then(response => response.json())
  .catch(err => {
    if (err.name === "AbortError") console.log("timed out after 5s");
  });

Cross-origin requests and CORS

A request whose URL shares the current document's protocol, hostname, and port is same-origin and always allowed. A request to any other origin is cross-origin, and browsers block it by default — not because fetch() refuses to send it, but because the browser will not hand your script the response unless the server explicitly opts in.

When you fetch() a cross-origin URL, the browser automatically attaches an Origin header (you cannot override or remove it) identifying where the request came from. The server must respond with an Access-Control-Allow-Origin header naming that origin (or *) for the browser to release the response to your script; otherwise the Promise fetch() returned rejects.

This is enforced unilaterally by the browser

CORS is not something the client can negotiate its way around by design — there is no client-side header or option that makes a browser ignore a missing Access-Control-Allow-Origin. The policy exists to protect the user (whose cookies and session might be attached to the request), not to protect the server, so it can't be disabled from the calling page.

Other request options

Two more options round out the fetch configuration surface: cache, which overrides the browser's normal HTTP caching behavior, and redirect, which controls what happens when the server responds with a 3xx.

cache valueBehavior
"default"Normal HTTP caching: serve fresh entries from cache, revalidate stale ones
"no-store"Ignore the cache completely, in both directions
"reload"Always hit the network, but still store the result in cache afterward
"no-cache"Always revalidate before using a cached value, fresh or not
"force-cache"Serve from cache even if stale
redirect valueBehavior
"follow" (default)Redirects are followed automatically; you never see a 3xx status
"error"A redirect response causes the returned Promise to reject
"manual"You get the raw 3xx Response back and must follow its Location header yourself

A referrer option is also available to override the Referer request header (yes, historically misspelled with three R's) — set it to "" to omit the header entirely.

Server-Sent Events: one-way server push

HTTP is fundamentally client-initiated: the client asks, the server answers. Server-Sent Events work around that by having the client open a connection and then having neither side close it - the server writes new data to the same open connection whenever it has something to say, and the client's EventSource object translates each write into a JavaScript event. If the connection drops, EventSource reconnects automatically on your behalf — you don't have to write any retry logic. 

let ticker = new EventSource("/stockprices");
ticker.addEventListener("bid", (event) => {
  displayNewBid(JSON.parse(event.data));
});

Every event object has the usual type (the event name) and a data property holding whatever the server sent. If the server doesn't label an event, its type defaults to "message". On the wire, the server writes plain-text frames terminated by a blank line: 

event: bid
data: GOOG
data: 999

(The two consecutive data: lines are joined with a newline into a single data string.) The protocol also supports per-event IDs so a reconnecting client can tell the server the last event it saw and have missed events replayed, but that machinery is invisible on the client side.

A natural application is a chat room: post outgoing messages with fetch(), and receive the stream of everyone else's messages through an EventSource: 

let chat = new EventSource("/chat");
chat.addEventListener("chat", (event) => {
  let div = document.createElement("div");
  div.textContent = event.data;
  document.querySelector("#messages").append(div);
});

document.querySelector("#input").addEventListener("change", (event) => {
  fetch("/chat", { method: "POST", body: event.target.value })
    .catch(err => console.error("failed to send:", err));
  event.target.value = "";
});
When to reach for SSE

SSE is a good fit whenever data only ever needs to flow server to client — live prices, notifications, dashboards, progress updates — and you'd rather not run a separate protocol. The moment the client also needs to push data over the same connection (rather than via separate fetch() calls), reach for WebSockets instead.

WebSockets: full-duplex messaging

WebSockets are a distinct network protocol, layered on top of an initial HTTP handshake (the browser sends an Upgrade: websocket request, and if the server agrees, the connection switches protocols). Unlike fetch() or SSE, a WebSocket connection is symmetric: once open, either side can send messages to the other at any time, and messages may be binary as well as text. URLs use ws:// or, almost always in practice, wss:// (browsers generally restrict plain ws:// to pages that were themselves loaded insecurely). 

let socket = new WebSocket("wss://example.com/chat");

Creating a WebSocket begins connecting immediately, but the object is not yet connected when the constructor returns. socket.readyState tracks the connection's lifecycle:

ConstantMeaning
WebSocket.CONNECTINGHandshake in progress
WebSocket.OPENConnected, ready to send/receive
WebSocket.CLOSINGClose in progress
WebSocket.CLOSEDClosed, or the initial connection attempt failed
socket.addEventListener("open", () => {
  socket.send(JSON.stringify({ type: "join", room: "general" }));
});

socket.addEventListener("message", (event) => {
  // event.data is a string for text frames; a Blob (by default) or an
  // ArrayBuffer (if you set socket.binaryType = "arraybuffer") for binary ones.
  let msg = JSON.parse(event.data);
  displayMessage(msg);
});

socket.addEventListener("error", (event) => {
  console.error("WebSocket error", event);
});

socket.addEventListener("close", (event) => {
  console.log(`connection closed: code ${event.code}`);
});

// Later, to end the conversation cleanly:
socket.close();

send() accepts a string, Blob, ArrayBuffer, typed array, or DataView. It buffers the message and returns immediately — it does not wait for the network write to actually complete. If you need to know how much is still queued, check socket.bufferedAmount (there is, notably, no event that fires when that value reaches zero, so polling is the only option if you need to track it).

No structured clone here

Despite MessageEvent being used by several browser APIs that do support the structured clone algorithm for rich payloads, WebSockets is not one of them: every message is just a single string or a single blob of bytes. Your application defines its own message format on top — JSON-encoded strings are the overwhelmingly common choice.

Because the protocol itself says nothing about message structure, long-lived services often need a way to evolve. Two complementary techniques handle that: bumping the URL path (e.g. wss://example.com/chat/v2) for a hard break, or passing a second, array argument to the WebSocket() constructor listing the sub-protocols your client understands, letting the server pick one during the handshake: 

let socket = new WebSocket("wss://example.com/ticker", ["v2.price-feed", "v1.price-feed"]);
socket.addEventListener("open", () => {
  console.log("server chose protocol:", socket.protocol);
});
