Regular Expressions

A regular expression is an object that describes a textual pattern — a tiny, dense language of its own for matching, extracting, and rewriting text. JavaScript's RegExp class implements this language, and both String and RegExp expose methods that use it to search, test, and replace. This page works through the grammar symbol by symbol first — what each piece of punctuation means — and then moves to the API that actually runs a pattern against a string. It closes with the two places people get burned in practice: quantifiers that don't backtrack the way you'd guess, and a stateful lastIndex property that silently corrupts loops built around a reused global regex.

Defining a pattern: literal vs. constructor

Just as a string literal is text between quotation marks, a regular expression literal is a pattern between a pair of forward slashes. This is by far the more common way to write one, because the pattern is usually known in advance and baked into the source code: 

let pattern = /s$/;   // Matches any string ending in the letter "s"

Most characters in a pattern — letters and digits — simply match themselves. /java/ matches any string containing the substring "java". Other characters are metacharacters: they don't match themselves but carry special meaning. The $ above means "end of string," not a literal dollar sign. A pattern can also carry one or more trailing flags, written after the closing slash, which change how matching behaves without changing what the pattern text says. Adding i makes the match case-insensitive: 

let pattern = /s$/i;   // Also matches strings ending in "S"

The equivalent way to build the same regex is the RegExp() constructor, taking the pattern body as a string and the flags as an optional second string argument: 

let pattern = new RegExp("s$", "i");

// You can also pass an existing RegExp to copy it while changing its flags:
let exactMatch = /JavaScript/;
let caseInsensitive = new RegExp(exactMatch, "i");

The constructor is the form you reach for whenever the pattern isn't known until runtime — for example, building a search regex out of text a user typed. Because both regular expression syntax and string literal syntax use backslash for escaping, any backslash that should end up in the pattern must be doubled when it is written as a string: 

// Matches five ASCII digits in a row, with the "g" (global) flag
let zipcode = new RegExp("\\d{5}", "g");
When in doubt, escape it

A number of punctuation characters are metacharacters somewhere in regex grammar: ^ $ . * + ? = ! : | \ / ( ) [ ] { }. If you want one of them matched literally, precede it with a backslash — \., \(, \$, and so on. It is always safe to backslash-escape a punctuation character even where it isn't strictly required. The opposite is not true: letters and digits often gain a special meaning once you put a backslash in front of them (\d, \b, \w…), so never escape a letter or digit you actually want matched literally.

Literal characters and escape sequences

Alongside ordinary letters and digits, a handful of backslash escapes let a pattern refer to characters that are awkward to type directly, such as tabs and newlines:

EscapeMatches
\0The NUL character (code point 0)
\tTab (code point 9)
\nNewline / line feed (code point 10)
\vVertical tab (code point 11)
\fForm feed (code point 12)
\rCarriage return (code point 13)
\xnnThe Latin-1 character with hex code nn, e.g. \x0A is the same as \n
\uxxxxThe Unicode character with hex code xxxx, e.g. \u0009 is the same as \t
\u{n}The Unicode character at codepoint n (1–6 hex digits, up to 10FFFF). Requires the u or v flag
\cXThe control character produced by Ctrl-X, e.g. \cJ is the same as \n

To match a literal backslash character, escape it with another backslash: /\\/. Quotation marks, @, and most other punctuation that isn't in the metacharacter list above already match themselves with no escaping required.

Character classes

A character class matches exactly one character out of a set you define, by placing candidates inside square brackets. Prefixing the set with ^ negates it — match any one character not in the set — and a hyphen inside the brackets denotes a range: 

/[abc]/        // Matches "a", "b", or "c"
/[^abc]/       // Matches any character EXCEPT "a", "b", or "c"
/[a-z]/        // Any lowercase Latin letter
/[a-zA-Z0-9]/  // Any Latin letter or digit
/[Ѐ-ӿ]/  // Any one Cyrillic character (an explicit Unicode range)

To include a literal hyphen in a class, put it last, right before the closing bracket, so it can't be read as a range separator. Because certain classes come up constantly, JavaScript provides one-letter escapes for them, and each has an uppercase counterpart that matches its negation:

SyntaxMatches
[...]Any one character listed (or ranged) between the brackets
[^...]Any one character not listed between the brackets
.Any character except a line terminator — or truly any character, including line terminators, with the s flag
\w / \WASCII "word" character, equivalent to [a-zA-Z0-9_] / its negation
\s / \SAny Unicode whitespace character / any character that is not whitespace
\d / \DASCII digit, equivalent to [0-9] / its negation
[\b]Literal backspace character — the one place \b does not mean "word boundary"

These class escapes can be nested inside a bracketed class: /[\s\d]/ matches one whitespace character or digit. Note the \d/\w family only covers ASCII — a French accented letter or a Devanagari digit will not satisfy \w or \d.

Unicode property escapes ES2018

Because \d and \w are ASCII-only, matching "any digit" or "any letter" across the world's scripts needs a different tool. When a pattern carries the u (or v) flag, \p{...} and its negation \P{...} match characters by Unicode category — categories defined by the Unicode standard itself, not by JavaScript, so the exact set of characters they cover can shift as Unicode is revised. 

/\p{Decimal_Number}/u     // One decimal digit from ANY writing system
/\P{Decimal_Number}/u     // Any character that is NOT a decimal digit
/\p{Number}/u             // Any number-like character: digits, fractions, roman numerals

// An internationalized approximation of \w:
/[\p{Alphabetic}\p{Decimal_Number}\p{Mark}]/u

// Matching characters from a specific script:
let greekLetter = /\p{Script=Greek}/u;
let cyrillicLetter = /\p{Script=Cyrillic}/u;
The v flag and set notation ES2024

The newer v flag is a strict upgrade to u: it enables everything u does, plus set-operator syntax inside classes — [\p{Letter}&&\p{Script=Latin}] for intersection and [\p{Letter}--\p{ASCII}] for subtraction — and it allows classes to contain multi-codepoint strings, not just single characters. You cannot set both u and v on the same regex; pick one. For most new code that needs Unicode-aware classes, prefer v.

Quantifiers: repeating a pattern

Repetition operators always follow the element they apply to — a single character, a character class, or a parenthesized group — and say how many times that element may repeat.

SyntaxMeaning
?Zero or one occurrence (the item is optional). Equivalent to {0,1}
*Zero or more occurrences. Equivalent to {0,}
+One or more occurrences. Equivalent to {1,}
{n}Exactly n occurrences
{n,}n or more occurrences
{n,m}At least n, no more than m, occurrences
let r = /\d{2,4}/;   // Between two and four digits
r = /\w{3}\d?/;       // Exactly three word characters, then an optional digit
r = /\s+java\s+/;     // "java" surrounded by one or more spaces on each side
r = /[^(]*/;          // Zero or more characters that are not an open paren

To repeat something more complex than a single character or class — an entire sequence of characters, or an alternation — wrap it in a group first (see the next section); a quantifier right after ) applies to everything the group matched.

* and ? can match nothing

Because they permit zero occurrences, /a*/ matches the string "bbbb" — zero a's is a perfectly valid match, found at position 0, with an empty matched string. Code that expects "no match" when there's clearly no "a" in the string, and instead gets an empty match, has run into this rule.

Greedy vs. lazy quantifiers Deep dive

Every quantifier above is greedy by default: it consumes as many characters as it possibly can while still letting the rest of the pattern succeed. Appending an extra ? to a quantifier — ??, +?, *?, or {1,5}? — makes it lazy (also called "non-greedy"): it consumes as few characters as it can, only expanding when forced to by a later part of the pattern failing. 

"aaa".match(/a+/)[0]    // => "aaa"  — greedy: grabs every "a" available
"aaa".match(/a+?/)[0]   // => "a"    — lazy: grabs the minimum, just one "a"

// A classic case where laziness changes the result: matching an
// HTML-ish tag's contents.
let markup = "<em>first</em> and <em>second</em>";
markup.match(/<em>(.*)<\/em>/)[1]    // => "first</em> and <em>second"  (greedy: spans BOTH tags)
markup.match(/<em>(.*?)<\/em>/)[1]   // => "first"                     (lazy: stops at the FIRST closing tag)

That second example is the standard justification for reaching for lazy quantifiers: greedy .* will happily swallow everything up to the last possible closing delimiter in the string, rather than the nearest one.

Laziness doesn't mean "shortest match anywhere" — it means "shortest match from the first viable start"

A regex engine picks the leftmost position at which a match is possible at all, and only then does greedy vs. lazy decide how much to consume from that position onward. It never abandons an already-found match at an early position to go look for a shorter one starting later. Consider /a+b/ against "aaab": it matches the entire string "aaab", because a+ greedily eats all three a's and then backtracks just enough to let the final b match. Now compare the lazy version, /a+?b/, against the very same string. You might expect it to prefer a short match like just the last "ab" — but it also matches the entire string "aaab": 

"aaab".match(/a+b/)[0]    // => "aaab" — greedy version
"aaab".match(/a+?b/)[0]   // => "aaab" — lazy version: SAME RESULT!

// Why: a match starting at index 0 is possible, so the engine commits to
// index 0 and never tries starting the match at index 1 or 2, even though
// those would have produced a shorter overall match ("ab").

The lazy quantifier only changes how greedily the engine backtracks within a single candidate start position — here, it still has to consume all three a's, one at a time, backtracking forward until b is found, because a+? must match at least one a starting right at index 0, and no b appears until index 3. The takeaway: lazy quantifiers shrink a match relative to greedy ones only when there are multiple points at which the trailing part of the pattern could succeed from the same start position — they do not search for a better start position.

Alternation, grouping, and backreferences

Parentheses and the pipe character give a regex three closely related powers: choosing between alternatives, treating a sub-pattern as a single unit, and later referring back to whatever text a sub-pattern matched.

SyntaxMeaning
|Alternation — match the subexpression to the left OR the one to the right
(...)Capturing group — groups items into one unit usable with * + ? | etc., and remembers the matched text for later reference
(?:...)Non-capturing group — groups for repetition/alternation purposes only; does not create a numbered backreference
\nBackreference — matches the same text that numbered group n matched. Groups are numbered by the position of their opening (, left to right; (?: groups are not numbered
/ab|cd|ef/          // Matches "ab", "cd", or "ef"
/\d{3}|[a-z]{4}/     // Matches three digits OR four lowercase letters

/java(script)?/      // "java" with an optional "script" — one group, unit-quantified with ?
/(ab|cd)+|ef/        // "ef", or one-or-more repetitions of "ab"/"cd"
/([Jj]ava(?:[Ss]cript)?)\sis\s(fun\w*)/
// Group 1 is (Jj]ava(?:[Ss]cript)?), group 2 is (fun\w*) — the
// non-capturing (?:[Ss]cript) does not consume a group number, so
// there is no separate group 2 for "Script".

// Backreference: enforce that the closing quote MATCHES the opening one
/(['"])[^'"]*\1/
// Without the backreference, /['"][^'"]*['"]/ would happily accept a
// string that opens with ' and closes with ", which is wrong.
Alternation is tried left to right, and stops at the first match

| does not pick the "best" or longest alternative — it commits to the first one (reading left to right) that succeeds. /a|ab/ matched against "ab" matches only the single letter "a", because that alternative is tried first and succeeds; the engine never backtracks to try ab instead.

Backreferences can't appear inside a character class

/(['"])[^\1]*\1/ is not valid the way you might hope — a \1 written inside [...] is not treated as "whatever group 1 matched"; character classes only understand literal characters and class escapes.

Named capture groups ES2018

Numbering groups by counting opening parentheses works, but it makes a pattern hard to read and fragile to edit — insert a new group anywhere and every later number shifts. Named groups solve both problems: write (?<name>...) instead of (...), and refer to the captured text by name. 

// Validate/parse the last line of a US mailing address
let address = /(?<city>\w+) (?<state>[A-Z]{2}) (?<zipcode>\d{5})(?<zip9>-\d{4})?/;

// A named backreference uses \k<name> instead of \1
let quoted = /(?<quote>['"])[^'"]*\k<quote>/;

Named groups are still numbered too (a name doesn't remove the positional number), and the same name cannot be reused twice in one pattern outside of separate alternation branches. You'll see how to read named captures back out of a match result in the RegExp API and String method sections below.

Anchors and word boundaries

Most regex elements match an actual character. Anchors are different — they match a position in the string, consuming no characters themselves, and are used to "pin" a pattern to a specific place.

SyntaxMatches
^The beginning of the string, or (with the m flag) the beginning of any line
$The end of the string, or (with the m flag) the end of any line
\bA word boundary — the position between a \w character and a \W character, or between a \w character and the start/end of the string
\BA position that is not a word boundary
/^JavaScript$/     // Matches only if the ENTIRE string is exactly "JavaScript"

// Matching "Java" as a standalone word (not the "Java" inside "JavaScript")
/\sJava\s/          // Works, but requires actual space characters and
                    // fails at the start/end of a string, and the match
                    // includes the surrounding spaces you probably don't want
/\bJava\b/          // Better: anchors to word boundaries, consumes no spaces

/\B[Ss]cript/       // Matches "JavaScript" and "postscript" (script is NOT
                    // at a word boundary there) but not standalone "script"
                    // or "Scripting" (where it IS at a boundary)

Lookahead and lookbehind assertions

Lookaround takes the anchor idea further: instead of a fixed position rule like "start of string," you supply an entire sub-pattern that must (or must not) match at the current position — without consuming any of the characters it checks. That means the checked text is not included in the overall match.

SyntaxMeaning
(?=p)Positive lookahead — what follows must match p, but p is not consumed
(?!p)Negative lookahead — what follows must not match p
(?<=p) ES2018Positive lookbehind — what precedes the current position must match p
(?<!p) ES2018Negative lookbehind — what precedes must not match p
// Match the name of a language, but only when followed by a colon
/[Jj]ava([Ss]cript)?(?=:)/
// Matches "JavaScript" in "JavaScript: The Definitive Guide"
// Does NOT match "Java" in "Java in a Nutshell" (no colon follows)

// Negative lookahead: "Java" NOT followed by "Script"
/Java(?!Script)([A-Z]\w*)/
// Matches "JavaBeans", matches "JavaScrip" (note: not the full word
// "JavaScript"), does NOT match "JavaScript" or "JavaScripter"

// Lookbehind: a 5-digit zip code, only when it follows a US state code
/(?<=[A-Z]{2} )\d{5}/

// Digits NOT preceded by a currency symbol or decimal point
/(?<![\p{Currency_Symbol}\d.])\d+(\.\d+)?/u
Lookahead vs. lookbehind: direction, not power

Both forms exist purely to check context around a match without including that context in the result. Lookahead checks what comes after the current position; lookbehind checks what comes before it. Lookbehind arrived later (ES2018) and is the one more likely to be missing from an older engine, though all current evergreen browsers and Node support it.

Flags

Flags change matching behavior without changing the pattern text, and are written after the closing slash of a literal (or as the second argument to the constructor). They can be combined freely and in any order.

FlagNameEffect
gglobalFind all matches rather than stopping at the first. Also switches match()/exec()/test() into stateful, lastIndex-driven mode
iignoreCaseCase-insensitive matching
mmultiline^ and $ additionally match the start/end of each line, not just the whole string
sdotAll. matches line terminators too, not just "any character except a newline"
uunicodeMatches full Unicode codepoints instead of raw 16-bit code units; enables \u{...} and \p{...}. Use it by default so emoji and non-BMP characters aren't split in half
vunicodeSets ES2024Superset of u: adds set-operator class syntax and multi-codepoint string entries in classes. Mutually exclusive with u
ystickyThe next match must start at exactly lastIndex — no scanning forward to find a later match
/script/gi      // global AND case-insensitive
new RegExp("script", "giu")   // same, plus Unicode mode

The RegExp object: construction and properties

A RegExp instance carries the pattern, its flags, and — for stateful patterns — a cursor into the last string it searched.

PropertyDescription
sourceRead-only. The pattern text, as it would appear between the slashes of a literal
flagsRead-only. A string of the active flag letters, e.g. "gi"
globalRead-only boolean — true if g is set
ignoreCaseRead-only boolean — true if i is set
multilineRead-only boolean — true if m is set
dotAllRead-only boolean — true if s is set
unicodeRead-only boolean — true if u is set
stickyRead-only boolean — true if y is set
lastIndexRead/write integer. For g or y patterns, the character position where the next search begins. Consulted and updated by exec() and test()

Every property except lastIndex is read-only and derived entirely from how the RegExp was constructed — lastIndex is the one piece of mutable state on the object, and it's the subject of its own deep dive below.

test() and exec()

RegExp itself defines two matching methods. test() is the simple one: pass it a string, get back true or false. Internally it's just exec() with the result collapsed to a boolean, which matters because it means test() inherits all of exec()'s statefulness around lastIndex. 

/^\d+$/.test("123")   // => true
/^\d+$/.test("12a")   // => false

exec() is the most powerful and most low-level way to run a pattern. Given a string, it returns null on no match, or — on success — an array just like the one String.prototype.match() returns for a non-global pattern: element 0 is the full match, subsequent elements are the capturing groups, and the array carries extra properties index (where the match started), input (the searched string), and groups (an object of named captures, or undefined if the pattern has none).

The crucial difference from match(): exec() always returns single-match detail, regardless of the g flag — it never switches to returning a flat array of strings. Instead, when g or y is set, each successful call moves lastIndex to just past the match, so calling exec() again continues from there. That's what makes the classic "loop over every match" pattern work: 

let pattern = /Java/g;
let text = "JavaScript > Java";
let match;
while ((match = pattern.exec(text)) !== null) {
  console.log(`Matched ${match[0]} at ${match.index}`);
  console.log(`Next search begins at ${pattern.lastIndex}`);
}
// Matched Java at 0
// Next search begins at 4
// Matched Java at 14
// Next search begins at 18

The lastIndex trap Classic bug

A pattern with the g or y flag is stateful: the RegExp object itself remembers where the last successful match ended, via lastIndex, and exec()/test() resume from there on the same object's next call. That statefulness is exactly what a manual match-everything loop wants — and exactly what silently breaks any code that reuses the same global-flagged RegExp for something other than a clean, sequential scan.

Failure mode 1: a literal in the loop condition never advances

Suppose you want the index of every <p> tag in an HTML string: 

let match, positions = [];
while ((match = /<p>/g.exec(html)) !== null) {  // POSSIBLE INFINITE LOOP
  positions.push(match.index);
}

If html contains even one <p>, this never terminates. The regex literal /<p>/g is re-evaluated on every iteration of the loop, which creates a brand-new RegExp object each time — with lastIndex freshly reset to 0. Every call restarts from the beginning of the string, finds the same first match, and the loop condition is always truthy. The fix is to build the RegExp exactly once, outside the loop, so the same object (and its advancing lastIndex) is reused across iterations: 

let tag = /<p>/g;             // Created ONCE
let match, positions = [];
while ((match = tag.exec(html)) !== null) {
  positions.push(match.index);
}

Failure mode 2: reusing a shared regex across unrelated calls

The mirror-image bug: sometimes you keep one RegExp variable around for convenience, not realizing that using it once changes its behavior the next time. Suppose you scan a dictionary for words containing a doubled letter (like the "pp" in "apple"): 

let dictionary = ["apple", "book", "coffee"];
let doubleLetter = /(\w)\1/g;    // has "g" — carries state between calls!
let doubleLetterWords = dictionary.filter(word => doubleLetter.test(word));
doubleLetterWords   // => ["apple", "coffee"]  — "book" is WRONGLY missing!

Walking through it: test("apple") finds "pp" starting at index 1, and because g is set, doubleLetter.lastIndex is left at 3 (just past the match). The next call, test("book"), does not start scanning "book" from position 0 — it starts from position 3, per the shared object's leftover lastIndex, which is already past the "oo" in "book". No match is found, "book" is skipped, and the RegExp resets lastIndex back to 0 — which is why "coffee" (checked next, from a clean position 0) matches successfully and masks the fact anything went wrong.

Three ways to fix it — and which one to prefer

1) Drop the g flag if you never needed global matching in the first place (as here — test() just needs a yes/no per word). 2) Reset re.lastIndex = 0 immediately before each independent use. 3) Best for "loop over every match" use cases specifically: use String.prototype.matchAll() instead of manual exec()/test() calls — it is documented below and, unlike every other regex method, it never reads or mutates lastIndex on the RegExp you pass it, so there is no shared state left over to trip on.

Pattern matching with String methods

The RegExp methods above are low-level tools. In everyday code, the regex-aware methods on String.prototype are usually more convenient — each accepts a regex (or a plain string, which is promoted to a regex or matched literally depending on the method) and does something specific with it.

MethodReturns
str.search(re)Index of the first match, or -1. Always ignores the g flag — there's no such thing as a "global" single index
str.replace(re, repl)New string with match(es) replaced. Replaces only the first match unless re has the g flag
str.replaceAll(re, repl)New string, all matches replaced. If re is a regex, it must have the g flag or this throws a TypeError
str.match(re)Without g: one match-detail array (like exec()). With g: a flat array of matched strings only, no capture/index info, or null if nothing matched
str.matchAll(re)An iterator of match-detail objects for every match. Requires g. Never touches lastIndex
str.split(re)Array of substrings split on the pattern. Capturing groups in the separator are spliced into the result array

search()

The simplest of the five: it returns where the first match starts, or -1. 

"JavaScript".search(/script/ui)   // => 4
"Python".search(/script/ui)       // => -1

replace() and replaceAll()

With a plain replacement string, $-sequences let you splice captured text into the output: $1...$9 refer to numbered capture groups, $<name> refers to a named one, and $& refers to the entire match. 

// Normalize capitalization no matter how the input was cased
text.replace(/javascript/gi, "JavaScript");

// $1 refers to the first capturing group — the text inside the quotes
let quote = /"([^"]*)"/g;
'He said "stop"'.replace(quote, '«$1»')   // => 'He said «stop»'

// Named groups: reference by $<name> instead of a number
let namedQuote = /"(?<quotedText>[^"]*)"/g;
'He said "stop"'.replace(namedQuote, '«$<quotedText>»')  // => 'He said «stop»'

The second argument can also be a function, invoked per match and expected to return the replacement text. It receives: the full matched text; then one argument per capturing group (in order); then the match's starting offset; then the whole original string; and finally, if the pattern has named groups, an object mapping names to captured text. 

// Convert every run of decimal digits to hexadecimal
let s = "15 times 15 is 225";
s.replace(/\d+/gu, n => parseInt(n).toString(16))   // => "f times f is e1"

replaceAll() is the more explicit sibling of replace() for the "replace every match" case: it takes the same replacement forms, but if you pass it a regex without the g flag it throws, rather than silently only replacing the first occurrence. 

"a.b.c".replaceAll(".", "-")     // => "a-b-c" (plain string separator — fine, no flag needed)
"a.b.c".replaceAll(/\./g, "-")   // => "a-b-c" (regex MUST carry g)
"a.b.c".replaceAll(/\./, "-")    // => TypeError: replaceAll must be called with a global RegExp

match()

Behavior splits sharply depending on the g flag. Without it, match() returns the same rich detail array that exec() does — full match at index 0, capture groups after it, plus index, input, and groups: 

let url = /(?<protocol>\w+):\/\/(?<host>[\w.]+)\/(?<path>\S*)/;
let text = "Visit my blog at http://www.example.com/~david";
let match = text.match(url);
match[0]                // => "http://www.example.com/~david"
match.input             // => text
match.index             // => 17
match.groups.protocol   // => "http"
match.groups.host       // => "www.example.com"
match.groups.path       // => "~david"

With g, all of that detail is discarded — you get back a flat array of the matched substrings only, with no index or capture information: 

"7 plus 8 equals 15".match(/\d+/g)   // => ["7", "8", "15"]  — no groups, no index
The y flag's effect on match()

If g and y are both set, match() still returns the flat array of strings, but the first match must start at the very beginning of the string and every subsequent one must start immediately where the previous match ended — no skipping ahead to find a later match. With y alone (no g), match() looks for one match constrained to start at lastIndex (default 0), and updates lastIndex to just after a successful match — or resets it to 0 on failure: 

let vowel = /[aeiou]/y;
"test".match(vowel)      // => null: "test" doesn't begin with a vowel
vowel.lastIndex = 1;     // Force the next attempt to start at index 1
"test".match(vowel)[0]   // => "e": found a vowel right at position 1
vowel.lastIndex          // => 2: auto-advanced past the match
"test".match(vowel)      // => null: no vowel at position 2
vowel.lastIndex          // => 0: reset after the failed match

Calling match() with a non-global regex is exactly equivalent to calling exec() on that regex with the string — same return value, same properties.

matchAll() ES2020

matchAll() combines the best of both worlds above: it requires the g flag, but instead of collapsing to bare strings, it returns an iterator that yields the same rich match-detail object match() gives you without g — full match, capture groups, index, and named groups — for every match in the string. 

const words = /\b\p{Alphabetic}+\b/gu;
const text = "This is a naïve test of the matchAll() method.";
for (let word of text.matchAll(words)) {
  console.log(`Found '${word[0]}' at index ${word.index}.`);
}

You can prime where matching starts by setting lastIndex on the RegExp before calling matchAll() — but unlike every other method covered on this page, matchAll() never reads it again mid-loop and never writes to it, which is precisely why it sidesteps the lastIndex trap above entirely. For any new code that needs to iterate every match with full detail, prefer matchAll() over a manual exec() loop.

split()

split() breaks a string into an array of pieces using the argument as the separator. A plain string separator is matched literally; a regex separator lets the boundary itself be a pattern: 

"123,456,789".split(",")             // => ["123", "456", "789"]
"1, 2, 3,\n4, 5".split(/\s*,\s*/)     // => ["1", "2", "3", "4", "5"]
Capturing groups in the separator leak into the result

If the separator regex has capturing groups, the text those groups matched is spliced into the returned array, interleaved with the surrounding pieces — a detail that surprises people who expect only the "outer" substrings back. 

const htmlTag = /<([^>]+)>/;   // "<", one or more non-">" characters, ">"
"Testing<br/>1,2,3".split(htmlTag)   // => ["Testing", "br/", "1,2,3"]
// "br/" is the text captured by group 1, spliced into the array between
// the two pieces the tag actually separated.

Quick reference

A condensed cheat sheet of everything above, for scanning while you write a pattern:

Once a pattern is built, hand it to RegExp.prototype.test()/exec() or to the String methods (search(), replace()/ replaceAll(), match(), matchAll(), split()) documented above. Regular expressions are also the pattern-matching foundation you'll see reused when parsing dates and formatting numbers in Dates, JSON, Intl & Utilities, and they show up again anywhere you're extracting structured data out of the collection types covered in Collections & Typed Arrays.
