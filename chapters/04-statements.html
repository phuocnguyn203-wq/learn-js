Statements

If expressions are the phrases of JavaScript, statements are its sentences. A program is nothing more than a sequence of statements, executed one after another, each one terminated by a semicolon. Most of them — conditionals, loops, jumps — exist to bend that default top-to-bottom order into branches and repetitions. This page works through every statement form in the language, including the ones tutorials tend to skip: the empty statement, the full label/break/continue system, exactly how finally interacts with return and thrown exceptions, and the banned with statement.

5.1 Expression statements

The simplest statement in JavaScript is an expression evaluated purely for its side effect, with a semicolon tacked on the end. Assignments are the classic case — total = total + tax; is an expression (an assignment expression, which itself evaluates to the assigned value) used as a statement because we care about the mutation, not the value it produces. The increment/decrement operators fall in the same bucket, since counter++; is really shorthand for an assignment. Function and method calls are the other major category: console.log(x); and form.submit(); are expressions whose return value is thrown away because the reason for writing them is what they do, not what they evaluate to. 

greeting = "Hello " + name;   // assignment statement
i *= 3;                       // compound assignment statement
counter++;                    // increment, used for its side effect
delete o.x;                   // delete's usefulness IS the side effect
console.log(debugMessage);    // function call statement

// A pure expression with no side effect, standing alone, is pointless:
Math.cos(x);                  // computes something and discards it — useless

// The same expression only earns its keep when its value is captured:
cx = Math.cos(x);

The rule of thumb: if an expression has no side effect (no assignment, no mutation, no I/O), writing it as a bare statement is almost always a bug — either you forgot to assign the result, or the statement does nothing at all and a linter will (rightly) flag it.

5.2 Compound and empty statements

Just as the comma operator glues several expressions into one, a statement block — a sequence of statements wrapped in curly braces — glues several statements into one compound statement that can be used anywhere JavaScript's grammar expects a single statement (the body of an if, a while, and so on). 

{
  x = Math.PI;
  cx = Math.cos(x);
  console.log(`cos(pi) = ${cx}`);
}

Two details are easy to miss. First, the block itself takes no trailing semicolon — only the primitive statements inside it do. Second, the indentation you see is purely a readability convention; the interpreter doesn't care about whitespace at all.

At the opposite extreme is the empty statement: a single, bare semicolon that tells the interpreter to do nothing at all. It exists because JavaScript's grammar always requires a statement in certain slots (a loop body, for instance) even when you have nothing left for that slot to do — typically because you crammed all of the loop's work into its header expressions: 

// Initialize every element of array a to zero.
// The assignment a[i++] = 0 does all the work; there's nothing left for a body.
for (let i = 0; i < a.length; a[i++] = 0) ;
A stray semicolon silently swallows your loop or if body

Because ; alone is a perfectly legal statement, an accidental semicolon right after the closing parenthesis of an if, while, or for compiles fine and fails silently at runtime — the next line just always runs, unconditionally: 

if ((a === 0) || (b === 0));   // Oops — this semicolon IS the entire if-body
  o = null;                    // This line always runs, condition or not!

When you really do mean to write an empty loop body, make the intent obvious with a comment so the next reader (including future you) doesn't "fix" it: for (let i = 0; i < a.length; a[i++] = 0) /* empty */ ;

5.3 Conditionals

Conditional statements are the branch points of your program: they evaluate an expression and, depending on whether it's truthy or falsy, choose which of several paths of code to run next.

if and if/else

if is JavaScript's fundamental conditional. In its single-branch form, the body executes only when the condition is truthy: 

if (username == null)          // catches both null and undefined
  username = "John Doe";

// Any falsy value (null, undefined, false, 0, "", NaN) triggers this branch too:
if (!username) username = "John Doe";

The parentheses around the condition are mandatory syntax, not stylistic choice. Adding an else clause gives you the two-branch form, executing one statement or the other depending on truthiness: 

if (n === 1)
  console.log("You have 1 new message.");
else
  console.log(`You have ${n} new messages.`);

The dangling-else trap Classic gotcha

JavaScript's grammar allows exactly one statement after an if's condition, and exactly one after an else — but that single statement can itself be another if. When you nest conditionals without braces, an else always binds to the nearest unmatched if, no matter what your indentation implies. 

let i = 1, j = 1, k = 2;

// The indentation below LIES about what actually happens:
if (i === j)
  if (j === k)
    console.log("i equals k");
else
  console.log("i doesn't equal j");   // Looks attached to the outer if...

// ...but the interpreter actually reads it as this:
if (i === j) {
  if (j === k)
    console.log("i equals k");
  else
    console.log("i doesn't equal j");   // Attached to the INNER if — wrong!
}
// Since i === j and j !== k, nothing is printed at all, even though
// the misleading indentation suggests "i doesn't equal j" should log.
Always brace nested conditionals

Wrapping every if/else body in { }, even single-statement ones, makes the binding explicit and eliminates this whole class of bug: 

if (i === j) {
  if (j === k) {
    console.log("i equals k");
  }
} else {                              // Unambiguous: this else pairs with the OUTER if
  console.log("i doesn't equal j");
}

else if chains

else if isn't a distinct statement — it's simply what you get when the statement following an else happens to be another if. Written flat, a chain of else ifs reads as a multiway branch, even though it's syntactically just nested if/else underneath: 

if (n === 1) {
  // block #1
} else if (n === 2) {
  // block #2
} else if (n === 3) {
  // block #3
} else {
  // fallback
}

// This is exactly equivalent to the fully nested form below —
// the else-if idiom just avoids the staircase indentation:
if (n === 1) {
  // block #1
} else {
  if (n === 2) {
    // block #2
  } else {
    if (n === 3) {
      // block #3
    } else {
      // fallback
    }
  }
}

switch Fallthrough gotcha

When every branch tests the same expression against a set of constant values, repeating that expression in an else if chain is wasteful. switch evaluates the controlling expression exactly once, then searches its case labels, in source order, for one whose expression matches. Crucially, matching uses === — strict equality, no type coercion — so case 1: never matches the string "1". If nothing matches, execution jumps to a default: label if one exists (it can appear anywhere in the block, not necessarily last); if there's no default, the whole block is skipped. 

function convert(x) {
  switch (typeof x) {
    case "number":              // matches only if typeof x === "number"
      return x.toString(16);
    case "string":
      return `"${x}"`;
    default:
      return String(x);
  }
}

Here's the part that trips people up: case labels mark entry points into the block, not self-contained branches. Once execution starts at a matching label, it keeps running statements line-by-line — through every subsequent case label, ignoring them as if they weren't there — until it hits a break, a return (if inside a function), or the closing brace of the switch. This is called fallthrough, and it is the single most common source of switch-related bugs. 

// BUGGY: someone forgot the break after case 1
function describe(n) {
  let result = [];
  switch (n) {
    case 1:
      result.push("one");
      // <- missing break! Execution falls through into case 2's body too.
    case 2:
      result.push("two");
      break;
    case 3:
      result.push("three");
      break;
    default:
      result.push("many");
  }
  return result;
}

describe(1);   // => ["one", "two"]   -- WRONG, caller almost certainly wanted just ["one"]
describe(2);   // => ["two"]          -- this one is fine
describe(3);   // => ["three"]
// INTENTIONAL fallthrough: multiple case labels sharing one body.
// This is the one pattern where omitting break is idiomatic and safe,
// because there is no code between the grouped labels that could
// accidentally "leak" into the next case.
function isWeekend(day) {
  switch (day) {
    case "Saturday":
    case "Sunday":
      return true;
    case "Monday":
    case "Tuesday":
    case "Wednesday":
    case "Thursday":
    case "Friday":
      return false;
    default:
      throw new Error(`Not a day: ${day}`);
  }
}
Default rule: end every case with break or return

Unless you're deliberately stacking labels with no statements between them (as in the weekend example), always terminate a case body with break or, inside a function, return. Both stop execution from leaking into the next case. Because JavaScript evaluates case expressions at runtime (unlike C/C++/Java, where they must be compile-time constants eligible for a jump-table optimization), you should also avoid putting side effects — function calls, assignments — inside a case expression; only some of them run each pass, which makes such code very hard to reason about.

5.4 Loops

JavaScript has five looping constructs — while, do/while, for, for/of (with its asynchronous for/await/of variant), and for/in — each bending the interpreter's straight-line path back on itself to repeat a block of code.

while

while is the most basic loop: test the condition, and if it's truthy, run the body and test again. If the condition starts out falsy, the body never runs at all. 

let count = 0;
while (count < 10) {
  console.log(count);
  count++;
}
// count must change inside the body (or be otherwise affected) — otherwise
// a truthy condition never becomes falsy and the loop runs forever.

do/while

do/while moves the test to the bottom of the loop, so the body always executes at least once before the condition is checked. It's used far less often than plain while in practice, simply because "run it once no matter what" is a less common requirement than "run it zero or more times." 

function printArray(a) {
  let len = a.length, i = 0;
  if (len === 0) {
    console.log("Empty array");
  } else {
    do {
      console.log(a[i]);
    } while (++i < len);
  }
}

Syntactically, do needs both keywords — do to open the loop and while(...) to close it — and the whole statement must end with a semicolon (a plain while loop needs no trailing semicolon when its body is a brace block).

for

for packages the three moving parts of a typical counting loop — initialize, test, increment — into one header, which is easier to scan than scattering them across the loop body: 

for (let count = 0; count < 10; count++) {
  console.log(count);
}

// Roughly equivalent to (see the try/finally section below for why
// this equivalence with while breaks down once continue is involved):
{
  let count = 0;
  while (count < 10) {
    console.log(count);
    count++;
  }
}

Any of the three header expressions may be omitted (the two separating semicolons are still mandatory), and the comma operator lets you pack multiple variables into the initializer and incrementer: 

// All three clauses omitted individually or combined:
for (;;) { /* infinite loop, same as while (true) */ }

// Traverse a linked list — no initializer needed, "increment" does the walking:
function tail(node) {
  for (; node.next; node = node.next) /* empty */ ;
  return node;
}

// Comma operator drives two loop variables at once:
let sum = 0;
for (let i = 0, j = 10; i < 10; i++, j--) {
  sum += i * j;
}

for/of ES6

for/of loops over the values produced by any iterable object — arrays, strings, Set, Map, and any custom object that implements the iterator protocol (see Iterators & Generators). Plain objects are not iterable by default. 

let data = [1, 2, 3, 4, 5, 6, 7, 8, 9];
let sum = 0;
for (let element of data) {
  sum += element;
}
sum;   // => 45

Array iteration is live: the loop re-checks the array's current length on every pass, so mutating the array from inside the body can change how many times the loop runs — even create an infinite loop if you keep pushing elements onto the end. Strings iterate one Unicode codepoint at a time, not one UTF-16 code unit at a time — the string "I ❤😀" has a .length greater than the number of visible characters because of surrogate pairs, but for/of correctly yields one iteration per actual character. Map yields [key, value] pairs (perfect for destructuring in the loop head), and Set yields its elements. See Collections for both. 

// Destructuring right in the loop head:
let m = new Map([[1, "one"], [2, "two"]]);
for (let [key, value] of m) {
  console.log(key, value);   // 1 "one", then 2 "two"
}

// Frequency count over a string, one codepoint per iteration:
let frequency = {};
for (let letter of "mississippi") {
  frequency[letter] = (frequency[letter] ?? 0) + 1;
}
frequency;   // => { m: 1, i: 4, s: 4, p: 2 }

Plain objects aren't iterable, so plugging one straight into for/of throws. The idiomatic fix is to iterate an array derived from the object using Object.keys(), Object.values(), or Object.entries() (which pairs perfectly with array destructuring): 

let o = { x: 1, y: 2, z: 3 };

for (let v of o) { }
// TypeError: o is not iterable

for (let k of Object.keys(o)) console.log(k);        // "x", "y", "z"
for (let v of Object.values(o)) console.log(v);      // 1, 2, 3
for (let [k, v] of Object.entries(o)) console.log(k, v);  // "x" 1, "y" 2, "z" 3
// Unlike direct array iteration, this snapshot is NOT live — later edits
// to o don't affect a loop already in progress over Object.entries(o).

for/await/of, added in ES2018, is the asynchronous sibling: it consumes an async iterable (such as a network stream), pausing at each iteration until the next value's promise resolves. It's only legal inside an async function. The full mechanics — and what makes an object async-iterable — are covered in Asynchronous JavaScript and Iterators & Generators; here's the shape to recognize: 

async function printStream(stream) {
  for await (let chunk of stream) {
    console.log(chunk);
  }
}

for/in

for/in looks almost identical to for/of but does something entirely different: it loops over the enumerable property names (as strings) of any object — no iterator protocol required. It predates for/of by roughly two decades, which is why it gets the more "natural" in keyword. 

let o = { x: 1, y: 2, z: 3 };
for (let p in o) {
  console.log(p, o[p]);   // "x" 1, "y" 2, "z" 3
}

If the object expression evaluates to null or undefined, for/in simply skips the loop instead of throwing — a small but useful bit of leniency for/of does not share. Two enumeration rules matter in practice: symbol-keyed properties are never visited, and only properties whose internal [[Enumerable]] flag is true are visited — which is why built-in methods like toString() never show up in a for/in loop, even though every object inherits one. Own enumerable properties and inherited enumerable properties both get visited, which is a common source of surprise when a library adds properties to a shared prototype.

Undefined enumeration order under mutation

If the loop body deletes a property that hasn't been visited yet, it will be skipped. If the body adds new properties, whether they get visited during the same pass is unspecified. Avoid mutating an object's own property set from inside a for/in loop over it.

for/of vs. for/in Frequently confused

These two loops share almost identical syntax — swap of for in and the meaning completely changes — which makes mixing them up one of the most common JavaScript bugs, especially with arrays.

let scores = [88, 92, 76];

// If you then try arithmetic assuming for/in gave you numbers, it silently
// breaks because these are strings:
for (let k in scores) {
  console.log(k + 1);   // "01", "11", "21" -- string concatenation, not addition!
}
// Example 2: for/of on a plain object throws; for/in on an array picks
// up more than you bargained for once someone augments Array.prototype
// or the array itself.
let dict = { en: "hello", fr: "bonjour" };

// TypeError: dict is not iterable

let list = ["a", "b", "c"];
list.label = "letters";           // an ordinary enumerable property on the array

Rule of thumb

Arrays, strings, Map, Set → always for...of. Plain objects whose keys you need → either for...in with an Object.prototype.hasOwnProperty guard, or — preferred in modern code — for...of over Object.keys(o), Object.values(o), or Object.entries(o), which sidesteps inherited properties entirely.

5.5 Jumps

Jump statements transfer control to a different point in the source code instead of letting execution fall through to the next line. JavaScript's jumps are break, continue, return, yield, and throw — the first two can target a labeled statement, and the last two carry a value across the jump.

Labeled statements

Any statement may be prefixed with identifier:, giving it a name that a break or continue elsewhere in the program can refer to. Labels live in their own namespace, separate from variable and function names, so reusing an identifier as both is legal (if confusing). A statement cannot repeat a label already used by one of its own enclosing statements, but two unrelated, non-nested statements may share a label, and a single statement can carry more than one label. 

mainloop: while (token !== null) {
  // ...
  continue mainloop;   // jump straight to mainloop's next test
  // ...
}

break and continue, including labeled jumps out of nested loops Nested-loop control flow

Bare break; immediately exits the innermost enclosing loop or switch; it's a syntax error to use it anywhere else. Bare continue; skips the rest of the current iteration's body and jumps to the loop's next iteration — legal only inside a loop, never inside a bare switch. Both come in a labeled form (break label; / continue label;) that targets a specific enclosing labeled statement rather than always the nearest one — essential once loops are nested, because unlabeled break/ continue only ever see the innermost loop.

What continue actually restarts differs by loop type: in a while loop it jumps straight back to the condition test; in a do/while it jumps to the bottom condition test; in a for loop it runs the increment expression first, then retests; and in for/of/for/in it simply advances to the next iterated value or property name. That extra increment step is exactly why a for loop cannot be perfectly simulated by a plain while loop — see the try/finally section below for the one construct that can reproduce it. 

// Example 1: labeled continue skips to the next ROW, not the next cell
let matrix = [[1, 2, NaN], [4, 5, 6], [7, -1, 9]];

outer: for (let x = 0; x < matrix.length; x++) {
  for (let y = 0; y < matrix[x].length; y++) {
    if (Number.isNaN(matrix[x][y])) continue outer;   // abandon this row entirely
    console.log(matrix[x][y]);
  }
}
// Logs 1, 2 (row 0 stops at the NaN), then 4, 5, 6 (all of row 1), then
// the loop reaches row 2...
// Example 2: labeled break abandons BOTH loops at once, and a label
// can even sit on a plain block, purely so break has something to
// jump to that isn't a loop or a switch:
let sum = 0, success = false;

computeSum: if (matrix) {
  for (let x = 0; x < matrix.length; x++) {
    let row = matrix[x];
    if (!row) break computeSum;             // bail out of the whole block
    for (let y = 0; y < row.length; y++) {
      if (row[y] < 0) break computeSum;      // abandon BOTH for-loops at once
      sum += row[y];
    }
  }
  success = true;
}
// Execution resumes right here whether we finished normally or broke out early.
No line break before the label

Because of automatic semicolon insertion, break and continue must be immediately followed by their label on the same line. A newline in between is treated as an implicit semicolon, silently turning your labeled jump into the plain unlabeled form. Neither jump can cross a function boundary either — you can't label a function body and then break to it from inside a nested function.

return

return expression; is legal only inside a function body; it immediately hands control back to the caller, and the invocation expression evaluates to whatever expression produced. A function with no return statement — or a bare return; with no expression — implicitly returns undefined once it falls off the end of its body. 

function square(x) { return x * x; }
square(2);   // => 4

function displayObject(o) {
  if (!o) return;              // early return, no value -- caller gets undefined
  // ... rest of the function ...
}

Like break/continue and their labels, automatic semicolon insertion means the expression after return must start on the same line as the keyword — a line break there silently inserts a semicolon and turns your intended return value; into return; followed by dead code.

yield ES6

yield is return's cousin for generator functions (function*): it produces the next value in a generated sequence without ending the function, suspending execution until the caller asks for another value. It's really an operator, not a statement, but it only ever appears in statement position inside generator bodies: 

function* range(from, to) {
  for (let i = from; i <= to; i++) {
    yield i;   // pause here, hand i to the consumer, resume on next .next()
  }
}
[...range(1, 3)];   // => [1, 2, 3]

The full mechanics of generators, iterators, and what yield can receive back from the caller belong to Iterators & Generators.

throw

throw expression; raises an exception — any value can be thrown, not just an Error, though throwing an Error (or a subclass) is the convention because it carries a name and a message. Throwing immediately halts normal execution and unwinds the call stack looking for a handler. 

function factorial(x) {
  if (x < 0) throw new Error("x must not be negative");
  let f;
  for (f = 1; x > 1; f *= x, x--) /* empty */ ;
  return f;
}
factorial(4);    // => 24
factorial(-1);   // throws Error: x must not be negative

If the code that throws isn't inside a try block with a matching catch, the interpreter checks the next-enclosing block, then the function that called the current one, and so on up the call stack — propagating through both lexical scope and the runtime call stack — until a handler is found or the exception reaches the top and is reported as an uncaught error.

try/catch/finally Control-flow interactions

try/catch/finally is JavaScript's exception-handling statement. The try block contains code that might throw; the optional catch clause runs if — and only if — the try block throws, receiving the thrown value bound to its parameter; the optional finally block runs unconditionally, whether the try completed normally, exited via return/break/continue, was handled by catch, or is still propagating an unhandled exception. A bare try must have at least one of catch or finally; all three clauses require braces even for a single statement. 

try {
  let n = Number(prompt("Enter a positive integer", ""));
  let f = factorial(n);
  alert(`${n}! = ${f}`);
} catch (ex) {
  alert(ex);           // ex is whatever was thrown, e.g. an Error object
}

// ES2019+: a bare catch when you don't need the error value at all
function parseJSON(s) {
  try {
    return JSON.parse(s);
  } catch {             // no (e) required
    return undefined;
  }
}

The subtle part is exactly when finally runs relative to catch, and — more importantly — what happens when finally itself tries to jump somewhere. 

// Deep dive 1: finally silently OVERRIDES a pending return value.
function f() {
  try {
    return "from try";
  } finally {
    console.log("cleanup always runs");
    // No return here, so the try's return value of "from try" survives.
  }
}
f();   // logs "cleanup always runs", returns "from try"

function g() {
  try {
    return "from try";
  } finally {
    return "from finally";   // <- this REPLACES the pending return entirely
  }
}
g();   // => "from finally" -- the string "from try" is discarded, unseen
// Deep dive 2: finally can SWALLOW an in-flight exception completely.
function h() {
  try {
    throw new Error("boom");
  } finally {
    return "swallowed";   // the Error is discarded -- h() returns NORMALLY
  }
}
h();   // => "swallowed" -- no exception ever reaches the caller!

// Same danger with break/continue instead of return:
function scanRows(rows) {
  let seen = [];
  for (let row of rows) {
    try {
      if (row == null) throw new Error("null row");
      seen.push(row);
    } finally {
      continue;   // swallows the "null row" exception on every iteration,
                   // since continue in finally overrides the pending throw
    }
  }
  return seen;
}
Never put return, break, continue, or throw inside finally

Any jump statement executed inside finally — including one reached indirectly by calling a function that itself throws — abandons whatever the try/catch was in the middle of doing, whether that was returning a value, propagating an exception, or breaking out of a loop, and substitutes the new jump instead. This is essentially never what you want. Reserve finally strictly for cleanup — closing a connection, releasing a lock, resetting a flag — and never let it decide control flow.

Used properly (cleanup-only), try/finally without a catch at all is genuinely useful — for example, it's the only way to make a hand-written while loop replicate a for loop's continue semantics, since (as noted above) a continue inside a for loop runs the increment before retesting, while a bare while loop's continue skips the increment entirely: 

// Simulating for(initialize; test; increment) body; with while + try/finally,
// so that a `continue` inside body still runs the increment correctly:
initialize;
while (test) {
  try { body; }
  finally { increment; }
}
// Note this is still not a PERFECT equivalence: a `break` inside body behaves
// slightly differently (it runs one extra increment on the way out here,
// since finally always runs) than break does in a real for loop.

5.6 Miscellaneous statements

with

with (object) statement temporarily adds an object's properties to the front of the scope chain, letting you reference them as if they were bare local variables inside statement. It was meant to reduce repetition when working with deeply nested objects: 

with (document.forms[0]) {
  name.value = "";
  address.value = "";
  email.value = "";
}
// versus, without with:
let f = document.forms[0];
f.name.value = "";
f.address.value = "";
f.email.value = "";
Banned in strict mode, deprecated everywhere else

with is a syntax error under "use strict" (and therefore inside every class body and ES module, since both are automatically strict), and should be treated as forbidden even in legacy non-strict code. The reason is twofold: it makes it impossible for an engine to statically determine whether an identifier refers to a scope variable or a property of object — which disables major optimizations and makes such code noticeably slower — and it makes code much harder to read, since a bare name's meaning now depends on runtime object shape. Prefer assigning the object to a short local variable and accessing properties through it explicitly, as shown above. One more wrinkle: declaring a variable with const, let, or var inside a with body creates an ordinary variable — it does not define a new property on object.

debugger

The debugger statement is a no-op unless a debugger is actively attached, in which case it behaves like a breakpoint — execution pauses right there and you can inspect variables and the call stack in your browser's or runtime's dev tools. It's handy as a temporary, conditional breakpoint you can commit and remove later: 

function f(o) {
  if (o === undefined) debugger;   // pause only for the buggy call site
  // ... rest of the function ...
}

Merely having dev tools installed isn't enough — the debugger console (or an attached inspector) actually has to be open for the breakpoint to fire; otherwise the statement is silently ignored.

"use strict"

"use strict" is a directive, not a true statement — it's just a string-literal expression statement that must appear before any real code, at the very top of a script or the very top of a function body, and it opts the code that follows into strict mode. Strict mode is automatic (no directive needed) inside any class body or ES module — see Modules — which means fully modular, class-based modern code rarely needs to write the directive by hand at all. The concrete rule changes it brings:

5.7 Declarations

const, let, var, function, class, import, and export are, strictly speaking, declarations rather than statements — they don't "make something happen" at runtime so much as define names and bind them to values, classes, or modules before the code around them actually executes. Because they look and read like statements, this book (and this site) treats them informally as part of the same family. 

const TAU = 2 * Math.PI;   // block-scoped constant
let radius = 3;             // block-scoped variable
var circumference = TAU * radius;   // function-scoped, legacy -- prefer let/const

function area(r) {          // hoisted: name + implementation both move to the
  return Math.PI * r * r;   // top of the enclosing scope
}
area(2);                    // fine to call before this point in source order

class Circle {               // NOT hoisted like function -- lives in a
  constructor(r) { this.r = r; }   // temporal dead zone until this line runs
  area() { return Math.PI * this.r ** 2; }
}

import { PI, TAU as Tau } from "./constants.js";
export const goldenRatio = 1.618;
export default class Vector { /* ... */ }

var-declared variables are scoped to the nearest enclosing function, not the nearest block, which is a persistent source of bugs in older code; let and const are properly block-scoped and there's essentially no reason to reach for var in new code. function declarations are fully hoisted — both the name binding and the implementation move to the top of the scope, so calling a function textually before its declaration works fine. class declarations look similar but behave like let: the binding exists but is uninitialized until the class statement actually executes, so referencing it earlier throws a ReferenceError rather than silently returning undefined. import and export connect module-private names to and from other files — see Modules for the several forms each can take, including named imports/exports, aliasing with as, and export default.
