Expressions & Operators

An expression is any phrase of JavaScript that can be evaluated to produce a value. Every program you write is, underneath its statements and control flow, a tree of expressions: literals, variable references, property lookups, function calls, and the operators that glue them together. This chapter works through the full catalog — the primary expressions that stand alone, the compound expressions built from object/array initializers, property access, invocation and object creation, and then the complete operator set: arithmetic, relational, logical, assignment, and a handful of miscellaneous operators that don't fit any other category. Along the way we cover the exact rules JavaScript uses for precedence, associativity, order of evaluation, and the type coercions that make operators like + and == behave in ways that surprise newcomers.

4.1 Primary expressions

A primary expression is the simplest kind there is: it doesn't contain any smaller expressions inside it. Everything more complex in this chapter is built by combining primary expressions with operators or with the compound-expression syntaxes (initializers, property access, invocation) described below. JavaScript has three kinds of primary expression.

The first is a literal — a constant value spelled out directly in your source code: 

1.23        // A number literal
"hello"     // A string literal
/pattern/g  // A regular expression literal

Number and string literal syntax is covered in Types, Values & Variables; regular expression literals get their own full treatment in Regular Expressions. All three forms produce a value the instant the parser sees them — no lookup, no computation, just a value baked into the program text.

The second kind is a small set of reserved keywords that evaluate to a fixed value or, in one case, a context-dependent one: 

true    // The boolean true value
false   // The boolean false value
null    // The null value — "no object"
this    // The "current" object — changes depending on where it appears

this is the odd one out: it isn't a constant at all. Inside a method it evaluates to the object the method was called on; at the top level of a script it refers to the global object (or is undefined in a module or in strict-mode function code). Its full behavior — including how arrow functions deliberately opt out of having their own this — is covered in Functions and Classes.

The third kind of primary expression is a bare identifier reference — a variable, constant, or global name written by itself: 

i           // Evaluates to whatever value the variable i currently holds
sum         // Same, for the variable sum
undefined   // The "undefined" property of the global object — also a keyword-like value
Undeclared identifiers throw, they don't return undefined

When JavaScript sees a bare identifier, it looks it up as a variable, constant, function, or global-object property. If no binding with that name exists anywhere in scope, evaluating it throws a ReferenceError — it does not silently evaluate to undefined. That only happens for a variable that exists but hasn't been assigned a value yet.

4.2 Object and array initializers

Object and array initializers — often called object and array literals — are expressions that create a brand-new object or array every time they're evaluated. They aren't primary expressions in the strict sense, because their contents are themselves subexpressions that compute the property or element values, but they behave like literals in everyday use. Full coverage of both data structures lives in Objects and Arrays; this section is about their expression syntax.

An array initializer is a comma-separated list of expressions inside square brackets: 

[]              // An empty array: zero elements
[1 + 2, 3 + 4]  // A 2-element array: [3, 7]

let matrix = [[1, 2, 3], [4, 5, 6], [7, 8, 9]]; // Nested arrays

// Omitting a value between commas leaves a "hole" — an undefined element,
// but NOT the same as an element explicitly set to undefined:
let sparse = [1, , , , 5]; // 5 elements; indices 1-3 are holes

// A single trailing comma is harmless and does NOT add a hole:
let three = [1, 2, 3,]; // still just 3 elements

Because the element expressions are re-evaluated every time the initializer itself runs (e.g., each time a function containing it is called), an array literal can produce a different array — with different contents — on every evaluation.

Object initializers use curly braces instead of square brackets, and each subexpression is prefixed with a property name and a colon: 

let p = { x: 2.3, y: -1.2 };  // An object with two properties
let q = {};                   // An empty object
q.x = 2.3;
q.y = -1.2;                   // q now has the same properties as p

let rectangle = {             // Object literals can nest
  upperLeft: { x: 2, y: 2 },
  lowerRight: { x: 4, y: 5 },
};

Modern (ES6+) object-literal syntax adds several shortcuts that are worth knowing well because they show up constantly in real code: 

let x = 1, y = 2;

// Shorthand properties: { x } is shorthand for { x: x }
let point = { x, y };            // => { x: 1, y: 2 }

// Computed property names: the bracketed expression is evaluated to
// produce the property NAME, not the value
let propName = "z";
let point3d = { ...point, [propName]: 3 };  // => { x: 1, y: 2, z: 3 }

// Spread in an object literal: copies another object's own enumerable
// properties into the new one (later keys override earlier ones)
let defaults = { timeout: 1000, retries: 3 };
let config = { ...defaults, retries: 5 };   // => { timeout: 1000, retries: 5 }

// Spread in an array literal: expands any iterable in place
let a = [1, 2, 3];
let b = [0, ...a, 4];             // => [0, 1, 2, 3, 4]
let letters = [..."abc"];         // => ["a", "b", "c"] — strings are iterable too
Spread copies shallowly

Both object-spread and array-spread copy top-level properties or elements only. If a property's value is itself an object or array, the copy shares a reference to that same nested value — mutating it through the copy mutates the original too. Spread is not a deep clone.

Because array spread works on any iterable, not just arrays, it composes naturally with the generator and iterator machinery covered in Iterators & Generators.

4.3 Function definition expressions

A function definition expression defines a function and evaluates to that newly created function value — in the same sense that an object initializer is an "object literal," a function expression is a "function literal." The classic form uses the function keyword, a parenthesized, comma-separated parameter list, and a body in curly braces: 

// An anonymous function expression assigned to a variable
let square = function(x) { return x * x; };

// Function expressions can optionally carry their own name, useful
// for stack traces and for recursive references from inside the body
let factorial = function fact(n) { return n <= 1 ? 1 : n * fact(n - 1); };

// ES6 arrow function syntax — more compact, and with different `this` binding
let cube = x => x * x * x;

A function can also be defined with a function statement rather than an expression — the difference matters for hoisting and is covered alongside arrow functions, default parameters, rest parameters, and closures in full in Functions.

4.4 Property access expressions

A property access expression evaluates to the value of an object property or an array element. JavaScript has two syntaxes for it: 

expression.identifier
expression[expression]

The dot form requires a literal identifier — it can't have spaces, punctuation, or start with a digit, and you must know the name when you write the code. The bracket form takes any expression, converts it to a string, and looks up the property with that name; it's required whenever the name is computed at runtime or isn't a legal identifier (numeric array indices, keys with spaces, etc.): 

let o = { x: 1, y: { z: 3 } };
let a = [o, 4, [5, 6]];

o.x         // => 1
o.y.z       // => 3
o["x"]      // => 1   (same as o.x)
a[1]        // => 4
a[2]["1"]   // => 6   (bracket index is converted to a string internally)
a[0].x      // => 1

In both forms, the expression before the . or [ is evaluated first. If it evaluates to null or undefined — the only two JavaScript values that cannot have properties — the whole expression throws a TypeError. If the named property simply doesn't exist on an object that is valid, the result is undefined, not an error.

4.4.1 Conditional property access ES2020

Optional chaining — ?. for a named property and ?.[…] for a computed one — guards against exactly the null/undefined TypeError described above. If the expression to the left of ?. is nullish, the whole property access evaluates to undefined instead of throwing, and the right-hand side is never even looked at. 

let a = { b: null };

a.b.c    // TypeError: Cannot read properties of null (reading 'c')
a.b?.c   // => undefined — short-circuits cleanly, no error
The part everyone gets wrong: it short-circuits the WHOLE chain, not just one link

?. isn't a local "null-safe dot" that only protects the one access it's attached to. The instant evaluation hits a nullish value at a ?., the entire remaining expression — everything chained after it, including subsequent ./[]/() that have no ? of their own — is abandoned and the whole thing evaluates to undefined. Wrapping part of the chain in parentheses defeats this, because the parenthesized subexpression is forced to fully resolve (to undefined) before the outer access is attempted on it — and accessing a property of undefined throws. 

let a1 = { b: null };
a1.b?.c.d     // => undefined — a1.b is null, so ?.c short-circuits the ENTIRE
              //    rest of the chain; .d is never attempted
(a1.b?.c).d   // TypeError! The parens force a1.b?.c to resolve to undefined
              //    FIRST, and now .d is a plain (non-optional) access on it

// Short-circuiting also skips side effects further down the chain — including
// computed keys and function arguments — not just further property reads:
let a2;                 // undefined
let calls = 0;
function next() { calls++; return calls; }

a2?.[next()].method(next())  // => undefined
calls                         // => 0 — neither next() call ever ran

// Compare to what happens without the guard:
let index = 0;
try { a2[index++]; } catch (e) { /* TypeError */ }
index                          // => 1 — the increment DID happen before the throw
a2?.[index++];                 // => undefined, and...
index                          // => 1 — this time it did NOT increment; ?.[ ] never evaluated it

Optional chaining also composes with itself for chains where more than one link might be missing: 

let b = { b: {} };
b.b?.c?.d   // => undefined — b.b exists, but .c doesn't, so the second
            //    ?. is what catches it and stops further evaluation

4.5 Invocation expressions

An invocation expression calls (executes) a function or method. It's a function expression, followed by an open parenthesis, zero or more comma-separated argument expressions, and a close parenthesis: 

f(0)             // f is the function expression; 0 is the argument
Math.max(x, y, z) // Math.max is the function; x, y, z are the arguments
a.sort()         // a.sort is the function; no arguments

Evaluation order: the function expression is evaluated first, then each argument expression left-to-right, then — if the function expression's value isn't callable — a TypeError is thrown before any function body runs. Otherwise the arguments are bound to parameters and the body executes; a return statement's value becomes the expression's value, and with no explicit return the value is undefined. What happens when argument count and parameter count don't match is covered in Functions.

When the expression before the parentheses is itself a property access — a.sort() — the call is a method invocation, and the object on the left of the dot becomes the value of this for the duration of the call. That's the mechanism behind essentially all of JavaScript's object-oriented style; see Classes for the full picture.

4.5.1 Conditional invocation ES2020

?.() pairs with optional chaining: if the expression to the left of the ?. is null or undefined, the entire invocation evaluates to undefined instead of throwing — and, crucially, none of the argument expressions inside the parentheses are evaluated either, so any side effects in them are skipped along with the call: 

// Before ES2020, an optional callback parameter needed an explicit guard:
function square(x, log) {
  if (log) log(x);
  return x * x;
}

// With ?.(), the guard collapses into the call itself:
function square2(x, log) {
  log?.(x);          // calls log(x) only if log is not null/undefined
  return x * x;
}

let f = null, x = 0;
f?.(x++);   // => undefined; f is null so the call (and x++) never happens
x           // => 0 — the argument expression was never evaluated
?.() only checks for nullish, not "is this even a function"

?.() guards solely against null/undefined on the left. If that value is defined but isn't callable — a number, a plain object — the call still throws a TypeError. It's a null guard, not a type guard. It's also worth keeping the three related forms straight: o.m() requires both o and o.m to exist; o?.m() tolerates a missing/nullish o but still requires m to exist and be callable if o is present; o.m?.() requires o to exist but tolerates a missing/nullish m.

4.6 Object creation expressions

An object creation expression — new plus an invocation — creates a new object and runs a constructor function to initialize it. With no arguments, the empty parentheses can be omitted entirely: 

new Object()
new Point(2, 3)

new Object   // Same as new Object() — parens optional with zero arguments
new Date     // Same as new Date()

The value of the whole expression is the newly created object. Everything about how constructors initialize instances and set up the prototype chain is covered in Classes.

4.7 Operator overview

Operators combine one or more operand expressions into a new, larger expression. Most are written with punctuation (+, =), and a few are written as keywords (delete, instanceof, typeof, in, void) — keyword operators behave exactly like punctuation operators, just spelled with letters. Every operator has three defining properties, covered in the subsections below: how many operands it takes (arity), in what order operators of different precedence combine (precedence), and in what order operators of the same precedence combine (associativity).

4.7.1 Number of operands

Most operators — *, +, &&, ==, and so on — are binary: they take two operands and combine them. JavaScript also has a good number of unary operators that act on a single operand — -x, typeof x, !x, delete x.y — and exactly one ternary operator that takes three: the conditional operator ?:.

4.7.2 Operand and result types

Some operators are polymorphic — they accept operands of any type (==, &&) — but most expect a specific type and will coerce their operands to it as needed. * expects numbers, so "3" * "5" is legal and evaluates to the number 15, because both string operands convert to numbers first. Since every JavaScript value is either truthy or falsy, any operator that "expects" a boolean — like the test in ?: — actually accepts an operand of any type at all. Several operators in the reference table below are documented as expecting an lvalue — a historical term for "an expression legal on the left side of an assignment": a variable, an object property, or an array element. =, ++, --, and delete all require one.

4.7.3 Operator side effects

Evaluating an expression like 2 * 3 never changes any state — run it a thousand times and every future computation is unaffected. A handful of operators are different: assignment (plain and compound), ++/-- (which are implicit assignments), and delete (which removes a property, similar to — but distinct from — assigning it undefined) all mutate the program's state as a side effect of evaluation. No other operators have side effects directly, though a function call or new expression can obviously have arbitrary side effects buried inside the function body it runs.

4.7.4 Operator precedence

Precedence determines which operator "grabs" its operands first when two different operators compete for the same value. In w = x + y*z, * binds tighter than +, so y*z is computed before the addition — and =, sitting at the very bottom of the precedence table, always runs last. Parentheses override precedence explicitly: w = (x + y) * z forces the addition first. Note also that property access, computed access, and invocation — ., [], () — bind tighter than every operator in the table below, which is why typeof my.functions[x](y) applies typeof to the result of the property lookup, indexing, and call, not to my alone.

4.7.5 Operator associativity

Associativity governs the order in which operators of the same precedence combine. Left-to-right ("L" above) means the leftmost operation happens first: w = x - y - z means w = ((x - y) - z). Right-to-left ("R") means the opposite — and it applies to exponentiation, the unary operators, assignment, and the conditional operator: 

let y = a ** b ** c;   // same as a ** (b ** c) — right-to-left
let xx = ~-y;           // same as ~(-y)
let w = x = y = z;      // same as x = (y = z) — chained assignment, right-to-left
let q = a ? b : c ? d : e ? f : g; // same as a ? b : (c ? d : (e ? f : g))

4.7.6 Order of evaluation

Precedence and associativity decide which operations combine with which — they say nothing about the order subexpressions are actually evaluated in. That order is always strictly left to right, regardless of how parentheses or precedence reshape which values get combined with which operator. In w = x + y * z, w is evaluated first (to determine where to assign), then x, then y, then z — parentheses can change which operations happen on those values, but never the left-to-right order in which the subexpressions themselves are visited. This only matters when a subexpression has a side effect that a later subexpression depends on — e.g., if evaluating x increments a variable that z also reads.

Deep dive: precedence and associativity gotchas Hard

Two mistakes account for most real-world precedence bugs.

1. typeof binds tighter than you'd expect, but member access binds tighter still. Because typeof is a unary operator sitting near the top of the table, it grabs only the expression immediately next to it under normal precedence rules — but property access, computed access, and calls outrank everything in the operator table, so they're resolved first regardless: 

let obj = { getValue: () => 42 };
typeof obj.getValue()     // => "number" — the call and property access happen
                           //    FIRST, then typeof inspects the *result*, 42

typeof obj.getValue       // => "function" — no call here, so typeof inspects
                           //    the function itself instead

// Where typeof genuinely binds "too tight" is against operators BELOW it:
typeof 2 + 3               // => "number3"! Parsed as (typeof 2) + 3
                            //    ("number" + 3, string concatenation), NOT
                            //    typeof (2 + 3)
typeof (2 + 3)              // => "number" — parentheses fix it

2. Chained assignment silently reads right-to-left, which bites when the left-hand targets aren't independent. 

// Safe: three independent variables, right-to-left is invisible
let i, j, k;
i = j = k = 0;     // k = 0, then j = (that result), then i = (that result)

// Subtle: when a later target's evaluation depends on an earlier assignment
let arr = [0, 0];
let n = 0;
arr[n] = n = 1;    // Is arr[0] or arr[1] set? The LEFT-HAND target "arr[n]" is
                   // evaluated (index resolved to 0) before the right side
                   // runs, so this sets arr[0] = 1, THEN n becomes 1 —
                   // arr is now [1, 0], not [0, 1]. Rewrite as two statements
                   // if this is ever load-bearing for readability.

4.8 Arithmetic expressions

The core arithmetic operators are ** (exponentiate), *, /, % (remainder), +, and -. All but + (covered in its own subsection below because of its string behavior) simply convert both operands to numbers and compute the obvious result; anything that can't convert to a number becomes NaN, and a NaN operand almost always makes the whole result NaN. Most of these operators also accept BigInt operands, but never a mix of BigInt and regular number in the same expression — that throws a TypeError. 

5 / 2         // => 2.5 — JS has one numeric type, so division is never truncated
5 / 0         // => Infinity — not an error
0 / 0         // => NaN     — not an error
5 % 2         // => 1
-5 % 2        // => -1     — result takes the sign of the FIRST operand
6.5 % 2.1     // => 0.2    — % works on floats too, not just integers

2 ** 2 ** 3   // => 256 (2 ** 8), NOT 64 (4 ** 3) — ** is right-associative
// -3 ** 2    // SyntaxError — write (-3) ** 2 or -(3 ** 2) instead

Math.pow() has existed since the earliest versions of JavaScript and computes exactly what ** does; ** itself is a much newer (ES2016) addition to the language.

4.8.1 The + operator Hard

+ is the one arithmetic operator with two entirely different jobs: numeric addition and string concatenation. Which one happens is decided by a fixed, three-step algorithm that runs every single time + is evaluated — it is not "guess the intent," it's a strict procedure:

  1. If either operand is an object, convert it to a primitive first, using the object-to-primitive algorithm from Types, Values & Variables. Date objects convert via their toString() method; every other built-in object tries valueOf() first and falls back to toString() only if valueOf() doesn't return a primitive (which, for most plain objects, it never does — so most objects effectively convert via toString(), yielding "[object Object]").
  2. After that conversion, if either operand is now a string, the other operand is converted to a string too, and the result is concatenation.
  3. Otherwise — neither operand is or became a string — both convert to numbers (or to NaN) and the result is numeric addition.

The critical detail is the ordering: object-to-primitive conversion always happens first, before the string-vs-number decision is even made. This matters because a custom valueOf() can redirect an object that "looks stringy" into numeric addition instead: 

1 + 2          // => 3         both already numbers: add
"1" + "2"      // => "12"      both already strings: concatenate
"1" + 2        // => "12"      one string: 2 converts to "2", concatenate
1 + {}         // => "1[object Object]"   {} has no useful valueOf(), so it
               //                          falls back to toString()
true + true    // => 2         booleans convert to numbers: 1 + 1
2 + null       // => 2         null converts to the number 0
2 + undefined  // => NaN       undefined converts to NaN, and NaN poisons +

// Object-to-primitive conversion runs BEFORE the string check — an object
// with a numeric valueOf() takes the addition path even next to nothing
// stringy:
let money = {
  valueOf()  { return 100; },
  toString() { return "$100"; },
};
money + 1        // => 101        valueOf() wins: numeric addition
`${money}`       // => "$100"     template literals force toString() instead

// Date is the deliberate exception: it prefers toString() over valueOf()
let d = new Date(2024, 0, 1);
d + 1            // => "Mon Jan 01 2024...1" — concatenation, not epoch-ms + 1
+d               // => a number (unary + forces numeric conversion, calling valueOf())

One more consequence worth internalizing: because + is left-associative, grouping visibly changes the result once strings and numbers are mixed in the same chain: 

1 + 2 + " blind mice"    // => "3 blind mice"   — 1+2 (numbers) first, THEN concatenate
1 + (2 + " blind mice")  // => "12 blind mice"  — 2 + string concatenates first,
                          //                       then 1 concatenates with that

4.8.2 Unary arithmetic operators

Unary +, unary -, ++, and -- all convert their single operand to a number (they never do string concatenation, unlike binary +), and all are high-precedence and right-associative.

  • Unary plus (+x) converts its operand to a number and returns it — a quick numeric-coercion idiom. It cannot be used on a BigInt.
  • Unary minus (-x) converts to a number, then flips its sign.
  • Increment (++) requires an lvalue operand. Pre-increment (++x) increments first and evaluates to the new value; post-increment (x++) evaluates to the old value and increments as a side effect afterward: 
    let i = 1, j = ++i;   // i is 2, j is 2 (pre: increments THEN returns)
let n = 1, m = n++;   // n is 2, m is 1 (post: returns THEN increments)

// x++ is NOT the same as x = x + 1: ++ always numerically increments,
// even on a string that + would have concatenated:
let s = "1";
++s        // => 2 (number)
s + 1      // => "11" (string concatenation, since s is still "1" here)
  • Decrement (--) is the mirror image of ++, with the same pre/post distinction.
Automatic semicolon insertion trap

You cannot put a line break between a postfix ++/-- and the operand before it — JavaScript's automatic semicolon insertion will treat the operand as a complete statement and silently insert a semicolon before the operator, changing your program's meaning.

4.8.3 Bitwise operators

The bitwise operators treat their numeric operands as 32-bit integers and operate bit by bit, rather than on the number as a whole. They convert each operand to a number, then to a 32-bit integer (dropping any fractional part and any bits beyond the 32nd); the shift operators additionally require their right-hand operand to be between 0 and 31, achieved by dropping all but its lowest 5 bits. NaN, Infinity, and -Infinity all convert to 0 under this process — none of them throw. Most of these operators (all except >>>) also accept BigInt operands. 

0x1234 & 0x00FF   // => 0x0034  AND: bit set only if set in BOTH operands
0x1234 | 0x00FF   // => 0x12FF  OR: bit set if set in EITHER operand
0xFF00 ^ 0xF0F0   // => 0x0FF0  XOR: bit set if set in EXACTLY ONE operand
~0x0F             // => -16     NOT: flips every bit (equivalent to -x - 1)

7 << 2            // => 28      shift left = multiply by 2 per position
7 >> 1            // => 3       shift right, sign-preserving = divide by 2
-7 >> 1           // => -4      sign bit is preserved on the way in
-1 >>> 4          // => 0x0FFFFFFF   zero-fill shift ignores sign entirely
-1 >> 4           // => -1      (contrast with >>> above)

These are rarely needed in application code and mostly show up in low-level bit-flag manipulation, hashing, or binary protocol work; if you're not already comfortable with two's-complement integers, it's safe to treat this subsection as reference material rather than something to memorize up front.

4.9 Relational expressions

Relational operators test a relationship between two values and always produce a boolean — they're the operators that drive if, while, and the rest of the control-flow statements covered in Statements.

4.9.1 Equality and inequality operators

=== (strict equality) and == (loose equality) both test "sameness," using different definitions; !== and != are their exact negations. === never converts types — if the operands aren't already the same type, they're simply unequal. Its rules:

  • Different types → never equal.
  • null === null and undefined === undefined → equal (to themselves only — null === undefined is false).
  • Same boolean value → equal.
  • NaN is never equal to anything, including itself. Test for it with Number.isNaN(x) or x !== x, never x === NaN.
  • Same number and same value → equal; 0 === -0 is true (the one exception where "same value" is generous).
  • Same sequence of UTF-16 code units → equal. No Unicode normalization is performed, so two visually identical strings built from different code-unit sequences are not equal.
  • Objects, arrays, and functions compare by reference: only identical to themselves, never to a different object with identical contents.

== runs the same strict comparison when the types already match; when they don't, it performs at most one round of type conversion and retries — it's a fixed lookup table, not a fuzzy or recursive process:

  • null == undefined is true (and each equals only the other, plus itself, under ==).
  • number vs. string → the string converts to a number.
  • boolean vs. anything → the boolean converts to 0/1 first, then the comparison is retried from scratch.
  • object vs. number-or-string → the object converts to a primitive (same object-to-primitive algorithm as +: valueOf() preferred, toString() for Date), then retried.
  • anything else → not equal.
"1" == true   // => true — true becomes 1, "1" becomes 1, 1 === 1
null == undefined  // => true
null === undefined // => false — different types under strict equality
NaN === NaN   // => false
0 === -0      // => true
Default to ===

=='s implicit conversions are a well-documented source of bugs. Use ===/!== by default and reach for ==/!= only for the one genuinely useful case: treating null and undefined as interchangeable with x == null.

4.9.2 Comparison operators

<, >, <=, and >= compare order. Any operand that's an object first converts to a primitive (same algorithm as above); after that, if both operands are strings, they're compared alphabetically by UTF-16 code unit value — otherwise both convert to numbers and compare numerically. If either operand is or becomes NaN, every one of the four comparison operators returns false, with no exception. 

11 < 3       // => false  both numbers: numeric compare
"11" < "3"   // => true   both strings: "1" < "3" alphabetically (code-unit order!)
"11" < 3     // => false  mixed: "11" converts to 11, numeric compare
"one" < 3    // => false  "one" converts to NaN, and NaN comparisons are always false

"Zoo" < "aardvark"  // => true! Capital letters sort BEFORE all lowercase
                     //    letters in UTF-16/ASCII code-unit order

For real natural-language sorting, use String.prototype.localeCompare() or the Intl.Collator class (see Dates, JSON, Intl & Utilities), or normalize case first with toLowerCase()/toUpperCase(). Note also that <= and >= aren't literally defined in terms of == — <= means "not greater than" and >= means "not less than," which only differs from the intuitive reading when NaN is involved (all four operators return false for it, rather than <= somehow being "more true" than <).

4.9.3 The in operator

in expects a property name (string or symbol) on the left and an object on the right; it's true if that object has a property with that name, own or inherited: 

let point = { x: 1, y: 1 };
"x" in point         // => true
"z" in point         // => false
"toString" in point  // => true — inherited from Object.prototype!

let data = [7, 8, 9];
"0" in data          // => true — array indices are property names, as strings
1 in data            // => true — numbers are converted to strings
3 in data            // => false — no element at index 3

This is a different question from obj.key !== undefined: in also returns true for a property that genuinely exists but whose value literally is undefined.

4.9.4 The instanceof operator

instanceof expects an object on the left and a constructor function on the right; it walks the object's prototype chain (see Objects) looking for right.prototype, returning true if found — which also makes it "superclass-aware": 

let d = new Date();
d instanceof Date    // => true
d instanceof Object  // => true — every object is an instance of Object
d instanceof Number  // => false

let arr = [1, 2, 3];
arr instanceof Array  // => true
arr instanceof Object  // => true
arr instanceof RegExp  // => false

If the left operand isn't an object, instanceof simply returns false; if the right operand isn't a function-like object with a prototype, it throws a TypeError.

4.10 Logical expressions

&&, ||, and ! perform Boolean algebra, usually combining relational expressions into larger conditions. Understanding them fully requires the truthy/falsy rules from Types, Values & Variables — the falsy values are exactly false, null, undefined, 0, -0, NaN, and ""; everything else, including every object, is truthy.

4.10.1 && and || return operand values, not just booleans Hard

At the simplest level, with boolean operands, && and || behave exactly like every other C-family language's AND and OR. But their real behavior — the one worth understanding deeply — is this: neither operator ever actually computes a fresh boolean. Each evaluates its left operand first, and depending on whether that value is truthy or falsy, either short-circuits and returns that exact left-hand value untouched, or evaluates and returns the exact right-hand value. No conversion to true/false happens at any point. 

// && : if the left side is falsy, return it AS-IS, without touching the right.
// If the left side is truthy, evaluate and return the right side.
let o = { x: 1 };
let p = null;
o && o.x   // => 1     o is truthy, so the expression becomes o.x
p && p.x   // => null  p is falsy — p.x is NEVER evaluated, avoiding a TypeError

// || : if the left side is truthy, return it AS-IS. Otherwise evaluate and
// return the right side.
let max = maxWidth || preferences.maxWidth || 500;  // first truthy value wins

// Short-circuiting is often used purely for its control-flow effect:
if (a === b) stop();       // equivalent, idiomatic JS:
(a === b) && stop();      // stop() only runs if a === b is truthy
Careful with side effects on the right-hand side

Because the right operand of &&/|| may or may not run, any assignment, increment, or function call placed there executes conditionally — which is exactly the short-circuiting idiom above when done on purpose, and a subtle bug when done by accident.

! is different from both: it's unary, and it does convert its operand to boolean before inverting — so ! always yields a genuine true/false, and !!x is the standard idiom for "coerce anything to its boolean equivalent." As a high-precedence unary operator, inverting a compound expression like p && q requires explicit parens: !(p && q). Two useful identities (De Morgan's laws), true for every p and q: 

!(p && q) === (!p || !q)   // => true, always
!(p || q) === (!p && !q)   // => true, always

4.13.2 ?? vs. ||: nullish, not falsy ES2020

||'s "pick the first truthy operand" idiom has a well-known flaw: 0, "", and false are all falsy, so || discards them even when they're legitimate, intentional values rather than "nothing was provided." The nullish coalescing operator ?? fixes exactly this: it only falls through to its right operand when the left is null or undefined — every other falsy value is treated as defined and returned as-is. Like &&/||, it short-circuits: the right operand is evaluated only when needed. 

let options = { timeout: 0, title: "", verbose: false, n: null };

options.timeout ?? 1000      // => 0      — 0 is a real, intentional value
options.timeout || 1000      // => 1000   — WRONG: || can't distinguish 0 from "unset"

options.title ?? "Untitled"  // => ""     — empty string is respected as-is
options.verbose ?? true      // => false  — false is respected as-is
options.n ?? 10              // => 10     — n IS null, so ?? falls through here
options.missing ?? "default" // => "default" — undefined also falls through

// The classic default-parameter bug this fixes:
function setVolume(level) {
  level = level || 50;   // BUG: setVolume(0) silently becomes 50
}
function setVolumeFixed(level) {
  level = level ?? 50;   // correct: only null/undefined trigger the default
}
setVolumeFixed(0);   // level stays 0, as intended

If a has no side effects, a ?? b is exactly equivalent to (a !== null && a !== undefined) ? a : b.

Mixing ?? with &&/|| requires parentheses

a ?? b || c is a flat-out SyntaxError — the spec deliberately leaves ??'s precedence relative to &&/|| undefined, so you must write (a ?? b) || c or a ?? (b || c) and mean it.

4.11 Assignment expressions

= assigns a value to a variable or property. Its left operand must be an lvalue; its right operand may be any value. The expression's value is the right-hand value, and as a side effect that value is also stored into the lvalue: 

i = 0;      // Set i to 0 — and the expression "i = 0" itself evaluates to 0
o.x = 1;    // Set property x of o to 1

// Because assignment IS an expression with a value, it can be embedded in a
// larger expression — usually with parentheses, since = binds so loosely:
(a = b) === 0    // assign b to a, then compare the result to 0

// = is right-associative, enabling chained assignment:
i = j = k = 0;   // k = 0 first, then j = 0, then i = 0

4.11.1 Assignment with operation

Every binary arithmetic and bitwise operator has a compound "operate and assign" form: total += salesTax means total = total + salesTax — including +='s string-concatenation behavior when the operands are strings. The full set: **=, *=, /=, %=, +=, -=, <<=, >>=, >>>=, &=, ^=, |=.

a op= b isn't always exactly a = a op b

They differ when a has a side effect, because the compound form evaluates a only once, while the expanded form evaluates it twice: 

let data = [1, 2, 3], i = 0;
data[i++] *= 2;                     // i becomes 1; data[0] becomes 2
// vs.
let data2 = [1, 2, 3], i2 = 0;
data2[i2++] = data2[i2++] * 2;      // i2 becomes 2 (incremented TWICE);
                                     // reads data2[0] but writes to data2[1]!

4.11.2 Destructuring assignment as an expression

Array and object patterns can appear on the left of = to unpack multiple values at once — and because it's still an assignment expression, the whole thing still evaluates to the assigned (right-hand) value: 

let [a, b] = [1, 2];              // a = 1, b = 2
[a, b] = [b, a];                   // swap, no temporary variable needed
let { x, y: renamed, ...rest } = { x: 1, y: 2, z: 3, w: 4 };
// x = 1, renamed = 2, rest = { z: 3, w: 4 }

let result = ([a, b] = [10, 20]);  // result is [10, 20] — the whole
                                    // assignment expression's value

Destructuring targets, defaults, and nested patterns are covered fully in Objects and Arrays; the point to take from this chapter is that destructuring is still fundamentally an assignment expression with the usual semantics — it has a value, not just a side effect.

4.12 Evaluation expressions

eval() parses and executes a string as JavaScript source, returning the value of the last expression or statement it evaluated: 

eval("3 + 2")   // => 5

eval is technically a function, but it's documented here as an honorary operator, because the language spec treats it as one: modern engines cannot safely optimize any function that calls eval(), since the evaluated string might read or write that function's local variables. To limit the damage, the spec distinguishes a direct eval — a call written literally as eval(...) — from an indirect eval, any call reached through another reference to the same function (e.g., assigning let f = eval; and calling f(...)). Only a direct eval runs in the caller's local variable scope; an indirect eval always runs as if it were independent, top-level global code, and cannot read or write local variables at all: 

const geval = eval;                // an indirect reference to eval
let x = "global", y = "global";

function f() {
  let x = "local";
  eval("x += 'changed';");         // DIRECT eval: sees and mutates local x
  return x;
}
function g() {
  let y = "local";
  geval("y += 'changed';");        // INDIRECT eval: runs against globals only
  return y;                        // local y is untouched
}

f(); x   // => "localchanged", "global"    (local x mutated, global x untouched)
g(); y   // => "local", "globalchanged"    (opposite: global y mutated)

Variables declared with var inside an evaluated string leak into whichever scope the eval runs in (local for direct, global for indirect); let and const declarations inside the string are always scoped to the eval itself and never escape it. In strict-mode code — or when the evaluated string itself starts with "use strict" — eval() always gets its own private variable environment, even when called directly: it can read and modify the caller's existing locals, but it can no longer declare new ones into the caller's scope. Strict mode goes further still, effectively reserving the identifier eval: you cannot reassign it, and you cannot name a variable, parameter, or function eval.

Avoid eval() in real code

It defeats engine optimizations for any function that uses it, and it's a serious security liability the moment any part of the evaluated string can be influenced by user input — there's no reliable way to sanitize arbitrary JavaScript source. Many sites disable it outright via a Content-Security-Policy header. Almost every legitimate use case has a safer alternative (dynamic property access, Function constructors used with fully trusted input, JSON parsing for data).

4.13 Miscellaneous operators

4.13.1 The conditional operator (?:)

JavaScript's only ternary operator: cond ? ifTrue : ifFalse. The first operand is evaluated and treated as a boolean; depending on its truthiness, exactly one of the remaining two operands is evaluated and becomes the result — never both: 

let abs = x > 0 ? x : -x;

greeting = "hello " + (username ? username : "there");
// equivalent to:
// if (username) { greeting = "hello " + username; }
// else           { greeting = "hello there"; }

It's right-associative, which is what lets chained ternaries read as an if/else-if/else ladder (see the associativity example earlier in this chapter).

4.13.3 The typeof operator

typeof is unary and returns a string naming its operand's type:

Operandtypeof result
undefined"undefined"
null"object" (a 25+ year-old bug, frozen into the spec forever)
true/false"boolean"
any number, including NaN"number"
any BigInt"bigint"
any string"string"
any symbol"symbol"
any function"function"
any other object/array"object"

Because every non-function object collapses to the single result "object", typeof is only useful for distinguishing primitives from objects and from each other — not for telling object classes apart. For that, reach for instanceof (§4.9.4 above) or a constructor check, both covered further in Classes. See the precedence deep dive above for the classic typeof 2 + 3 parsing surprise.

4.13.4 The delete operator

delete removes a property from an object (or an element from an array) entirely — it does not merely set the value to undefined. Its operand must be an lvalue; on anything else it's a no-op that returns true. 

let o = { x: 1, y: 2 };
delete o.x;     // => true
"x" in o;       // => false — the property is genuinely gone
typeof o.x;     // => "undefined" — but so is any nonexistent property
delete o.x;     // => true again — deleting a nonexistent property still "succeeds"

let a = [1, 2, 3];
delete a[2];    // => true — removes the element...
a.length;       // => 3   — ...but length is unchanged; a is now SPARSE
                //           (a "hole" at index 2 — see the Arrays chapter)

delete Object.prototype;  // => false (non-strict) — non-configurable properties
                           //    can't be deleted; throws TypeError in strict mode

// delete o;  // => false, or SyntaxError in strict mode — bare variable/function
              //    identifiers were never deletable; only property access
              //    expressions are valid delete targets

4.13.6 The void operator

void expr evaluates its operand, discards the value, and always yields undefined. It only makes sense on an operand with a side effect, since the value itself is thrown away. It's rare in hand-written code, occasionally showing up to force an expression-bodied arrow function to return nothing on purpose: 

let counter = 0;
const increment = () => void counter++;  // discards counter++'s value
increment();   // => undefined
counter;       // => 1 — the side effect still happened

4.13.7 The comma operator (,)

The comma operator evaluates its left operand, discards that value, evaluates its right operand, and returns that. It's essentially useless unless the left side has a side effect, and the one place it shows up idiomatically is squeezing multiple update expressions into a single for-loop header (the commas separating multiple let declarations are ordinary declaration syntax, not this operator — only the one in the update clause below is the comma operator): 

for (let i = 0, j = 10; i < j; i++, j--) {
  console.log(i + j);  // always 10 — i and j move toward each other in lockstep
}

Spread in function calls

The same ... spread syntax used in array literals (§4.2 above) also works directly inside a function call's argument list, expanding any iterable into individual positional arguments at call time: 

function sum3(a, b, c) { return a + b + c; }
let nums = [1, 2, 3];
sum3(...nums);            // => 6, same as sum3(1, 2, 3)
Math.max(...[3, 1, 4, 1, 5]); // => 5

// It composes with ordinary arguments and multiple spreads freely:
function log(label, ...values) { console.log(label, values); }
log("scores:", ...[10, 20], 30, ...[40]);  // "scores:" [10, 20, 30, 40]

This is the modern replacement for the old fn.apply(thisArg, argsArray) idiom, and it pairs naturally with the rest-parameter syntax on the receiving side, covered in Functions.

4.13.5 The await operator

await takes a Promise operand and makes code behave as though it paused until that promise settles, without actually blocking the thread or preventing other work from proceeding — its value is the promise's fulfillment value, and it's legal only inside functions declared async. It's foundational enough to asynchronous JavaScript that it gets full treatment of its own in Asynchronous JavaScript rather than here.

4.14 Summary

Expressions are the phrases JavaScript programs are built from, and every expression evaluates to a value — sometimes alongside a side effect like a variable assignment. Primary expressions (literals, keywords, bare identifiers) combine via property access, invocation, object creation, and the full operator set into arbitrarily complex expressions, governed by strict, fully specified rules for precedence, associativity, and left-to-right evaluation order. A few points are worth carrying forward as you move on to Statements: the + operator's dual add/concatenate identity depends on an object-to-primitive conversion that runs before the string-vs-number decision is even made; &&, ||, and ?? all return one of their actual operand values rather than a fresh boolean, and all three short-circuit — skipping evaluation (and any side effects) of whatever they don't need; and optional chaining (?., ?.[], ?.()) short-circuits an entire expression chain the instant it hits a nullish value, not just the one access it's attached to.
