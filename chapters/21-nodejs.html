Node.js

Node is JavaScript with bindings to the operating system: it can read and write files, execute other programs, and talk to the network directly, without any of the sandboxing a browser imposes. It is a shell-scripting replacement, a general-purpose language runtime, and — because of a single-threaded, asynchronous-by-default event loop borrowed straight from the browser — a popular way to write highly concurrent servers. This page is long because the API surface is large: every major module (fs, streams, HTTP, child processes, threads) ships with its own set of conventions, and the gotchas hide in the differences between them.

16.1 Node programming basics

A Node program is, at the top level, just a JavaScript file executed from top to bottom by the node executable. There is no window, no DOM, and no default way to display anything — instead Node hands you a process object and a module system for structuring larger programs.

Console output isn't just for debugging

In a browser, console.log() is a developer-tools convenience. In Node it is the ordinary way for a program to produce output: it writes to the stdout stream, the same stream a Unix command line tool writes its normal output to. console.error() is not just a "scarier" version of the same thing — it writes to the separate stderr stream. That distinction matters in practice: if a user redirects your program's stdout to a file (node report.js > out.txt), text printed with console.log() disappears into that file, while anything printed with console.error() still shows up on the terminal. Command-line tools conventionally use console.error() for progress messages and warnings, and reserve console.log() for the actual data the program was asked to produce.

The process object

process is a global — you never require() it — and it describes the currently running Node instance: its command-line invocation, its environment, and its lifecycle. 

process.argv       // array: [node path, script path, ...user args]
process.env         // object: environment variable name -> string value
process.cwd()       // current working directory (a function call, not a property)
process.chdir(dir)  // change the working directory
process.exit(code)  // terminate immediately; nonzero code means failure
process.exitCode    // set this instead of calling exit() to let pending I/O finish
process.pid         // this process's OS process id
process.platform    // "linux", "darwin", "win32", etc.
process.version     // Node's own version string
process.stdin       // Readable stream connected to standard input
process.stdout      // Writable stream connected to standard output
process.stderr      // Writable stream connected to standard error

process.argv is the classic gotcha for anyone coming from other languages: index 0 is always the absolute path to the node binary itself, and index 1 is always the absolute path to the script being run — your program's own arguments only start at index 2. Anything you pass to node itself before the script name (like --trace-warnings) is consumed by the Node executable and never appears in argv at all. 

$ node argv.js --verbose input.txt
# process.argv is:
# [ "/usr/local/bin/node", "/home/me/argv.js", "--verbose", "input.txt" ]

process.env exposes the process's environment variables as an ordinary object of strings — there is no automatic type coercion, so process.env.PORT is always the string "3000", never the number 3000, even if that is obviously what was meant. This is the idiomatic way to pass configuration (API keys, feature flags, the deployment environment name) into a Node program without hardcoding it in source, and most deployment platforms populate it for you.

Two more useful globals: __dirname and __filename

Inside a CommonJS module (see below), Node quietly defines __filename as the absolute path to the current file and __dirname as the absolute path to the directory containing it. These are indispensable for building paths to other files that ship alongside your code, because they are correct no matter what directory the user happened to be in when they invoked node — unlike process.cwd(), which tracks the shell's working directory, not your script's location.

Program life cycle, signals, and uncaught errors

A Node program does not necessarily exit when it reaches the last line of its main file. Node keeps running as long as there is outstanding asynchronous work — a pending timer, an open server socket, a callback that has not yet fired. A program with no pending work exits automatically; a network server that is still listen()ing will, in principle, run forever, since there is always the possibility of one more connection event. Calling process.exit(code) forces an immediate stop regardless of pending work.

Users conventionally stop a running program by typing Ctrl-C in its terminal, which sends the process a SIGINT signal. By default this kills the process, but you can intercept it (for example, to close database connections cleanly before quitting) because process is itself an event emitter for OS signals: 

process.on("SIGINT", () => {
  console.error("Shutting down gracefully...");
  server.close(() => process.exit(0));
});

An exception that escapes every catch block normally prints a stack trace and crashes the process — and because so much of Node's API is asynchronous, an exception thrown inside a callback or event handler cannot be caught by a try/catch wrapped around the code that registered it; by the time the callback runs, that surrounding stack frame is long gone. If you want a last line of defense instead of an immediate crash, you can register global handlers for both uncaught synchronous exceptions and unhandled Promise rejections: 

process.on("uncaughtException", (err) => {
  console.error("Uncaught exception:", err);
  // The process is now in an unknown state — log and exit, don't just carry on.
  process.exit(1);
});

process.on("unhandledRejection", (reason, promise) => {
  console.error("Unhandled rejection:", reason);
});
Global handlers are a safety net, not a strategy

Once uncaughtException fires, the process may be in a corrupted state (a half-finished operation, a lock never released), so the conventional advice is to log the error and exit rather than try to keep serving requests. Unhandled promise rejections are non-fatal today but are widely expected to become fatal in future Node versions, so treat every rejected promise as a bug to fix, not a message to suppress.

CommonJS modules: require and module.exports

Node predates JavaScript having any standard module system, so it invented its own, now called CommonJS. A module exports values by assigning to module.exports (or by adding properties to the shorthand exports object, which starts out as a reference to the same object as module.exports), and another file pulls those values in with the require() function: 

// stats.js — exporting
function mean(data) { return data.reduce((a, b) => a + b) / data.length; }
function stddev(data) { /* ... */ }
module.exports = { mean, stddev };
// equivalently, incrementally:
// exports.mean = mean;
// exports.stddev = stddev;

// main.js — importing
const { mean, stddev } = require("./stats.js");
const fs = require("fs");            // a built-in module, no path needed
const express = require("express");  // a package installed into node_modules/

The crucial difference from ES import is that require() is an ordinary function call, evaluated at the point it appears — it can be wrapped in an if, called inside a function body, or built from a computed string, none of which is legal with static import declarations. Node resolves the string you pass to require() using a fixed algorithm: a name with no leading ./, ../, or / (like "fs" or "express") is looked up first among Node's built-in modules, then in the nearest node_modules/ directory, walking up the directory tree until one is found; a path starting with a dot or slash is resolved relative to the requiring file and, if it doesn't already end in .js/.json/.node, Node tries those extensions in turn, and finally tries treating the path as a directory containing an index.js. require() also caches: requiring the same resolved file twice returns the exact same exports object both times, rather than re-running the module.

Node 13 and later also support standard ES modules alongside CommonJS, but the two systems don't mix freely — a CommonJS file gets require/module/exports predefined and cannot use import/export syntax, while an ES module file gets import/ export enabled and does not get require, module, or exports defined at all. Node decides which mode applies to a given .js file by looking for the nearest package.json and checking its top-level "type" field: "type": "module" means ES modules, "type": "commonjs" (or no type field, or no package.json at all) means CommonJS. You can sidestep the lookup entirely by naming the file explicitly: .mjs is always an ES module, .cjs is always CommonJS, regardless of package.json. An ES module is allowed to import a CommonJS module, but the reverse — require()ing an ES module — is not supported. See Modules for the full contrast with import/export syntax and semantics; for new code, ES modules are generally the better default.

npm and package.json

A Node installation bundles npm, the Node Package Manager, which downloads third-party libraries and tracks which ones your project depends on inside a package.json file at your project root. Running npm init in an empty project directory interactively creates a starter package.json; running npm install <package> downloads that package and all of its own dependencies into a local node_modules/ directory and records the dependency in package.json (with an exact pinned version in the accompanying package-lock.json). Handing your source code and package.json to someone else lets them recreate your exact dependency tree with a single npm install — nobody commits node_modules/ to version control. 

{
  "name": "my-server",
  "version": "1.0.0",
  "type": "module",
  "main": "index.js",
  "scripts": { "start": "node index.js" },
  "dependencies": {
    "express": "^4.18.2"
  }
}

The "type" field is also where a project opts into ES modules for all of its plain .js files, as described above. Beyond dependency management, this chapter otherwise sticks to Node's built-in modules — nothing here requires installing anything with npm.

16.2 Node is asynchronous by default

Node's defining architectural choice is to achieve concurrency without threads. Multithreaded programming is notoriously easy to get subtly wrong, and heavyweight besides — a server handling hundreds of concurrent connections with one OS thread each would burn a prohibitive amount of memory just on thread stacks. Node instead keeps a single JavaScript thread (the same model the browser uses) and makes its I/O APIs nonblocking by default, so that thread is never stuck waiting on a disk or a socket.

Node takes this further than most environments: not just network I/O, but filesystem operations too default to asynchronous, nonblocking functions. This made more sense when spinning hard drives had millisecond-scale seek latency, and it still makes sense today when the "local" filesystem might actually be network-attached storage. In Node's model, calling a function to read a file doesn't block — instead you register a callback, the underlying OS call is dispatched, and your callback fires later when the data is ready, along with everyone else's registered callbacks, on the single JS thread's event loop. The high-level phases of that loop, in rough order each iteration: timers (setTimeout/ setInterval callbacks whose time has come), pending I/O callbacks, poll (retrieving new I/O events and running their callbacks), setImmediate() callbacks, and finally close callbacks (like a socket's "close" event) — with microtasks (resolved Promise continuations, process.nextTick() callbacks) drained between every one of those phases. You rarely need the phase names memorized, but the model to hold onto is: nothing runs in parallel, and every callback runs to completion before the next one starts.

Because Node predates the Promise class, its asynchronous APIs were designed around plain callbacks, using a specific convention called the error-first callback: the callback's first parameter is null on success or an Error (or error-shaped value) on failure, and any actual result is passed as the second parameter. Putting the error argument first is deliberate — it makes it awkward to silently forget to check for one. 

const fs = require("fs");

function readConfigFile(path, callback) {
  fs.readFile(path, "utf8", (err, text) => {
    if (err) {                 // Always check the first argument first.
      console.error(err);
      callback(null);
      return;
    }
    let data = null;
    try {
      data = JSON.parse(text);
    } catch (e) {
      console.error(e);
    }
    callback(data);
  });
}

Because Node is fairly disciplined about the error-first convention, it is straightforward to wrap a callback-based function to return a Promise instead, using the built-in util.promisify(): 

const util = require("util");
const fs = require("fs");
const readFileP = util.promisify(fs.readFile);

async function readConfigFile(path) {
  let text = await readFileP(path, "utf8");
  return JSON.parse(text);
}
// Node itself already ships a promisified fs — fs.promises.readFile — so
// in practice you reach for util.promisify() mainly for third-party or
// older callback-style APIs that don't offer their own Promise variant.

See asynchronous JavaScript for the general treatment of callbacks, Promises, and async/await — everything there applies directly to Node, which is simply the environment where the callback style originated and still shows up throughout the built-in API.

16.3 Buffers

Text has an encoding, but raw bytes — the contents of an image file, a network packet, encrypted data — do not. Node needed a byte-array type for this before JavaScript itself had one, so it defined Buffer. Now that Uint8Array is a standard part of the language (see typed arrays), Buffer is implemented as a subclass of it: every Buffer is a Uint8Array, and every Uint8Array method works on one, but Buffer adds convenient two-way conversion to and from strings via named text encodings.

EncodingNotes
"utf8"Default when none is specified; general-purpose Unicode
"utf16le"Two-byte little-endian Unicode; "ucs2" is an alias
"latin1"One byte per character (ISO-8859-1); also called "binary"
"ascii"7-bit English-only, a strict subset of UTF-8
"hex"Each byte becomes two hex digit characters
"base64"Each 3 bytes becomes 4 ASCII characters
let b = Buffer.from([0x41, 0x42, 0x43]);   // <Buffer 41 42 43>
b.toString();                              // "ABC" — default utf8
b.toString("hex");                         // "414243"

let computer = Buffer.from("IBM3111", "ascii");
for (let i = 0; i < computer.length; i++) {
  computer[i]--;                           // Buffers are mutable byte arrays
}
computer.toString("ascii");                // "HAL2000"

// Allocating buffers directly:
let zeros = Buffer.alloc(1024);            // 1024 zero bytes
let ones  = Buffer.alloc(128, 1);          // 128 bytes, each equal to 1
let dead  = Buffer.alloc(1024, "DEADBEEF", "hex"); // repeating byte pattern

// Reading multi-byte numeric values out of a buffer at an offset:
dead.readUInt32BE(0);       // 0xDEADBEEF, big-endian
dead.readUInt32LE(1020);    // 0xEFBEADDE, little-endian
dead.readBigUInt64BE(6);    // 0xBEEFDEADBEEFDEADn

Many Node APIs — file reads, socket data, streams in general — can hand you either a Buffer or a decoded string depending on whether you told them which text encoding to use. If you only ever deal with text, specifying the encoding up front (e.g. fs.readFile(path, "utf8", cb)) often means you can avoid touching Buffer directly at all; reach for it explicitly once you're manipulating genuinely binary data.

16.4 Events and EventEmitter

Error-first callbacks work well when an operation produces exactly one result exactly once. Many Node objects instead represent ongoing activity that can fire the same kind of notification repeatedly, or several different kinds of notification over their lifetime — a network server accepts many connections, a socket receives many chunks of data. These objects are all instances of EventEmitter (or a subclass of it), the pattern underlying almost every non-trivial Node API. 

const EventEmitter = require("events"); // module name != class name
const net = require("net");
let server = new net.Server();
server instanceof EventEmitter;   // true — Servers are EventEmitters

server.on("connection", (socket) => {  // register a listener
  socket.end("Hello, world!\n", "utf8");
});
server.once("close", () => console.log("server closed")); // fires at most once
// server.off("connection", handler)  removes a previously added listener
// server.emit("customEvent", 1, 2)   fires listeners yourself (rare in user code)

on() (aliased addListener()) registers a handler for a named event type; once() registers one that automatically removes itself after firing a single time; off() (aliased removeListener()) removes a previously registered handler. If several listeners are registered for the same event, they run in registration order.

hard Emission is synchronous, and unhandled "error" events crash the process

Unlike DOM events, which are dispatched through the browser's own scheduling, emit() is an ordinary synchronous function call: it invokes every registered listener for that event type, one after another, on the current call stack, and does not return until the last one has returned. If one listener is slow — say it calls a blocking function — every other part of your single-threaded program, including other events waiting to be handled, is blocked until it finishes. If a listener throws, the exception propagates out of emit() itself, and any listeners registered after the one that threw never run for that emission.

The special case that catches people off guard is the "error" event. Node's event-based APIs use it as the equivalent of the error-first callback's first argument — an EventEmitter that hits a problem emits "error" rather than throwing directly. But if you emit("error", ...) on an emitter that has no listener registered for "error", Node's default behavior is to throw that error itself, asynchronously, which you cannot catch with a surrounding try/catch — and an uncaught throw crashes the whole process. Every EventEmitter you don't fully control — every socket, every stream, every child process — needs an "error" listener attached, even if all it does is log: 

// A socket, stream, or server with NO "error" listener is a crash waiting
// to happen the moment something goes wrong on the network or disk:
let socket = net.createConnection(80, "example.com");
socket.on("error", (err) => console.error("connection failed:", err));

// Same idea for a Readable stream used for a file that might not exist:
let input = fs.createReadStream("maybe-missing.txt");
input.on("error", (err) => console.error("read failed:", err));

For CPU-heavy work that needs to happen in response to an event without blocking the rest of the loop, defer it with setTimeout(fn, 0) or Node's own setImmediate(fn), which runs fn as soon as the current poll phase's I/O callbacks are done, ahead of any newly-scheduled timers.

16.5 Streams

The simplest way to process data is to read it all into memory, do something with it, and write it all back out. That falls apart at scale: a naive "read the whole file, then write the whole file" copy function has to hold the entire file in RAM at once, can't start writing until reading is completely finished, and gets worse the more concurrent copies are in flight. Node's streams solve this by moving data through your program in small chunks, so the full dataset is never resident in memory at one time.

TypeDirectionExamples
Readablesource onlyfs.createReadStream(), process.stdin, an HTTP request body on the server
Writablesink onlyfs.createWriteStream(), process.stdout, an HTTP response on the server
Duplexboth, independentlya net.Socket — reading and writing are unrelated data flows
Transformwritable in, readable out (related)zlib.createGzip(), crypto.createCipheriv()

A Transform stream differs from a plain Duplex stream in that what you write to it and what you read from it are the same logical data, passed through some transformation — gzip compression, encryption — rather than two unrelated streams sharing an object. By default, streams read and write raw Buffer chunks; calling setEncoding(name) on a Readable stream makes it hand you decoded strings instead.

Pipes: the easy connector

The most common thing to do with a stream is connect its output directly to another stream's input — read a file and send it to a socket, or run data through a compressor on the way to disk. The pipe() method does exactly this and, critically, handles the coordination between the two streams' differing speeds automatically: 

const fs = require("fs");
const zlib = require("zlib");

// Three streams chained into a pipeline: read -> gzip -> write.
fs.createReadStream("in.txt")
  .pipe(zlib.createGzip())
  .pipe(fs.createWriteStream("in.txt.gz"))
  .on("finish", () => console.log("done"))
  .on("error", (err) => console.error(err));

Remember to attach an "error" listener somewhere in a pipe chain — per the EventEmitter rule above, an unhandled "error" on any stream in the chain will otherwise crash the process. A more involved worked example is a custom Transform stream implementing a Unix-grep-like filter, which overrides _transform() to process each incoming chunk and _flush() to handle any leftover partial data at the very end: 

const stream = require("stream");

class GrepStream extends stream.Transform {
  constructor(pattern) {
    super({ decodeStrings: false }); // keep strings as strings, don't re-encode
    this.pattern = pattern;
    this.incompleteLine = "";        // carries a partial line across chunks
  }
  _transform(chunk, encoding, callback) {
    let lines = (this.incompleteLine + chunk).split("\n");
    this.incompleteLine = lines.pop();       // last "line" may not be complete yet
    let output = lines.filter((l) => this.pattern.test(l)).join("\n");
    if (output) output += "\n";
    callback(null, output);                  // always call back, even with ""
  }
  _flush(callback) {
    if (this.pattern.test(this.incompleteLine)) {
      callback(null, this.incompleteLine + "\n");
    } else {
      callback();
    }
  }
}

let pattern = new RegExp(process.argv[2]);
process.stdin
  .setEncoding("utf8")
  .pipe(new GrepStream(pattern))
  .pipe(process.stdout)
  .on("error", () => process.exit());

Asynchronous iteration over a Readable stream

Since Node 12, a Readable stream is itself an async iterable, so you can pull chunks out of it with ordinary for await...of syntax inside an async function — no event handlers needed for the common case of "process each chunk in order": 

async function grep(source, destination, pattern, encoding = "utf8") {
  source.setEncoding(encoding);
  destination.on("error", () => process.exit());
  let incompleteLine = "";
  for await (let chunk of source) {
    let lines = (incompleteLine + chunk).split("\n");
    incompleteLine = lines.pop();
    for (let line of lines) {
      if (pattern.test(line)) destination.write(line + "\n", encoding);
    }
  }
  if (pattern.test(incompleteLine)) {
    destination.write(incompleteLine + "\n", encoding);
  }
}

grep(process.stdin, process.stdout, new RegExp(process.argv[2]))
  .catch((err) => { console.error(err); process.exit(); });

for await...of reads more like ordinary synchronous code than the event-based APIs below, which is why it (and pipe()) are the recommended default; reach for raw "data"/"readable" events only when you need finer control that those higher-level APIs don't expose. See async iterators and for await for the general language feature.

Writing to streams and backpressure hard

Backpressure: why naive writes balloon memory

writable.write(chunk) always accepts and buffers the data you hand it — Node will grow the stream's internal buffer as large as it needs to. But it also returns a boolean: true if the internal buffer still has room, false if the buffer is now full or over capacity. That false return value is backpressure — a signal that you are producing data faster than the destination can drain it. The danger is concrete: a tight loop that calls write() repeatedly while ignoring the return value will keep buffering data in memory indefinitely, because nothing is ever slowing the producer down to match the consumer's real throughput. Given a slow destination (a laggy network client, a full disk) and enough data, that buffer growth is unbounded — a classic way for a Node server to balloon its memory usage or fall over outright.

Worse, this is externally triggerable: an HTTP client that opens a request for a large file and then simply never reads the response body forces the server's write buffer for that connection to grow without limit if the server doesn't respect backpressure — a realistic denial-of-service vector against a naively written file server.

The correct response to a false return is to stop writing until the stream emits a "drain" event:

// Manually respecting backpressure with a callback:
function write(stream, chunk, callback) {
  let hasRoom = stream.write(chunk);
  if (hasRoom) {
    setImmediate(callback);          // fine to continue right away
  } else {
    stream.once("drain", callback);  // wait for room before writing more
  }
}

// The same idea, Promise-based, so it composes with async/await:
function writeAsync(stream, chunk) {
  let hasRoom = stream.write(chunk);
  return hasRoom ? Promise.resolve() : new Promise((resolve) => stream.once("drain", resolve));
}

async function copy(source, destination) {
  destination.on("error", () => process.exit());
  for await (let chunk of source) {
    await writeAsync(destination, chunk);  // pause here until there's room
  }
}
copy(process.stdin, process.stdout);

This is precisely why pipe() (and, when you write your own loop, for await...of combined with an awaited write helper like writeAsync above) are preferred over calling write() in a bare loop: pipe() watches the destination's return value and the "drain" event for you and automatically pauses the source when the destination is full, resuming it once the destination signals it has room again. Handling backpressure by hand — as the flowing-mode example below does explicitly — is instructive, but in real code you almost always want pipe() or an awaited write helper to do it for you rather than re-deriving the coordination logic yourself.

Reading with events: flowing mode and paused mode

Before pipe() and async iteration existed, Readable streams exposed two distinct event-based reading APIs, and both are still in use in older code (and worth understanding, since they're what pipe() and for await...of are built on top of). You must pick one mode and stick to it — mixing "data" handlers with manual read() calls on the same stream produces confusing results.

In flowing mode, registering a "data" listener switches the stream into push mode: chunks are emitted to you as soon as they're available, with no explicit read() call needed. A stream is not in flowing mode until you attach that first "data" listener (or call pipe(), or resume()). This full example copies a file using flowing mode while manually implementing backpressure with pause()/resume() — exactly the coordination pipe() would otherwise do for you: 

function copyFile(sourceFilename, destinationFilename, callback) {
  let input = fs.createReadStream(sourceFilename);
  let output = fs.createWriteStream(destinationFilename);

  input.on("data", (chunk) => {
    let hasRoom = output.write(chunk);
    if (!hasRoom) input.pause();      // stop reading until output drains
  });
  input.on("end", () => output.end());
  input.on("error", (err) => { callback(err); process.exit(); });
  output.on("drain", () => input.resume());  // resume reading once there's room
  output.on("error", (err) => { callback(err); process.exit(); });
  output.on("finish", () => callback(null));
}

In paused mode — the default when you never attach a "data" handler or call pipe() — the stream never pushes data at you. Instead it emits a "readable" event whenever there's data to consume, and you must call read() in a loop until it returns null, which both drains what's currently available and re-arms the stream to emit another "readable" event later. Forgetting to drain the buffer completely means you simply never get another "readable" event and your program hangs. Here's a SHA-256 file-hashing example using paused mode: 

const crypto = require("crypto");

function sha256(filename, callback) {
  let input = fs.createReadStream(filename);
  let hasher = crypto.createHash("sha256");
  input.on("readable", () => {
    let chunk;
    while ((chunk = input.read()) !== null) {  // must drain fully each time
      hasher.update(chunk);
    }
  });
  input.on("end", () => callback(null, hasher.digest("hex")));
  input.on("error", callback);
}

In practice, prefer pipe() or for await...of for new code; reach for these lower-level event APIs only when maintaining legacy code or when you genuinely need control they don't offer.

16.6 Process, CPU, and operating system details

Beyond the basics already covered, process exposes a grab-bag of lower-level details about the running program: 

process.arch             // CPU architecture, e.g. "x64"
process.cpuUsage()       // { user, system } microseconds of CPU time consumed
process.memoryUsage()    // heap size, RSS, and other memory stats
process.hrtime.bigint()  // nanosecond-resolution timestamp, for precise timing
process.uptime()         // seconds since this process started
process.kill(pid, sig)   // send a signal to another process by pid
process.getuid()         // Unix user id of the current user (POSIX only)
process.title            // name shown for this process in `ps` listings

The separate os module — unlike process, you must require("os") explicitly — describes the machine itself rather than this one Node process: 

const os = require("os");
os.cpus()               // per-core info, including usage times
os.totalmem() / os.freemem()  // RAM in bytes, total and currently free
os.platform()           // "linux", "darwin", "win32"
os.homedir()            // current user's home directory
os.tmpdir()             // default directory for temporary files
os.networkInterfaces()  // addresses for each network interface
os.loadavg()            // [1min, 5min, 15min] load averages (POSIX only)
os.EOL                  // native line terminator: "\n" or "\r\n"

Most application code never touches os directly, but it underpins cross-platform tooling — build scripts that need a scratch directory, monitoring code that reports memory pressure, or anything that has to behave correctly on both Windows and POSIX systems.

16.7 Working with files

The fs module is Node's comprehensive filesystem API, paired with the path module for manipulating filenames and directory paths as plain strings (with no filesystem access of its own). Some of the lower-level fs function names are blunt, Unix-inherited terminology — deleting a file, for instance, is fs.unlink(), not fs.delete(), because removing a file is really just removing one hard link to its data.

The three-flavor pattern hard

Sync, callback, and Promise — and why the sync one is dangerous

Nearly every meaningful operation in fs — and this three-way split shows up throughout Node's broader API, not just here — comes in three forms, and picking the right one for the situation matters:

  • Synchronous, suffixed Sync (fs.readFileSync()): blocks the entire process until the operation completes, then returns the result directly or throws on failure.
  • Callback-based (fs.readFile()): Node's original async style — nonblocking, takes an error-first callback as the last argument.
  • Promise-based (fs.promises.readFile()): nonblocking, returns a Promise, composes naturally with async/await.
const fs = require("fs");

// 1. Synchronous — simple, but BLOCKS the whole event loop until disk I/O finishes.
let text1 = fs.readFileSync("data.csv", "utf8");

// 2. Callback-based — nonblocking, original Node style.
fs.readFile("data.csv", "utf8", (err, text) => {
  if (err) { console.error(err); return; }
  console.log(text.length);
});

// 3. Promise-based — nonblocking, preferred in new code.
async function load() {
  let text = await fs.promises.readFile("data.csv", "utf8");
  console.log(text.length);
}

The reason the synchronous flavor is dangerous in a server is that Node has exactly one JavaScript thread. While fs.readFileSync() is waiting on the disk, that thread can do absolutely nothing else — no other request can be accepted, no other request already in flight can make progress, no timer can fire. A single slow synchronous disk read stalls every concurrent client your server is supposed to be serving, for the full duration of that read. Contrast this with the callback and Promise forms, where the actual I/O happens off the JS thread (handled by Node's internal thread pool or native async OS APIs) and your code only resumes when the result is ready, letting the event loop service everything else in the meantime. 

// DANGEROUS in a running server: blocks every other in-flight request
// for as long as this file read takes.
app.get("/report", (req, res) => {
  let data = fs.readFileSync("huge-report.json", "utf8");  // do not do this
  res.json(JSON.parse(data));
});

// Correct: the event loop stays free to handle other requests while
// this read is in flight.
app.get("/report", async (req, res) => {
  let data = await fs.promises.readFile("huge-report.json", "utf8");
  res.json(JSON.parse(data));
});

The synchronous flavor is genuinely the right tool in a narrow set of cases: one-off CLI scripts where there's no concurrency to protect, and reading configuration during process startup before the server has begun accepting any connections (at that moment there's nothing else for the thread to be doing anyway). It is essentially never the right choice inside a request handler on a server that's already running.

Paths, file descriptors, and FileHandles

Before operating on a file you need to name it. A path is either absolute (anchored at the filesystem root) or relative (meaningful only in combination with some base directory, usually the current working directory). Because separator characters, duplicate slashes, and ../ segments differ across platforms and are easy to mishandle by hand, the path module provides pure string-manipulation helpers with no filesystem access of their own: 

const path = require("path");
let p = "src/pkg/test.js";
path.basename(p);              // "test.js"
path.extname(p);                // ".js"
path.dirname(p);                // "src/pkg"
path.normalize("a/b/c/../d/");  // "a/b/d/" — resolves ".." segments
path.join("src", "pkg", "t.js"); // "src/pkg/t.js" — joins and normalizes
path.resolve("t.js");           // absolute path, resolved against process.cwd()

// __dirname / __filename combined with path.join/resolve is the
// idiomatic way to locate files that ship alongside your own code:
let configPath = path.join(__dirname, "config.json");

Some lower-level fs functions operate on an open file rather than a path — a file descriptor, an integer handle obtained from fs.open()/fs.openSync(), or its Promise-API equivalent, a FileHandle object returned by fs.promises.open(). You only need one of these if you're using the lowest-level fs.read()/ fs.write() functions to jump around within a file at specific byte offsets; remember to close() whatever you open, since a process can only have a limited number of files open at once.

Reading files

For small files where memory efficiency doesn't matter, reading the whole thing in one call is simplest, in any of the three flavors above; pass an encoding to get a decoded string instead of a raw Buffer: 

let buffer = fs.readFileSync("test.data");        // raw Buffer
let text = fs.readFileSync("data.csv", "utf8");    // decoded string

For large files, stream them instead — see Streams above — for example piping a file straight to process.stdout with fs.createReadStream(filename).pipe(process.stdout). For precise control over exactly which bytes get read and when, open the file and use fs.read()/fs.readSync() with an explicit buffer, length, and file offset — useful for parsing binary file formats with fixed-size headers.

Writing files

Creating a file is simply writing to a path that doesn't exist yet. As with reading, there are three ways to write a complete chunk of data at once: 

fs.writeFileSync(path.join(__dirname, "settings.json"), JSON.stringify(settings));
fs.writeFile("out.txt", "hello", (err) => { if (err) console.error(err); });
await fs.promises.writeFile("out.txt", "hello");

// Append instead of overwrite:
fs.appendFileSync("log.txt", "another line\n");

For data produced incrementally, use a Writable stream instead of one big call: 

let output = fs.createWriteStream("numbers.txt");
for (let i = 0; i < 100; i++) output.write(`${i}\n`);
output.end();

Passing a flag option controls open semantics precisely — for instance, "wx" fails instead of silently overwriting if the file already exists, which is valuable any time an accidental overwrite would be a real loss: 

fs.createWriteStream("messages.log", { flags: "wx" }); // error if it exists

Finally, a successful write callback/Promise only guarantees Node has handed the data to the operating system, not that it's physically on disk — data may still sit in an OS buffer. To force a real flush to storage, call fs.fsync()/fs.fsyncSync() on an open file descriptor.

Common whole-file operations

Beyond read and write, fs defines direct equivalents of familiar file-management commands, each with the usual sync/callback/ Promise trio: 

fs.copyFileSync("ch15.txt", "ch15.bak");
fs.renameSync("ch15.bak", "backups/ch15.bak");   // move and/or rename
fs.unlinkSync("backups/ch15.bak");               // delete a file
fs.mkdirSync("dist/lib", { recursive: true });   // create nested directories
fs.rmdirSync("dist/lib");                        // remove an EMPTY directory

File metadata: stat()

fs.stat() (and its sync/Promise variants) retrieves metadata about a file or directory without reading its contents — size, type, timestamps, ownership and permission bits: 

let stats = fs.statSync("book/ch15.md");
stats.isFile();          // true
stats.isDirectory();     // false
stats.size;              // size in bytes
stats.mtime;             // Date — last modified
stats.mode.toString(8);  // permission bits, as an octal string

fs.lstat() behaves like fs.stat() except that for a symbolic link it reports on the link itself rather than following it to whatever it points at — the "l"-prefixed variants found throughout fs (like fs.lchmod()) follow this same convention.

Watching files and listing directories

fs.watch(path, callback) notifies you when a file or directory changes on disk — useful for development tooling like auto-reloading servers, though its exact event granularity is notoriously platform-dependent and it's common to debounce the callback rather than trust every individual event. Listing a directory's contents comes in a batch form and a streaming form: 

// Batch: read the whole directory listing at once.
let names = fs.readdirSync("/tmp");                     // array of filename strings
let entries = await fs.promises.readdir("/tmp", { withFileTypes: true });
entries.filter((e) => e.isDirectory()).forEach((e) => console.log(e.name));

// Streaming: better for directories that might have huge numbers of entries.
async function listDirectory(dirpath) {
  let dir = await fs.promises.opendir(dirpath);
  for await (let entry of dir) {
    console.log(entry.isDirectory() ? entry.name + "/" : entry.name);
  }
}

fs.watch("./config", (eventType, filename) => {
  console.log(`${filename} changed (${eventType})`);
});

16.8 HTTP clients and servers

The http and https modules are full but low-level implementations of the HTTP protocol — comprehensive, but you build routing, body-parsing, and middleware yourself, which is why real applications almost always sit a framework like Express or Fastify on top rather than working with these modules directly. Both the request you send and the request/response your server handles are ordinary streams, so everything from Streams above applies to them directly.

A minimal HTTP server

const http = require("http");

const server = http.createServer((request, response) => {
  // `request` is a Readable stream (the request body); `response` is Writable.
  response.writeHead(200, { "Content-Type": "text/plain" });
  response.end("Hello, world!\n");
});
server.listen(8080, () => console.log("listening on 8080"));

server here is itself an EventEmitter; createServer()'s callback argument is just a shorthand for registering a "request" listener. Because request is a Readable stream, reading a POST body works exactly like reading any other stream — accumulate "data" events, or, more idiomatically, for await over it: 

const server = http.createServer(async (request, response) => {
  if (request.method === "POST") {
    let chunks = [];
    for await (let chunk of request) chunks.push(chunk);
    let body = Buffer.concat(chunks).toString("utf8");
    response.end(`Received ${body.length} bytes\n`);
  } else {
    response.writeHead(404);
    response.end();
  }
});

Making outbound HTTP requests

http.get()/https.get() issue a simple GET request; the more general http.request()/ https.request() support any method and let you write a request body before ending the request. The callback fires as soon as the response headers arrive — the body streams in afterward exactly like a Readable stream anywhere else: 

const https = require("https");

function postJSON(host, endpoint, body) {
  return new Promise((resolve, reject) => {
    let bodyText = JSON.stringify(body);
    let request = https.request({
      method: "POST",
      host,
      path: endpoint,
      headers: {
        "Content-Type": "application/json",
        "Content-Length": Buffer.byteLength(bodyText),
      },
    });
    request.on("error", reject);
    request.on("response", (response) => {
      if (response.statusCode !== 200) {
        reject(new Error(`HTTP status ${response.statusCode}`));
        response.resume();  // discard the body so the socket can be released
        return;
      }
      response.setEncoding("utf8");
      let text = "";
      response.on("data", (chunk) => { text += chunk; });
      response.on("end", () => {
        try { resolve(JSON.parse(text)); } catch (e) { reject(e); }
      });
    });
    request.write(bodyText);
    request.end();  // the request is not sent until end() is called
  });
}
Modern alternative: fetch()

Recent Node versions ship a global fetch(), the same Promise-based API browsers expose, which is usually simpler than http.request() for straightforward request/response use. The stream-based API above is still worth understanding because it's what fetch() is built on, and because fine-grained control (custom headers per chunk, streaming a request body, low-level timeout handling) sometimes still requires it.

16.9 Non-HTTP network servers and clients

HTTP is so ubiquitous it's easy to forget Node is a general networking environment. The net module works with raw TCP sockets: a net.Server created with net.createServer() emits a "connection" event for each incoming client, and the Socket passed to that event is a Duplex stream — reading from it gets you the client's data, writing to it sends data back: 

const net = require("net");

let server = net.createServer();
server.listen(6789, () => console.log("listening on 6789"));
server.on("connection", (socket) => {
  socket.write("Welcome!\r\n");
  socket.on("data", (chunk) => socket.write(`You said: ${chunk}`));
  socket.on("error", (err) => console.error(err)); // required, per EventEmitter rules
});

// A client connects the same way pipes connect any two streams:
let client = net.createConnection(6789, "localhost");
client.pipe(process.stdout);
process.stdin.pipe(client);

net also supports Unix domain sockets (identified by a filesystem path instead of a host/port pair) for fast local interprocess communication. For protocols that need UDP instead of TCP — no connection setup, no delivery guarantee, lower overhead — the dgram module provides datagram sockets: 

const dgram = require("dgram");

let socket = dgram.createSocket("udp4");
socket.on("message", (msg, rinfo) => {
  console.log(`Got ${msg.length} bytes from ${rinfo.address}:${rinfo.port}`);
});
socket.bind(41234);

// Sending a datagram from elsewhere:
let sender = dgram.createSocket("udp4");
sender.send(Buffer.from("hello"), 41234, "localhost");

And tls is to net what https is to http — the same raw-socket model, wrapped in TLS encryption. In practice, reach for net/dgram only when you're implementing a genuinely custom protocol; nearly everything web-facing is better served by http/ https.

16.10 Working with child processes

The child_process module runs other programs — shell commands, other executables, or even other Node scripts — as separate OS processes and lets you capture their output or communicate with them while they run. It offers several functions, trading off simplicity, streaming ability, and whether a shell gets involved.

FunctionBlocking?Shell?Use when
execSync(cmd)yesyesquick script, need shell features (pipes, wildcards), blocking is fine
execFileSync(file, args)yesnosame, but no shell parsing overhead/risk
exec(cmd, cb)noyesneed shell features, output arrives all at once when the process exits
execFile(file, args, cb)nonosame, without invoking a shell

const child_process = require("child_process");

// execSync(): simplest, but blocks and runs through a shell.
let listing = child_process.execSync("ls -l web/*.html", { encoding: "utf8" });

// execFileSync(): same idea, no shell — safer if any argument is untrusted.
let listing2 = child_process.execFileSync("ls", ["-l", "web/"], { encoding: "utf8" });
Shell commands and untrusted input don't mix

Because exec()/execSync() run your string through an actual shell, they support pipes, wildcards, and semicolon-separated commands — and for that exact reason, you must never build that command string out of user-supplied input. An attacker who controls even a fragment of the command can break out of your intended command entirely and run arbitrary shell syntax. If you don't need shell features, prefer execFile()/ spawn(), which take the executable and its arguments as separate values and never invoke a shell to parse them.

spawn() is the function to reach for when you need streaming access to a long-running child's output, or need to interactively send it input based on what it's already printed. It returns a ChildProcess — itself an EventEmitter — exposing stdout/stderr as Readable streams and stdin as a Writable stream (note the inversion: what the child treats as its output stream, the parent reads as an input stream): 

let child = child_process.spawn("grep", ["error", "-r", "./logs"]);
child.stdout.on("data", (chunk) => process.stdout.write(chunk));
child.stderr.on("data", (chunk) => process.stderr.write(chunk));
child.on("exit", (code) => console.log(`grep exited with code ${code}`));

fork() is a specialized spawn() for running another Node script as a child, and it adds a convenient structured message channel on top of the plain stdio streams: the parent calls child.send(value) and listens for child.on("message", ...), while the child calls process.send(value) and listens for process.on("message", ...). Values passed through send() are JSON-serialized under the hood, so only JSON-compatible data survives the trip: 

// parent.js
let child = child_process.fork(`${__dirname}/child.js`);
child.send({ x: 4, y: 3 });
child.on("message", (message) => {
  console.log(message.hypotenuse); // 5
  child.disconnect();
});

// child.js
process.on("message", (message) => {
  process.send({ hypotenuse: Math.hypot(message.x, message.y) });
});

Starting a child process is relatively expensive, so fork()-based interprocess communication only pays off when the child is doing substantially more work than the overhead of starting it — for lighter CPU-bound work within the same process, a worker thread (next section) is usually the better fit.

16.11 Worker threads

Node's core concurrency model is single-threaded, but worker_threads (since Node 10) provides genuine multithreading within one process, deliberately modeled on the browser's Web Workers API. Like Web Workers, Node's worker threads do not share memory by default — communication happens exclusively via postMessage(), avoiding the classic hazards of shared-memory threading (races, locks, deadlocks) almost entirely.

child_processworker_threads
IsolationSeparate OS process — a crash can't take down the parentSame process, separate thread — a bad crash can affect the process
Startup costRelatively expensiveLighter, but still not free — don't spin one up for trivial work
Best forRunning a separate program, isolating untrusted or crash-prone codeCPU-bound JavaScript computation that would otherwise block the event loop
Communicationstdio streams, or JSON messages via fork()'s send()/"message"postMessage() using the structured clone algorithm, plus optional shared memory

There are three situations where reaching for a worker thread makes sense: genuinely CPU-bound work (image processing, hashing, parsing) that needs more than one core; keeping the main thread responsive when occasional requests require a burst of blocking computation, so other requests aren't stalled behind it; and wrapping unavoidably synchronous legacy code so the rest of the program can treat it as asynchronous. If your program isn't CPU-bound and isn't struggling with responsiveness, you very likely don't need worker threads at all — most Node servers are I/O-bound and never touch this module.

Creating workers and passing messages

const threads = require("worker_threads");

// A common trick: one file serves as both the main-thread entry point
// and the worker's code, branching on threads.isMainThread.
if (threads.isMainThread) {
  module.exports = function reticulateSplines(splines) {
    return new Promise((resolve, reject) => {
      let worker = new threads.Worker(__filename);
      worker.postMessage(splines);
      worker.on("message", resolve);
      worker.on("error", reject);
    });
  };
} else {
  threads.parentPort.once("message", (splines) => {
    for (let spline of splines) spline.reticulate();
    threads.parentPort.postMessage(splines); // send the result back
  });
}

A second, self-contained example — offloading a CPU-heavy prime check so it doesn't stall a server's event loop: 

// prime-worker.js
const { parentPort, workerData } = require("worker_threads");
function isPrime(n) {
  for (let i = 2; i * i <= n; i++) if (n % i === 0) return false;
  return n > 1;
}
parentPort.postMessage(isPrime(workerData));

// server.js
const { Worker } = require("worker_threads");
function checkPrimeInWorker(n) {
  return new Promise((resolve, reject) => {
    let worker = new Worker("./prime-worker.js", { workerData: n });
    worker.on("message", resolve);
    worker.on("error", reject);
  });
}

Whatever you pass to postMessage() is copied via the same structured clone algorithm used by window.postMessage() in browsers (see Web Workers) — the worker receives an independent copy, not a live reference, and types like Map, Set, Date, and typed arrays survive the trip, but host-specific objects like sockets and streams do not. A Buffer specifically arrives on the other side as a plain Uint8Array; wrap it back in Buffer.from() if you need Buffer-specific methods again.

The worker execution environment

Code inside a worker thread mostly behaves like ordinary Node code, with a handful of differences worth knowing:

  • threads.isMainThread is false inside any worker, true in the main thread.
  • threads.parentPort (a MessagePort) is how a worker sends/receives messages with its parent; it is null in the main thread.
  • threads.workerData carries the value passed as the workerData option to the Worker constructor — a way to hand the worker its initial input before it has to wait for a first "message" event.
  • By default a worker's process.stdout/stderr are piped straight to the parent's, so console.log() "just works" the same in a worker; passing stdout: true/stderr: true instead exposes them as readable streams on the Worker object.
  • Calling process.exit() inside a worker only ends that thread, not the whole process.
  • OS signals (like SIGINT) are only ever delivered to the main thread, never to a worker.
  • A worker cannot call process-wide mutators like process.chdir() — they throw if called from a worker.

Transferring and sharing typed arrays

Copying large binary payloads on every message is wasteful, so postMessage() accepts an optional second argument, a list of objects to transfer instead of copy — after a transfer, the sending side can no longer use that object at all, which is what makes it safe without locking: 

let pixels = new Uint32Array(1024 * 1024); // 4 MB
worker.postMessage(pixels, [pixels.buffer]); // moved, not copied; unusable here now

Going further, a SharedArrayBuffer-backed typed array is genuinely shared, readable and writable by both threads at once — the one case in JavaScript where real shared-memory concurrency exists, and correspondingly the one case where classic race conditions become possible again. Incrementing a shared counter from two threads without synchronization loses updates, because ++ is not atomic (read, then increment, then write, as three separate steps); the Atomics object (Atomics.add(), Atomics.load(), etc.) provides real atomic operations on shared array elements, at a real performance cost, and is the only safe way to mutate shared memory from more than one thread. This is a genuinely niche corner of Node — reach for a SharedArrayBuffer only when threads operate on disjoint regions of memory (a parallel merge sort splitting an array in half is the classic case) or when Atomics is providing the actual synchronization.

Custom MessageChannels

Beyond the default parent/worker connection, worker_threads supports the same MessageChannel/MessagePort API browsers use: new threads.MessageChannel() produces a connected pair, port1 and port2, where posting on one delivers a "message" event on the other. This is useful when two independently created workers need to talk directly to each other rather than relaying every message through the main thread — one port gets transferred to each worker via their normal default channel, and afterward they can communicate peer-to-peer.

16.12 Summary

Node turns JavaScript into a general-purpose systems language by pairing it with OS bindings, and holds onto the browser's single-threaded, asynchronous-by-default model to do it without the usual perils of multithreaded programming. The load-bearing ideas from this chapter: process and CommonJS require()/module.exports as the basics of any Node program; an event loop and error-first callbacks (with Promise wrappers layered on top) as the concurrency model; Buffer as the binary counterpart to strings; EventEmitter as the pattern behind nearly every stateful API, complete with its synchronous-emission and crash-on-unhandled- "error" behavior; streams — and specifically backpressure — as the mechanism for processing data without exhausting memory; the recurring sync/callback/Promise three-way split found throughout fs and beyond, and why the sync variant is a server-side liability; http/ https for web traffic and net/ dgram for everything else; and, for real parallelism, child_process for running separate programs versus worker_threads for CPU-bound work inside the same process.
