Components & Graphics

HTML gives you a fixed vocabulary of tags, but real interfaces need more: reusable widgets with their own private markup and styling, resolution-independent vector art, an imperative pixel canvas for everything a fixed tag set can't express, and a couple of ways to make noise. This page covers the four browser-native APIs that fill those gaps — Web Components, SVG, <canvas>, and audio — building on the DOM fundamentals from DOM & CSS Scripting.

Web Components

Frameworks like React and Angular popularized the idea of a reusable UI element with its own markup, styling, and behavior bundled behind a single custom tag. Web Components bring that idea into the browser platform itself, with no build step or runtime library required. The feature isn't one API but three cooperating ones, each covered in its own subsection below: custom elements associate a JavaScript class with a new tag name, shadow DOM gives that class a private, style-isolated subtree to render into, and <template> gives it an efficient, parse-once stamp for the markup it repeats on every instance.

Consuming a web component

Before authoring one, it helps to know the rules from the consumer's side, since they explain some otherwise-odd requirements later. Because a component's behavior lives in JavaScript, the script that defines it has to run before the tag does anything useful: 

<script type="module" src="/components/rating-stars.js"></script>

<rating-stars value="3" max="5"></rating-stars>
  • Every custom tag name must contain a hyphen (rating-stars, not ratingstars). This is not a style convention — it's how the spec guarantees future native HTML tags will never collide with a page's custom elements.
  • Custom elements cannot self-close. Writing <rating-stars/> is invalid; you must always write both the opening and closing tag, even with no children.
  • Some components accept regular children; others render specially labeled children into named "slots" (see Shadow DOM slots below). The component's own documentation is the only way to know which attributes, slots, and child content it supports — there's no way to introspect this generically the way TypeScript types let you introspect a function signature.
Custom tags render before they're defined

Because type="module" scripts run deferred (after parsing), the browser will often encounter <rating-stars> in the markup before the script that calls customElements.define() has executed. Rather than erroring, the HTML parser inserts a generic, inert HTMLElement placeholder and silently "upgrades" it to the real class later once the definition runs. Until that upgrade happens, any children you supplied will likely render with no styling at all. A common fix is to hide undefined instances with the :not(:defined) CSS pseudo-class: 

/* Reserve the component's eventual footprint and hide it until upgraded,
   so the rest of the page doesn't visibly reflow when it appears. */
rating-stars:not(:defined) {
  display: inline-block;
  width: 6em;
  height: 1.2em;
  opacity: 0;
}

Once a component is defined, you interact with its element the same way you would any DOM node — document.querySelector() to find it, and whatever properties/methods its author chose to expose (commonly a getter/setter pair mirroring each supported attribute).

The <template> element and DocumentFragment

The <template> tag holds markup that the browser parses but never renders and never runs (images inside it don't load, scripts inside it don't execute) until you explicitly clone it into the live document. It exists purely as an efficient stamp for structure you'll duplicate many times — table rows, list items, or, most commonly, the internals of a web component.

In JavaScript, a template's contents live behind its .content property, which is a DocumentFragment — a special container node that can hold a set of sibling nodes without itself having a parent. The detail that matters: when you insert a DocumentFragment into the document (via append(), for example), the fragment node itself is never inserted — only its children are, and the fragment is left empty afterward. This lets you build up a batch of nodes off-tree and then splice all of them into place with a single, efficient operation instead of one append per node. 

let tableBody = document.querySelector("tbody");
let rowTemplate = document.querySelector("#row-template");

for (let record of records) {
  let row = rowTemplate.content.cloneNode(true); // deep clone the fragment
  row.querySelector(".name").textContent = record.name;
  row.querySelector(".score").textContent = record.score;
  tableBody.append(row); // only the <tr> children are actually inserted
}

A <template> doesn't need to exist in the HTML source at all — components very often build one in JavaScript by creating a <template> element and setting its innerHTML once, up front, then cloning it cheaply on every instantiation rather than re-parsing an HTML string each time. You'll see that pattern in the full component example later on this page.

Custom elements

customElements.define(tagName, class) is what links a hyphenated tag name to a JavaScript class. The class must extend HTMLElement (not a more specific subtype like HTMLButtonElement — extending built-in elements beyond the generic base is inconsistently supported across browsers). If the class defines a constructor, it must call super() with no arguments before touching this, exactly like any other subclass constructor.

The browser drives instances of the class through a small set of lifecycle callbacks it invokes automatically:

CallbackInvoked when…
connectedCallback()the element is inserted into the document — the usual place to do setup, since this.isConnected and layout info aren't reliable in the constructor
disconnectedCallback()the element is removed from the document — used less often, mainly for teardown like clearing timers
attributeChangedCallback(name, oldValue, newValue)an attribute listed in observedAttributes is set, changed, or removed — including the first time it's parsed from HTML
adoptedCallback()the element is moved into a different document (rare — e.g. via document.adoptNode())

Note that attributeChangedCallback only fires for attributes named in a static observedAttributes getter — the browser has no reason to pay the cost of watching every attribute on every custom element, so you opt in explicitly. 

customElements.define("inline-badge", class InlineBadge extends HTMLElement {
  connectedCallback() {
    this.style.display = "inline-block";
    this.style.borderRadius = "999px";
    this.style.padding = "0 0.5em";
    this.style.font = "inherit";
    if (!this.style.backgroundColor) {
      this.style.backgroundColor = "#ddd"; // sensible default
    }
  }

  // Only changes to these two attributes trigger attributeChangedCallback.
  static get observedAttributes() { return ["tone", "count"]; }

  attributeChangedCallback(name, oldValue, newValue) {
    if (name === "tone") {
      this.style.backgroundColor = newValue === "danger" ? "#f8d7da" : "#ddd";
    } else if (name === "count") {
      this.textContent = newValue;
    }
  }

  // Mirror the attributes as JavaScript properties, as component authors
  // conventionally do. Setting the property sets the attribute, which in
  // turn re-triggers attributeChangedCallback above.
  get tone() { return this.getAttribute("tone"); }
  set tone(value) { this.setAttribute("tone", value); }
  get count() { return this.getAttribute("count"); }
  set count(value) { this.setAttribute("count", value); }
});
This example isn't a real component yet

InlineBadge mutates its own style attribute directly — behavior no native HTML element exhibits, and a leaky implementation detail for anyone inspecting the page. It also has no protection against page-level CSS accidentally targeting its internals. Turning it into a properly encapsulated component is exactly what shadow DOM is for, next.

Shadow DOM Hard

A shadow root is a second, private tree of descendants attached to an element (the "shadow host") in addition to its normal children. Think of the <video> element: it renders play/pause buttons, a scrubber, and a volume slider, but none of that UI shows up if you inspect its children or run querySelector() against the page — it's rendered from a shadow tree the browser keeps hidden from ordinary DOM traversal. Shadow DOM exposes that exact mechanism to your own components.

The regular, ordinary DOM children of a shadow host — the ones you'd write between its opening and closing tag in markup — are called the light DOM in contrast to the shadow tree. Both trees exist simultaneously on the same host element; how they're reconciled into one rendered result is covered in the slots subsection below.

Attaching a shadow root is a single call: element.attachShadow({ mode: "open" }). This returns the new shadow root (itself a DocumentFragment-like node you can append into or set innerHTML on) and also stores it on element.shadowRoot. Passing mode: "closed" instead creates the shadow tree but leaves shadowRoot as null from the outside — a genuinely sealed subtree that even the component's own consumers cannot reach from JavaScript. Closed mode is rare in practice; open mode already provides the encapsulation that matters, which is CSS and query isolation, not secrecy.

That isolation is the entire point of the feature, and it cuts in both directions:

  • Elements inside a shadow root are invisible to document.querySelectorAll() and similar whole-document traversals run from outside — you must go through element.shadowRoot.querySelector() instead.
  • CSS rules written inside a shadow root never leak out to style the rest of the page, and page-level stylesheets never reach in to restyle the component's internals — regardless of how generic the selectors are on either side. Only inherited properties (like font and color) and CSS custom properties cross the boundary, much as they'd inherit into a nested document. An <iframe> is not quite the right mental model, though — think of a shadow tree instead as its own miniature document that happens to inherit a few properties from its host.
  • Some events, like load, stay confined to the shadow tree. Others — focus, mouse, keyboard — bubble out across the boundary as normal, but when they do, their target is rewritten to the shadow host itself, so outside code never learns anything about the component's internal structure just by inspecting an event.

Two worked examples make the encapsulation concrete.

Example 1: outer styles don't leak in.

<style>
  /* A page-wide rule that (the author hopes) makes every paragraph red */
  p { color: red; font-weight: bold; }
</style>

<p>This paragraph is red, as expected.</p>
<fancy-quote></fancy-quote>
customElements.define("fancy-quote", class extends HTMLElement {
  connectedCallback() {
    this.attachShadow({ mode: "open" });
    this.shadowRoot.innerHTML = `
      <style>
        /* This p rule only ever matches the <p> below, never the
           light-DOM <p> sitting next to <fancy-quote> in the page. */
        p { color: slateblue; font-style: italic; }
      </style>
      <p>A quote, styled entirely by its own component.</p>
    `;
  }
});

Even though the page's p { color: red; } rule is as generic as a selector can be, the paragraph inside <fancy-quote>'s shadow root renders slateblue, not red. The page's stylesheet simply cannot see across the shadow boundary.

Example 2: inner styles don't leak out.

customElements.define("danger-button", class extends HTMLElement {
  connectedCallback() {
    this.attachShadow({ mode: "open" });
    this.shadowRoot.innerHTML = `
      <style>
        /* Styling a plain button tag, inside the shadow root only */
        button { background: crimson; color: white; border: none; padding: .5em 1em; }
      </style>
      <button><slot>Delete</slot></button>
    `;
  }
});
<danger-button></danger-button>

<!-- An ordinary button elsewhere on the same page -->
<button>Save</button>

The crimson styling defined inside <danger-button>'s shadow root has no effect whatsoever on the plain <button>Save</button> sitting elsewhere in the page, even though both match the exact same button selector. Each shadow root's stylesheet is scoped to that tree alone. This is what lets a component's author and a component's consumer write CSS without ever coordinating naming conventions like BEM to avoid collisions — the platform enforces the boundary for them.

A component can still style itself from outside using the :host and :host() selectors, written inside the shadow root's own stylesheet: 

:host {
  display: inline-block;   /* default display for the host element itself */
  border: 1px solid #ccc;
}
:host([disabled]) {        /* matches <my-widget disabled> from outside */
  opacity: 0.5;
}

These are only defaults, though: light-DOM CSS that targets the host element by tag name, class, or ID from outside will always win over :host rules, giving consumers the final say over layout and positioning while the component keeps control of its internals.

Slots: mixing light DOM into a shadow tree

A shadow host effectively has two children lists at once: the real children array (light DOM) and the shadow root's own descendants. The <slot> element is how a shadow tree makes room for the host's light-DOM children to actually appear on screen:

  • If the shadow tree contains no <slot> at all, any light-DOM children of the host are parsed and kept in the DOM but never rendered anywhere.
  • An unnamed <slot> renders all of the host's light-DOM children in its place.
  • A <slot name="left"> only renders light-DOM children carrying a matching slot="left" attribute.
  • If a named slot has no matching light-DOM child, whatever fallback content is written directly inside the <slot>…</slot> tag in the shadow tree is rendered as the default.

Crucially, "slotting" a light-DOM node into a shadow-tree slot is a purely visual reprojection — the node doesn't move. It's still reachable via querySelector() as a normal child of the host, and it's still styled by the page's own stylesheets, not the component's. Only its on-screen position changes. 

<search-box>
  <img src="/icons/search.svg" slot="left" alt="Search">
  <img src="/icons/close.svg" slot="right" alt="Clear">
</search-box>

If the component's internal <slot> elements ever need to react to which nodes are currently assigned to them (say, to re-measure layout), they can listen for the slotchange event fired directly on the <slot>.

Putting it together: a <search-box> component

The following combines all three technologies — a <template> built once and cloned per instance, a shadow root for style isolation, and named slots so consumers can swap in their own icons — into a self-contained search input that dispatches its own search and clear custom events. 

class SearchBox extends HTMLElement {
  static observedAttributes = ["placeholder", "disabled", "value"];

  // Build the template once, on the class, and clone it per instance
  // instead of re-parsing an HTML string every time one is constructed.
  static template = (() => {
    let t = document.createElement("template");
    t.innerHTML = `
      <style>
        :host { display: inline-flex; align-items: center;
                border: 1px solid #999; border-radius: 6px; padding: 2px 8px; }
        :host([disabled]) { opacity: 0.5; }
        input { border: 0; outline: none; font: inherit; background: transparent; }
        slot { cursor: pointer; user-select: none; }
      </style>
      <slot name="left">🔍</slot>
      <input id="field" type="text" />
      <slot name="right">✕</slot>
    `;
    return t;
  })();

  constructor() {
    super(); // must run before touching `this`
    this.attachShadow({ mode: "open" });
    this.shadowRoot.append(SearchBox.template.content.cloneNode(true));
    this.input = this.shadowRoot.querySelector("#field");

    this.shadowRoot.querySelector('slot[name="left"]').onclick = () => {
      if (this.disabled) return;
      this.dispatchEvent(new CustomEvent("search", { detail: this.input.value }));
    };
    this.shadowRoot.querySelector('slot[name="right"]').onclick = () => {
      if (this.disabled) return;
      let e = new CustomEvent("clear", { cancelable: true });
      this.dispatchEvent(e);
      if (!e.defaultPrevented) this.input.value = "";
    };
  }

  attributeChangedCallback(name, oldValue, newValue) {
    if (name === "disabled") this.input.disabled = newValue !== null;
    else if (name === "placeholder") this.input.placeholder = newValue ?? "";
    else if (name === "value") this.input.value = newValue ?? "";
  }

  get disabled() { return this.hasAttribute("disabled"); }
  set disabled(v) { v ? this.setAttribute("disabled", "") : this.removeAttribute("disabled"); }
}
customElements.define("search-box", SearchBox);
Reach for a library before writing this by hand often

Getting focus handling, ARIA attributes, and form participation right for a hand-rolled component is genuinely hard — the example above deliberately skips accessibility wiring to keep the three core APIs visible. Libraries like Lit exist specifically to take over that boilerplate; know the raw platform APIs so you can read what they generate, even if you rarely write it by hand.

SVG: Scalable Vector Graphics

SVG is a vector image format: instead of a grid of pixel values, an SVG document is an XML description of the shapes to draw, which lets it scale to any resolution or zoom level without blurring. There are three ways to get SVG onto a page — as a standalone .svg file referenced by an <img> tag, embedded directly as inline markup in an HTML document, or built up node-by-node with the DOM API. The last two are what make SVG interesting from a scripting standpoint, since SVG's XML tags become ordinary (if slightly unusual) nodes in the same DOM tree as the rest of the page.

Embedding SVG in HTML

Because SVG's XML grammar is so close to HTML's, an <svg> element and its descendants can be written directly inline, and the HTML parser is forgiving enough to accept them without namespace prefixes. A handful of primitive shape elements cover most simple graphics: <circle>, <rect>, <line>, <ellipse>, <polygon>, and the general-purpose <path> for arbitrary curves. <g> groups related shapes (much like a <div>), and <text> draws labels. 

<svg id="gauge" viewBox="0 0 100 100" width="150" height="150">
  <!-- viewBox defines the internal coordinate system; width/height are
       the on-screen CSS pixel size -- SVG rescales one to fit the other -->
  <circle class="dial" cx="50" cy="50" r="45"/>
  <line class="needle" x1="50" y1="50" x2="50" y2="12"/>
</svg>

<style>
  /* CSS can style SVG presentation attributes directly */
  #gauge .dial { fill: #eee; stroke: black; stroke-width: 2; }
  #gauge .needle { stroke: crimson; stroke-width: 3; stroke-linecap: round; }
</style>
SVG's CSS properties aren't quite normal CSS

Properties like fill, stroke, and stroke-width only exist for SVG content — they have no equivalent on HTML elements. And the CSS font shorthand doesn't work on SVG text; you must set font-family, font-size, and font-weight as separate declarations.

Scripting SVG

Because inline SVG becomes real DOM nodes, ordinary DOM methods work on it exactly as they do on HTML — querySelector() to find a shape, setAttribute() to change how it's drawn, event listeners to make it interactive. A live clock face is a natural example: the hour and minute hands are just <line> elements whose rotation is updated on a timer using the SVG transform attribute. 

function updateClockHands() {
  let now = new Date();
  let minutes = now.getMinutes() + now.getSeconds() / 60;
  let hours = (now.getHours() % 12) + minutes / 60;

  let minuteHand = document.querySelector("#gauge .minute-hand");
  let hourHand = document.querySelector("#gauge .hour-hand");
  minuteHand.setAttribute("transform", `rotate(${minutes * 6} 50 50)`);
  hourHand.setAttribute("transform", `rotate(${hours * 30} 50 50)`);

  setTimeout(updateClockHands, 10_000); // refresh every 10 seconds
}
updateClockHands();

Because these are ordinary DOM elements, you can also attach a normal click or pointerenter listener directly to an individual <circle> or <path> and it will fire only when that specific shape is hit — a capability canvas fundamentally cannot offer without you rebuilding hit-testing yourself, as the deep dive below explains.

Creating SVG elements with JavaScript

SVG tags are XML elements in a different namespace than HTML, so the ordinary document.createElement() silently produces a useless, unrendered generic element if you hand it an SVG tag name. Building SVG programmatically instead requires document.createElementNS(), passing the SVG namespace URI as the first argument.

createElement() doesn't work for SVG

Always use document.createElementNS("http://www.w3.org/2000/svg", tagName) when building SVG nodes from JavaScript. Forgetting the namespace is one of the most common SVG-scripting mistakes — the element gets created but never renders, with no error to point you at the cause.

This makes SVG well suited to rendering data visualizations built from live data, since each data point becomes an addressable, individually stylable node. A minimal pie-chart builder illustrates the pattern, including the compact path grammar (M move to, L line to, A elliptical arc) used to describe each wedge: 

function pieChart(data, { cx, cy, r }) {
  const SVG_NS = "http://www.w3.org/2000/svg";
  let svg = document.createElementNS(SVG_NS, "svg");
  svg.setAttribute("viewBox", `0 0 ${cx * 2} ${cy * 2}`);

  let entries = Object.entries(data);
  let total = entries.reduce((sum, [, value]) => sum + value, 0);
  let angle = 0;

  for (const [label, value] of entries) {
    let startAngle = angle;
    angle += (value / total) * 2 * Math.PI;
    let x1 = cx + r * Math.sin(startAngle), y1 = cy - r * Math.cos(startAngle);
    let x2 = cx + r * Math.sin(angle),      y2 = cy - r * Math.cos(angle);
    let largeArc = angle - startAngle > Math.PI ? 1 : 0;

    let slice = document.createElementNS(SVG_NS, "path");
    slice.setAttribute("d", `M${cx},${cy} L${x1},${y1} A${r},${r} 0 ${largeArc} 1 ${x2},${y2} Z`);
    slice.setAttribute("fill", `hsl(${(angle * 60) % 360} 70% 55%)`);
    slice.setAttribute("data-label", label); // each slice stays addressable later
    svg.append(slice);
  }
  return svg;
}

document.querySelector("#chart").append(
  pieChart({ JavaScript: 71.5, Python: 37.9, "C#": 35.3 }, { cx: 200, cy: 200, r: 180 })
);

Notice data-label on each slice — because the pie chart is a live DOM tree rather than a flattened bitmap, you can attach a listener to a single slice, look up a slice by its label later, or animate one slice's fill color independently, all without redrawing anything else. That capability, and its cost at large element counts, is the crux of the SVG-vs-canvas decision below.

Graphics in a <canvas>

A <canvas> element has no appearance of its own — it's a blank drawing surface that exposes a rich imperative API through a "context" object, obtained by calling canvas.getContext("2d") for two-dimensional graphics. Every drawing operation below is a method or property on that context object, not on the canvas element itself.

The immediate-mode drawing model Hard

The single most important thing to internalize about canvas, and the idea most beginners trip over after coming from SVG or a DOM-based UI framework: a canvas has no retained scene graph. When you call arc() followed by fill(), the browser rasterizes a circle-shaped set of pixels into the bitmap right now and then forgets you ever drew a circle. There is no node representing "the circle," no way to ask the canvas what shapes it contains, and no way to select, move, restyle, or delete that circle afterward except by erasing pixels and drawing something new in their place. Everything the canvas remembers is a flat grid of RGBA pixel values — nothing more.

This is the direct opposite of SVG's model, where every shape is a permanent, addressable node in a real DOM tree that persists until you explicitly remove it. Picking the wrong one for a job is a classic beginner mistake: reaching for canvas to build an interactive diagram means reinventing hit-testing, selection, and per-shape styling that SVG gives you for free; reaching for SVG to animate thousands of particles means fighting a DOM that was never designed to have that many live nodes.

Worked example 1 — there is no "the circle" to click.

let c = document.querySelector("canvas").getContext("2d");
c.beginPath();
c.arc(75, 75, 50, 0, 2 * Math.PI);
c.fillStyle = "steelblue";
c.fill();

// This listener fires for ANY click anywhere on the canvas element --
// the canvas has no idea a circle lives at (75,75). To know whether the
// click actually landed inside "the circle," you must redo the geometry
// test yourself using the same math you used to draw it.
canvas.addEventListener("click", (event) => {
  let rect = canvas.getBoundingClientRect();
  let x = event.clientX - rect.left, y = event.clientY - rect.top;
  let dx = x - 75, dy = y - 75;
  let clickedInsideCircle = Math.sqrt(dx * dx + dy * dy) <= 50;
  console.log(clickedInsideCircle ? "hit the circle" : "missed");
});

Compare this to the equivalent SVG version, where hit-testing is not code you write at all: 

// The <circle> element from an SVG document IS the hit target --
// no manual geometry required, and event.target is the circle itself.
document.querySelector("circle").addEventListener("click", () => {
  console.log("hit the circle");
});

Worked example 2 — "moving" a shape means redrawing everything.

Because nothing drawn to a canvas persists as an object, animating a shape doesn't mean changing a property on it — it means clearing the canvas and redrawing every visible shape, once per frame, at its new position. requestAnimationFrame() is the standard way to schedule that redraw in sync with the browser's repaint cycle (it also automatically pauses in background tabs, unlike a raw setInterval()): 

let x = 0;
function drawFrame() {
  c.clearRect(0, 0, canvas.width, canvas.height); // erase last frame entirely
  c.beginPath();
  c.arc(x, 75, 20, 0, 2 * Math.PI);               // redraw the "same" circle
  c.fill();                                        // ...at its new position
  x = (x + 2) % canvas.width;
  requestAnimationFrame(drawFrame);
}
requestAnimationFrame(drawFrame);

The SVG equivalent needs no clear-and-redraw step at all — you mutate the one retained node in place, and the browser handles repainting it: 

let circle = document.querySelector("circle");
let x = 0;
function moveCircle() {
  x = (x + 2) % 300;
  circle.setAttribute("cx", x); // the SAME node, just relocated
  requestAnimationFrame(moveCircle);
}
requestAnimationFrame(moveCircle);
A useful rule of thumb

If you find yourself wanting to ask "what did I draw at this position" after the fact, or wanting to change just one shape without touching the rest, that's a strong signal you want SVG (or a DOM-based approach) instead of canvas. Canvas earns its keep when the number of independently-tracked objects is too large for the DOM to comfortably hold, or when the visuals are generated per-pixel rather than per-shape.

Paths, fill, and stroke

Canvas has its own notion of a path, built imperatively rather than described as a string. beginPath() starts a fresh path; moveTo() starts a new subpath at a point; lineTo() extends the current subpath with a straight line; closePath() connects the subpath's end back to its start. Once a path is defined, fill() and stroke() render it using whatever fillStyle/ strokeStyle/lineWidth are set on the context at the moment those methods are called — these are properties of the drawing context, not attached to the path. 

c.beginPath();
c.moveTo(100, 100);
c.lineTo(200, 200);
c.lineTo(100, 200);
// The subpath is still "open" -- fill() treats it as if a line closed it,
// but stroke() only draws the two segments actually added above.
c.fillStyle = "#ccc";
c.fill();     // fills the implied triangle
c.strokeStyle = "#008";
c.lineWidth = 5;
c.stroke();   // strokes only two of the triangle's three sides

c.closePath(); // now connect the third side explicitly
c.stroke();    // this time all three sides are stroked
fill() and stroke() never clear the path

Calling fill() does not remove the path — stroke() immediately afterward operates on the exact same accumulated subpaths, and so would a third or fourth call. Forgetting to call beginPath() before starting the next shape is one of the most common canvas bugs: old subpaths silently keep getting redrawn underneath (or on top of) every new one.

When two subpaths overlap (or a single subpath crosses itself), canvas decides what counts as "inside" using the nonzero winding rule: the winding direction (clockwise vs. counterclockwise) each subpath was drawn in determines whether overlapping regions get filled or treated as a hole. Drawing a large polygon clockwise and a smaller one counterclockwise inside it, for instance, punches the smaller shape out as an unfilled hole — a common technique for donuts and cutouts.

Dimensions, coordinates, and crisp rendering

A canvas's width/height attributes set both the actual pixel buffer size and its default on-screen CSS size — the origin sits at the top-left, x increases rightward, y increases downward. Setting either dimension (even to its current value) wipes the canvas clean, discards the current path, and resets every graphics attribute, including any active transform or clip region.

Crisp canvases on high-DPI screens

If you size a canvas purely with CSS, the browser stretches its existing pixel buffer to fit, which looks blurry on high-DPI ("Retina") displays. The fix: set the CSS on-screen size with stylesheet rules, then set the canvas's width/ height attributes to that CSS size multiplied by window.devicePixelRatio, allocating a sharper pixel buffer than the CSS box it's displayed in. 

let ratio = window.devicePixelRatio || 1;
canvas.width = canvas.clientWidth * ratio;
canvas.height = canvas.clientHeight * ratio;
c.scale(ratio, ratio); // so drawing code can keep using CSS-pixel coordinates

Graphics attributes

A handful of context properties govern how every subsequent fill()/stroke()/fillText() call renders, independent of the drawing commands themselves — conceptually similar to how CSS separates presentation from markup.

  • Line styles: lineWidth (evaluated at stroke() time, centered over the path so half the width falls on either side), lineCap ("butt" default, or "round"/"square"), lineJoin ("miter" default, or "round"/"bevel", with sharp miters beyond miterLimit automatically beveled), and setLineDash([...]) for dashed/dotted strokes.
  • Colors, gradients, patterns: fillStyle/ strokeStyle accept a plain CSS color string, a CanvasGradient from createLinearGradient()/ createRadialGradient() (each color stop added via addColorStop(offset, color) with offset between 0 and 1), or a CanvasPattern from createPattern() built from an image, video, or another canvas.
  • Text styles: font (CSS font shorthand syntax), textAlign (start, left, center, right, end), and textBaseline controlling vertical alignment relative to the drawing y-coordinate.
  • Shadows: shadowColor, shadowOffsetX/shadowOffsetY, and shadowBlur apply a drop shadow to anything drawn while they're set; shadows default to fully transparent (invisible) until a color is assigned.
  • Translucency: use an rgba()/ hsla() color directly, or set globalAlpha to scale the opacity of everything drawn afterward, including images. globalCompositeOperation (default "source-over") controls how new pixels blend with what's already on the canvas.

Because every one of these lives on the single shared context object — there is only ever one context per canvas, no matter how many times you call getContext() — save()/restore() let you push and pop the entire graphics state (styles, transform, clip region, but not the current path) around a block of drawing code without manually resetting every property afterward.

Rectangles, curves, text, and images

Beyond straight-line paths, the 2D context provides several more shape and content primitives:

MethodDraws
fillRect(x,y,w,h) / strokeRect(...) / clearRect(...)A rectangle immediately, bypassing the path entirely; clearRect resets pixels to transparent
rect(x,y,w,h)Adds a rectangular subpath to the current path (doesn't draw by itself)
arc(x,y,r,start,end,ccw)A circular arc; connects from the current point with a straight line first if one exists
ellipse(x,y,rx,ry,rotation,start,end,ccw)Like arc() but with independent x/y radii and an overall rotation
arcTo(x1,y1,x2,y2,radius)A line plus a rounding arc between two tangent points — the standard way to draw rounded rectangle corners
quadraticCurveTo(cx,cy,x,y) / bezierCurveTo(...)A smooth curve to a new point, shaped by one or two control points
fillText(text,x,y) / strokeText(...)Text using the current font/fillStyle; measureText(text).width gives you its rendered width in advance

canvas.toDataURL() runs the opposite direction — it serializes the whole canvas's current pixels as a PNG data URL, letting you snapshot a drawing into a plain <img>: 

let snapshot = document.createElement("img");
snapshot.src = canvas.toDataURL();
document.body.append(snapshot);

Coordinate transforms

Every canvas keeps a current transformation matrix as part of its graphics state, mapping the coordinates you pass to drawing methods into the default pixel coordinate system. translate(dx,dy) moves the origin, rotate(angle) (radians, clockwise) rotates the axes, and scale(sx,sy) stretches or compresses them — a negative scale factor mirrors an axis. These compose in the order you call them, and because save()/restore() include the transform in the saved graphics state, wrapping a block of drawing in save()…restore() is the standard way to apply a temporary transform without it bleeding into subsequent drawing. 

function drawSpoke(c, angleDeg) {
  c.save();
  c.translate(150, 150);          // move origin to the hub
  c.rotate(angleDeg * Math.PI / 180);
  c.fillRect(0, -3, 80, 6);       // draw as if pointing along the x-axis
  c.restore();                    // undo translate+rotate for the next spoke
}
for (let i = 0; i < 8; i++) drawSpoke(c, i * 45);

For an arbitrary affine transform (shears, or rotation about a point other than the origin), transform(a,b,c,d,e,f) composes six matrix parameters onto the current transform, while setTransform(a,b,c,d,e,f) replaces it outright — useful for briefly resetting to the default pixel coordinate system (setTransform(1,0,0,1,0,0)) in the middle of otherwise transformed drawing code. Recursive use of save()/ translate()/rotate()/scale()/ restore() is also how classic self-similar fractals like a Koch snowflake get drawn with almost no trigonometry in the calling code — each recursive call just draws one line segment and lets the accumulated transform place it correctly.

Clipping regions

Calling clip() instead of (or in addition to) fill()/stroke() turns the current path into a clipping region: nothing drawn afterward renders outside it. Clipping can only ever shrink the current clip region, never enlarge it, and there's no method to reset it directly — the conventional pattern is to save() before clipping so you can restore() the unclipped region once you're done. 

c.save();
c.beginPath();
c.arc(100, 100, 60, 0, 2 * Math.PI);
c.clip();                          // restrict drawing to this circle
c.drawImage(photo, 40, 40, 120, 120); // photo appears masked to a circle
c.restore();                       // clip region reverts to what it was before

Pixel manipulation

Below the shape-drawing API sits raw pixel access. getImageData(x, y, w, h) returns an ImageData object exposing the requested rectangle's pixels as a flat, writable byte array in the fixed order red, green, blue, alpha, four bytes per pixel, row by row. After modifying the bytes, putImageData(imageData, x, y) writes them straight back. Both methods work in the canvas's default (untransformed) pixel coordinate system, and putImageData() bypasses compositing, globalAlpha, and shadows entirely — it overwrites pixels outright. 

// A simple horizontal "motion blur": each pixel becomes a weighted
// average of itself and the pixel to its left.
function smear(c, x, y, w, h, strength = 8) {
  let frame = c.getImageData(x, y, w, h);
  let px = frame.data;
  let keep = strength - 1;
  for (let row = 0; row < h; row++) {
    let rowStart = row * w * 4;
    for (let col = 1, i = rowStart + 4; col < w; col++, i += 4) {
      px[i]     = (px[i]     + px[i - 4] * keep) / strength; // R
      px[i + 1] = (px[i + 1] + px[i - 3] * keep) / strength; // G
      px[i + 2] = (px[i + 2] + px[i - 2] * keep) / strength; // B
      px[i + 3] = (px[i + 3] + px[i - 1] * keep) / strength; // A
    }
  }
  c.putImageData(frame, x, y);
}

This same building block underlies most in-browser image processing — blurs, color adjustments, thresholding, edge detection — all of it is just arithmetic over the same flat byte array.

Animating a canvas

Because the canvas remembers nothing between frames (see the immediate-mode deep dive above), every canvas animation follows the same shape: clear, recompute state, redraw everything, and schedule the next frame with requestAnimationFrame() rather than setInterval(), since it synchronizes with the display's refresh rate and automatically pauses while the tab is hidden or the page is backgrounded. 

let particles = createParticles(200);

function tick(timestamp) {
  c.clearRect(0, 0, canvas.width, canvas.height);
  for (let p of particles) {
    p.update(timestamp);
    c.beginPath();
    c.arc(p.x, p.y, p.radius, 0, 2 * Math.PI);
    c.fillStyle = p.color;
    c.fill();
  }
  requestAnimationFrame(tick);
}
requestAnimationFrame(tick);

3D graphics: WebGL, briefly

Passing "webgl" (or "webgl2") instead of "2d" to getContext() returns a context for hardware-accelerated 3D rendering, giving direct access to the GPU for custom shaders and vertex pipelines. It is a large, low-level API that most application developers reach through a higher-level library rather than by writing raw WebGL calls, and it's beyond the scope of this page — everything above concerns the 2D context only.

Audio APIs

Playback with <audio> / HTMLAudioElement

The <audio> (and <video>) element renders a substantial built-in playback UI, but crucially that UI itself lives in a browser-internal shadow tree, not the light DOM — it's the canonical real-world example motivating shadow DOM's design, mentioned earlier. Scripting playback doesn't require that built-in UI at all: play(), pause(), and properties like currentTime, volume, and playbackRate work whether or not the element is visible, or even attached to the document.

For simple sound effects, the Audio() constructor is a shortcut for creating an <audio> element without writing any HTML: 

// Load once, up front, so playback starts instantly on demand.
let clickSound = new Audio("/sounds/click.mp3");

document.addEventListener("click", () => {
  // cloneNode() creates a fresh, independent Audio instance each time, so
  // rapid clicks can overlap instead of cutting each other off. Clones
  // that are never attached to the document are still played and are
  // simply garbage collected once playback ends.
  clickSound.cloneNode().play();
});

The Web Audio API, briefly

<audio> and Audio() only play back existing recordings. Generating tones, mixing multiple sources, applying filters/effects, or analyzing frequency data for a visualizer requires the considerably larger Web Audio API instead. Its model is a graph of connectable AudioNode objects — oscillators as sources, gain nodes for volume envelopes, filters, analysers — wired together much like patch cords on a modular synthesizer, all driven by a single AudioContext. 

let audioContext = new AudioContext();

// A single oscillator generating a 440Hz sine tone
let tone = audioContext.createOscillator();
tone.frequency.value = 440;

// A gain node to fade the tone out instead of stopping it abruptly
let volume = audioContext.createGain();
volume.gain.setValueAtTime(1, audioContext.currentTime);
volume.gain.linearRampToValueAtTime(0, audioContext.currentTime + 1);

// Wire oscillator -> gain -> speakers, then play for one second
tone.connect(volume);
volume.connect(audioContext.destination);
tone.start();
tone.stop(audioContext.currentTime + 1);

The full API is substantial enough that using it well assumes some background in signal processing and electronic music concepts. Reach for it specifically when <audio>/ Audio() playback stops being enough — procedurally generated sound, real-time effects, or anything that needs to inspect or reshape a waveform rather than just play it back.
