Asynchronous JavaScript

Almost no real-world JavaScript program runs start-to-finish without stopping to wait for something: a timer, a user click, a file read, a network response. JavaScript itself contributes no asynchronous primitives to the "core" language — waiting is always mediated by a host environment (the browser or Node) that hands control back to your code later, through a callback. Everything in this chapter — Promises, async/await, and asynchronous iteration — is sugar layered on top of that one underlying mechanism. This page works through all three layers in depth: why callbacks alone don't scale, how Promises fix that, how async/await hides Promises almost entirely, and how asynchronous iterators let you loop over a stream of values that arrive over time.

13.1 Asynchronous programming with callbacks

A callback is a function you write and hand to some other piece of code, which invokes — "calls back" — your function later, when a condition is met or an event occurs. That's the entire idea. There is no special syntax for a callback; it's an ordinary function reference passed as an argument. What differs across APIs is when and how many times the callback fires, and what arguments it's called with. The subsections below walk through the four shapes of callback-based async you'll meet in real code: timers, DOM events, network requests, and Node's error-first convention.

Timers

The simplest form of asynchrony is "run this after some time has passed." setTimeout() registers a callback to run once, after a minimum delay in milliseconds (the browser or Node event loop makes no promise about exact timing — only that it won't fire earlier than requested): 

// Call checkForUpdates() once, no sooner than 60,000ms from now
setTimeout(checkForUpdates, 60000);

setInterval() is the repeating counterpart: it invokes the callback over and over, at the given interval, until you cancel it. Both functions return an opaque handle you use to cancel the pending or ongoing timer: 

// Check for updates once a minute, forever, until stopped
let updateIntervalId = setInterval(checkForUpdates, 60000);

function stopCheckingForUpdates() {
  clearInterval(updateIntervalId);   // setTimeout's canceler is clearTimeout()
}
Promises can't replace setInterval()

Keep this in mind for later: a Promise settles exactly once. It's a perfectly good fit for a one-shot setTimeout()-style delay (see the wait() helper further down this page), but it fundamentally cannot represent a repeating event source like setInterval() or a button that can be clicked many times. Those stay callback- or event-based, or move to asynchronous iteration if you need a loop-friendly form.

Events

Client-side JavaScript is overwhelmingly event-driven: rather than computing something on a schedule, code sits idle until the user clicks, types, or touches the screen, and the browser invokes whatever callbacks — called event handlers or event listeners — were registered for that kind of event on that element: 

let okay = document.querySelector("#confirmUpdateDialog button.okay");
okay.addEventListener("click", applyUpdate);

addEventListener()'s first argument names the event type ("click"), and the second is the callback the browser invokes when that event fires on that element, passing an event object with details like timestamp and pointer coordinates. Multiple listeners can be attached to the same element and event type; all of them run.

Network requests

Fetching data over the network is asynchronous for an obvious reason: you cannot block waiting on the other end of a socket. The historical browser API for this, XMLHttpRequest (its name is a holdover — it works with any response format, not just XML), exposes the result purely through callback properties: 

function getCurrentVersionNumber(versionCallback) {  // note callback argument
  let request = new XMLHttpRequest();
  request.open("GET", "http://www.example.com/api/version");
  request.send();

  request.onload = function() {
    if (request.status === 200) {
      let currentVersion = parseFloat(request.responseText);
      versionCallback(null, currentVersion);          // success: (null, value)
    } else {
      versionCallback(request.statusText, null);      // failure: (error, null)
    }
  };
  request.onerror = request.ontimeout = function(e) {
    versionCallback(e.type, null);
  };
}

Two things are worth noticing here, because they generalize to every callback-based API you'll write yourself. First, getCurrentVersionNumber() cannot return the version number the way a synchronous function would — by the time the function's own body finishes running, the network hasn't replied yet. Instead the caller supplies a callback and receives the result (or error) through it, whenever it's ready. Second, notice the two-headed callback signature: it's called with either an error and a null result, or a null error and a real result, never both. This is the precursor to the Node convention covered next. Also note that onload/onerror assign a single handler directly to a property, rather than calling addEventListener() — both styles exist; property assignment is simpler when you know only one listener is ever needed for that object and event.

Callbacks and events in Node

Node's built-in APIs are pervasively asynchronous and settle into one of two idioms. The first, used by most one-shot operations like reading a file, is the error-first callback convention: the callback's first parameter is reserved for an error (or null if none occurred), and the actual result comes second: 

const fs = require("fs");
let options = {};

fs.readFile("config.json", "utf-8", (err, text) => {
  if (err) {
    console.warn("Could not read config file:", err);
  } else {
    Object.assign(options, JSON.parse(text));
  }
  startProgram(options);   // runs either way
});

Every Node error-first callback follows this shape, so much so that the arguments are conventionally just named err and whatever the result is — muscle memory that pays off across the whole Node ecosystem. The second idiom is fully event-based, layering multiple named events on top of one operation because a single callback can't represent "headers arrived," "a chunk of body arrived," and "the whole response finished" as three separate moments: 

const https = require("https");

function getText(url, callback) {
  let request = https.get(url);
  request.on("response", response => {
    let httpStatus = response.statusCode;
    response.setEncoding("utf-8");
    let body = "";
    response.on("data", chunk => { body += chunk; });
    response.on("end", () => {
      if (httpStatus === 200) callback(null, body);
      else callback(httpStatus, null);
    });
  });
  request.on("error", (err) => { callback(err, null); });
}

Node's EventEmitter-style objects register listeners with .on() rather than addEventListener(), but the mental model is identical to DOM events: name the event, supply the callback, get invoked whenever it fires — possibly more than once.

The scaling problem: "callback hell"

None of the individual examples above look bad. The trouble starts when asynchronous steps depend on each other's results, so each new step has to be nested inside the callback of the previous one: 

getCurrentVersionNumber((err, version) => {
  if (err) return handleError(err);
  fetchChangelog(version, (err, changelog) => {
    if (err) return handleError(err);
    renderChangelog(changelog, (err) => {
      if (err) return handleError(err);
      notifyUserDone();
    });
  });
});
Why callbacks alone don't scale

This "pyramid of doom" is a readability problem — deep indentation, duplicated error-checking at every level — but there's a deeper structural problem underneath it: asynchronous code breaks exception handling. If fetchChangelog's internal, asynchronously-invoked callback throws, there is no try block anywhere on the call stack to catch it, because the code that originally called fetchChangelog() already returned and popped off the stack long before the callback runs. The only way to communicate failure is to pass it explicitly as a callback argument — the error-first convention exists purely to compensate for this. Every one of those nested if (err) return handleError(err) lines above is hand-rolled exception propagation, and it is easy to forget one and let an error vanish silently. Promises exist specifically to fix both problems: flatten the nesting into a linear chain, and give errors a real, standardized propagation path.

13.2 Promises

A Promise is an object representing the result of a single asynchronous computation — a result that may not be ready yet. Crucially, a Promise's design is deliberately opaque about timing: there is no way to synchronously ask a Promise "are you done, and what's your value?" You can only register a callback to be invoked once the value is ready. Framed that way, Promises are "just" a different way of packaging callbacks — but two concrete benefits justify the extra abstraction:

  • A sequence of dependent asynchronous steps can be written as a flat chain of .then() calls instead of nested callback pyramids.
  • Errors — including ones thrown as ordinary throw statements — get a standardized propagation path down the chain to a single .catch(), instead of requiring you to manually forward an error argument through every layer.
Promises represent single events, not repeating ones

Just like the callback APIs they wrap, a Promise settles once and never changes. You can build a Promise-based replacement for setTimeout() (shown later), but not for setInterval(), and a Promise is a fine substitute for a one-shot "load" event but a poor one for a recurring "click" handler.

This is the deep end of the chapter

The basic use of Promises is genuinely simple. But the fine details — what "resolved" actually means, how a thrown exception threads through a multi-stage chain, what happens when a .then() callback itself returns a Promise — are consistently the most misunderstood part of modern JavaScript. It is worth reading the next several sections slowly.

13.2.1 Using Promises

A Promise-returning function looks like this at the call site — no callback argument, just a returned object with a .then() method: 

getJSON(url).then(jsonData => {
  // invoked once, asynchronously, with the parsed result
});

Think of .then() as a callback-registration method, much like addEventListener() — except that, unlike an event target, a Promise represents exactly one computation, so each function you register with .then() fires at most once. It's idiomatic to chain .then() straight onto the call that produced the Promise, without an intermediate variable, and to name Promise-returning functions and their consumers with verbs so the call site reads like a sentence: 

function displayUserProfile(profile) { /* ... */ }

getJSON("/api/user/profile").then(displayUserProfile);
StateMeaning
pendingNot settled yet — no outcome decided
fulfilledCompleted successfully, with a value — like a normal function return
rejectedFailed, with a reason (usually an Error) — like a thrown exception

Once a Promise fulfills or rejects it is settled, and settled Promises never change state or value again — a Promise can never flip from fulfilled to rejected or vice versa, and its eventual value or reason is permanently fixed the moment it settles.

A registered callback always runs asynchronously

Even if the Promise you call .then() on has already settled, the callback you pass is never invoked synchronously, in the same turn of the event loop, as the .then() call itself. It's always deferred to a later microtask. This guarantee — covered in depth in the event loop deep dive below — is exactly what keeps Promise-based code predictable regardless of whether the underlying operation happened to finish "instantly" or not.

Handling errors with .then() and .catch()

.then() actually accepts two callbacks: a fulfillment handler and a rejection handler. 

getJSON("/api/user/profile").then(displayUserProfile, handleProfileError);

This mirrors why the two-callback form exists at all: an asynchronous computation's caller is no longer on the call stack by the time it completes or fails, so there's no way to synchronously return a result or throw an exception back to it. The two .then() arguments are the substitute channel for each outcome. In practice this two-argument form is rarely used, because it has a blind spot: if displayUserProfile itself throws, that error has nowhere to go — it isn't the first stage that failed, so handleProfileError never sees it. The idiomatic fix is to append a separate .catch() instead: 

getJSON("/api/user/profile")
  .then(displayUserProfile)
  .catch(handleProfileError);

Now either a rejection from getJSON() or an exception thrown inside displayUserProfile lands in handleProfileError. .catch(fn) is exactly shorthand for .then(null, fn) — the name is chosen to echo the catch clause of a try/catch statement, since a Promise chain's error handling really is the asynchronous analogue of exception propagation. Where a synchronous exception "bubbles up the call stack" looking for a catch, a rejected Promise "trickles down the chain" looking for a .catch().

13.2.2 Chaining Promises

The single most important fact about .then() is this: it does not attach another listener to the Promise you call it on — it returns a brand-new Promise, whose own eventual state depends entirely on what the callback does. That's what makes chaining work at all: 

fetch(theURL)          // task 1; returns promise 1
  .then(callback1)      // task 2; returns promise 2
  .then(callback2);     // task 3; returns promise 3

Walking through it step by step: fetch() starts the HTTP request ("task 1") and immediately returns promise 1. Calling .then(callback1) registers callback1 to run once promise 1 fulfills, and immediately (synchronously) returns a second, initially-pending Promise — promise 2. Calling .then(callback2) on that registers callback2 for when promise 2 fulfills, and returns promise 3. All of this setup happens synchronously the moment the expression executes; only afterward does the asynchronous wait for the network begin. When promise 1 eventually fulfills with a Response object, callback1 runs ("task 2" begins); whatever it returns becomes the fulfillment value of promise 2, which in turn triggers callback2 ("task 3"). A naive but common mistake is to nest instead of chain: 

// Naive: nested, exactly like callback hell, and defeats the purpose
fetch("/api/user/profile").then(response => {
  response.json().then(profile => {
    displayUserProfile(profile);
  });
});

// Idiomatic: flat chain
fetch("/api/user/profile")
  .then(response => response.json())
  .then(profile => displayUserProfile(profile));

13.2.3 Resolving Promises — "resolved" vs. "fulfilled" Deep dive

This is the single trickiest piece of terminology in the whole Promise model, and understanding it precisely is what separates "I can use .then()" from "I understand what's actually happening." The key claim: a Promise can be resolved without yet being fulfilled. "Resolved" and "fulfilled" are not synonyms.

Here's the mechanism. When you pass a callback c to .then(), it returns a new Promise p and arranges to invoke c later. Whatever c returns, call it v, becomes the thing that resolves p:

  • If v is an ordinary, non-Promise value, p is resolved and immediately fulfilled with v. In the overwhelmingly common case these two things happen in the same instant, which is exactly why the distinction usually doesn't matter and why the two words get used loosely as synonyms.
  • But if v is itself a Promise (or any thenable), then p becomes resolved — meaning it is now permanently "locked onto" v — but it is not yet fulfilled. p cannot settle until v settles. Once v fulfills, p fulfills to the same value; if v rejects, p rejects for the same reason. p sits in this resolved-but-pending limbo for as long as v takes to settle.

Trace it through the classic fetch() chain, naming every Promise involved — including the one produced by response.json(), which is easy to overlook: 

function c1(response) {         // callback 1
  let p4 = response.json();     // .json() itself returns a Promise: call it p4
  return p4;                    // task 2 "returns" promise p4, not real data
}
function c2(profile) {          // callback 2
  displayUserProfile(profile);
}

let p1 = fetch("/api/user/profile");  // promise 1, task 1
let p2 = p1.then(c1);                 // promise 2, task 2
let p3 = p2.then(c2);                 // promise 3, task 3

When c1 returns p4, promise 2 becomes resolved — locked onto p4 — but not fulfilled, so c2 (task 3) does not run yet. Only once the HTTP response body has fully arrived and .json() finishes parsing it does p4 fulfill; at that instant, promise 2 automatically fulfills to the same parsed value, and only then does c2 finally run. This is the entire mechanism that lets a chain "wait" for an inner asynchronous step without you writing any explicit waiting logic — returning a Promise from a .then() callback is itself the wait.

Worked example: a resolved-but-pending Promise you can observe
function slow(value, ms) {
  return new Promise(resolve => setTimeout(() => resolve(value), ms));
}

let inner = slow("inner value", 1000);   // settles in 1 second

let outer = Promise.resolve().then(() => {
  console.log("returning the inner promise now");
  return inner;              // <-- outer RESOLVES here, locked onto inner
});

outer.then(v => console.log("outer fulfilled with:", v));

// Console output:
// "returning the inner promise now"      (near-immediately)
// ... nothing for ~1 second ...
// "outer fulfilled with: inner value"    (only once `inner` settles)

outer became resolved the instant its callback returned inner, well before inner itself had fulfilled. For that entire one-second gap, outer is resolved but still pending — a state outer.then() alone can't distinguish from "not yet resolved at all," which is exactly why the distinction is subtle: from the outside, both look like "still waiting."

Why isn't it called Promise.fulfill()?

This is also why the Promise constructor's controls are named resolve and reject, never fulfill and reject, and why the static helper is Promise.resolve() rather than "Promise.fulfill()." Calling resolve(v) with a plain value fulfills immediately; calling resolve(otherPromise) only resolves — the real outcome is deferred to whatever otherPromise eventually does.

13.2.4 More on Promises and errors

A callback passed to .then() (or .catch()) can end in exactly three ways, and each maps to one Promise outcome:

Callback behaviorResulting Promise
Returns a plain valueFulfilled immediately with that value
Returns a PromiseResolved, pending on that Promise's outcome
ThrowsRejected with the thrown value

A realistic chain exercises all three paths: 

fetch("/api/user/profile")
  .then(response => {
    if (!response.ok) {
      return null;                              // treat 404 as a non-error
    }
    let type = response.headers.get("content-type");
    if (type !== "application/json") {
      throw new TypeError(`Expected JSON, got ${type}`);  // unrecoverable
    }
    return response.json();                     // returns a Promise
  })
  .then(profile => {
    if (profile) displayUserProfile(profile);
    else displayLoggedOutProfilePage();
  })
  .catch(e => {
    if (e instanceof TypeError) {
      displayErrorMessage("Something is wrong with our server!");
    } else {
      console.error(e);   // e.g. a NetworkError from fetch() itself failing
    }
  });

If the network is down, fetch()'s own Promise rejects with a NetworkError, which — since no rejection handler is attached at that stage — skips straight through to .catch(). If the server returns a 404, response.ok is false but this is still a successful HTTP exchange as far as fetch() is concerned, so the first .then() runs, returns null, and the second .then() handles that gracefully — no error handling required. If the content type is wrong, the explicit throw rejects the Promise that stage produced, which skips the second .then() entirely and lands in .catch(). Notice that a synchronous throw statement written directly in your code ends up being caught by an asynchronous .catch() — this is the payoff of the whole design.

.catch() mid-chain: recover and keep going

A .catch() doesn't have to be the last link in a chain. Insert one wherever a failure is recoverable, and — provided it returns normally rather than rethrowing — later .then() stages resume running with its return value as input, exactly as if the earlier stage had never failed: 

queryDatabase()
  .catch(e => wait(500).then(queryDatabase))  // on failure, wait and retry once
  .then(displayTable)
  .catch(displayDatabaseError);

If recoverFromError (here, the retry) itself throws, the error continues past the next .then() to the following .catch(). Only an uncaught rejection propagates further down the chain — once a .catch() callback returns normally, the error stops there.

The most common Promise bug: forgetting to return

Arrow function shorthand is a frequent trap here. Omitting the curly braces makes the expression's value an implicit return; adding braces switches back to needing an explicit return statement, and it's easy to add braces (say, to add a console.log) without remembering to add the return too: 

.catch(e => wait(500).then(queryDatabase))       // correct: implicit return

.catch(e => { wait(500).then(queryDatabase) })   // BUG: returns undefined!
                                                  // next .then() gets undefined
                                                  // instead of the retry result

13.2.5 Promises in parallel

Chains express a fixed sequence of steps. To run an arbitrary number of independent asynchronous operations concurrently and wait for the group, use one of the four combinator functions:

FunctionSettles whenResolves to
Promise.all(ps)All fulfill, OR the first one rejectsArray of fulfillment values (or rejects with the first error, immediately — even while others are still pending)
Promise.allSettled(ps) ES2020Every promise has settled, one way or anotherArray of {status:"fulfilled", value} or {status:"rejected", reason} objects — this one never rejects
Promise.race(ps)The first promise to settle, whichever wayThat promise's outcome (fulfillment or rejection)
Promise.any(ps) ES2021The first promise to fulfillThat value — rejects only if every input rejects
const urls = [ /* zero or more URLs */ ];
const promises = urls.map(url => fetch(url).then(r => r.text()));

Promise.all(promises)
  .then(bodies => { /* array of strings, in the SAME order as `urls` */ })
  .catch(e => console.error(e));   // any single failure rejects the whole group

Promise.allSettled([Promise.resolve(1), Promise.reject(2), 3]).then(results => {
  results[0];  // { status: "fulfilled", value: 1 }
  results[1];  // { status: "rejected", reason: 2 }
  results[2];  // { status: "fulfilled", value: 3 } -- non-Promise values pass through
});

Promise.all()'s array argument may freely mix real Promises with plain values; a plain value is treated as already fulfilled and copied through unchanged. Use Promise.allSettled() instead of Promise.all() whenever partial failure is acceptable and you want every outcome rather than having one failure short-circuit the rest. Promise.race() is for "whichever finishes first wins" — for example, racing a real request against a timeout Promise. Promise.any() is the fulfillment-only version of race: useful for "try several redundant servers, use whichever answers first, and only fail if literally all of them fail."

13.2.6 Making (creating) Promises

There are three distinct techniques for producing a Promise, depending on what you're starting from.

Promises based on other Promises

If you already have a Promise-returning function, wrapping more logic around it is just .then(): 

function getJSON(url) {
  return fetch(url).then(response => response.json());
}

function getHighScore() {
  return getJSON("/api/user/profile").then(profile => profile.highScore);
}

getJSON() has no error handling of its own here — it simply lets a bad HTTP status or malformed JSON body reject the Promise .json() already produces, and that rejection propagates through automatically.

Promises based on synchronous values

Promise.resolve(v) and Promise.reject(v) wrap an already-known value as an already-decided Promise — useful when a function must always return a Promise (to satisfy a Promise-based interface) but sometimes has a synchronous fast path or needs to report a synchronously-detectable error: 

function cachedFetch(url) {
  if (cache.has(url)) {
    return Promise.resolve(cache.get(url));   // fast path, still a Promise
  }
  return fetch(url).then(r => r.json()).then(data => {
    cache.set(url, data);
    return data;
  });
}
Prefer Promise.reject() over throwing synchronously

If you detect a bad argument before starting any async work, it's tempting to just throw right away. But then callers of your "Promise-based" function must handle errors two different ways — a synchronous try/catch for the up-front case, and an asynchronous .catch() for everything else. Returning Promise.reject(new Error(...)) keeps the error-handling path uniform.

Note that even Promise.resolve() and Promise.reject() settle asynchronously — the callbacks you attach still don't run in the same synchronous turn, only "soon" (typically within microseconds, as a microtask; see the event loop section below).

Promises from scratch: the Promise() constructor

To build a Promise around an API that offers neither a Promise-returning function nor a synchronous value to start from — typically an old-style callback or event API — use the Promise constructor directly. It synchronously invokes the function you pass it, supplying two functions, resolve and reject, that you call whenever (and from wherever, even deeply nested inside other callbacks) the outcome becomes known: 

function wait(duration) {
  return new Promise((resolve, reject) => {
    if (duration < 0) {
      reject(new Error("Time travel not yet implemented"));
    }
    // setTimeout invokes resolve() with no arguments -> fulfills with undefined
    setTimeout(resolve, duration);
  });
}

A fuller example wraps Node's callback- and event-based http module into a Promise-returning getJSON(), demonstrating the constructor pattern end to end — including making sure every failure path calls reject() exactly once: 

const http = require("http");

function getJSON(url) {
  return new Promise((resolve, reject) => {
    let request = http.get(url, response => {
      if (response.statusCode !== 200) {
        reject(new Error(`HTTP status ${response.statusCode}`));
        response.resume();               // drain the response, avoid a leak
      } else if (response.headers["content-type"] !== "application/json") {
        reject(new Error("Invalid content-type"));
        response.resume();
      } else {
        let body = "";
        response.setEncoding("utf-8");
        response.on("data", chunk => { body += chunk; });
        response.on("end", () => {
          try {
            resolve(JSON.parse(body));
          } catch (e) {
            reject(e);
          }
        });
      }
    });
    request.on("error", error => { reject(error); });
  });
}
resolve() / reject(), not fulfill() / reject()

The parameter names are always resolve and reject by convention, never fulfill — consistent with the resolved-vs-fulfilled distinction above. If you call resolve(anotherPromise), the Promise you're building only resolves, locking onto that inner Promise, rather than fulfilling outright.

13.2.7 Promises in sequence

Promise.all() covers a known, fixed-size batch of parallel work, and a hand-written chain covers a known, fixed number of sequential steps. Running an arbitrary-length array of operations strictly one-at-a-time — say, fetching URLs sequentially to avoid overloading a connection — needs a chain built dynamically at runtime: 

function fetchSequentially(urls) {
  const bodies = [];

  function fetchOne(url) {
    return fetch(url)
      .then(response => response.text())
      .then(body => { bodies.push(body); });  // deliberately no return value
  }

  let p = Promise.resolve(undefined);   // an already-fulfilled starting point
  for (const url of urls) {
    p = p.then(() => fetchOne(url));    // extend the chain by one more link
  }
  return p.then(() => bodies);
}

This builds a chain of Promises up front, like a row of dominoes, and then lets it fall. A more general version, promiseSequence(), takes any array of inputs and a Promise-returning promiseMaker function, and instead of building the chain up front, has each stage's callback create and return the next stage's Promise — resolving Promises to further Promises like nested dolls rather than a flat chain: 

function promiseSequence(inputs, promiseMaker) {
  inputs = [...inputs];

  function handleNextInput(outputs) {
    if (inputs.length === 0) {
      return outputs;                       // done: fulfill with all results
    } else {
      let nextInput = inputs.shift();
      return promiseMaker(nextInput)
        .then(output => outputs.concat(output))
        .then(handleNextInput);             // "recurse" through .then(), not the call stack
    }
  }

  return Promise.resolve([]).then(handleNextInput);
}

// Usage:
function fetchBody(url) { return fetch(url).then(r => r.text()); }
promiseSequence(urls, fetchBody)
  .then(bodies => { /* ... */ })
  .catch(console.error);

The event loop: microtasks vs. macrotasks Deep dive

Every one of the guarantees above — "a .then() callback never runs synchronously," "errors trickle down the chain" — is implemented on top of a single-threaded runtime's event loop. JavaScript has exactly one thread of execution. When there's no code currently running, the event loop pulls the next pending job off a queue and runs it to completion before pulling the next one. The trick — and the source of a lot of confusion — is that there are effectively two queues, checked with different priority:

  • The microtask queue — holds Promise reaction callbacks (.then()/.catch()/.finally() handlers) and a few other things like queueMicrotask() callbacks and Mutation Observer callbacks.
  • The macrotask (a.k.a. "task") queue — holds setTimeout/setInterval callbacks, I/O completion callbacks, and UI event dispatches.

The rule that explains almost every "why did this run in that order?" surprise: after each single macrotask finishes running, the event loop drains the entire microtask queue — including any new microtasks that were themselves queued while draining it — before it is allowed to move on and run even one more macrotask. Microtasks always win the race against macrotasks, no matter how small the macrotask's delay was set to.

Worked example 1: a resolved Promise beats setTimeout(fn, 0)
console.log("1: script start");

setTimeout(() => console.log("2: setTimeout callback"), 0);

Promise.resolve().then(() => console.log("3: promise .then() callback"));

console.log("4: script end");

// Console output, in order:
// 1: script start
// 4: script end
// 3: promise .then() callback
// 2: setTimeout callback

The synchronous script body ("1" and "4") always runs first and completely, uninterrupted — that's just ordinary single-threaded execution. Once that top-level script finishes, the engine drains the microtask queue before touching the macrotask queue, so the Promise callback ("3") runs before the timer callback ("2") even though the timer was scheduled first and asked for zero delay. A setTimeout delay of 0 does not mean "immediately" — it means "as soon as possible, but only after the current macrotask and the entire microtask queue are done."

Worked example 2: interleaving several sources
console.log("A");

setTimeout(() => console.log("B"), 0);

Promise.resolve()
  .then(() => console.log("C"))
  .then(() => console.log("D"));   // a second microtask, queued once "C" runs

setTimeout(() => console.log("E"), 0);

Promise.resolve().then(() => console.log("F"));

console.log("G");

// Console output, in order: A, G, C, F, D, B, E

Both synchronous logs ("A", "G") run first. Then all currently-queued microtasks run before either timer fires: "C" and "F" were both queued during the synchronous pass, so they run first, in the order they were queued. "D" was only queued once "C"'s callback actually ran — but since it's still a microtask, it still finishes before the engine is allowed to touch the macrotask queue. Only once the microtask queue is completely empty do the two setTimeout callbacks run, in the order they were scheduled: "B" then "E".

Why this matters in practice

You rarely need to reason about this explicitly when writing straight-line async/await code. But it explains real bugs: code that assumes a setTimeout(fn, 0) runs "before any Promise callback that was already pending" will be surprised, and libraries sometimes deliberately wrap a synchronous callback in Promise.resolve().then(...) specifically to force it to run asynchronously but still ahead of any pending timers.

13.3 async and await

ES2017 added two keywords, async and await, that don't add any new asynchronous capability — everything they do was already expressible with Promises — but they let you write Promise-based code that reads top-to-bottom like ordinary blocking code, including using real try/catch for errors. Under the hood it's still Promises and the same event loop described above; async/await is purely syntax.

13.3.1 await expressions

await takes a Promise (or Promise-returning expression) and converts it back into an ordinary value or a thrown exception: given a Promise p, await p pauses until p settles. If p fulfills, the whole expression evaluates to its fulfillment value. If p rejects, the expression throws the rejection value, right there, as if it were a synchronous throw. You'll almost always see await placed directly before a function call that returns a Promise, rather than a variable already holding one: 

let response = await fetch("/api/user/profile");
let profile = await response.json();
await does NOT block the thread

This is the most important thing to internalize about await: it does not freeze the program waiting for the Promise. The enclosing function's execution genuinely pauses and hands control back to the caller / event loop immediately; other code keeps running while the awaited Promise is pending. "Async code that reads like sync code" is a readability illusion the language is giving you — underneath, it's exactly as non-blocking as the equivalent .then() chain. Any function containing an await is, by definition, itself asynchronous.

13.3.2 async functions

await is only legal inside a function declared async (with one exception — top-level await, covered below). Declaring a function async guarantees it returns a Promise, even if nothing inside its body looks Promise-related: a normal return value fulfills that Promise with value, and a thrown exception rejects it. 

async function getHighScore() {
  let response = await fetch("/api/user/profile");
  let profile = await response.json();
  return profile.highScore;              // wraps in a fulfilled Promise
}

// Ordinary try/catch works again, because await turns rejection into a throw:
async function getHighScoreSafely() {
  try {
    return await getHighScore();
  } catch (err) {
    console.error("couldn't get score:", err);
    return 0;
  }
}

Because getHighScore() returns a Promise, code that isn't itself async still consumes it the old way, with .then()/.catch(): 

getHighScore().then(displayHighScore).catch(console.error);

async can modify any function form: a function declaration, a function expression, an arrow function, or a method shorthand in a class or object literal — see Functions for the full set of function syntaxes this applies to.

How it desugars

Conceptually, an async function f(x) { body } behaves as if it had been written as a plain function that wraps its body in a Promise constructor and a try/catch: 

function f(x) {
  return new Promise((resolve, reject) => {
    try {
      resolve((function(x) { /* body */ })(x));
    } catch (e) {
      reject(e);
    }
  });
}

await itself is harder to express as a literal source transform, but it helps to think of each await as a marker that slices the function body into separate synchronous chunks — the engine effectively turns each chunk into its own callback, handed to .then() on the Promise that the preceding await was waiting on. In other words, async/await really is "just" a Promise chain, restructured by the compiler so you get to write it as straight-line code with real control flow (loops, try/catch, early return) instead of nested callbacks.

13.3.3 Awaiting multiple Promises Common mistake

Because each await pauses the function until that one Promise settles, writing two independent awaits back-to-back accidentally serializes work that had no reason to be sequential: 

async function getJSON(url) {
  let response = await fetch(url);
  return await response.json();
}

// SLOW: the second fetch doesn't even START until the first fully finishes
let value1 = await getJSON(url1);
let value2 = await getJSON(url2);

If url2's fetch doesn't depend on value1, both requests should be in flight at the same time. The fix is the same Promise.all() combinator from earlier, used with await: 

// FAST: both requests start immediately; we only wait once, for both together
let [value1, value2] = await Promise.all([getJSON(url1), getJSON(url2)]);
A second trap: await inside .map() silently does nothing

Array.prototype.map() has no idea its callback is async; it just collects whatever the callback returns. An async callback always returns a Promise, so .map() with an async callback produces an array of Promises, not an array of resolved values — and if you forget that, code downstream silently receives [Promise, Promise, Promise] instead of real data: 

// BUG: results is an array of pending Promises, not fetched bodies
let results = urls.map(async url => {
  let response = await fetch(url);
  return response.json();
});
console.log(results);          // [Promise, Promise, Promise]
console.log(results[0].data);  // undefined -- that's a Promise, not the data!

// FIX 1: await the whole batch together (also runs them concurrently)
let results2 = await Promise.all(
  urls.map(async url => (await fetch(url)).json())
);

// FIX 2: if you truly need them one at a time, use a real loop instead of .map()
let results3 = [];
for (const url of urls) {
  results3.push(await (await fetch(url)).json());
}
Unhandled rejections

If a Promise rejects and nothing is attached to observe that rejection — no .catch(), no await inside a try — the runtime reports it as an unhandled promise rejection. In a browser this fires a window.onunhandledrejection event and typically logs a console warning; in Node, unhandled rejections can (depending on version and configuration) crash the process. A common way this happens by accident: calling an async function without await-ing or otherwise attaching a handler to its returned Promise ("fire and forget"), when that function can actually fail: 

async function saveDraft() { /* ... could reject ... */ }

function onKeyup() {
  saveDraft();   // BUG: rejection has nowhere to go if this fails
}

function onKeyupFixed() {
  saveDraft().catch(err => console.error("autosave failed:", err));
}

Top-level await ES2022

Ordinarily await requires an enclosing async function. As of ES2022, JavaScript modules are an exception: you may use await directly at the top level of a module file (not inside any function), which is useful for one-time setup that itself depends on an asynchronous resource: 

// config.js -- an ES module
const response = await fetch("/api/config");
export const config = await response.json();

A module that uses top-level await delays anything that imports it until the awaited Promise settles — the importing module's own evaluation effectively waits its turn. See Modules for how module evaluation order and this delay interact when several modules in a dependency graph each use top-level await.

13.4 Asynchronous iteration

Promises and await handle a single asynchronous result. Neither is a good fit for a stream of asynchronous values arriving one after another — a Node readable stream's "data" events, or a live sequence of user input events. ES2018 fills that gap with asynchronous iterators and a new loop form, for await...of, that pairs with them the way the ordinary for...of loop pairs with the synchronous iteration protocol from Iterators & Generators.

13.4.1 The for/await loop

Node's readable streams are asynchronously iterable out of the box, so you can pull successive chunks with a loop instead of a "data" event listener: 

const fs = require("fs");

async function parseFile(filename) {
  let stream = fs.createReadStream(filename, { encoding: "utf-8" });
  for await (let chunk of stream) {   // waits for each chunk as it arrives
    parseChunk(chunk);
  }
}

Like a plain await, for await...of is only legal inside an async function. It's also worth knowing that for await...of tolerates an ordinary synchronously-iterable array whose elements happen to be Promises — it will just await each one for you as it goes: 

const urls = [url1, url2, url3];
const promises = urls.map(url => fetch(url));

// Equivalent to manually awaiting each promise in a regular for/of loop:
for await (const response of promises) {
  handle(response);
}

That's convenient shorthand, but it's a different thing from a truly asynchronous iterable, covered next — here the done/finished-ness of the loop is decided synchronously (the array's length is already known); only each individual value happens to be a Promise.

13.4.2 Asynchronous iterators

Recall the synchronous iteration protocol: an iterable object implements [Symbol.iterator](), which returns an iterator object whose next() method returns { value, done } result objects directly. Asynchronous iteration mirrors this with two changes:

  • An asynchronously-iterable object implements [Symbol.asyncIterator]() instead of (or in addition to) [Symbol.iterator](). for await...of prefers Symbol.asyncIterator when both are present, falling back to Symbol.iterator otherwise (which is exactly the array-of-Promises case above).
  • The iterator's next() method returns a Promise that resolves to a { value, done } result object, rather than returning that result object directly.
A subtle but real distinction

With a synchronously-iterable array of Promises, only value is asynchronous — done is decided immediately. With a genuine async iterator, both are wrapped together in one Promise, so even the decision of "are we finished?" can itself depend on something asynchronous — useful when you don't know in advance how many values there will be.

13.4.3 Asynchronous generators

Just as a regular generator (function*) is usually the easiest way to implement a synchronous iterator, an async generator — the combined syntax async function* — is usually the easiest way to implement an async iterator. Inside its body you can use both await (because it's async) and yield (because it's a generator); every yielded value is automatically wrapped in a Promise for you: 

function elapsedTime(ms) {
  return new Promise(resolve => setTimeout(resolve, ms));
}

async function* clock(interval, max = Infinity) {
  for (let count = 1; count <= max; count++) {
    await elapsedTime(interval);   // wait for time to pass
    yield count;                  // yield the counter
  }
}

async function test() {                      // async, so we can use for/await
  for await (let tick of clock(300, 5)) {    // loop 5 times, every ~300ms
    console.log(tick);
  }
}
test();

13.4.4 Implementing asynchronous iterators directly

You don't have to use a generator; you can implement [Symbol.asyncIterator]() and an async next() method by hand. Doing so lets you fix a subtle flaw the generator version above has: nothing stops eager code from calling next() several times back-to-back before the first call has resolved, which — with the interval-based generator — produces several Promises that all fulfill at nearly the same moment instead of at evenly-spaced times. A hand-written iterator can track an absolute target time instead of a relative interval, and account for however long each loop body actually took: 

function clock(interval, max = Infinity) {
  function until(time) {
    return new Promise(resolve => setTimeout(resolve, time - Date.now()));
  }
  return {
    startTime: Date.now(),
    count: 1,
    async next() {                         // declaring next() async makes
                                            // it automatically return a Promise
      if (this.count > max) {
        return { done: true };
      }
      let targetTime = this.startTime + this.count * interval;
      await until(targetTime);
      return { value: this.count++ };
    },
    [Symbol.asyncIterator]() { return this; }  // the iterator is its own iterable
  };
}

A for await...of loop always awaits the Promise from one call to next() before requesting the next one, so this particular timing bug only bites code that manually calls next() outside of a for await loop. Harder still is building an async iterator around a source that's driven by an ordinary event callback (rather than something you can setTimeout yourself), because each call to next() must hand back a distinct Promise, and several calls to next() may arrive before the first has anything to resolve with. The clean solution is to encapsulate a queue of pending values and pending resolvers into a reusable AsyncQueue class: 

class AsyncQueue {
  constructor() {
    this.values = [];      // enqueued values not yet dequeued
    this.resolvers = [];   // resolve functions for next()s awaiting a value
    this.closed = false;
  }
  enqueue(value) {
    if (this.closed) throw new Error("AsyncQueue closed");
    if (this.resolvers.length > 0) {
      const resolve = this.resolvers.shift();
      resolve(value);                        // hand it straight to a waiting next()
    } else {
      this.values.push(value);
    }
  }
  dequeue() {
    if (this.values.length > 0) {
      return Promise.resolve(this.values.shift());
    } else if (this.closed) {
      return Promise.resolve(AsyncQueue.EOS);   // end-of-stream sentinel
    } else {
      return new Promise(resolve => { this.resolvers.push(resolve); });
    }
  }
  close() {
    while (this.resolvers.length > 0) {
      this.resolvers.shift()(AsyncQueue.EOS);
    }
    this.closed = true;
  }
  [Symbol.asyncIterator]() { return this; }
  next() {
    return this.dequeue().then(value => (value === AsyncQueue.EOS)
      ? { value: undefined, done: true }
      : { value: value, done: false });
  }
}
AsyncQueue.EOS = Symbol("end-of-stream");

// Turn any DOM event stream into an async-iterable object:
function eventStream(elt, type) {
  const q = new AsyncQueue();
  elt.addEventListener(type, e => q.enqueue(e));
  return q;
}

async function handleKeys() {
  for await (const event of eventStream(document, "keypress")) {
    console.log(event.key);
  }
}

This is the general recipe for bridging any push-style, callback- or event-driven source into for await...of: enqueue values as they arrive, and let dequeue() return an already-resolved Promise if a value is already waiting, or a not-yet-resolved one (whose resolve you stash for later) if the consumer is asking faster than values are arriving.

Async iteration is for one-at-a-time streams, not concurrency

for await...of processes one value, fully, before requesting the next — it's the async counterpart to generators, not a replacement for Promise.all() when what you actually want is several operations running at once.

13.5 Summary

  • Nearly all real-world JavaScript is asynchronous, and the language itself contributes no async primitives — waiting is always mediated by the host (browser or Node) through callbacks.
  • Callbacks are the foundation everything else is built on, but nested, dependent callbacks produce "callback hell," and — more fundamentally — asynchronous code breaks ordinary exception handling, since the caller is off the call stack by the time the callback runs.
  • A Promise represents the eventual result of one asynchronous operation, moving through pending to either fulfilled or rejected. "Resolved" is a related but distinct state: a Promise resolved with another Promise is locked onto it but not yet fulfilled, and won't settle until that inner Promise does.
  • .then() always returns a new Promise, which is what makes chaining — rather than nesting — possible. Errors trickle down a chain to the nearest .catch(), mirroring how exceptions bubble up a call stack to the nearest try/catch.
  • Promise.all(), allSettled(), race(), and any() combine multiple Promises running concurrently, each with different settling and rejection rules.
  • The event loop drains the entire microtask queue (Promise reactions) between every macrotask (timers, I/O, UI events) — which is why a resolved Promise's .then() always runs before a setTimeout(fn, 0) callback, no matter the requested delay.
  • async functions always return a Promise; await unwraps a Promise into a value or throws its rejection, letting ordinary try/catch work again — but it never blocks the thread. Independent awaits should usually be launched together via Promise.all() rather than serialized one after another, and an async callback inside .map() produces an array of Promises, not resolved values, unless you explicitly await the whole batch.
  • for await...of, async iterators (Symbol.asyncIterator), and async generators (async function*) extend this model to streams of asynchronous values arriving one at a time, as an alternative to repeated "data" events or similar callback-driven sources.
